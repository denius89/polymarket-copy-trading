# Совместная работа над проектом

Репозиторий пока находится на этапе проектирования. Главная задача участников — превращать гипотезы в проверяемые решения и не создавать код раньше согласованных gates.

Репозиторий пока не объявлен open source и не содержит лицензии. Внешние участники подключаются по договорённости с владельцем проекта; выбор лицензии нужен до открытого приёма сторонних вкладов.

## Перед началом работы

1. Прочитайте `docs/PROJECT_STATE.md`.
2. Найдите свою область в `docs/README.md`.
3. Проверьте очередь и критерий результата в `docs/ROADMAP.md`.
4. Прочитайте связанные ADR в `docs/decisions/`.
5. Убедитесь, что задача не зависит от ещё не принятого решения.

## Как брать задачу

Хорошая задача содержит:

- проблему или вопрос пользователя;
- один проверяемый результат;
- что входит и не входит в работу;
- затрагиваемые документы или компоненты;
- критерий готовности;
- способ проверки;
- открытые зависимости и ответственного за решение.

Если результата нельзя проверить за один рабочий цикл, задачу нужно разделить.

## Статусы информации

- **Решение основателя** — прямое продуктовое решение; меняется только новым явным решением.
- **Принято** — действующий ADR.
- **Предложено** — рекомендуемый вариант, ещё не утверждённый или не проверенный.
- **Гипотеза** — предположение, для которого указан способ проверки.
- **Исторический документ** — полезный контекст, который не определяет текущий порядок работ.

Не превращайте предложение в принятое решение только изменением формулировки. При конфликте приоритет имеют `docs/PROJECT_STATE.md`, действующие ADR и более новое прямое решение основателя.

## Изменения документации

- Обновляйте существующий основной документ, если тема уже существует.
- Новый документ создавайте для отдельного долгоживущего результата, а не для одной реплики.
- Существенное архитектурное или продуктовое решение оформляйте ADR.
- Для чисел указывайте формулу, исходные предположения и статус: факт, сценарий или прогноз.
- Для внешних меняющихся фактов указывайте источник и дату проверки.
- После завершённого блока обновляйте `docs/PROJECT_STATE.md` и при необходимости `docs/ROADMAP.md`.

## Изменения кода

Код приложения пока не создаётся до снятия паузы из ADR-0002. После разрешения разработки:

- один pull request должен давать один проверяемый результат;
- реальное исполнение остаётся выключенным по умолчанию;
- внешние API изолируются адаптерами;
- денежная логика сначала описывается инвариантами;
- повторяемые обработчики проектируются идемпотентными;
- интерфейс проверяется визуально;
- изменённое поведение покрывается соразмерной проверкой.

## Ветки, коммиты и pull requests

- Название ветки: `docs/<topic>`, `research/<topic>`, `feat/<topic>` или `fix/<topic>`.
- Коммит описывает завершённый результат глаголом: `Document pricing experiment`.
- Pull request объясняет проблему, итоговое поведение, проверку и оставшиеся ограничения.
- Не смешивайте массовое форматирование с содержательным изменением.
- Не переписывайте историю `main` и не публикуйте секреты.

## Проверка перед отправкой

```bash
npm run check
git diff --check
```

Дополнительно перечитайте изменённые формулы, статусы решений и относительные ссылки.

## Работа с чувствительными данными

Не добавляйте в Git:

- seed phrase и приватные ключи;
- рабочие API-токены, cookies и session signer;
- персональные данные агентов и пользователей;
- необезличенные записи интервью;
- внутренние договоры без отдельного решения о публикации.

Исходный handoff может храниться локально в `references/`, но публичные документы должны быть понятны без него.
