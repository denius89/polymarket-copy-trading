# Закрытый пакет запуска staff Q06

Пакет для отдельного временного пилота на подготовленной закрытой среде. В нём штатная админка из Git, отдельные процессы входа и чтения, HTTPS-шлюз с клиентскими сертификатами и операторские сценарии для закрепления двух демо-сессий, включения и отключения. Все примеры выключены. Проверенный профиль рассчитан на двух сотрудников и две явно назначенные демо-сессии. Сервер проверяет назначение и записывает каждое чтение карточки в аудит PostgreSQL.

## Сборка

Из корня репозитория выполните:

```sh
python3 tools/staff-q06-release/assemble.py HEAD /tmp/staff-q06-release
```

Архив содержит `release-lock.json` с Git-деревом, закреплённым образом Node и SHA-256 каждого исходного файла. Сборка исходников работает без сети. Для сборки фронтенда заранее загрузите закреплённый Node ARM64 образ, экспортируйте утверждённые `VITE_STAFF_Q06=1`, `VITE_STAFF_Q06_ORIGIN` и `VITE_STAFF_Q06_ORIGIN_SHA256`. Пин вычисляется как SHA-256 UTF-8 строки `{"origin":"https://staff.example.invalid:8443","version":"staff-paper-pilot-origin-v1"}` с фактическим HTTPS-адресом. Выполните `bash build-admin.sh` из пакета. Команда устанавливает npm-зависимости по lock и собирает штатный `apps/admin`. При сборке без флага служебная форма отключена.

## Управление доступом

1. Подготовьте отдельный закрытый Linux ARM64 хост, внутренний Docker bridge с PostgreSQL и два отдельных непривилегированных DB-логина. У auth и reader должны быть только соответствующие членства `pilot_staff_auth` и `pilot_staff_reader`. Образ из `release-lock.json` используется для обоих. PostgreSQL и процессы API работают в одной защищённой сети без публикации портов. В текущем runtime TCP к БД внутри этой сети без TLS.
2. Сверьте подготовленную БД и резервную копию до включения. Нужны законченные миграции схемы `pilot_staff`, совместимая V00/paper-схема и действующее чтение Q06 для имеющихся видов снимков. `staff-db/` содержит исходные SQL миграции staff-профиля. Для сессий с позициями требуется совместимая финансовая проекция `live-buy-session-v1`, уже подключённая к `polygon.pilot_staff_snapshot`. Полная последовательность для синтетической БД показана в изолированном стенде. К текущей базе миграции автоматически не применяются.
3. Укажите точный HTTPS origin на выделенном закрытом адресе. Этому адресу нужен серверный сертификат с корректной цепочкой и именем в SAN. Положите клиентский CA и два независимых SHA-256 отпечатка конечных клиентских сертификатов в настройку шлюза. Шлюз требует цепочку и совпадение с одним отпечатком. Ожидается прямой TLS до шлюза, поэтому адрес клиента берётся из соединения. Пример слушает только loopback. Для закрытой сети используйте её конкретный IPv4 и ограничьте доступ к порту на хосте.
4. Подготовьте приватный JSON-вход с `descriptor` и массивом `targetUserIds` из двух согласованных UUID. Дескриптор содержит `version=pilot-staff-deployment-v1`, новый UUIDv4 `runId`, тот же `origin`, времена `openedAt` и `cutoffAt` в UTC с миллисекундами. Текущее правило отсечки — 23:00 по Варшаве на следующий календарный день. С отдельной учётной записи оператора вызовите `python3 provision_material.py --expected-origin "$STAFF_ORIGIN" "$PRIVATE_INPUT" "$NEW_PRIVATE_DIR"`. Генерация работает офлайн и пишет временные ключи в новый закрытый каталог. Файлы `owner-*.json` выдаются по согласованному защищённому каналу.
5. Как доверенный DB-оператор, подайте приватное содержимое `provision.json` в переменную psql `provision_json` через защищённый вход, а также задайте `deployment_digest` из `runtime-binding.json`, новый `bind_request_id` и два UUID сессий `session_1`, `session_2`. Запустите `operator/provision.sql` как одну транзакцию. Порядок сессий соответствует `targetUserIds`. Сервер проверяет принадлежность и пригодность каждого снимка. Доступ остаётся выключенным до отдельного запуска `operator/activate.sql` с тем же digest и новым `request_id`. После активации состав пары в этом пилоте фиксирован.
6. Разнесите файлы ключей по ролям согласно шаблонам `config/`. Auth получает `permit`, `context`, `login`, `cipher` и свой ingress. Reader получает `login`, `logout` и свой ingress. Шлюз получает оба ingress и `network`. Файлы ключей и паролей доступны только своему служебному пользователю или root. UID auth — 1000, reader — 1001. Заполните `runId`, digest, отсечку, адреса и пароли из подтверждённого профиля. Включите `enabled` в приватных копиях. Запустите `docker compose up -d auth reader` с переменными по образцу `config/compose.env.example`. Перед запуском edge подтвердите `pilot_private_ready` у обоих процессов. Затем из пакета отдельным непривилегированным пользователем выполните `python3 -B gateway.py /absolute/private/edge.json`. Ожидается `STAFF_HTTPS_READY`.
7. Приёмка после разрешённого запуска состоит из входа сотрудника по HTTPS, чтения назначенной карточки и сверки аудита, отказа для неназначенной сессии и отказа без staff-входа. Любое расхождение требует остановки. Среде пользовательского приложения отдельный служебный адрес не нужен.

## Отключение

Остановите HTTPS-шлюз и снимите публикацию служебного адреса. Затем остановите два контейнера через `docker compose stop auth reader`. Под доверенным оператором выполните `operator/close.sql` с ожидаемым `deployment_digest` и новым `request_id`. Подтвердите `pilot_closed` в аудите. Серверная операция выключает пилот, отзывает разрешения и действующие служебные входы. Закрытие окончательно для этого пилота. Записи аудита и пользовательские сессии сохраняются.

Если БД недоступна, оставьте маршруты и контейнеры выключенными до завершения отзыва. Для возврата экрана опубликуйте штатную сборку админки с выключенным флагом. Отсечка служит дополнительным ограничением времени у шлюза, API и БД.

## Проверка пакета · 20.11.2026

Экспортирован пакет из Git и сверены SHA-256 его файлов. Штатная админка собрана
локально по npm lock с HTTPS-профилем. Офлайн-генератор принял материал только для
явно указанного адреса. На loopback с временными тестовыми сертификатами прошли
проверки выключенного профиля, обязательного клиентского сертификата, отказа
сертификату вне списка отпечатков и отказа при чужом Host. Для разрешённого
сертификата шлюз обработал запрос к неизвестному служебному маршруту как 404.

## Изолированный цикл включения и отключения · 20.11.2026

Проверено Git-дерево `3a5be9729e62f14e63ae3f4d12ffb5bc7d349a86` из PR №279. В одноразовой VM с PostgreSQL 17.11 под служебной ролью исполнены `operator/provision.sql`, `operator/activate.sql` и `operator/close.sql`. После привязки пары пилот был выключен до отдельной активации. HTTPS-шлюз взят из пакета и проверен штатным служебным входом с тестовым клиентским сертификатом.

- До закрытия Q06 вернул HTTP 200 по назначенной сессии `4a549ed6-d205-4c65-81c5-2268cfbba03e`, снимок `4436b6d1-98f6-48ad-b4ce-1d766458a8a8` версии 3, доступно 290,10 USD и одна позиция. Аудит чтения `941acb41-1d1a-4de1-ad7e-f737d37d1a57` ссылается на этот снимок.
- После `close_pilot` прежний служебный вход при том же HTTPS-запросе получил HTTP 503 `SERVICE_UNAVAILABLE` без данных сессии. Аудит закрытия `e2579703-fb31-4b44-aafc-032486b88309`. Активных разрешений, назначений и входов осталось по нулю. Исходный снимок и запись чтения остались в БД.

API-процессы подняты через Docker из закреплённых образов с раздельными ролями. Этот прогон проверял HTTPS, операторские команды и аудит. Приёмка интерфейса в браузере и запуск через Docker Compose в него не входили. Совместимость выбранной среды развёртывания требует отдельной сверки. Одноразовая VM удалена.
