# Доставка подтверждённых покупок Polygon

Адаптер `publishFinalizedPolygonBlock` принимает непрерывный диапазон по одному блоку. Источник передаёт нормализованные записи после сверки заголовков, квитанций и охвата диапазона. Ключ исполнения содержит сеть, хеш транзакции и `logIndex`. PostgreSQL записывает курсор и все задания блока одной транзакцией.

Для локальной проверки нужен пакет PGlite и JSON-массив `[{ header, log }]` из двух блоков, каждый с двумя записями BUY. В одной паре общий хеш транзакции, во второй разные хеши.

```sh
node tools/demo-signal-delivery/polygon-finalized-delivery-check.mjs /path/to/pglite /path/to/capture.json
```

24 ноября 2026 г. проверены блоки Tokor 97878474 и 97879281. Получено по два задания. После переоткрытия той же базы повтор записи дал ноль новых заданий. В той же сессии второе задание выдано после завершения первого с причиной отсутствия книги. Для проверки доставки время блоков сдвинуто к управляемому окну. Цена, комиссия, баланс и позиции в этом прогоне не рассчитываются.

## Проверка финансовой записи

```sh
CCT_DEMO_POLYGON_PAIR=/path/to/capture.json \
  node tools/demo-signal-delivery/polymarket-two-demo.mjs --postgres-bin /path/to/postgres/bin
```

Для прогона нужен локальный комплект SQL `local-data/polymarket-active-demo-20261122/isolated-replay`. Берутся первые две строки одного блока. Прогон 24 ноября 2026 г. использовал блок 97878474, индексы 495 и 503. Первый сигнал в обеих сессиях записан в «Активности» с причиной `book_unavailable`. Доступно 200 USD, открытых позиций нет. Для второго сигнала штатные функции создали по 4 762,36 доли и списали ровно по 10 USD с учётом контрольной комиссии. В каждой сессии осталось 190 USD. Подтверждение очереди выполнялось вместе с финансовой записью. Повтор вернул прежнюю квитанцию, а повторная публикация не создала заданий. Использованы подлинные идентификаторы и записи Polygon, время и котировка контрольные.

`polygon-result-ack.sql` добавляет подтверждение задания по точной записи Polygon. Для пропуска требуется сохранённое решение без финансового намерения. Для покупки требуется исполнение с совпадающей квитанцией. Обычный токен аренды, сессия и роль обработчика проверяются при подтверждении. Для этого обработчика выдаётся доступ к `acknowledge_polygon_result`, прямой вызов общего `acknowledge_bound` ему не нужен.

На временном PostgreSQL отказ по отсутствующей записи и по незавершённому допуску проверен в том же сценарии. После перезапуска в обеих сессиях сохранились позиции, баланс и ровно по одному исполнению. Названия и поля таблиц сверены с закрытой схемой Oracle чтением перед установкой очереди.

`polygon-pending-jobs.sql` устанавливается после схемы очереди, записи курсора и `polygon-result-ack.sql`. Он отделяет срок финансового исполнения от срока аренды задания. После истечения срока сделки задание остаётся в очереди с собственным ключом и выдаётся назначенному обработчику для записи пропуска. Следующее задание выдаётся после фиксации исхода предыдущего. Общая выдача исключает эти задания. Массовое завершение со статусом `expired` отклоняется, пока для такого задания требуется запись в «Активности».

В этом варианте сценария первый сигнал Tokor получает контролируемое истечение срока. Обработчик записывает `signal_expired` при балансе 200 USD, затем проводит вторую покупку и подтверждает списание 10 USD. Полномочия ограничены своей сессией. После перезапуска проверяются оба исхода.

Действующий персональный фасад Oracle требует квитанцию покупки к моменту фиксации диапазона. Изолированный прогон использует пакет штатных финансовых функций, в котором можно сохранить ожидающее исполнения наблюдение. Для подключения к закрытому Oracle нужно состыковать очередь с текущим персональным фасадом и проверить новое состояние ожидания на его точной схеме.

## Закрытый источник Tokor

24 ноября очередь установлена в закрытой базе Tokor. Начальная высота взята из действующей сессии, 97881038. Процесс `shadow-closed-tokor-queue-source.service` использует действующее чтение финализированных диапазонов и пишет только в очередь. Два запуска последовательно записали диапазоны 97881039–97881054 и 97881055–97881070 по 27 мс на запись. Фоновый процесс продолжил с 97881071 и записал до 97881086 за 28 мс. Первый участок содержал только пустые для Tokor блоки. Время записи измерено с открытием соединения и фиксацией, время чтения Polygon выведено отдельно.

Служба использует прежний срок закрытого доступа. Действующий обработчик теперь подтверждает задания в транзакции записи финансовой квитанции или пропуска. Если очередь получила блок позже финансового обработчика, источник сопоставляет задание с уже зафиксированным исходом. Сопоставление требует совпадения сессии, хеша заголовка, полного нормализованного лога и индекса исполнения. Для покупки дополнительно требуется квитанция `settle`.

На закрытом Oracle после перезапуска подтверждены три ранее сохранённых пропуска, финансовых исполнений по ним нет. На временном PostgreSQL проверен отказ для незавершённого допуска и подтверждение после записи покупки в той же транзакции. Финансовый обработчик ещё получает сигналы через исходный путь. Самостоятельная обработка нескольких покупок из очереди потребует отдельной записи ожидающих исполнений в действующем финансовом фасаде.

## Наблюдение до котировки

`polygon-waiting-observation.sql` добавляет ожидающее наблюдение, которое ссылается на точное задание очереди. В момент записи блока котировка и резерв не нужны. Доказательство наблюдения остаётся неизменяемым. Для истёкшего сигнала отдельная запись фиксирует пропуск и закрывает его задание одной транзакцией. Следующее исполнение может пройти с собственным финансовым допуском, свежим сроком и действующим токеном аренды.

```sh
CCT_DEMO_POLYGON_WAITING=1 CCT_DEMO_POLYGON_PAIR=/path/to/capture.json \
  node tools/demo-signal-delivery/polymarket-two-demo.mjs --postgres-bin /path/to/postgres/bin
```

На временном PostgreSQL обе покупки из блока Tokor 97878474 записались до котировки. Первая истекла с балансом 200 USD, затем вторая прошла через штатное резервирование и списание 10 USD. В «Активности» один пропуск и одно исполнение. Остаток 190 USD, позиция 4 762,36 доли. Котировка контрольная. Этот прогон проверяет финансовые функции временной базы. Для запуска из очереди на закрытом Oracle нужны адаптер получения котировки и проверка персонального фасада на точной копии.

## Привязка штатной котировки к очереди

`polygon-quote-job.sql` связывает канонический лог с наблюдением и выдаёт аренду только первому незавершённому заданию своей сессии. Истечение подтверждается отдельным методом после записи ожидающего наблюдения. Путь записи диапазонов получает оценки ожидания из очереди по полному нормализованному логу.

`closed_polygon_quote.py` использует штатный резолвер, окно книги, сверку рыночного исхода и финансовые методы существующего сборщика. Перед резервированием проверяется точная аренда. Подтверждение очереди входит в транзакцию покупки. Финальная проверка книги остаётся перед фиксацией, отказ откатывает покупку вместе с подтверждением задания. Патчи маршрута Maker / Taker и записи диапазона включаются явным переключателем `queued_quotes` в транспорте. По умолчанию используется действующий путь.

На временном PostgreSQL проверены получение оценок ожидания, автоматическое завершение первого истёкшего задания, отказ при подмене индекса и повторном захвате, исполнение второго задания с собственным допуском. Котировка контрольная. Патчи проверены по исходникам действующего закрытого Python-сборщика.

Метод `complete_polygon_refusal` закрывает ожидание до дедлайна при истечении проверенного окна книги. Учётную запись может создать только назначенный обработчик с действующим токеном и точным наблюдением. Ранний пропуск разрешён до выдачи финансового допуска. В «Активности» используется причина `book_unavailable`.

Сценарий `CCT_DEMO_POLYGON_BOOK_REFUSAL=1` проверен с реальными исполнениями 495 и 503 из блока Tokor 97878474. У заданий был общий ещё действующий дедлайн. Чужой токен не закрыл первое задание. После подтверждения отсутствия книги второе стало доступно и списало ровно 10 USD. Миграции ожидания и допуска также установились на локально восстановленной схеме закрытого Oracle PostgreSQL 17.11. Для сквозной проверки на свежей книге нужна отдельная финансовая копия с активной сессией.
