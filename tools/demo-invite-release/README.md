# Одноразовое приглашение в демо

Приглашение открывает существующую демо-сессию через обычную форму входа по email. После кода путь ведёт на «Главную». Шлюз принимает один активный выпуск, фиксирует пользователя и конкретный ID сессии в закрытой конфигурации, а также сохраняет связь с подтверждённой авторизацией. Ссылка расходуется атомарно. Срок действия ссылки по умолчанию 15 минут, доступ после открытия ограничен двумя часами.

## Подготовка выпуска

Соберите веб-приложение в новый каталог с выделенным префиксом:

```bash
VITE_PUBLIC_BASE=/app/invite/demo/ VITE_SHADOW_API_PREFIX=/app/invite/demo \
  npm run build --workspace @cct/web -- --outDir /absolute/private/release/dist
```

Запускайте [gateway.py](gateway.py) от отдельного системного пользователя. Рабочая копия [конфигурации](config.example.json) находится за пределами Git. Укажите действующий HTTPS origin, роль участника и ID его текущей сессии, сверенные по существующей административной записи. Пример содержит вымышленные значения. Настройте Edge → invite по отдельной приватной сети и invite → product gateway по действующему mTLS. Если Nginx и служба отличаются сетевыми пространствами, назначьте службе только приватный адрес для Nginx и разрешите вход на этот порт только ему. Не публикуйте порт на хосте. Создайте 32-байтовый случайный ключ Edge → invite в формате 64 hex в приватном файле. Настройте Nginx на перезапись заголовка `X-Shadow-Invite-Edge` этим ключом из закрытого include. Каталог SQLite и файлы с ключами доступны только службе и её оператору.

В [примере location](nginx-location.example.conf) `demo_invite_private` обозначает новый приватный upstream. В существующий список `$paper_route` добавьте `GET /app/invite/` и `GET /app/invite/demo/...` для страниц, ассетов и разрешённых API. Добавьте `POST /app/invite/redeem` и `POST /app/invite/demo/api/auth/...` для формы. Существующий серверный фильтр кандидатов должен пропускать этот префикс без предварительного Basic только в новый location. Проверки SNI, Host, Origin, лимиты и проверка тела продолжают выполняться. В маршрутах положитесь на точный префикс и порядок существующего `map`. Приватный шлюз независимо проверяет нужные методы и пути.

Ранее на закрытой копии Oracle подтверждены доставка письма во внутренний ящик, вход и чтение той же tradecraft-сессии с 200,00 виртуальных USD и 0 позиций. Перед включением проверьте, что коллеге доступен ящик для кода. Адреса тестового профиля в зоне `.invalid` работают через внутреннюю почту. Следует подтвердить способ доставки, доступный коллеге, до выдачи ссылки.

## Проверка и отключение

1. Сначала проверьте конфигурацию через `nginx -t` в закрытом окружении и убедитесь, что роль участника соответствует сессии. Отсутствие ответов от invite-службы должно закрывать только её префикс.
2. Один раз пройдите приглашение → письмо → «Главная» с ожидаемой сессией. Повтор ссылки должен получить отказ. Сверьте отказ для входа без приглашения, служебного маршрута и любого запроса изменения сессии. Проверьте существующий вход через шлюз и затем удалите закрытый тестовый выпуск.
3. При отдельном согласовании выпуска выдайте ссылку через приватный операторский канал. Не записывайте ссылку целиком в журналы, репозиторий или тикеты.

```bash
python3 -B gateway.py /absolute/private/config.json serve
python3 -B gateway.py /absolute/private/config.json issue --minutes 15
python3 -B gateway.py /absolute/private/config.json revoke
```

При откате отзовите приглашение и доступ, удалите только новый location и его записи в карте, проверьте `nginx -t`, перечитайте конфигурацию и остановите процесс. Работа с основной БД через отдельные команды и миграции для выпуска не требуется.
