# Автоматическое восстановление закрытого Tokor

В закрытом процессе включаются `--closed-auto-recovery` и прежний фиксированный `--closed-handover-until`. Путь профиля и каталог рядом с ним сохраняются между запусками. Перед изменением базы сборщик записывает и синхронизирует файл с типом операции и исходным идентификатором. При известном результате файл удаляется. Если файл остаётся после остановки, новый процесс завершает запуск с кодом 3 до включения записи. Даже неполный файл блокирует запуск. Для продолжения оператору нужно сверить исходный идентификатор по квитанциям и курсору.

Для закрытой службы на проверке использованы `Restart=on-abnormal`, `RestartPreventExitStatus=3`, `RestartSec=5s`, `StartLimitIntervalSec=120s`, `StartLimitBurst=3` и прежний `KillSignal=SIGUSR1` для плановой передачи. Эти параметры допускают перезапуск после аварийного сигнала в пределах окна. Обычное завершение и явный запрос сверки завершают процесс.

24 ноября на отдельной копии Oracle принудительная остановка после подтверждённой записи автоматически вернула тот же сеанс `b62e1bf8-dab3-4d33-ba04-d3217aae2377` к блоку `97869351` с тем же хешем. Следующий диапазон завершился на `97869355`. Затем в той же копии смоделировали падение сразу после записи маркера, до запроса в PostgreSQL. Автоматически запущенный процесс увидел маркер и вышел с кодом 3. Больше запусков после отказа не было. Число исполнений и финансовая версия в обоих сценариях остались 0 и 1. Временная копия удалена.
