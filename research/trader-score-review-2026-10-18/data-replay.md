## Новые находки

### DR-01 · P2 · Прежняя диагностика теряет доступную sub-ms точность, но её восстановление не устраняет replay mismatch

**Где:** `research/trader-score-aligned-2026-10-16/source-audit/analyze_pmxt_target.py:9–10,39,49,62–66,90`; объяснение `source-audit/PMXT_RESULT.md`, раздел о временных конфликтах.

**Новое evidence:** `data.timestamp` присутствует во всех **369 362** событиях. Разница с Parquet `timestamp_received`: от −0.000000477 до +0.000999451 секунды (машинная floating precision включена), медиана +0.000485897. Это похоже на сохранённую более точную версию received-time, **не доказательство биржевых часов/sequence**. Поле отличается от `timestamp_created_at` на −2.395395…−0.003702 секунды.

Все **63 807** per-token группы с одинаковыми обоими Parquet timestamps различимы по JSON timestamps. Различимы также все **1 642** группы конфликтующих snapshot availability. Пример из прежнего отчёта: price_change JSON `1772343006.9490216`, затем `1772343006.9495606`, snapshot `1772343006.9498518`; Parquet у них одинаковые received `.949` и created `.976`. Поэтому тезис «сами исходные данные содержат только неразличимые миллисекунды» слишком сильный.

**Новая проверка:** порядок по JSON timestamp даёт **те же 8 764 сравнения**, **8 691 совпадение глубины / 8 734 лучших цен**. Следовательно, **73/30 расхождения сохраняются**. Это не исправление источника, не доказанный непрерывный replay и не основание заменить старые 857 unknown-at-arrival на fills. Первичный JSON от 16 октября оставлен неизменным; новая проверка явно sensitivity, не новое слепое подтверждение.

**Размер расхождений, новая проверка:** из 73 случаев **32** включают отсутствующие/добавленные ценовые уровни, **41** — только разные объёмы на одинаковых уровнях. Ни один quantity-only случай не сводится к погрешности ≤1e−6: минимальная ненулевая разница объёма на общем уровне **5 токенов**, максимальная **1 799**. Во всех **30** top-price расхождениях разница >1e−6, максимальная абсолютная разница лучшей цены **$0.02**. Исторический tick size не проверен, поэтому число тиков не заявляется. JSON сохраняет три первых примера до/после по изменённым уровням: например ask 0.76, объём 107→46. Это не просто strict float equality noise; причинный источник пропуска/разницы ещё не установлен.

**Источники часов:** [текущий авторский collector](https://github.com/pmxt-dev/polymarket-orderbook-collector) описывает Rust ingestion/ClickHouse pipeline; его соответствие исторической мартовской V1 не подтверждено. Первичный архив PMXT при чтении 18 октября вернул timeout. [Описание зеркала](https://archive.pendulumflow.com/formats/v1) само сообщает, что V1 schema изучена из файлов, а не из опубликованной спецификации PMXT; это вторичный locator, не достаточная гарантия часов. На его подписи timestamp не опираемся как на доказанный контракт.

**Исправление и приёмка:** хранить raw JSON timestamp без потери точности, затем проверить первичный producer V1, момент присвоения timestamp, последовательность snapshot/update и порядок до/после записи. В новом протоколе раздельно определить event ordering и availability, сохранив late ingestion/gaps. Повторить next-snapshot сравнения и не разрешать надёжный replay, пока необъяснённые расхождения остаются. Даже успешное устранение ties не снимает signal observedAt, fees, inventory и ledger gates.

### DR-02 · P1 до повторного использования · Snapshot validator не гарантирует fail-closed поведение

**Где:** тот же `analyze_pmxt_target.py:11–28,41–49,64–66,83–89`.

**Новые контрпримеры из реальных функций кода, без их импорта с побочными эффектами:**

- `asks=[[0.5]]` корректно помечается `malformed_level`, но следующий безусловный `book(x)` выбрасывает `ValueError`.
- `asks=[[0.5,"unknown"]]` помечается `nonnumeric_level`, затем снова падает при преобразовании.
- Отсутствующее поле asks проходит validator без ошибок и превращается в пустую книгу/`fits_5_usd=false`: missing evidence смешивается с наблюдаемым отсутствием ликвидности.
- В группе одинакового availability valid snapshot и snapshot с дополнительным отрицательным bid-size имеют одинаковую подпись после `book()` (отрицательный уровень отфильтрован). При valid строке первой `gg[0]` сохраняет `invalid=false`, `conflicting=false`, `fits_5_usd=true`. Повреждённое evidence в группе не приводит к unknown. Перестановка строк меняет решение.

**Предел:** на текущем реальном срезе 8 766 snapshots содержат обе стороны; ранее и сейчас нет доказательства, что именно эти повреждения присутствуют. Это воспроизведённый дефект обработки будущего malformed input, **не доказанное завышение опубликованных 857**. Код не совершает сделок и итоговый gate остаётся закрытым.

**Исправление/приёмка:** одно безопасное parsing/validation представление, явное различие отсутствующего поля и пустого массива; invalid evidence не передавать в `book/capacity`; unknown bucket сохранять на последнем timestamp без fallback. Group validity должна учитывать все строки и быть независима от перестановки. Тесты: malformed/nonnumeric/missing side/negative size, обе перестановки mixed group, exact-arrival tie и invalid latest→older good. Повреждение должно дать определённый unknown/error artifact с coverage, а не ложную недостаточную ликвидность или сохранённый старый success-отчёт.

### DR-03 · P2 · «Первая покупка» исторического odds diagnostic иногда выбирается по цене, а не доказанному порядку

**Где:** `research/trader-score-real-2026-10-16/analyze_public.py:73–87`; соответствующее утверждение `README.md:58–60`.

`row_number` сортирует по секундному `block_timestamp`, затем `asset_id,price,usdc_amount`. Среди **9 385 wallet-condition групп** **1 246** имеют несколько ранних строк в одной секунде, **1 221** — различающиеся экономические значения; **953** — разные цены. Сортировка ASC по price систематически берёт меньшую цену при остальных равных, что не устанавливает первую покупку. В данном срезе исходы внутри таких групп одинаковы; проблема не в произвольном выборе winning outcome.

Независимая sensitivity DESC вместо ASC меняет band 0.50–0.90: **n=2963→2977**, win fraction **68.44%→67.95%**, среднее payoff−price **−3.73→−4.23¢**. Общий качественный вывод «win rate без цены недостаточен» устойчив, точные опубликованные числа зависят от неэкономического tie-break. Это не новая модель/forecast и не PnL.

**Исправление/приёмка:** до появления chain event/order identity называть объект «детерминированно выбранная строка из первого секундного bucket», либо исключать неоднозначные первые buckets с denominator/coverage, либо показывать bounds по всем возможным первым записям. Новая версия не должна заменять фактическую хронологию сортировкой цены. Тест перестановки входных строк + контроль price tie sensitivity.

### DR-04 · P2 · PMXT analyzer декларирует происхождение, но сам не проверяет входные hashes

**Где:** `analyze_pmxt_target.py:6–9,68–69,96–97`; для контраста `analyze_alignment.py:20–26` проверяет оба manifest.

PMXT читает manifest в `source`, но не сверяет `derived_sha256/derived_bytes` и hashes входных trade parquet. Поэтому модифицированный локальный parquet может породить новый отчёт, в котором прежний manifest будет выглядеть его доказательством. Здесь это статическая проверка пути исполнения, а не обнаруженная порча файлов.

**Новая фактическая проверка:** hashes всех **4 trade +5 quote +64 original real-data files** совпали; target parquet совпал по bytes/SHA. Значит нынешние сохранённые входы не объявлены повреждёнными.

**Исправление/приёмка:** до чтения аналитики проверять exact input list/bytes/SHA, token/condition scope, обязательные schema поля; фиксировать код, config/protocol и dependency versions. Mutated input должен завершать новый run ошибкой до публикации success; old result явно сохраняется как old run, а не свежий. Финальный файл с нулевыми Counter-полями также должен воспроизводиться кодом, а не дописываться вручную: сейчас отсутствующие zero keys выдаются как missing, что не меняет арифметику, но мешает строгому сравнению артефактов.

## Минимальный контракт: что обязательно именно для копии

**Уточнение scope, не ослабление денежных правил.** `model-readiness.json:10–18` связывает общий reconciliation gate с `ledger-audit/ledger-completeness.json`, который прежде всего описывает полный исторический кошелёк. Но сам frozen protocol `validation-protocol.md:49–51,110` уже различает leader PnL и собственный счёт копии. Поэтому абсолютный тезис «без полного leader wallet ledger нельзя двигать fixed-size copy research» был бы чрезмерным прочтением, а не принятым правилом.

| Объект оценки | Минимально необходимые данные | Что не требуется автоматически |
|---|---|---|
| $200 / zero-position fixed-size BUY-only инженерный probe | Полный scoped поток подтверждённых покупок и identity/dedup, signal observedAt либо явно условная latency, same-token книга/fees, собственные cash/positions/reserves и состояние на отсечке | Исторические collateral deposits/withdrawals лидера, его полный PnL или holdings других рынков |
| Стандартная копия с продажами по ADR-0016 | Всё выше + надёжное количество **у лидера перед каждой продажей** по затронутому token, все влияющие на него BUY/SELL/transfers/mint/merge/redeem с известным стартом либо независимым состоянием на нужной границе; tracked copy lots | Полная collateral-история лидера за всё прошлое, если размер новой покупки fixed и не зависит от неё |
| Покупка 3% от сделки по ADR-0017 | Подтверждённая сумма конкретной покупки и корректные единицы/fees semantics, остальные строгие проверки | Процент баланса лидера не нужен и не является принятой формулой |
| Наблюдаемый реальный PnL всего кошелька лидера | Независимые initial/final balances, все cash/token flows, fees, внешние потоки и известная переоценка | Нельзя заменить полным-looking архивом fills или собственным synthetic ledger |

BUY-only probe — отдельный инженерный estimand, **не замена принятого стандарта с продажами**. Для стандартного результата неизвестный знаменатель продажи остаётся unknown: нельзя считать нулём, пропускать неудобную продажу как будто её не было или продавать всё. Maker нельзя просто инвертировать относительно taker: mint/merge и aggregate fills требуют собственной проверенной семантики; прежний taker-only scope остаётся описательным, не полным потоком трейдера.

Собственный hypothetical ledger обязан сходиться по cash и каждому token в native precision, включая fees/reserves/partials. Но независимый RPC-balance виртуального кошелька не существует: здесь нужны независимая реализация расчёта/проверка проводок и исходных событий, с честной меткой `historical_conditional_copy`, а не требование получить onchain $200-счёт, которого не было. Реальный wallet audit сохраняет свой строгий independent endpoint reconciliation.

## ADR-инварианты для следующего replay и непроверенные сейчас ветви

Ни один нынешний quote analyzer не является денежным двигателем. Следующие acceptance проверки пока **не выполнены для runtime**, а не «провалены»:

- **0015/0017/0018:** новая самостоятельная покупка повторяется, sizing fixed/percentage не смешивается, полный объём проверяется; no silent clamp. Identity/дедуп обязательны до replay, split raw fill не равен новому самостоятельному сигналу автоматически.
- **0016:** продаётся подтверждённая доля только tracked остатка; неизвестный leader inventory не подменяется оценкой.
- **0019/0020:** local midnight фиксированной IANA зоны, DST, carry неизвестного остатка; исследовательская UTC допустима как явно заданная зона, не глобальная замена правила.
- **0021/0022:** purchase reserve занимает бюджет/позицию/дневной лимит; expense reserve — только бюджет. Cash, reserve и available отдельны. Более низкая фактическая fee не разрешает освобождать резерв без предусмотренной сверки/terminal confirmation.
- **0023:** observed-arrival sequence и неделимый precheck+reserve; block timestamp, price и row order не заменяют очередь. Пропущенное не переигрывается при позднем освобождении лимита.
- **0024/0025:** pre-intent data unknown → сигнал skipped с причиной, без выдуманного fill и резерва; подтверждённая недостаточность допустимой глубины → полный skip. Unknown уже созданного намерения сохраняет резерв. Это различие уже закреплено в `validation-semantics.md:111–115`; не заявляется новой находкой.
- **0026/0027:** подтверждённая частичная покупка остаётся, cancel request не освобождает остаток; новые fills во время отмены учитываются ровно один раз.
- **0028:** side/depth по допустимой цене + проверенные расходы, без leader price/mid/fallback и без дополнительного фиктивного spread charge. Standalone $5 capacity не доказывает precheck, cap, fee или fill.

Сценарий §5 «ждать первую книгу после arrival» требует до реализации конечного deadline, signal freshness и правила no-book/end-of-horizon; иначе ожидание может превратиться в выгодный выбор будущей цены. Это недоопределённость будущего research сценария, не уже совершённый lookahead в текущем анализаторе.

## Что проверено и что не подтвердилось

- Существующий `test_alignment.py` вновь прошёл: future/stale/invalid/conflicting/tie/NULL BBO, обе стороны, common cohort, missing fees, input integrity и закрытый score gate. Это ограниченные тесты join, не приёмка финансового replay.
- Independently пересчитана first-BUY sensitivity и новые malformed fixtures; результаты выше. Проверены manifests и numeric source bounds.
- Гипотеза о выходе Jan–Feb 2024 выборки за UTC-интервал **не подтвердилась**: min `1704067555`, max `1709250975`, строк до Jan1 и после/на March1 — 0. Фильтрация отсутствующих metadata не изменила первую временную точку ни в одной из представленных 9 385 групп. Эти гипотезы не включены в defects.
- Первоначально предполагалось противоречие §5 future-wait и ASOF реализации. После чтения **§12, пункт 3 / строка 151** вывод **отозван**: frozen protocol явно разделяет два estimand и заранее задаёт past-ASOF для этого probe. Скрытой смены primary не установлено.
- Полнота денежных событий, достоверность signal observedAt, market-specific fees, maker/cross lifecycle, terminal liquidation, Limitless и полные 30-дневные outcomes остаются прежними непроверенными слоями. Новая проверка не превращает их в финансовые убытки/нулевые fills и не подтверждает преимущество CE или LCB.

Принцип separation данных и оценки сопоставлен с [первичным разделом scikit-learn о leakage](https://scikit-learn.org/stable/common_pitfalls.html#data-leakage), прочитанным 18 октября. Это общее правило, не внешнее доказательство пригодности наших исторических финансовых данных.

## Порядок следующего исправления

1. Зафиксировать новый preprocessing contract для raw timestamps + источник их семантики; воспроизвести оставшиеся 73 mismatch на нескольких соседних events без расширения периода.
2. Исправить DR-02/DR-04, добавить adversarial regression и immutable run manifest; версия результатов отдельно от 16 октября.
3. Уточнить DR-03 в описательной статистике, сохранив старую версию и чувствительность.
4. Разделить data gates по estimand: scoped leader inventory + собственный copier ledger, а полный исторический leader PnL вести отдельным audit.
5. Только после этого расширять сохранение сигналов/книг и проверять денежные переходы ADR. Для нового подтверждающего model test нужен ещё не просмотренный период; текущий срез остаётся инженерным.
