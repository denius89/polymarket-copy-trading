# Перенос forward shadow в облако

Статус18.10.2026: подготовлен переносимый пакет; облачный запуск **не выполнен**. В проекте нет настроенного сервера, cloud CLI или SSH host config. Площадка/аккаунт и допустимые расходы ещё не указаны. Локальный сбор продолжает работать в прежних пределах24ч/256МиБ.

## Готовый артефакт

`cloud-package.tar.gz`: только исследовательский collector/supervisor/status reader, текущая публичная pilot-конфигурация, пояснения и checksums. Сырые данные, другие файлы репозитория, ключи и настройки аккаунтов не включены. Пакет не создаёт инфраструктуру и не отправляет ордера.

Среда: Linux с Python3.11+ и зафиксированным `websockets==15.0.1`, использованным в проверенном локальном примере. Отдельный непривилегированный пользователь и сохраняемый каталог данных; входящий HTTP для сборщика не нужен. Нужен исходящий HTTPS/WSS к публичным API из collector. Доступ для обслуживания/восстановления определяется выбранной облачной площадкой. Стоимость CPU/памяти/диска, traffic, архивов и мониторинга проверяется перед созданием ресурсов; покупка и бюджет не предполагаются.

Перед рабочим запуском надо проверить разрешённую доступность обеих площадок из выбранного региона, сетевые ответы/схемы, UTC/синхронизацию часов, Python/dependency versions, права записи и лимит диска. Отказ доступа сохраняется как отказ; смена маршрута для обхода ограничений не входит в перенос.

## Последовательность переноса

1. Получить целевую площадку/сервер, разрешённый доступ и бюджет. Новые credentials/приватные SSH-ключи в чат или пакет не помещать; использовать настроенное подключение либо локальную авторизацию провайдера.
2. Проверить SHA пакета, распаковать в изолированный каталог и установить pinned dependency в отдельное окружение. Настройка постоянного worker/service зависит от реальной среды и ещё не выполнена.
3. До сбора зафиксировать новый scope/config: часть текущих рынков быстро перестаёт быть активной. Старую выборку не переписывать как будто она всегда содержала новые рынки. Политика полной панели адресов и динамической подписки на их активы остаётся отдельным gate.
4. Запустить bounded smoke в новом каталоге, проверить hashes, HTTP/schema, market updates, timestamps и остановку. Затем запустить исследовательский worker с отдельными cloud run IDs и ограничениями. Локальный heartbeat сам по себе не контролирует облачный процесс; контроль нужно перенести на выбранную площадку.
5. Проверить закрытие и восстановление архива: decoded SHA/config/source совпали, процесс пишет новые части. Сохранить время переключения и overlap/gaps между двумя host. Monotonic clocks разных host напрямую не сравниваются. Нельзя просто склеить overlap как новые экономические сигналы.
6. Только после подтверждённой работы cloud collector остановить локальный через `observations/STOP`; уже собранные данные сохранить. Если cloud smoke не проходит, локальный процесс остаётся в прежних пределах; дорогая/неограниченная повторная попытка не запускается.

## Что облако не исправляет само

Оно убирает зависимость от Mac, но не доказывает непрерывность API, economic identity, полный inventory/fees или допустимые H30 результаты. Нужны monitoring/retention/restore evidence и тот же comparison protocol. Production score и реальные деньги остаются выключены. Для полноценного30дневного сбора нужно отдельно установить бюджет/хранение/объём, а не автоматически снять текущий лимит256МиБ.
