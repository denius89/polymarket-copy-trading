# Пригодность истории для ускоренного исследования · 18 октября 2026

Процедуры: S11 (provenance/время/полнота), S12 (исполняемость копирования). Проверены сохранённые источники и новый conditional proxy; реальные ордера и сборщик forward не менялись. Результат не вводит новый публичный скор.

## Вывод

**История пригодна для ограниченного предварительного сравнения направленной цены покупки, но не для сравнения реальной чистой доходности копировщиков.** Пригодных H30 денежных траекторий по замороженному стандарту по-прежнему **0**. Проверенных исторических timestamp первого получения итогового исхода — **0**. Условное приближение `resolved_at + embargo` не устраняет этот пробел.

Архив 2024 года даёт ненулевую панель для вспомогательного вопроса: выделяют ли простые оценки адресов покупки с более высоким последующим `итоговая выплата − цена лидера` **на других условиях рынка**? Единица — одна первая наблюдаемая покупка адреса в condition; метрика в долларах на одну долю, не процент доходности и не PnL. Цена лидера здесь определяет сам диагностический объект, а не цену нашей копии.

## Источник и проверка

Сохранённый Polymarket-v1 / Standard Binary / taker-only, revision `5aa1b9d52316a8b2e789e81c8ae42c7ed532e8aa`, TimeSeventeen, CC-BY-4.0. Взяты 60 локальных файлов `daily_aligned` за январь–февраль 2024; имена партиций UTC+8, фильтры применяются по Unix секундам в UTC. Фактические timestamps: 1704067555–1709250975; **72 977 строк, 539 condition, 4 975 taker**. Это ограниченная удобная выборка старого режима v1 и сохранённых resolved рынков, не репрезентативная история всех пользователей.

[Новый исполняемый аудит](history_fitness.py) заново проверил хеши, размеры, допустимые имена и схемы **69 исходных файлов** reference-пакета (64 archive/meta/readme, 4 мартовских trade subsets, 1 PMXT) и **5 quote-файлов**. [Результат с input lineage](history_fitness-v2.json) содержит SHA256 кода и проверенных результатов. Исторические данные и прежние отчёты не перезаписаны.

Важные пределы полей источника: `resolved_at` и final winner — ретроспективные metadata. Нет доказанного recorded `known_at`; даже дата завершения раньше cutoff не гарантирует доступность метаданных пользователю в тот момент. Формальное сравнение ниже **условно** предполагает эту доступность после временного буфера. Snapshot revision/hash доказывает происхождение файла, но не своевременную публикацию каждой записи.

## Отбор без искусственной хронологии

1. Адрес — lowercase taker; maker не инвертируется и не прибавляется как второй независимый наблюдатель.
2. Сначала выбирается самый ранний block second **среди всех идентифицируемых BUY** данного адреса/condition. Невалидная первая запись не заменяется более поздней валидной.
3. Если в этом earliest second более одной исходной строки, группа исключается целиком. Полных экономических ID нет, поэтому даже похожие дубли не очищаются предположением. Цена не используется для порядка.
4. Затем требуются singleton, `0 < price < 1`, конечная цена, непустые asset/outcome/winner/resolution, `trade < resolved_at`, статус resolved. На condition требуется одна согласованная winner/resolution и ни одной строки с missing metadata.
5. Модель обучается на январских покупках только с `resolved_at + 24h < 1 февраля UTC`. Чувствительность: 0 и 168 часов; это тест условной предпосылки, не доказательство истинного known_at.
6. Из февральского теста глобально удаляются condition, встречавшиеся **во всех январских исходных строках**, включая не попавшие в обучающие labels/eligibility. Участие адреса в обоих периодах допустимо — вопрос именно о ранжировании того же адреса на другом condition. Общий event/underlying может оставаться зависимым, независимость condition не доказана.

## Что остаётся непригодным

- Реальная цена/глубина и момент доступности сигналов для январского архива отсутствуют; нулевые source fee не доказывают бесплатность копирования.
- Позиции лидера/наши tracked lots, пропорциональные продажи, reserves, расходы и ликвидация открытых позиций не восстановлены. Нельзя получить CE по выдуманной положительной денежной трансформации этой edge-метрики.
- Мартовский aligned/PMXT срез остаётся диагностическим: 193 045 trade rows, 38 токенов/19 condition; в targeted book replay остаются **73 несовпадения глубины, 30 несовпадений BBO**. Новая история не исправляет этот отдельный источник.
- Final payout в auxiliary diagnostic не заменяет mark-to-market на дату H30 и не проверяет своевременную продажу.
- Свежий forward пилот не закрывает месяцы истории задним числом; отсутствующие данные не подставляются нулём.

Следующий исследовательский выбор может касаться только **кандидата для forward-проверки**, с превосходством не подтверждённым. Основная финансовая цель и ранее согласованные веса скора остаются без изменения.

### Уточнение барьера после межагентской сверки

Первый сохранённый `history_fitness.json` применял более слабое удаление только condition с пригодными обучающими метками (59 адресов /733 наблюдения /245 condition). Он оставлен как исторический диагностический output и **не используется как основной результат**. После независимой сверки применён более строгий барьер всех 340 январских raw condition: основной результат `history_fitness-v2.json` — **48 адресов /433 наблюдения /143 condition**. Это исправление границы набора, а не настройка по результатам моделей; численные рейтинги моделей аудитор не использовал.

## Дополнительная проверка Q4 2023

После первого расчёта мощности владелец основного исследования добавил заранее описанную sensitivity: увеличить **обучающую** историю октябрём–декабрём 2023, сохранив февраль для условного будущего. Это exploratory extension, не новая независимая проверка и не настройка гиперпараметров на прибыли.

[Независимый extension audit](extension_fitness.py), [immutable результат v3](extension-fitness-v3.json): все **92 файла, 4 191 023 байта**, SHA256 совпали одновременно с новым manifest и зафиксированными LFS OID источника; точная 24-польная схема совпала с исходной. Получено **71 373 строки, 859 condition, 3 222 taker**, без missing identity в проверенных трёх полях. Все строки каждого файла оказались внутри соответствующих UTC-суток по block timestamp. Это проверка фактического диапазона, не доказательство отсутствия пропущенных chain events.

Обнаружено расхождение с общей фразой README поставщика «Spilt by UTC +8»: в измеренных Q4-файлах нет строк вне filename UTC-day; последняя базовая партиция `2024_02_29` содержит события **00:04:42–23:56:15 UTC 29 февраля**. Поэтому нельзя объявлять отсутствующими последние восемь часов февраля только на основании README и отсутствия файла `2024_03_01`. Анализ фильтрует actual timestamps; полнота цепочки всё ещё не подтверждена. Утверждение об UTC+8 выше относится к описанию поставщика, не к доказанному контракту локальных партиций.

Более длинный train не создаёт наблюдаемые исторические label-known timestamps, стаканы или расходы; **0 strict H30 paths /0 verified label observation times** остаются без изменения. Результат модели на увеличенном train сохраняется отдельно от основного сравнения.
