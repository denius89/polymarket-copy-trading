# Денежная сверка Polymarket v1 за единый период

16 октября 2026. Исследовательский аудит. Публичный скор и ADR не изменяются.

Для проверки результата копирования недостаточно сопоставить покупки и конечные исходы. Нужны движение collateral, фактические токены, продажи, mint/merge/redeem и доступные цены выхода в одном временном окне. Срез HF Polymarket-v1 содержит торговые и CTF события, но не содержит полные ERC20/ERC1155 переводы, начальные остатки или стаканы. Поэтому даже полный набор этих файлов сам по себе не даёт сверенный PnL адреса.

## Что установлено по источникам

[HF Polymarket-v1](https://huggingface.co/datasets/TimeSeventeen/Polymarket-v1) на зафиксированной версии `5aa1b9d52316a8b2e789e81c8ae42c7ed532e8aa` имеет raw IDs `chainId_blockNumber_logIndex`. У CTF таблиц в опубликованной схеме нет времени блока: его требуется получить по blockNumber; имя дневного файла использует UTC+8. Срез календаря нужно ограничивать по фактическому UTC timestamp, а не по одному имени файла. Полный опубликованный `CTF/splits.parquet` занимает 4 957 001 014 байт, `redemptions.parquet` — 2 792 374 236 байт. Их полная загрузка без фильтра не нужна для минимального теста. Схема не содержит таблиц Transfer.

[Исходник Polymarket v1 Trading.sol](https://raw.githubusercontent.com/Polymarket/ctf-exchange/main/src/exchange/mixins/Trading.sol) показывает три существенных случая: встречные заявки, две покупки через mint и две продажи через merge. Нельзя автоматически назначить maker противоположную taker сторону того же токена. Контракт также испускает индивидуальные maker-fill события и суммарное taker-fill событие с exchange в качестве контрагента. Сложение обоих как независимых денежных движений удваивает часть оборота. Комиссия удерживается из получаемого актива: для BUY это outcome tokens, для SELL collateral. Исходник прочитан из официального архивного репозитория; точное соответствие bytecode развёрнутому контракту на выбранном блоке ещё требует проверки. Поле архива `fee_usdc` требует проверки преобразования и привязки к стороне; нулевые комиссии старого среза не проверяют этот код для современных рынков.

[ConditionalTokens.sol](https://raw.githubusercontent.com/gnosis/conditional-tokens-contracts/master/contracts/ConditionalTokens.sol) задаёт split, merge и redemption. Для вложенных collections и nontrivial partition нельзя применять упрощённую формулу root binary. Количество burned shares при redemption и выплаченный collateral — разные единицы.

Текущая [документация позиций](https://docs.polymarket.com/trading/positions/how-positions-work) описывает одновременно CTF и Protocol V2. Для архива 2024 года требуются именно исторические CTF/USDC.e contract addresses и decimals; современный pUSD/PositionManager не является заменой.

## Проверка доступа к независимым остаткам

Read-only `eth_getBlockByNumber` исторического блока отправлен на три открытых endpoint без аккаунта, подписи и ключей. Ответы сохранены в [rpc-probe.json](rpc-probe.json): dRPC и PublicNode вернули HTTP 403, polygon-rpc.com — HTTP 401. Запрос не получал исторические balances или receipts. Это наблюдение доступности из данной среды, а не утверждение об отсутствии публичного Polygon API. [Официальный список Polygon](https://docs.polygon.technology/pos/reference/rpc-endpoints) описывает публичные endpoints и ограничения.

## Минимальный проверяемый денежный контур

1. Заморозить один UTC период и block boundaries. Адреса выбирать по активности до периода проверки, не по последующему результату. Сохранять proxy/safe адрес владельца позиций; signer не всегда держатель токенов.
2. Получить historical balanceOf collateral и каждого задействованного outcome token перед первым и после последнего блока. Для полного кошелька нужен полный universe токенов; проверка выбранных токенов остаётся частичной.
3. Получить canonical receipt/logs всех переводов этих активов, включая внешние поступления/выводы, ERC1155 TransferSingle/TransferBatch, mint/burn. ERC20 transfer с exchange ещё не автоматически прибыль/внешний поток: классифицировать по контексту transaction.
4. Transfer logs задают фактическое изменение актива. OrderFilled и CTF lifecycle объясняют его. Не складывать оба представления повторно. Группировать по transactionHash; canonical ID включает chainId, blockHash и logIndex. HF ID без hash требует отдельной проверки canonicality.
5. Для известного начального остатка проверить exact-unit равенство `ending = opening + received − sent` по collateral и каждому токену. Использовать целые onchain единицы; float Parquet не является точным учётом.
6. Отделить external flow от торговли. Общая экономическая прибыль равна изменению стоимости портфеля минус чистые внешние поступления. Считать только наблюдаемый адрес, без заявления о полноте стратегии человека и внешних хеджах.
7. Для стандартного копировщика начать с явно заданного cash и нулевых позиций. Получать размер продажи лидера как долю его реально восстановленной позиции; неизвестный знаменатель — неизвестная продажа, не 100%. Сохранять резервы, partial fills и пропуски.
8. Переоценить открытые позиции по наблюдаемой книге на конец периода. Недостаточная глубина делает стоимость выхода частичной/интервальной. Последняя сделка или будущий settlement не подменяют доступный bid.

## Независимые проверки для допуска результата

| Проверка | Что должно сойтись |
|---|---|
| ID и порядок | Ни один canonical log не применён дважды; receipt принадлежит выбранному блоку; порядок transactionIndex/logIndex сохранён |
| Collateral | Opening balance + все transfer дельты = независимый ending balance |
| Outcome tokens | То же равенство для каждого token ID; batch раскрыт без потери элементов |
| Mint и merge | Root binary split уменьшает collateral и создаёт обе ноги; merge выполняет обратное, без создания доходности из ничего |
| Redemption | Погашенные токены и payout соответствуют известным на этот момент payout numerators/denominator |
| Fill и fee | Изменение полученного актива совпадает с fill за вычетом fee в правильной единице; maker/taker aggregate не задвоен |
| External flow | Пополнение не увеличивает прибыль; вывод не создаёт убыток |
| Equity | Cash + наблюдаемая ликвидационная стоимость − external flows согласованы с итоговой метрикой |
| Исполнение копии | Ни одной сделки до observedAt; книга не из будущего; объём не превышает доступную глубину и лимиты |
| Полнота | Необъяснённые расхождения остаются явным failure, не «прочими расходами» и не нулём |

Проверка формулы на этих инвариантах — тест учёта. Прогнозную надёжность модели она не доказывает: для неё необходимы раздельные периоды обучения, выбора и нового результата, достаточное число событий и отдельная проверка исполнения. Buy-to-settlement диагностический тест нельзя обозначать полным копированием.

## Ограниченная попытка получить raw fills за март

[Официальный HF filter API](https://huggingface.co/docs/dataset-viewer/filter) поддерживает SQL comparison predicates, `offset` и `length` не более 100. Запрос `/splits` вернул `orderfilled/train`, без pending/failed. Запрос на 100 строк с `1772323200 <= block_timestamp < 1772582400` и сортировкой по timestamp завершился timeout 50 секунд: [параметры и результат](hf-filter-march.json). Уменьшенный запрос на 10 строк без сортировки вернул HTTP500 с сообщением о загрузке индекса: [ответ](hf-filter-march-10.json); один [повтор после ожидания](hf-filter-march-10-retry.json) дал тот же HTTP500. Получено 0 raw rows. Это интервал 1–3 марта 2026 UTC, выбранный для сопоставления с книгами, а не январский диагностический срез.

API dataset viewer не фиксирует revision параметром этого запроса. Даже успешный ответ требовал бы записи версии индекса и сопоставления с raw file IDs; первые 10 или 100 строк не представляли бы весь период или полный кошелёк.
