# Координация чатов и сохранение контекста

Согласовано владельцем 03.11.2026. Общее правило для рабочих чатов проекта Shadow / Polymarket Copy Trading MVP. Описывает рабочий порядок, не запускает разработку, фоновые опросы или новые автоматизации.

Переписка объясняет решения, но не заменяет фиксацию общего результата. Макет не доказывает работу сервера, свежая дата не превращает предложение в принятое решение.

## Один ответственный и прямое общение

- У каждой задачи один ведущий чат. Он собирает контекст, согласует зависимости и возвращает владельцу единый результат. Если задача передаётся другому чату, обозначить нового ведущего и получить подтверждение принятия.
- Чаты вправе самостоятельно запрашивать недостающий контекст и передавать результаты внутри этого проекта. Владелец не должен вручную пересылать сообщения. Сохраняются явные ограничения для конкретных чатов, включая ранее установленную паузу на сообщения в чат админки, пока владелец её не снимет.
- Передавать минимум необходимого, без секретов и персональных данных. Указывать конкретный вопрос, статус решения, ссылку на источник с версией и ожидаемый ответ. Не пересылать целые истории и не выдавать полученный текст за новое поручение владельца.
- Уведомлять только направления, чья работа зависит от изменения. Получатель подтверждает, что изменение учтено, или называет противоречие. Различать «отправлено», «получено» и «учтено»; молчание не означает согласия.
- Не запускать цепочки взаимных подтверждений, постоянные опросы, массовые рассылки и повторное исследование уже закрытого вопроса. Если ответ нужен, использовать ограниченное ожидание; продолжать независимую работу, а зависимую часть обозначить ожидающей ответа.
- Сначала разрешать расхождение по актуальным источникам. Если остаётся противоречие или требуется изменить согласованное продуктовое правило, ведущий приносит владельцу один вопрос с вариантами и общей рекомендацией. Не принимать решение за владельца и не обсуждать его бесконечно между чатами.

## Актуализация без лишнего чтения

1. При существенной новой задаче прочитать AGENTS, краткую актуальную часть ROADMAP/PROJECT_STATE и нужную строку карты. Подробности открывать по зависимости. Простой вопрос не требует полного погружения.
2. В памятке задачи сохранять последний проверенный main SHA, пути документов и, при работе с дизайном, Figma file/node, версию при доступности и время чтения. Локальная копия сама по себе не подтверждает свежесть GitHub.
3. При продолжении проверить, изменился ли источник. Если baseline известен, читать только соответствующий diff и связанные решения. Если baseline потерян, источник недоступен или возник конфликт, выполнить ограниченную повторную сверку и обозначить неизвестное. Не считать старый контекст актуальным без проверки.
4. Для дизайна читать затронутые экраны и компоненты. Если нет надёжного diff Figma, проверить эти узлы непосредственно; не заявлять, что весь файл неизменен. Для задачи без зависимости от интерфейса посещение Figma не обязательно.
5. При недостающем объяснении задать профильному чату точечный вопрос. Не перечитывать все чаты, все ADR, исторический журнал или весь каталог навыков при каждом возвращении.

## Памятка для продолжения

После значимого этапа, перед длительным перерывом или передачей работы обновлять короткий блок в существующем документе направления. Не создавать новый отчёт на каждую реплику и не копировать общие правила в каждый файл. Памятка содержит ссылки на источники, а не их пересказ целиком.

| Поле | Что сохранять |
| --- | --- |
| Задача и ведущий | Результат поручения, границы, ответственный чат |
| Проверенный контекст | main SHA, затронутые документы, Figma узлы/версия/время при необходимости |
| Решения | Ссылки и статус «предложено», «согласовано», «реализовано» или «заменено»; для принятого решения — основание согласования |
| Выполнено и проверено | Конкретный результат, PR/commit, охват и итог проверок; документ не называть реализацией |
| Осталось и зависимости | Открытый вопрос, адресат, состояние ответа, занятые общие участки |
| Продолжение | Следующий конкретный шаг; ветка/рабочая копия при незавершённой работе |

Подробная история остаётся в PR, ADR и журнале. PROJECT_STATE получает короткую запись со ссылкой. ROADMAP меняется при изменении очереди, а не ради каждой памятки. Эта карта не дублирует текущие статусы всех задач.

## Совместные правки и качество

Перед изменением общего файла, контракта или компонента проверить активную работу и обозначить ведущего, участок и ветку/узлы в памятке либо прямом сообщении затронутому чату. Если участок занят, договориться о порядке и получить подтверждение. Это рабочая договорённость, не техническая блокировка; перед публикацией повторно проверить исходную версию и diff. Чужие изменения не перезаписывать, общую рабочую папку не переключать во время чужой работы. При необходимости изолировать правки.

Для существенного междисциплинарного изменения запросить адресную проверку затронутого направления — например, выполнимость интерфейса у бэкенда или полноту хранения у БД. Мелкие правки проходят соразмерную локальную проверку. Доступ к чату не доказывает, что проверка состоялась. Фиксировать реальные замечания и результат их разрешения.

## GitHub без повторных разрешений

Постоянное разрешение владельца распространяется на проверенные commit/push/PR/merge проектных материалов в рамках поручения. Порядок работы — поручение → работа → проверки → публикация → ссылка на результат. Не заканчивать готовую задачу вопросом «публиковать ли в GitHub?» и не запрашивать новое общее разрешение. Применять проверки и правила сохранения из [REPOSITORY_GUIDE](REPOSITORY_GUIDE.md).

Разрешение не расширяет объём поручения и не разрешает deploy, реальные сделки, изменение доступа или публикацию чувствительных данных. Настройки разрешений плагина этим документом не изменяются. Если системная проверка блокирует операцию, указать конкретное действие, причину и что осталось несохранённым; выполнить доступную часть, не выдавать блокировку за отсутствие разрешения владельца. Не обходить системные ограничения.

## Применение и проверка удобства

Правила применяются при следующей связанной задаче, без обязательного пробуждения всех чатов. Текущий чат при существенной работе сверяет AGENTS; памятки заполняются по фактическому продвижению. Не обещать мгновенное обновление контекста всех открытых чатов.

На первой задаче, затрагивающей несколько направлений, проверить, что владелец поставил задачу один раз, ведущий сам получил необходимый контекст, изменение учтено затронутыми чатами, результат опубликован и работу можно продолжить по короткой памятке. Исправлять обнаруженные неудобства, не вводя постоянный полный аудит. Ожидаемый эффект — меньше пересылок, повторных объяснений и чтения; численную экономию токенов без измерения не заявлять.
