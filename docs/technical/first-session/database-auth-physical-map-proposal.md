## 1. Объём и статус

Приняты **37 собственных служебных таблиц auth_control**, AC01–AC37 ниже. Собственный документальный каталог — **36 Shadow + 37 auth_control = 73 таблицы**. Внутренние таблицы Supabase, внешний журнал witness, хранилище файлов evidence и изолированный test-control в это число не входят. Ни одна таблица этой работой не создана. Число73 не означает, что внутренняя база провайдера полностью описана или интеграция доказана.

Пакет описывает таблицы/колонки/типы/ссылки, обязательность по вариантам, уникальность и полноту, writers/readers, транзакции и исправленный порядок защиты. Это не SQL/DDL, не миграция и не код. Все предметные проверки — «не выполнялось».

Разделяем: (а) прежние принятые C04/C05/C06/claim/Q06/Q02, Auth PR №199 и продуктовый P-RESET; (б) принятую этой записью физическую дельту P01–P05; (в) ещё не завершённое полное издание API/реестра D02 и фактические доказательства D03. ## 2. Общие поля и способы обеспечения

Все37 таблиц имеют `environment:text`, `id:uuid`, `created_at:timestamptz`, все NOT NULL; PK(environment,id). Собственные IDs серверные UUIDv4; client operationId хранится отдельно. Время UTC с миллисекундами, срока нет после now≥expires_at. Счётчики bigint положительные, без сброса/overflow; вне БД строки. Идентификаторы среды берутся из доверенного контекста.

Обозначения: U=uuid, V=bigint, T=timestamptz, S=text, B=boolean, H=bytea32, BY=bytea, J=jsonb, I=integer; `?` — допускается NULL только в названном варианте. Остальные поля обязательны. `→ACnn` — составной FK своей environment; `→shadow.name` — FK собственной среды на существующую таблицу Shadow. Все ссылки на login дополнительно проверяют realm/actor, ссылки на ownership — draft; ссылки на factor/challenge/case — subject/purpose/version. Точные составные target keys создаются для таких ссылок, а не заменяются сравнением UUID в приложении.

N/L — NOT NULL/локальная форма/закрытый discriminator; U/F — немедленная scoped уникальность/FK; D — отложенная проверка полноты и согласия **с обеих сторон** до commit; W — запрет произвольной записи/изменения истории; T — единый writer/guard/транзакция; B — защита транспорта и криптографическая проверка адаптера. D не изображается межтабличным CHECK. Чтение повреждённого обязательного комплекта после допуска — RECORD_UNAVAILABLE, не default/пустой успех.

Mutable таблицы дополнительно имеют `version:V, updated_at:T`, далее помечены **M**. Исторические — **H**: вставка и утверждённые одноразовые terminal-поля; последующие значения результата не переписываются. Для одноразового terminal-перехода W/T фиксирует его только один раз и замыкает D. Обычный runtime не удаляет историю. Стирание секретного ciphertext/digest — отдельный узкий путь §5, не удаление результата/FK.

`record_format:S` у новых Auth результатов/manifest — самостоятельный Auth-формат v1 принятой карты; он не добавляет пятый тип к четырём прежним Shadow форматам. `kind/purpose/action/stage/reason` замкнуты на конкретные таблицы принятых Auth §§2–14 и кандидатных API §§1–9, с явной матрицей допустимости. Для полного издания словарей нужен отдельный registry delta D02; неизвестные значения не разрешаются как произвольный text.

WebAuthn raw assertion/attestation не копируются в историю: хранится canonical public-payload digest и проверенные typed refs. Сравнение проверяет оба компонента намерения, не только общий payload_digest. Принятый предел новых Auth JSON-полей —65536 компактных UTF-8 байт/глубина8, без дублей/неизвестных ключей/усечения; audit safe_details отдельно16384. Новые записи и переходы допускаются только после полного варианта decoder; отсутствующая обязательная typed ссылка не заменяется JSON.

## 6. Транзакции и восстановление

### 6.1. Внешний Auth и результат

Три отдельные границы: admission/seal; внешний вызов; локальный finalizer. До dispatch seal короткая T фиксирует AC04+AC08/нужный challenge и admitted epoch; внешний вызов вне SQL locks. Provider response сам по себе не локальный login. Finalizer под текущими guards сохраняет AC05, AC04.result/phase, нужные challenge/steps/counters/security/login/window/audit одной T. Обязательные циклы замыкаются до commit. Ошибка с unknown seal или external outcome запрещает новый вызов; saved result возвращается после действующего допуска.

Supabase capability correlation и точные TOTP steps остаются блокирующей **проверкой возможности реализации**, не решаются количеством таблиц. Если достаточного provider proof нет, outcome uncertain и затронутый доступ ограничен. Это не неверный OTP, не exactly-once письма и не разрешение заменить принятый профиль. BA-G07 должен получить отдельное свидетельство после разрешения реализации.

### 6.2. Completion, cookie и Q01

Подтверждённый completion одной локальной T замыкает login+AC05+AC16+AC07 и при staff — прежний slot/отзыв; source operation/context сохраняются. Q01/current staff и все пути повторной выдачи cookie заранее берут X AC16 в G2 после выбранного login. Первый successful current read закрывает окно до200, не трогает idle; неизвестная фиксация не200 с обещанием закрытия. Восстановление первым может подготовить ответ, физически доставленный после Q01; это не новое разрешение и не оживление отозванного login.

Recovery deadline неизменяем; closing/result/secret lifetime различаются. Связь source result/login/secret целая; AC16 без login/неверного realm либо secret до обязательного закрытия — повреждение, не новый login. Повтор закрытия идемпотентен, история completion не обновляется. Первый Q01 после истечения recovery-window по всё ещё действующему full login остаётся допустим: отсутствие права повторно выдать cookie не отменяет уже существующий вход; first_confirmed_at может быть позже прежнего closed_at. Удалённая временная recovery-копия не делает такой current read повреждённым, если стирание законно отмечено.

### 6.3. Claim admission и epoch fence

Принят AC19 как **история исполнительного допуска**, без изменения тела claim, unique(environment,draft_id), собственного receipt и advisory guard. Подготовка consent сама AC19 не создаёт. Первый допущенный POST до помещения во внутреннюю очередь сохраняет source consent/epoch/token под G0…G3; повтор с неопределённым AC19 не запускает второго исполнителя. Если факт admission неизвестен, сначала сверка того же consent; server token не выбирается заново клиентом.

Предметная claim-T берёт S gate и проверяет **сохранённый**, а не заново назначенный epoch, затем текущий доступ/consent, G3 и AC19, G5 draft. Прежние CLAIM-OK/ownership/pointer/audit и AC19.committed замыкаются одной T. Точный уже завершённый результат читается по Shadow цепочке без старого живого proof; разрешённый202 опирается на AC03 и имеющийся AC19, если admission уже сохранён, вместе с текущим доказанным user; отсутствие AC19 не стирает доказанную историческую связь consent. При timeout/неясном commit AC19 не объявляется closed_without_effect. Разрешённые три rollback-попытки остаются внутри прежнего бюджета и одного admission, только после доказанного конца предыдущей попытки.

Консервативный fence: control writer X G0 дожидается старых DB-T, закрывает среду и увеличивает epoch; новые обычные mutating paths/observer не допускаются. Уже отложенный handler со старым AC19 epoch после открытия отвергается, даже если никогда не достигал G3. Reconciler подтверждает завершение/прекращение прежних исполнителей; claim не имеет очереди автоresume. В новой primary T после fence проверяются полные receipt/ownership; без эффекта старый consent.execution_closed_at и, если AC19 существует, его closed_without_effect с evidence фиксируются вместе. Если AC19 ещё не создан, закрытие consent и отдельное Auth audit/evidence не создают фиктивную историю admission; старый запрос затем отвергается по execution_closed_at. Только затем новое явное согласие может допустить новую попытку.

Не допускать тупика «gate закрыт, поэтому нельзя завершить сверку, необходимую для открытия»: закрытый gate допускает отдельные минимальные **reconcile-only** операции по уже запечатанным действиям. Они записывают доказанный outcome/закрывают старый допуск, но не выполняют новый claim, не посылают повторный provider effect, не выпускают full login/cookie и не открывают business paths. Внешний уже начатый Auth effect может быть только установлен и отражён с ограниченным principal state; невозможность установить исход сохраняет gate/затронутый доступ закрытым. Допуск ограничен перечисленными здесь reconciliation/closure действиями и writers §5; точные маршруты/закрытые result-варианты должны быть сведены в D02. Произвольный bypass не разрешён.

Цена принятого P03 механизма — временная остановка изменяющих операций среды при таком восстановлении. Это явно принятый дополнительный допуск поверх C04/C06, без пересогласования их семантики. Их ключи/результаты/полнота остаются прежними; новый admission слой не меняет исторический outcome и не разрешает новый ключ. Свободный G3/пустой SELECT/expiry не заменяют fence.

### 6.4. Guest и Q02

Guest creation даёт AC03/06, не draft/CMD. Guest refresh под X context сохраняет тот же ID/proof и исходный result операции; точный replay не продлевает срок. Принятая связь с C04 применяется только к **created/updated** в той же T: guest.expires_at=max(старого, draft.expires_at). Unchanged/exact replay/ошибка/GET не продлевают guest/draft. В том числе допустимый нечисловой raw с успешной C04-правкой — обычный updated, не новое правило валидации. Это явно принятая P05 дельта guest lifecycle RD03; код C04 не создавался.

Q02: candidate binding только locator. В одном Serializable-снимке защищаются G0 и **все G1**: scope parents → paper controls → полный набор sources/traders и нужный login policy. Scope S защищает состав members, publishers полного каталога соблюдают прежние guards. Затем G2 binding/security/reader/login и candidate tuple проверяются; лишь после этого разрешена выдача. Если guard изменился/нужна другая ранняя ссылка — полный технический исход без автоматического retry; не идти из G2 обратно за G1. Далее весь manifest/страница из этого же снимка; не новое чтение после ожидания.

Binding publisher заранее определяет старые/новые scope parents, X их в G1, X binding в G2; текущий mapping и version публикуются вместе. При любой замене разрешённого основания publisher меняет scopeRevision затронутых областей даже при возврате к прежнему scope ID. Иначе A→B→A может оживить старый cursor, поскольку bindingVersion не входит в принятый fingerprint. Формат cursor/readContextId не меняется. Полный old/new набор не подтверждён — откат, не поздняя блокировка.

### 6.5. Witness и уже сохранённый результат

Принятый P04 witness protocol: внешний intent с уникальным witness_id и ожидаемой областью → AC34(intent_registered) → предметная T с бизнес-фактом, AC35 и AC34(local_committed) → внешний confirmed → отдельная отметка AC34.confirmed. Сетевые вызовы вне долгих SQL locks. Epoch/target/version повторно проверяются перед эффектом; intent для отменённого плана не становится обещанием эффекта. No-effect отметка требует доказательства, не отсутствия строки после restore.

После локального commit результат **уже сохранён**: отсутствие внешнего confirmed не превращает succeeded/rejected в новый outcome и не разрешает повтор/новый ключ. Транспорт может остаться технически неопределённым; разрешённое чтение актуального primary результата восстанавливает исходный receipt при доказанном текущем доступе. Когда неизвестна свежесть восстановленной копии или сам допуск —503/закрытый gate, а не ложное разрешение. Внешний pending intent заставляет restore разбирать этот интервал; наличие локального receipt без новой проверки fresh epoch не открывает восстановленную среду.

Это явно принятый P04 operational слой RD06. Связь AC34/35 с прежними CMD/CLAIM/REVIEW обязательна в принятом проекте, без ослабления их локальной атомарности. External journal failure до intent останавливает новое защищённое изменение; цена доступности принята, соблюдение прежних5s/10s ещё должно быть измерено. Внешний root/head/подписанные подтверждения нельзя восстановить вместе с БД и считать независимыми.

### 6.6. Staff/reset/уведомление

Bootstrap manifest+два handle целы, handle consume+context+result целы. Recovery-code consume+ограниченный context/result целы; выдача нового набора+отзыв старого+10 children+несекретный result целы. Полный staff replacement только после актуального credential/security/grants, с прежним slot/отзывом и audit. Pair complete финализирует обе стороны одной локальной T, не одну сначала.

Reset/disable сначала публикуют transition barrier, который проверяет каждый новый login; внешний factor change отдельно; подтверждённый local finalizer закрывает прежние login и ставит нужное mfa_requirement. Enroll сохраняет прежние входы, disable→none, reset→enrollment_required. Повтор результата не отзывает входы, созданные после завершённого изменения. Случай нового login во время transition закрыт до сверки, не определяется старым provider token. Уведомление AC36 создаётся с соответствующим result, а его dispatch не меняет результат защиты.

Принятые budgets/retry не меняются. Постоянный S gate не глобальная X-очередь, но fence намеренно задерживает всю среду; эта цена доступности явно принята в P03.
