## 1. Общие условия и обозначения

Каждый вариант — отдельный изолированный прогон с собственными синтетическими IDs и исходным состоянием. Берётся настройка S-case, а не уже использованный draft другого прогона. Внутри сценария повтора, гонки или восстановления сохраняются именно его исходные IDs/key/payload. Историю не стирают и slot не освобождают ради следующего примера. Нужный контролируемый стенд, точки остановки процесса и средства наблюдения ещё предстоит подготовить по H05; этот документ не разрешает вмешательство в рабочую систему.

Наборы S01/S02/S03/S04 — Polymarket/Limitless × fixed/percent с B200. В F01–F03 и F14–F16 повторить существенные варианты на всех четырёх наборах: каждый раз ожидаются cash/free/equity=200/1, P=20/1, D=30/1, резерв/позиции/торговый результат=0/1. F04 использует B200 против B300 по K05; F10/F11/F12 — также S13/S14 с B110 и точными P=77/10, D=143/10. Это выборка по риску, не полный декартов набор всех значений и отказов.

Сотрудники обозначаются только **«владелец 1» и «владелец 2»**, равноправные постоянные principals. Тестовые состояния отозванного/неподходящего назначения — отдельные изолированные состояния существующего контракта, не изменение полномочий реальных владельцев. Полный вход/guest proof/актуальные grants подтверждаются H01/H03; UUID, роль из запроса и существующий FK не заменяют авторизацию.

Профили START, REJECT, INVALID, ROLLBACK, REPLAY, SAVE, CLAIM-OK, REVIEW-OK, READ-U, READ-A, WORKER и группы FIN/CMD/AUD/EVT/LOGIN/STAFF берутся из матрицы. **«Ноль изменений» относится к измеряемой операции и её scope**, а не к чужой конкурентной транзакции. Разрешённая foreground-активность своего login может иметь служебную дельту; admin-read не продлевает user login. Внешний Auth и Shadow не считаются одной транзакцией.

Ориентир START: +1 session, +1 settings, +1 initial flow, +1 journal, +2 entries, +1 snapshot; по +1 key/receipt/details; +1 start audit и +1 outbox. При исходном absent slot — +1 slot с generation=1, pointer на свою session; draft получает целую used-пару без изменения version/TTL ввода. Начальный journal: cash=+B/1, source=−B/1, сумма=0/1. Первоначальный snapshot: free/equity/initial_funding=B/1; остальные финансовые суммы и торговые счётчики нулевые. До worker/admin-read нет consumer receipt/audit_authorizations. Полные FK/версии/форматы проверяются вместе с количеством.

## 2. Общий порядок сверки исхода

1. **Зафиксировать исходную точку.** A-ID/вариант/F-ID/S-case, environment/постоянный actor, исходный clientCommandId и hash/version, draft/ownership/review, guards, slot observation/generation, IDs/версии имеющихся строк. Payload намерения сохраняется в предусмотренном защищённом контексте; его полное тело и секреты не копируются в диагностику.
2. **Зафиксировать точку сбоя.** Какая локальная транзакция/операция, какой шаг, подтверждён ли commit/rollback либо исход пока неизвестен. В гонке — порядок захвата/публикации и результат каждой транзакции. Одного сетевого таймаута или текста UI недостаточно.
3. **Перепроверить текущий доступ.** Повтор/Q05 не раскрывает чужую команду и не обходит отозванный login. Допустимый новый полный login того же постоянного user может прочитать свой результат; это не новый actor/key. До разрешения неопределённости UI не показывает оптимистичный успех/отказ и не подставляет нулевой баланс.
4. **Установить исход в свежем согласованном чтении.** Основное хранилище, не отстающая реплика/кэш/старый Serializable-снимок. Найденный корректный receipt имеет приоритет. Первое отсутствие receipt не доказывает rollback: прежняя транзакция может быть in-flight. Продолжение исходного намерения допустимо только под общей защитой того же ключа, после получения права исполнения и текущих проверок. Неизвестный/повреждённый receipt не делает ключ свободным.
5. **Сравнить дельту и неизменность.** После установленного исхода — полный комплект соответствующего профиля, точные связи/числа/версии, отсутствие второго funding, неизменность исходных review/истории и чужих scopes. После подтверждённого rollback наблюдать из новой транзакции. Проверять деньги по заранее заданным S-значениям и паре проводок, не повторным вызовом того же builder.
6. **Зафиксировать доказанный результат или предел.** Неизвестный исход остаётся неизвестным; отсутствующий обязательный снимок — техническая недоступность, а не EMPTY. Повтор чтения/доставки не ремонтирует деньги. Для restore дополнительно нужен разбор непокрытого периода F19, прежде чем разрешать затронутые входы/повторы/worker.

| Наблюдение | Ожидание после сверки | Запрещённый вывод |
| --- | --- | --- |
| Подтверждён rollback | Комплект этой операции отсутствует, прежнее состояние цело | Создать rejected только из технического отката |
| Корректный succeeded receipt | Один прежний START; REPLAY тех же IDs/версий | Новый key/session/funding из-за потерянного ответа |
| Корректный rejected receipt | Прежний окончательный отказ, его reason/details; FIN не создан | Запуск при том же key после улучшения условий |
| БД недоступна / commit не выяснен / первое Q05 пусто | Неопределённость, прежнее намерение/key | Считать отсутствие ответа подтверждённым отсутствием команды |
| Обязательная строка/связь повреждена или формат неизвестен | Затронутая операция недоступна, безопасная диагностика | Обнуление, пересборка EMPTY/funding, освобождение slot |

Сверка графа использует следующие независимые признаки. Для rollback они сравниваются с исходным состоянием; для START/restore — с подтверждённым исходным результатом и конкретным S-case. Наличие всех строк без согласованных значений не считается успехом.

| Группа | Что сопоставляется |
| --- | --- |
| USER/LOGIN/STAFF | Environment/realm/provider subject и постоянный principal, full-auth, текущие сроки/отзывы/slot/назначения. Историческая evidence не подменяет текущую авторизацию; данные после backup отдельно по F19 |
| CAT/RULE/REVIEW | Та же venue/source/trader revision и immutable policy; raw/normalized/mode/guards/проверенная версия draft. Исторические ссылки не заменяются последними указателями каталога |
| DRAFT/CLAIM | Current ownership и целый claim-result; source draft/review/ownership session; used_at/used_by_session_id вместе. Служебный claim/used не продлевает TTL ввода; guest review не переназначен |
| SLOT/FIN | Один slot env/user/paper, правильный current_session_id/generation; session/settings/snapshot принадлежат друг другу, current snapshot pointer и state согласованы, начальные sequence/version=1 |
| Учёт внутри FIN | Ровно один initial flow B, один journal и две противоположные entries той же unit/session; баланс0/1; cash/free/equity=B/1, нулевые резервы/торговые суммы/счётчики для пустого S-case; P/D и F либо q — по его эталону |
| CMD | Key/receipt/details замкнуты, actor/type/clientCommandId/hash совпадают; result IDs/версии успеха ведут к тому же комплекту, rejected не создаёт собственный FIN. Отсутствие details сейчас повреждение, не архив |
| AUD | Один start audit подтверждённого запуска; отдельные audits Q06 имеют свои request_id и достаточную историческую evidence. Наличие audit не подтверждает доставку ответа и не является торговым событием |
| EVT | Неизменяемые event/resource/command/version и один consumer receipt на env/consumer/event; подтверждённый локальный эффект согласован с receipt. Lease/attempt/processed проверяются отдельно; старый token и восстановленная очередь не дают права на новый эффект |

## 3. Запуск, повторы и конкуренция

### F01. Обрыв до commit в каждом шаге START

**Связи:** A13, A19, A60, A100, A103; S01–S04. **Зависимости:** H02/H05. **Таблицы:** весь START.

**Подготовка:** доступный user draft/review, absent slot, новый scoped key; снять исходные counts/версии. **Воздействие:** в отдельных прогонах прервать транзакцию после резервирования key; после slot; после session/settings; после funding/journal/каждой из двух entries; после snapshot/pointer; после used-пары; после receipt/details; после audit; после outbox; перед commit. Если реализация группирует шаги, H05 должен обеспечить наблюдаемую границу для проверки каждой обязательной связи; фиктивные committed промежуточные состояния не создаются.

**Ожидание:** только после доказанного rollback профиль ROLLBACK всего C06: FIN/CMD/start audit/outbox +0, новый slot отсутствует, draft прежний, used-пара пуста. Не допускается ни key без receipt, ни одна entry без второй, ни session без snapshot/источника. Ошибки самих отложенных проверок полноты отдельно — F10.

**Сверка:** новый согласованный снимок хранилища, сравнение всех обязательных детей и исходных значений. В отдельном варианте подтверждённый serialization/deadlock допускает повтор по F09; произвольное падение не объявляется таким конфликтом. Успешное разрешение прежнего намерения позже даёт ровно один START.

### F02. Commit состоялся, ответ потерян; отдельно исход пока неизвестен

**Связи:** A13, A18, A29, A69, A106; S01–S04, K03. **Зависимости:** H01/H02/H05.

**Действия:** (а) подтвердить commit C06, оборвать ответ до клиента; (б) задержать/оборвать связь внутри commit, первое Q05 ещё не видит receipt; (в) сохранить недоступность БД; (г) отдельно доказать rollback после таймаута. Клиент сохраняет key/payload, затем закрывает/открывает страницу или получает новый полный login того же user. Для (б) предусмотреть обе развязки — поздний commit и доказанный rollback.

**Ожидание:** (а)/поздний commit — весь прежний START и REPLAY без дельты FIN/CMD/start audit/outbox; (в) — никакого утверждения об исходе; (г) — ROLLBACK, после исчерпания исходного бюджета временная недоступность без rejected. Новый login не меняет actor команды. При отозванном доступе результат не выдаётся до допустимого входа.

**Сверка:** общий порядок §2; успешные IDs/receipt и единственный funding=B/1 совпадают. Первое пустое Q05 и истёкшие 5 секунд не доказывают rollback; механизм выяснения исхода не обещает завершиться за 5 секунд. Неизвестный формат найденного receipt — F17, не новый запуск.

### F03. Одинаковый ключ: два запроса, другой payload, сохранённый отказ

**Связи:** A11, A15, A29, A46, A101; S01–S04, N07, K03. **Зависимости:** H01/H02/H05.

**Действия:** два запроса одного actor/type/key с тем же payload одновременно при отсутствующем ключе; проверить обе очередности победителя и ожидание чужого commit. Затем повтор после нового login; отдельно тот же key с изменённым payload. В отдельном прогоне получить окончательный авторизованный REJECT (например, новый C06 по предметно отклонённому review N07, если контракт H02 допускает достижение ключа), затем повторить его после смены языка/условий.

**Ожидание:** успех — суммарно один START, второй возвращает тот же результат после разрешения конфликта; не обязательно оба сетевых ответа успевают стать успешными в одном бюджете. Другой payload конфликтует, прежний core/details не изменяются. Повтор ранее сохранённого отказа возвращает прежний reason/безопасные параметры, не запускает session. Если отказ N07 произошёл до допуска к key, это INVALID, а не доказательство REJECT-варианта.

**Сверка:** уникальный полный scope key, один комплект CMD, одно финансирование; новый request/login не новый actor. После ожидания чужой транзакции проверка выполняется свежим чтением. RU/EN меняют отображение причины, не её сохранённый смысл.

### F04. Разные ключи, один пользователь: площадки и источники запуска

**Связи:** A12, A17, A27, A61, A62, A101; S01/S08, K05. **Зависимости:** H02/H05; исторически свободный slot — M02.

**Действия:** один U-X, PM B200 и LM B300 в двух drafts/reviews при absent slot; одновременно два ключа. Отдельно: два key одного review и два review одного draft. В каждом варианте задать обе очередности, не выбирать победителя по площадке.

**Ожидание:** максимум один START. Если PM первый — free/equity=200/1, если LM — 300/1; никогда500. Один current slot; проигравший draft не used. Авторизованный окончательный отказ после key — REJECT, подтверждённый технический rollback — без CMD этой попытки. Нельзя требовать два receipts при любом тайминге. В варианте общего draft used ссылается только на победившую session/review.

**Сверка:** sum funding по созданным этим прогоном sessions равна бюджету победителя; проверить исторические unique draft/review, не только current slot. Проверка повторного использования после действительного завершения session требует M02; STOPPED сам по себе не делает slot свободным, историю не сбрасывают.

### F05. Сохранение формы: атомарный результат, no-op и replay

**Связи:** A27, A28, A54–A57, A98, A100, A102; S01, K02/K07, C04-E01–E08 синтетического документа. **Зависимости:** H02/H05; post-claim/target/FK приняты блоком3; точные DTO/декодеры/испытания — остаток M01.

**Действия:** create — сбой между draft/ownership/current pointer/last_input_receipt_id/key/receipt/details и перед commit; update raw F «20»→«20.00» — сбой после изменения ввода/version/pointer до результата. Отдельно commit с потерей ответа, последующая правка и exact replay прежнего key. Сравнить новый unchanged с актуальной version и новый stale no-op; два новых key с одной expectedVersion; гонку SAVE↔C06 в обеих очередностях. Использовать отдельно C04-E06 с коротким invalid raw/сохранёнными fieldErrors.

**Ожидание:** подтверждённый rollback не оставляет ни части CMD, ни изменения draft/ownership/pointer. Успешный create/updated/новый unchanged имеет по одному key/receipt/details; только created/updated меняет last_input_receipt_id. Новый unchanged сохраняет прежние version/TTL/ввод/pointer, но свой исходный результат; stale после допуска к key даёт rejected CMD без изменения draft. Exact replay возвращает исходные result version/моменты/changeKind/fieldErrors, без CMD +1 и без отката текущей формы. Невалидный короткий raw может быть сохранён, FIN не возникает. Unknown сначала выясняется по исходному ключу, не объявляется rollback.

**Сверка:** все шесть C04 result-полей и mandatory details; текущая версия ввода ссылается на свой created/updated receipt, исторический result не требует равенства новой текущей version. Claim/used не меняют input pointer. SAVE с изменением раньше C06 делает прежний review stale; START раньше запрещает новые изменения/новый no-op used draft, но не авторизованное чтение старого результата. Result/атомарность приняты блоком 2; точные FK/доказанный post-claim поиск приняты блоком 3. Принятие не означает выполненный тест.

**Принятое дополнение C04, блок3:** C04-E09/E12/E14: потерянный guest create восстанавливается без draftId; rejected update хранит только проверенную target-пару. В обеих гонках с claim сохраняются целый результат/ввод и неизменный original key; после победившего claim нового guest C04 нет. Проверить version/времена/fieldErrors старого ответа после user-правки, без отката current input.

### F06. Неоднозначный Auth и claim гостевого draft

**Связи:** A02, A23, A26, A35, A100, A107; S01, K01. **Зависимости:** H01/H02/H05.

**Действия:** потеря ответа verify провайдера; затем подтверждение фактической identity полным доверенным входом. Claim одного guest draft: сбой после новой ownership, до current pointer/закрытия handle/claim receipt; отдельно commit с потерей ответа. Ещё вариант — два разных полностью вошедших пользователя с доказательством одного guest draft; другой девайс без доказательства; обращение по старому handle после commit.

**Ожидание:** локальный rollback claim возвращает весь прежний комплект, внешнюю Auth-сессию не объявляет отменённой. Commit — ровно CLAIM-OK; повтор тем же user возвращает его, другой не присваивает и не читает draft. Старый guest review неизменен; новый user review создаётся отдельно, FIN/C06 +0 до явного запуска. Недоказанный/неполный вход не создаёт full auth_session и не обходит MFA/recovery.

**Сверка:** provider subject/realm связан с одним постоянным principal, current ownership/claim receipt согласованы; старый handle закрыт. Потеря ответа не повод автоматически объединить аккаунты или переназначить старый review. Защита одноразового verify требует доказательств Auth-компонента, одного FK недостаточно.

**Принятое дополнение C04, блок3:** C04-E10–E14: current user ownership и claim того же draft/user ведут к original guest ownership успеха либо target ownership отказа update; context равен actor key. Проверить чужой user, совпадение client ID разных scopes, потерю draftId/несколько собственных claims, rejected create без draft, закрытый старый proof и независимый другой draft контекста. Поиск/чтение не переносят key и не исполняют отсутствующий guest key. Подтверждённый claim не меняет input version/TTL/pointer.

### F07. Сбой сохранения review и изменение исходных данных

**Связи:** A28, A36, A40, A60, A100; S13/S14, N08/N11. **Зависимости:** H02/H05.

**Действия:** прервать C05 после чтения draft/controls, при записи нормализованных полей, перед commit; одновременно опубликовать новую trader revision/изменить draft. Отдельно сохранить предметный отказ N08 или N11; отдельно потерять ответ успешного C05.

**Ожидание:** rollback — setup_reviews +0; commit — одна полная неизменяемая запись конкретной транзакции с согласованными исходными ссылками/guards либо сохранённый предметный отказ. Invalid normalization: все normalized NULL, raw сохранены, allowed_to_start=false. Сбой хранилища не превращается в business review. Ни один C05 не создаёт FIN/slot/C06 receipt.

**Сверка:** подтверждённый review сверяется с его source version, а не с последним raw. Старый review не обновляют под новый каталог. После потери ответа C05 контракт поиска/повтора определяется H02: здесь не вводится неописанный C05 idempotency key и не обещается глобально одна review на любые повторные запросы. C06 требует точного review и отдельного подтверждения.

### F08. Изменение допуска во время запуска

**Связи:** A16, A36, A47, A102; S03/S04. **Зависимости:** H01/H02/H05/H06.

**Действия:** по одному конфликту за прогон: отзыв user login/доступа, изменение активной policy, trader/start controls, publication новой revision; C06 остановлен после предварительного чтения или на ожидании guard. Воспроизвести обе сериализованные очередности. Независимый отзыв staff Assignment проверить отдельно как контроль scope.

**Ожидание:** C06 раньше — полный START с доказанными действовавшими версиями; значимое изменение раньше — перепроверка и соответствующий отказ либо полный serialization rollback. При недействующем actor нет выдачи/нового авторизованного бизнес-результата от его имени. Нельзя пройти C06 по старому снимку только потому, что parent lock дождался освобождения. Изменение дочерних назначений/прав сопровождается предусмотренным guard, не пропускается как отсутствие старой строки.

**Сверка:** trace порядка + сохранённые versions/IDs + дельта профиля; прежние policy/revisions не переписаны. Значимое изменение, требующее нового review, не подменяется автоматическим принятием новых условий за пользователя. Независимый staff revoke не запрещает обычный user C06; его действие на Q06 — F13. Успех с последующим отзывом не удаляется и не запускается снова.

### F09. Классы ошибок, три попытки и общий бюджет

**Связи:** A48, A67–A72, A105; S02/S04. **Зависимости:** H02/H05/H06.

**Варианты:** одна или две подтверждённые serialization/deadlock ошибки, затем успех; три подтверждённых отката; бизнес-отказ; unique/constraint error; unknown commit. Для повторов — общий монотонный бюджет 5 секунд с начала обработки до ожидания БД, максимум три попытки включая первую, выбранные паузы 50–150 мс. Отдельные ориентиры: потрачено4 с → следующее ожидание максимум1 с; остаток80 мс/пауза120 мс → новой попытки нет; пауза сначала помещалась, но после неё бюджет исчерпан; скачок UTC вперёд/назад.

**Ожидание:** только подтверждённые разрешённые конфликты допускают автоматическую повторную полную транзакцию с теми же key/payload и всеми проверками. Откатившиеся попытки не оставляют CMD/FIN. Третий rollback/исчерпание бюджета — временная недоступность, не durable rejected. Пауза не сокращается ради новой попытки, бюджет не сбрасывается. Unique/constraint не маскируются под serialization; unknown — F02. UTC-сроки проверяются независимо от монотонной длительности.

**Сверка:** trace начала/конца каждого ожидания/паузы/попытки и подтверждения rollback; конечная дельта START/REJECT/ROLLBACK. Одна сумма created_at не доказывает бюджет. Не применять правила автоматического C06 retry к C04/claim/Q06 без их отдельного контракта.

## 4. Целостность и защищённое чтение

### F10. Неполный комплект, чужие ссылки и неверная точная сумма

**Связи:** A19, A31, A32, A40, A59–A63, A95, A103; S13/S14, K04/K07. **Зависимости:** H05.

**Действия:** отдельно для C04 — draft без last_input_receipt_id, изменения raw без нового updated результата, receipt без details, unchanged как pointer; для START — commit родителя без каждого обязательного ребёнка, незамкнутой пары key↔receipt/session↔snapshot/used↔session; одну entry вместо двух, третью entry, разные units, несовпадающую сумму; trader revision другой venue/source, чужой actor/ownership; одновременно effective F и q; неполную n/d/used-пару, zero denominator, несокращённую 154/20 вместо77/10, пустую format-метку. Отдельно — изменение immutable истории и удаление используемых draft/review/settings. Положительный контроль — полный корректный S13/S14 со всеми циклами в одном commit.

**Ожидание:** нарушающий commit целиком отклонён самой БД; старые строки/версии сохранены. Запрет API не заменяет доказательство ограничения БД. Корректный контроль проходит, P=77/10 и D=143/10, funding=110/1, две entries +110/1/−110/1. Ни округление до7/14, ни частичное создание session не допускаются.

**Сверка:** сравнить все обязательные ссылки/канонические пары из новой транзакции. Механизм H05 должен покрывать вставку родителя без детей и прямые допустимые пути записи, не только проверку insert entry. Реальных нарушений в рабочей БД не вносить; текст не разрешает отключение её ограничений.

**Принятое дополнение C04, блок3:** C04-E15: по отдельности несовпадение key/receipt.command_type; половина target-пары/чужой actor; result ownership другого draft; повторный created; updated с неправильной expected+1; unchanged как current pointer; raw при прежнем pointer; receipt без details. Отдельно подставить C04 в session/settings/funding/journal/start audit/outbox C06. Все нарушения отклоняются до commit; положительный C04 и полноценный C06 проходят, old receipt version1 законен после current version2. Это проверки будущей БД, не выполненные тесты.

### F11. Повреждение snapshot и атомарность current pointer

**Связи:** A33, A53, A64–A66, A110; S14, K06. **Зависимости:** H02/H05/H06, M03.

**Действия:** в отдельно подготовленной повреждённой копии — отсутствующий обязательный snapshot, ссылка на чужую session, повреждённые обязательные поля. READ-U и READ-A после проверки доступа. В другом контролируемом состоянии M03 — публикация целого следующего snapshot и state/pointer: сбой между частями; варианты current3→4, повтор3 при current3, попытка3→2. Имитировать поздний ответ старой версии. Отдельно различить as_of и created_at.

**Ожидание:** повреждение закрывает затронутое чтение с безопасной причиной; FIN/CMD/SLOT не ремонтируются, slot не освобождается. Публикация — весь согласованный новый комплект либо rollback, pointer не уходит назад/на чужую цель. Повтор той же текущей версии — no-op без новой записи, меньшая версия — отказ. READ не меняет version/as_of и не создаёт snapshot.

**Сверка:** фиксированные IDs/session/version/формат и безопасный код ошибки; значения в UI не заменяются нулями. Отдельная диагностика не audit разрешённой выдачи несуществующего снимка. Writer следующих версий и способ подготовки повреждённой копии требуют M03; новые продуктовые endpoints/торговые строки для этого не изобретаются.

### F12. Сбой аудита при чтении админки и потеря ответа

**Связи:** A05, A24, A37, A49, A52, A104; S14, K06. **Зависимости:** H01/H02/H03/H05.

**Действия:** владелец 1 имеет текущий полный доступ. Остановить Q06 после проверки/чтения snapshot, после audit до evidence, перед commit; отдельно вызвать ошибку сохранения audit/evidence или превышение допустимого JSON-поля. Другой вариант — commit состоялся, ответ потерян, затем новый запрос чтения от владельца 1 и независимый от владельца 2.

**Ожидание:** rollback — нет частичного audit/evidence и защищённого ответа. Commit — +1 audit выдачи с достаточной evidence на request_id, даже если человек ответа не получил. Каждый новый разрешённый запрос — отдельный audit, не повтор START. Оба владельца видят те же session/settings/snapshot/version/as_of и free/equity110/1, P77/10, D143/10. FIN/CMD/SLOT без изменений; user login не продлён.

**Сверка:** сетевой trace доказывает отсутствие защищённого ответа до commit; строки аудита сами не доказывают доставку/просмотр. Число evidence определяется реально использованными grants, не всегда равно1. При неизвестном Q06 commit не утверждать нулевой audit только из таймаута; выяснить результат, не выдавая данные до подтверждения.

### F13. Отзыв назначения и замена staff login во время Q06

**Связи:** A24, A30, A100, A104, A107; S14, K06. **Зависимости:** H01/H03/H05.

**Действия:** для владельца 1 Q06 конкурирует с отзывом подходящего назначения/изменением grants либо полной заменой staff login, обе очередности. В замене login отдельно прервать локальный commit между новым login, отзывом старого и slot; отдельно потерять ответ после commit. Неполный/неудачный passkey — отдельный отрицательный вариант. Владелец 2 остаётся отдельным principal.

**Ожидание:** допустим согласованный READ-A до отзыва либо отказ/rollback после него; старое назначение из кэша не даёт обхода. Полная замена login фиксирует новый/отозванный старый/slot атомарно, после rollback прежний локальный комплект цел. Неполный вход не вытесняет рабочий. При unknown устанавливается фактический staff slot, не создаются два рабочих входа. Внешнее подтверждение passkey не считается частью локального rollback.

**Сверка:** текущие версии guards/assignment/grants/login и историческая evidence аудита совпадают с доказанной очередностью. Не собирать право из несовместимых частей разных grants. Отзыв владельца 1 не отзывает владельца 2 и не изменяет финансовые данные user.

## 5. Outbox и повторная обработка

### F14. Worker падает до локального эффекта и consumer receipt

**Связи:** A14, A108; S01–S04. **Зависимости:** H04/H05.

**Подготовка:** START уже committed, outbox pending, consumer receipt отсутствует. **Действия:** успешный захват, затем падение до локальной транзакции эффекта; отдельно внутри неё перед receipt/перед commit. После подтверждённого rollback и разрешённого нового захвата — обработка того же eventId/consumer.

**Ожидание:** захват расходует попытку даже при падении; до effect commit нет ни локального эффекта, ни consumer receipt. При дальнейшем успехе ровно один receipt, служебная доставка завершается. Переход/повтор учитывает lease и согласованные паузы. FIN/CMD/start audit +0 на всём пути; session доступна до worker. Первый consumer — локальное наблюдение, без почты, торговых команд и повторного финансирования.

**Сверка:** состояние outbox, attempt/lease и уникальность env/consumer/event; сравнить FIN с исходным S-case. Не вводить дополнительную таблицу эффекта: точное локальное наблюдение/его доказательство определяется H04 в границах уже принятого consumer.

### F15. Эффект сохранён, processed не подтверждён; пятая попытка

**Связи:** A14, A108, A109; S01–S04. **Зависимости:** H04/H05.

**Действия:** commit локального эффекта вместе с consumer receipt, затем падение до outbox processed — если реализация разделяет эти транзакции. При общей транзакции effect/receipt/processed проверяется её commit с потерянным ответом. Повторить крайний случай: это пятый успешный захват. Отдельный контрпример — пятый захват завершился доказанным rollback без receipt.

**Ожидание:** существующий корректный receipt проверяется прежде решения о новом эффекте. Только завершение служебной доставки, без шестого эффекта/повторного funding; attempt не сбрасывается. Пятый сбой без успешного receipt → needs_review с сохранением исходного события. Сам needs_review не разрешает повторный эффект. Если состояние эффекта неизвестно, сначала сверка receipt/атомарной транзакции, а не предположение об отсутствии.

**Сверка:** один consumer receipt и подтверждённый локальный результат, event payload/ресурс неизменны. H04 должен определить конкретный путь завершения доставки после пятого commit без нового захвата эффекта; документ не подменяет этот открытый контракт обещанием готового worker.

### F16. Старый lease, пять сбоев, неизвестный формат и позднее событие

**Связи:** A33, A108, A109; S01–S04; поздние версии — M03. **Зависимости:** H02/H04/H05.

**Действия:** worker W1 задержан, его lease истёк, W2 получил новый token; W1 пытается сохранить эффект/завершить новую попытку. В независимом прогоне пять подтверждённых временных сбоев без receipt: захваты1…5, паузы1/5/30/120 с. Ещё два варианта — неподдерживаемый формат события и позднее событие старой версии после подтверждённой публикации новой проекции.

**Ожидание:** перед commit сверяются действующий token и время; W1 не завершает захват W2. Уникальность receipt остаётся обязательной даже при lease. После пяти неуспехов/неизвестного формата — needs_review, запись не удаляется; неизвестный формат не интерпретируется как старый. Позднее событие не переносит snapshot/pointer назад и не пересоздаёт обязательный стартовый снимок.

**Сверка:** trace времени захватов/паузы и выданных tokens без секретов, один receipt максимум, FIN/CMD неизменны. Конкретные bounded lease/renewal/timeouts — H04; числа lease не выбираются из этого примера. Сценарий поздней проекции не разрешает добавить новый consumer/финансовое действие.

## 6. Форматы, резервная копия и сверка после восстановления

### F17. Неизвестный формат или повреждённый receipt

**Связи:** A51, A80–A82, A94, A95, A110; S02/S14. **Зависимости:** H02/H05/H06, M03/M05.

**Действия:** по отдельному изолированному варианту каждого из четырёх типов review/settings/snapshot/receipt — реально неподдерживаемая text-метка либо повреждённое обязательное содержимое. Запрос соответствующего чтения/старта/повтора после доступа. Для receipt отдельно отсутствующие обязательные details/несовпадающая result-ссылка. Положительный контроль — четыре независимых v1-читателя.

**Ожидание:** затронутая операция недоступна; исходная запись не меняется, тип+формат не угадываются. Неизвестный receipt/key не освобождается и не запускается заново, отсутствие details не считается разрешённым архивом. Нельзя переписать метку в v1, создать EMPTY или новый funding.

**Сверка:** безопасная диагностика тип/полный ID/environment/формат/код; для snapshot — session/version. Полное содержимое/суммы/секреты не дампятся. Хранилище диагностики M05 ещё не определено; неподдерживаемую метку не вводить в продуктовый реестр лишь ради теста.

**Принятое дополнение C04, блок3:** C04-E09–E13/E16: original scope определяется после текущей авторизации и claim-цепочки, не по одному UUID. Неизвестный формат/пропавшие details после допустимого доступа дают техническую недоступность; неподтверждённая цепочка не раскрывает чужое существование. Exact replay использует исходный fingerprint/actor, Q05 не пересчитывает result по current draft. Expiry/used не удаляют доступный historical result.

### F18. Восстановленная копия с известным полным START

**Связи:** A20, A87, A88, A108, A111; S07, K03. **Зависимости:** H01/H02/H04/H05/H06, M05.

**Подготовка будущего прогона:** доверенная копия изолированной среды после полного S07 (Limitless/fixed B300); зафиксированы точка/ID копии и состояние обработки event. Два варианта: receipt consumer отсутствовал на момент копии; receipt уже был, processed мог отставать. **Действия:** restore в отдельную изолированную среду при закрытых рабочих входах/запусках/worker; сверка всего графа и полный обход четырёх форматов F20.

**Ожидание:** тот же slot/session/settings/draft/review/key/receipt, cash+300/1/source−300/1, free/equity300/1, P30/1/D45/1, нулевые резервы/торговые суммы. Не создаются новый START или audit его повторного исполнения. Отсутствующий consumer receipt не доказывает отсутствие эффекта после точки копии — проверить непокрытый период F19.

**Сверка:** сравнить USER/LOGIN/STAFF и их текущую допустимость, DRAFT/REVIEW/CAT/RULE, FIN/SLOT/CMD, AUD/EVT и дедуп. Только после доказанной сверки и явного допуска изолированного прогона — REPLAY/контролируемая WORKER-проверка без нового финансирования. Истёкший lease сам не открывает очередь. Это не разрешение заменить рабочую БД.

### F19. Копия старше последнего START, эффекта или отзыва

**Связи:** A20, A34, A86, A111; S07, K03/K06. **Зависимости:** H01/H04/H05/H06, M05.

**Действия:** обозначить T0 — точка доверенной копии; после T0 в исходном изолированном контексте отдельно подтвердить START B300, commit consumer receipt/эффекта, отзыв user login/назначения либо замену staff login. Восстановить T0 в закрытую отдельную копию. Проверить два набора доказательств: достаточные доверенные записи о периоде после T0 и неполные/противоречивые сведения.

**Ожидание:** отсутствующий в T0 receipt не означает «команда никогда не выполнялась»; старое назначение/login не становится снова действующим. Пока период не подтверждён, затронутые запуски/доступы/повторы/worker закрыты. Нет второго B300 из-за старого отсутствия key и нет повторного эффекта события. Отчёт честно содержит непокрытый период, а не утверждение о пустой истории.

**Сверка:** по каждому исходному command/event/actor установить доверенный факт и источник доказательства, сопоставить постоянные IDs, отзыв/текущий slot и дедуп. Место хранения/полнота доказательств и конкретная процедура восстановления недостающих данных — H06/H01/H04; их нельзя заменить ручным новым funding или объявить гарантированное восстановление утраченного периода. Успешная сверка — необходимое условие дальнейшего явного допуска, не автоматический запуск.

**Принятое дополнение C04, блок3:** C04-E16: копия до C04/claim не доказывает отсутствие оригинальной команды или действительность старого guest proof. В барьер сверки входят key/type/target/result/details, current input pointer, historical ownership и claim, Auth evidence после точки backup. Пока исход/отзыв не доказан, затронутые действия закрыты; новый draft/key/перенос scope не способ ремонта.

### F20. Полный обход форматов и неизменяемый отчёт совместимости

**Связи:** A79–A94; S01/S14 как обычные записи. **Зависимости:** H02/H06, M03/M05.

**Действия:** на изолированной согласованной копии перечислить фактические пары тип/формат и прочитать **все** записи review/settings/snapshot/receipt выбранным кандидатом сервера. Отдельные варианты: неизвестная пара вне реестра; повреждённая строка вне начальной выборки; обрыв обхода; один тип действительно пуст в отдельном допустимом исходном наборе; новый прогон после ошибки/смены версии сервера, схемы или набора форматов. Не удалять связанные строки из S-case для создания пустого типа. Будущая новая версия одного типа допускается только при наличии отдельно принятой спецификации.

**Ожидание:** ошибка/неизвестная пара блокирует подтверждение совместимости; частичный обход не success. Пустой тип — «Нет данных для проверки», не успех и не доказательство неисправности. Новый ID/отчёт каждого прогона; прежний не переписывается. Кандидат обновления/старый сервер при возврате не допускаются, если не читают фактическую историю. Смысловое изменение требует отдельной версии затронутого формата; опечатка документа сама метку не меняет.

**Сверка отчёта:** версия сервера/схемы, ID/дата/точка копии, фактические пары и число просмотренных/непрочитанных строк, завершённость, результаты каждого типа и безопасные ошибки с полным ID. Количества служат доказательством полноты, не новой продуктовой метрикой. Отчёт не новая таблица из 34; размещение/доказательства — M05. Возврат старого сервера не выполняет автоматический restore и не стирает новые данные после backup. Форматный gate не означает готовность всей эксплуатации.

## 7. Входные пределы, сроки и варианты с открытыми стыками

### F21. Неверный транспорт и превышение размера дополнительных данных

**Связи:** A49, A50, A73–A78, A98, A99; S01/S04, N20 как короткий raw-контроль. **Зависимости:** H02/H05, M05.

**Действия:** отдельно C04/C06: несжатое тело65536/65537 исходных UTF-8 байт; Unicode/пробелы; дубликаты имени в одном объекте с равными и разными значениями; глубина8/9 при корне1; compressed request; неизвестное поле закрытого DTO. Отдельно дополнительное поле review/details/audit/outbox16384/16385 байт единого компактного сериализатора. Добавить безвредный уникальный контрольный маркер в отклоняемое тело для проверки отсутствия содержимого в диагностике; реальные секреты не использовать.

**Ожидание:** превышение/неподдерживаемый транспорт — INVALID до SAVE/C06, прежние draft/raw/version/TTL/receipt сохранены. Граница размера/глубины проходит только своё ограничение, не весь DTO. Нельзя обрезать строку, распаковать неподдерживаемое, выбрать first/last key или удалить неизвестное поле молча. Ошибка сформированного сервером обязательного audit/outbox/details откатывает всю содержащую его транзакцию; это не всегда ранний INVALID.

**Сверка:** байтовые размеры и безопасная причина без тела/контрольного маркера во всех доступных диагностических каналах. HTTP-размер до parse отличается от компактного JSON-поля, значимые пробелы внутри строки сохраняются. Точное допустимое DTO/поле для граничного наполнения — H02; не изобретать новое поле ради65536 байт. Raw «abc» N20 может сохраняться как ввод, хотя не проходит нормализацию.

### F22. Длина raw/чисел, каноничность и переполнение версий

**Связи:** A32, A39, A40, A43, A45, A96, A97; S13/S14, N01–N22, K02. **Зависимости:** H02/H05.

**Действия:** 64/65 Unicode code points raw и 64/65 десятичных цифр компонента n/d без знака; отрицательный denominator/NaN/infinity/дробный компонент; round-trip version/sequence/generation как строк; попытка +1 на пределе допустимого типа. Для EVT attempt отдельно переходы в рамках0…5, не общий bigint. Две допустимые последовательные правки с одинаковым timestamp; версии1/2/10 сравниваются численно.

**Ожидание:** 65 и некорректный exact тип отклоняются без частичного изменения; 64 проходит только размер, а не диапазон/нормализацию. Невалидный короткий raw может SAVE, normalized остаются NULL при отказе review. Переполнение — откат соответствующей операции, без reset/wraparound/частичного pointer. Равные времена не дают одинаковую новую version, JSON number не округляет большие версии, поскольку wire использует строки.

**Сверка:** целые компоненты/сокращение и диапазоны отдельно, исходный raw без обрезания; N-наборы без FIN. Предельные состояния счётчиков — контролируемый H05-набор, не миллиард фиктивных реальных команд и не обход рабочей истории. Политика торговых расчётов за первым пустым сценарием здесь не расширяется.

### F23. Expiry после ожидания и сохранённый календарный deadline

**Связи:** A28, A42–A44, A47, A58, A59; S01/S14, временной пример §4.3 синтетического документа. **Зависимости:** H01/H02/H05/H06.

**Действия:** новый C06/изменение draft за1 мс до, ровно на и после expiry; отдельно истечение во время ожидания lock. Проверить user/staff absolute/inactivity сроки раздельно и наличие полного входа. Для обычной зоны Etc/UTC START2026-11-02T12:02:00.000Z → deadline2026-11-16T12:02:00.000Z. После commit — чтение/REPLAY при изменении локали/зоны устройства/версии tzdb; отдельные будущие календарные случаи gap/overlap подобрать с проверенной tzdb по H06.

**Ожидание:** равенство expiry уже закрывает новый допуск, после ожидания условия проверены заново. Просроченный login — отказ доступа; при полном актуальном входе предметно устаревший review — REJECT после допуска к ключу. Уже committed успех остаётся прежним независимо от expiry его review. Used не возвращается в editable; чтение/worker не продлевают draft. Deadline неизменен; gap — первый существующий момент, overlap — первое вхождение по принятому правилу.

**Сверка:** UTC с миллисекундами, сохранённые IANA/расчёт/tzdb, версия и expiry до/после. Пограничный момент до expiry допускает лишь дальнейшие проверки, не гарантирует START. Конкретные даты DST и библиотека пока не подтверждены — эти варианты остаются зависимыми H06, обычный UTC-пример не выдаётся за их доказательство.

### F24. Блокирующая история и будущий архив без потери дедупликации

**Связи:** A06, A17, A34, A38, A61, A112; S01/S07, K03/K05. **Зависимости:** H02/H04/H05/H06, M02/M04.

**Действия после закрытия стыков:** подготовить отдельные согласованные состояния paused/stopped/manual/unknown/dust и действительно завершённую историю; проверить новый key/review и старый REPLAY. Для будущего разрешённого архива — старый command/event после архивирования подробностей по ещё подлежащему согласованию протоколу. Сейчас эти состояния не создаются; пропажа details/parent outbox проверяется как повреждение F17, не успешный архив.

**Ожидание:** блокирующая session сохраняет slot, нет нового финансирования; STOPPED не достаточен для освобождения. Даже после доказанного завершения исходный draft/review не создают вторую session, исторический ключ возвращает исходный результат при текущем доступе. Архив должен сохранить core key/receipt и consumer dedup, обязательные FK и возможность распознать старый результат. Текущий consumer receipt ссылается на outbox: удалить родителя без отдельно принятой совместимости нельзя.

**Сверка:** полнота истории/уникальность/прежние результаты, отсутствие нового эффекта. Реализуемые тестовые состояния, архивный признак/читатель и совместимость FK пока открыты; этот документ не добавляет таблицы торговли, retention-процесс или право очистки.

## 8. Карта сценариев и границы доказательств

F-ID обозначает карточку, а не замену исходному A-критерию. Точная связь с A-ID и S/N/K указана в начале каждой карточки; каждый перечисленный вариант будущего прогона получает собственный результат. Вариант с незакрытой зависимостью не превращается в «пройдено» по соседнему успешному варианту.

## 9. Протокол будущего результата и открытые зависимости

Для каждого прогона: F-ID/вариант/A-ID/S-N-K, точные версии приложения/схемы/четырёх форматов, безопасные IDs среды/actor/resources/key, исходная точка, точка сбоя и очередность, известность commit/rollback, изменения строк/версий/сумм, независимая сверка, результат по слоям и оставшиеся ограничения. Не хранить bearer, OTP, passkey/recovery-секреты, полное тело отклонённого запроса или повреждённой записи. Табличные ожидаемые суммы синтетического набора — эталон документа, не разрешение дампить финансовые данные в аварийный лог.

Статус «пройдено» возможен только при фактическом выполнении данного варианта и наличии достаточных доказательств. «Не выполнено», «зависимость не закрыта», «частично проверено» и «исход неизвестен» различаются. Успешная проверка Markdown/соответствий — только редакционная проверка, не прогон карточки. Ошибка реализации не устраняется молчаливым изменением ожидаемого продукта.
