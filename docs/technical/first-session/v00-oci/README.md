## Среда и фактическая конфигурация

- Oracle OCI Frankfurt, Ubuntu 26.04.1 LTS ARM64, 4 ядра, 23 GiB RAM. Один диск 46,6 GiB, при входной проверке свободно 42 GiB. На Mac используется SSH-клиент.
- Docker `29.1.3-0ubuntu4.1`, Compose `2.40.3+ds1-0ubuntu1` из подписанного репозитория Ubuntu. Установка сверена с заявленной поддержкой ARM64 и Ubuntu 26.04 в [документации Docker](https://docs.docker.com/engine/install/ubuntu/).
- Chrony использует [локальный источник времени OCI](https://docs.oracle.com/en-us/iaas/Content/Compute/Tasks/configuringntpservice.htm). Конфигурация в `/etc/chrony/sources.d/shadow-oci.sources`. Исходный файл Ubuntu сохранён с суффиксом `.disabled`: его NTS-источники не давали отсчётов, а доступный источник OCI не выбирался при смешанной конфигурации. После изменения `NTPSynchronized=yes`, Chrony `Leap status: Normal`. Это снимок состояния, а не проверка отказа часов.
- Три службы в одной внутренней сети Docker. У контейнеров отсутствует публикация портов. Auth использует собственную роль и схему PostgreSQL. Локальный Mailpit принимает только синтетические письма этого прогона. Ресурсы ограничены на уровне контейнеров. Автозапуск контейнеров отключён, пока это испытательный профиль.
- Адрес сервера, SSH-ключи, токены, исходные письма и содержимое `.env` хранятся вне публичного репозитория. SSH и облачные правила доступа при этой работе сохранены. Восстановление через консоль Oracle не испытано.

## Воспроизведение и эксплуатация

Действующая папка на сервере `/opt/shadow-v00` принадлежит root, права 0700. [Compose](compose.yaml) и [инициализация БД](init-db.sql) содержат только шаблоны. При новом развёртывании проверь ARM64 и SHA каждого скачанного образа через `docker image inspect`; при расхождении остановись и пересмотри профиль. Создай локальный `.env` с правами 0600. Каждому из `PG_ADMIN_PASSWORD`, `AUTH_DB_PASSWORD`, `AUTH_JWT_SECRET` назначь независимое случайное значение из `openssl rand -hex 32`. Действующие секреты не перегенерировать поверх созданного тома. Файл `init-db.sql` должен читаться службой PostgreSQL.

Из каталога стенда под root:

```sh
docker compose config --quiet
docker compose up -d --pull never
docker compose ps
docker network inspect shadow-v00_lab --format '{{.Internal}}'
docker inspect --format '{{json .HostConfig.PortBindings}}' shadow-v00-auth-1 shadow-v00-db-1 shadow-v00-mail-1
```

Проверку [probe.py](probe.py) запускать на самом сервере под оператором с правом `sudo -n docker`. Она создаёт один новый искусственный аккаунт и выводит только статусы и счётчики. У исходного сценария первая миграция Auth завершилась ошибкой прав на схему `public`; отдельный `search_path` для роли Auth исправил запуск без расширения прав на `public`. Для паузы используй `docker compose stop`, для возобновления `docker compose up -d --pull never`. Том БД при паузе сохраняется.

## Порядок трёх следующих проверок

Поручение владельца от 04.11.2026 охватывает проверку однократности TOTP, сверку исхода Auth при потере ответа и внешнее резервирование с восстановлением. Исходная версия для этой работы — PR 224, `74fc31f5fd7096882703134a50c22133b4c6c66c`. Тестовые аккаунты и данные синтетические. Развёртывание ограничено существующим стендом, бюджет дополнительных расходов — ноль.

| Направление | Ответственный | Что требуется до прогона |
| --- | --- | --- |
| Стенд, изоляция, резервирование и сводный результат | Серверный чат. Он единственный оператор Oracle | Согласовать версии пакетов, отдельные схемы и сети, запуск и возврат в исходное состояние |
| TOTP и сверка исхода Auth | Бэкенд | Воспроизводимый контроллер и независимые ожидаемые результаты, согласованные с БД |
| Атомарность, права и независимая техническая проверка восстановления | БД | Тестовые миграции и запросы проверки, ожидаемые исходы до испытания, сверка очищенных результатов после него |

Чаты подтвердили свои роли. Уточнение параметров исполнения и передачу пакетов считать отдельным шагом. Он ещё не завершён.

- **TOTP.** Две параллельные попытки для одного фактора и шага должны дать не более одного успеха. Проверить специально подготовленный код, совпадающий с несколькими шагами. Контроллер должен учитывать все совпадения, версию фактора и отсутствие побочных эффектов при отказе. Из отдельной сети клиента проверить, что контроллер доступен, а прямые подключения к Auth и БД недоступны.
- **Обрыв Auth.** Зафиксировать независимый эталон для запроса, который не достиг провайдера, применённого эффекта с потерей ответа и неподтверждённого исхода. Коррелировать с конкретной операцией по доверенному наблюдению. Счётчик строк и HTTP-статус отдельно недостаточны. При неопределённом исходе зависимый вход остаётся закрыт, повтор внешнего эффекта запрещён.
- **Восстановление.** Создать физическую копию отдельной синтетической БД, затем сделать изменения, попадающие в разные сегменты WAL. Одна цель восстановления должна предшествовать отзыву доступа, другая — включать отзыв. Проверить обе цели, ожидаемые роли и данные. В отдельном отрицательном прогоне убрать необходимый сегмент. Критерий отказа — целевая точка не достигнута и восстановленная среда не открывается. Исходный стенд остаётся доступен, восстановленная БД изолирована.

Для внешнего хранения кандидат — закрытый OCI Object Storage. До подключения проверить домашний регион, остаток квот по хранилищу и запросам, а также условия Free Trial конкретного аккаунта. Нужны назначенные хранитель, отдельный проверяющий и получатели ключей, а также отдельные минимальные полномочия на загрузку и чтение. SSH-доступ к стенду не подтверждает такие полномочия. Архив и WAL шифруются до передачи. Закрытый ключ не хранится на стенде. Независимый проверяющий подтверждает чтение внешней копии, хеши, доверенную подпись и достижение контрольной точки. Семь успешных копий хранятся вместе с необходимыми сегментами WAL.

Замеры для испытания: время потери источника и время последней подтверждённой точки в восстановленной копии для наблюдаемого RPO, начало процедуры и момент завершения проверки пригодности для наблюдаемого RTO. При отсутствии внешнего объекта или необходимых полномочий результат остаётся локальным, полное резервирование и восстановление не подтверждены. До отдельной сверки запрещено открывать восстановленные входы и разрешать повторы операций с неизвестным исходом.

### Разрешение на испытания и фактическая проверка восстановления

Владелец 04.11.2026 отдельно разрешил проверочный код, тестовый SQL, развёртывание и испытания для трёх пунктов V00. SQL и Auth-контроллер используют отдельный экземпляр провайдерских служб с отдельными данными и секретами. Исходная среда из PR 224 остаётся доступной. Серверный чат выполняет изменения на Oracle, БД и бэкенд передают проверенные пакеты и сверяют результаты.

Локальное упражнение [restore-rehearsal.sh](restore-rehearsal.sh) выполнено 04.11.2026 на PostgreSQL 17.11 ARM64. Для него создан отдельный источник с синтетическими схемами и три отдельных контейнера восстановления без сети. Проверены `pg_verifybackup` и SHA-256 файлов физической копии и WAL. Цели находятся в разных сегментах.

| Точка | Состояние и события | Проверки | Локальное время до сверки |
| --- | --- | --- | --- |
| До отзыва, LSN `0/40001E8` | Доступ активен. События `seed,start` | WAL остановлен в цели, режим только чтение, читателю запрещено UPDATE | 3,426 с |
| После отзыва, LSN `0/50001F8` | Доступ отозван. События `seed,start,revoke` | Те же проверки. Запись после цели отсутствует | 1,836 с |
| После отзыва без нужного сегмента | Цель не достигнута | PostgreSQL завершился с ошибкой недостижения заданной точки | — |

Тестовый интервал между точкой и симулированным инцидентом — 1,439 с. Эти числа относятся к локальному прогону на малой фикстуре. Полный RTO включает получение и расшифрование внешних данных и независимую сверку. Полный RPO зависит от реально подтверждённой доставки WAL. Оба показателя внешнего восстановления ещё не измерены. Хранение копий, ключи, подпись манифеста и отдельный доверенный witness остаются открытыми.

Метаданные Oracle подтвердили фактический shape `VM.Standard.A1.Flex`, 4 OCPU и 24 ГБ, Frankfurt. Фактический остаток облачных квот из SSH не виден. Для подключения хранилища нужны отдельные подтверждения доступа и назначений.

### Изолированный прогон контроллера

Используется отдельный проект Compose с собственными Auth 2.197.0, PostgreSQL 17.11, почтой и секретами. Исходный проект из PR 224 не участвует в прогоне. На ARM64 собран runner на основе зафиксированного PostgreSQL-образа, `python3.11 3.11.2-6+deb12u9`, `postgresql-client-17 17.11-1.pgdg12+2`, локальный образ `sha256:e45473afeeddd4a12da5a1842c22b754a72438c47c02acffab97dc8a72e1faae`.

Две отдельные внутренние сети Docker. Из служебной сети оба реальных TCP-адреса Auth и БД были доступны. Из клиентской сети оба соединения завершились отказом. Контроллер подключается к обеим сетям. Контейнер клиента получает только клиентскую фикстуру, без административного подключения к PostgreSQL или Docker socket.

На первом интеграционном прогоне с версией контроллера `22900f8` запрос к Auth был заблокирован до отправки: у Auth включён RLS для `users` и `sessions`, а тестовая роль наблюдателя не видела синтетического пользователя. Наличие пользователя и совпадение дайджеста подтверждены отдельной проверкой администратора. На момент остановки в таблицах seal, confirmation и outcome было ноль строк. Установка наблюдателя без политики видимости не считается прохождением D03-04.

## D03-07 · Вход, восстановление cookie и выход

На изолированном Oracle-стенде завершены 39 проверок SQL, 24 HTTP-проверки, 37 проверок Chromium и отдельная сверка БД. Наблюдалось восстановление после двух вариантов обрыва ответа входа, выход только из выбранного входа и безопасный 503 с последующим подтверждением исхода при потере подтверждения COMMIT. Синтетический upstream, оставшиеся границы и точные результаты описаны в [матрице D03-07](d0307-matrix.md).

По следующему поручению владельца развернуты отдельные Supabase Auth 2.197.0, Mailpit 1.32.0, PostgreSQL 17.11 и сервер тестовых шаблонов. У всех контейнеров закрытая сеть и нет опубликованных портов. Компонентная проверка получила в Mailpit шестизначный OTP без ссылки, проверила его в Auth, зарегистрировала и подтвердила синтетический TOTP и получила признак AAL2. Признак считан из ответа тестового провайдера при регистрации фактора. Полная цепочка через Shadow и корреляция existing-user после потери ответа остаются в работе. [Остаток V00 и условия V01](v00-exit-checklist.md).

После повторной проверки разрешения V00-06 read-only инспекция новой тестовой БД выполнена штатно. Проверены фактические имена, типы и ограничения ключей `auth.users`, `auth.sessions` и `auth.mfa_factors`. У одного активного синтетического фактора форма seed совпала с Base32, значение не выводилось. В образе доступен `pgcrypto` 1.3, на момент проверки расширение не было установлено. Это часть [проверки возможностей провайдера](upstream-db-verification/provider-manifest.md), без переноса выводов на другие факторы или production.

Отдельный существующий синтетический аккаунт получил новое письмо с шестизначным кодом при `create_user=false`. Правильный код подтвердил исходного пользователя с HTTP 200. Неверный и повторно предъявленный правильный код оба дали HTTP 403 и `otp_expired`. Одного кода ошибки недостаточно, чтобы доказать состояние исходной операции.

Сеть браузера не имеет прямого доступа к Auth, БД и Mailpit. Подготовлен закрытый HTTPS origin `https://session-upstream.invalid:8443` с проверкой имени и тестового CA. ### Исходные условия и предложения до внешнего прогона

Ниже сохранён прежний срез подготовки. Наблюдения после загрузки и восстановления приведены выше.

04.11.2026 · В консоли OCI подтверждены Free Trial, Frankfurt как домашний регион, 10 GiB бесплатного Standard Storage и примерно 0 байт текущего использования Object/Archive Storage до создания бакета. Сервисная квота Frankfurt показывала 0 бакетов и 0 байт использования. Значение `Unlimited` в колонке ёмкости означает сервисный лимит, а бесплатный объём указан отдельно. Создан отдельный бакет Standard, видимость Private, серверное шифрование ключом Oracle. На момент проверки в нём 0 объектов.

Готовый синтетический материал для ограниченного прогона занимает около 175 МБ до сжатия: 124 МБ физическая копия с шестью файлами WAL для упражнения PITR и около 50 МБ отдельная физическая копия интеграционного экземпляра. До загрузки проверить фактический размер зашифрованных файлов, получателей ключей и раздельный доступ. Прогон ограничен одним комплектом. Постоянная доставка и хранение семи копий требуют отдельного расчёта с измеренным приростом WAL.

Предложение по ответственности: владелец 1 — хранитель копий, владелец 2 — независимый проверяющий. Оба получают копию через шифрование на свои публичные ключи; каждый хранит свой закрытый ключ вне сервера. Для доверенной подписи манифеста проверяющий заранее получает публичный ключ подписанта по согласованному каналу. Подтверждение назначений и открытых ключей ожидается. Права загрузчика и проверяющего ещё не выдавались, данные в бакет не загружались.

До прогона восстановления назначить внешнее хранилище, отдельные права загрузчика и проверяющего, получателей ключей и независимый witness. Кандидат — приватный OCI Object Storage в домашнем регионе, отдельный от диска сервера, с шифрованием до загрузки и проверкой квоты Free Tier. Нужны отдельные полномочия доступа и подтверждение бюджета по аккаунту. Ключ расшифрования хранится вне сервера, проверяющий подтверждает чтение и целостность. Восстановление, непрерывность WAL, RPO и RTO пока не подтверждены.

Предлагаемый профиль IAM ограничивает загрузчика правом `OBJECT_CREATE` на один префикс закрытого бакета. Отдельному проверяющему нужны `OBJECT_INSPECT` и `OBJECT_READ` в том же префиксе. Запись выполняется под уникальным именем, замена или удаление объекту загрузчика запрещены. Перед зачётом доставки проверить независимое чтение шифротекста, отказ в перезаписи и чтении загрузчиком, отказ в записи проверяющим, а затем подпись манифеста, ключ расшифрования и непрерывность WAL. Политика пока не установлена. [Разграничение объектов OCI](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/managingobjects.htm).

На имеющейся машине подтверждены 4 OCPU и 24 ГБ. Для Ampere A1 Oracle сейчас указывает лимит Always Free **2 OCPU и 12 ГБ суммарно на аккаунт**. Перед окончанием пробного периода проверить оставшуюся квоту, сделать проверенную внешнюю копию и согласовать план уменьшения размера. Исходный профиль трёх контейнеров имеет суммарный лимит памяти 1,75 GiB, но на уменьшенной машине нужен контрольный запуск. [Условия Oracle Free Tier](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm) и [квоты ресурсов](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).
