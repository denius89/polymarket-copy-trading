## Обязательства и границы

Источники: [D03-07](../../backend-auth-d03-validation-passport.md),
[Auth §§7–9](../../backend-auth-contracts-addendum.md),
[единая карта §5.2/§6, AC03–09/16/38](../../auth-storage-unified.md),
[матрица ошибок D02 §7](../../backend-auth-d02-contracts.md).
Трассировка — E07/E08/E09/E11 и DA02/03/05/06. Никаких новых денежных правил,
CommandReceipt/Q05, реальных пользователей или новых инфраструктурных полномочий.

Исторический result не содержит секрет/current navigation. Постоянный verifier
cookie сохраняется после законного стирания временного cipher. Deadline окна
неизменен и равен min(completed_at+300s,context.expires_at); now>=deadline запрещает
выдачу даже до работы eraser. Первый успешный Q01 закрывает окно до200, не touch idle.
Recovery повторяет только исходную cookie, не создаёт login/новый result/rotation.
Любой replay выдачи соблюдает то же окно. Current revoke имеет приоритет перед CLOSED.

Результат полной операции восстанавливается только с допустимым исходным proof.
Истечение Auth context закрывает это чтение; самостоятельный полный login имеет
собственный срок. Повреждённая обязательная запись или недоступный ключ →503,
не202/401/CLOSED. Законно erased cipher не повреждение уже действующего login.

Выход A неизменно относится к A. Login B того же пользователя может доказывать
право продолжить выход A, но не становится целью. Подготовка/чтение не отзывают;
результат подтверждает ровно первоначальную цель. Unknown не204, новый logout
context и новая явная операция не переписывают исходную историю.

## Криптография и передача результата

Ключи остаются у закрытого адаптера вне БД. Верификаторы и encrypted recovery
material не являются HTTP result. Recovery выполняется в открытой локальной T:
получить X window/secret → прочитать cipher → адаптер расшифровывает и сверяет
постоянный verifier, продолжая держать T → подтверждённый COMMIT → Set-Cookie.
Ошибка до commit откатывает; потеря подтверждения не разрешает выдачу/новый login.
Нельзя выдать decrypted secret до подтверждения commit или завершить recovery T
до проверки immutable verifier. Результат подготовленного HTTP может задержаться;
актуальный login guard остаётся обязательным при следующем Q01.

Независимый срез не включает cipher, raw cookie, proof или ключи. Он включает
IDs/source refs, состояния, deadlines, markers, audit и immutable result, чтобы
отличать сохранённую историю от текущего права. Результаты pass/fail/not_run
зафиксированы по адресным actual единственного оператора, без переноса pass между слоями.

## Реализация проверочного профиля и вычитка

Закрытый интерфейс, точные поля, порядок блокировок и запуск —
[manifest](../../../../../scripts/v00-session-db/manifest.md).
Схема `v00_session` размещается только в отдельной `shadow_d0307`; роли owner/executor/observer
разделены. Приложение не получает прямого чтения таблиц, operator revoke и изменения часов.
Наблюдатель возвращает безопасные факты и подавляет повреждённый result.

Бэкенд адресно вычитал 001/002/003/manifest: совпадение source refs, closed DTO до
fingerprint conflict, неизменность цели выхода A при авторизации B и порядок locks.
По вычитке добавлены общий валидатор сохранённого результата и отдельное immutable
`resolved_at`: исторический GET отказа не подставляет время текущего чтения.
Это проверочный контракт, не новое решение продуктового ADR и не расширение каталога78.

Первые 001–004 уже были установлены оператором к моменту уточнения `resolved_at`.
[005-candidate-upgrade.sql](../../../../../scripts/v00-session-db/005-candidate-upgrade.sql)
явно сохраняет старые fixtures: прежнее содержимое сверяется внутри одной T, отсутствовавший
timestamp остаётся unknown/NULL, а новый валидатор отклоняет такие старые результаты.
Новые записи требуют timestamp через ограничение. Старые строки не исправляются догадкой.
Для новой пустой БД достаточно актуальных001–004;005 повторно не применяется.

Прогоны используют свежие UUID. Fixed-clock отдельно проверяет299.999/300/300.001s;
один wall-clock случай держит plan через истечение контекста и требует отказа complete
после этапа crypto. Последовательности конкурентных операций подтверждаются реальным
`wait_event_type=Lock`. Повреждения вводятся только оператором в транзакции с последующим
ROLLBACK; приложение не получает такого механизма. Неполный plan/bundle не проходит COMMIT.

**Остаётся отдельно:** настоящий provider completion/полный78-table Auth; криптографический
и браузерный actual бэкенда/оператора; потеря подтверждения COMMIT в сети; persistent
распределённые лимиты D03-10; точный production byte codec AC07/AC38 (D03-08).
Изолированный `v00-test-*` codec не принимается автоматически как production.
Ни этот SQL, ни успешные локальные проверки репозитория не закрывают весь D03 или V01.
