## 3. Исходные строки и ожидаемая нормализация

В S-таблице B/F/q/p/d указаны как значения формы. Для raw Budget/F/p/d используется обычная десятичная строка без разделителей тысяч: например «200», «20», «10», «15»; q=3,5% в русской подписи соответствует точному значению 3.5, для документального raw-примера — строка «3.5». Конкретное принятие запятой/точки внешним DTO относится к H02; локаль не должна менять число.

Для fixed по умолчанию raw_copy_percent=NULL; для percent raw_fixed_amount=NULL. K07 отдельно проверяет сохранённый неактивный ввод. В draft остаются исходные строки, в review — их копия и нормализованный выбранный набор; в settings — только выбранный действующий режим. Ровно одна пара F либо целый q заполнена. Нулевой q/F не используется вместо NULL.

| Обозначение | Исходное поле draft/review | Нормализованные поля review/settings |
| --- | --- | --- |
| B | raw_budget | budget_n, budget_d |
| F | raw_fixed_amount | fixed_amount_n, fixed_amount_d |
| q | raw_copy_percent | copy_percent |
| p | raw_market_limit_percent | market_limit_percent |
| d | raw_loss_limit_percent | loss_limit_percent |
| P / D | Вычисляются по B/p/d, не отдельный ввод | effective_market_limit_n/d и effective_loss_limit_n/d |

В последней строке n/d обозначает две отдельные колонки с суффиксами _n и _d, не одну колонку с дробью. Полные определения — в [каталоге и review](database-physical-catalog-review.md) и [сессии и учёте](database-physical-session-ledger.md).

| Выбранный процент формы | Сохранённое целое в сотых процентного пункта |
| --- | --- |
| q=1%; 3%; 3,5%; 20% | 100; 300; 350; 2000 |
| p=5%; 7%; 10%; 20% | 500; 700; 1000; 2000 |
| d=10%; 13%; 15%; 30% | 1000; 1300; 1500; 3000 |

P=B×p/100 для процентов таблицы, D=B×d/100; при сохранённых целых знаменатель расчёта — 10000. Для нового fixed F≤floorUSD(min(P,D)), дополнительно действуют диапазон/шаг policy. B/F в этих положительных примерах целые, хранятся как B/1 и F/1. Все n/d сокращены, d>0; ноль — 0/1. На wire n/d и версии передаются строками, не числами IEEE float.

**q не вычисляется от B:** это доля подтверждённого отдельного BUY трейдера. Пустой первый сценарий такого BUY не содержит. При B200/q3% нет автоматической записи «сделка на 6 USD», резервирования 6 USD или вычисленного объёма позиции. Отсутствие продуктового минимума $5 для percent сохраняется в policy; одни пустые запуски не доказывают будущий торговый расчёт/минимум инструмента.

### 4.2. Количество и ссылки после START

Для каждого S-case задаётся цепочка U-case → D-case/ownership → R-case → session/settings/flow/journal/snapshot. Настройки/review/session ссылаются на одну venue/source/trader revision; CMD key принадлежит U-case, realm=user, type=C06. Точные physical names и составные ключи — в четырёх блоках схемы.

| Измеряемое изменение относительно состояния после review | Ожидание |
| --- | --- |
| paper_sessions / settings_revisions | +1 / +1; settings sequence=1, previous=NULL, session version=1 |
| funding_flows / journals / journal_entries | +1 initial / +1 journal sequence=1 / ровно +2 entries |
| session_snapshots | +1 version=1, record_schema_version=v1, ledger_sequence=1, settings своей session |
| command_keys / command_receipts / command_receipt_details | По +1; receipt succeeded, result IDs и версии исходного результата |
| audit_events / outbox_events | +1 start audit / +1 event для зарегистрированного локального consumer |
| audit_authorizations / consumer_event_receipts | +0 на момент START до admin-read и worker |
| user_session_slots | +1: current_session_id своей session, generation=1 при согласованном исходном absent |
| setup_drafts | Обновлены used_at/used_by_session_id; version/raw/last_saved_at/expiry ввода прежние |
| setup_reviews / draft_ownerships / каталог / policy | Новых строк от C06 нет; сохранённые review/ownership/версии не переписаны |

Это полнота одного commit, не последовательность доступных промежуточных состояний. До подтверждённого commit успешный ответ не отправляется. Атомарный rollback оставляет исходное состояние после review; неизвестный исход не объявляется rollback. Обработка события позже только подтверждает локальное наблюдение, не создаёт второй snapshot/funding.

У исходного review и созданных settings/snapshot/receipt обязательна собственная текстовая метка record_schema_version=v1. Совпадение надписи v1 не объединяет четыре разных формата и не заменяет их отдельные читатели H02.

Если отдельно проверяется запрещённый новый C06 по такому review, он не создаёт FIN; окончательный авторизованный предметный отказ после ключа сохраняется по REJECT, ранний invalid request — по INVALID. Изначально N-case заканчивается на проверке настройки; наличие C06 receipt в нём автоматически не ожидается.

## 8. Зависимости и редакционная проверка

Для будущей загрузки/прогона нужны H01–H06: реальные поддерживаемые Auth/identity/session refs, явные enum/DTO/форматы/hash, актуальные grants, worker lease/consumer, ограничения/драйвер/точная арифметика, библиотека времени/tzdb/изолированные копии. M01–M05 матрицы остаются открытыми стыками; этот пакет их не закрывает новыми таблицами или предполагаемым результатом кода.

Редакционная проверка этого документа должна подтвердить: уникальные S/N/K IDs; полный 2×2×2 основной набор; числа/диапазоны/шаги по policy; точные сокращённые P/D; валидность всех S и числовую недопустимость/неполноту N; все ссылки на S/A существуют. Ожидаемые значения сверяются независимо с рациональной арифметикой, а при будущих испытаниях — с заранее зафиксированными здесь значениями, не с повторным вызовом того же application builder.

Успех такой сверки означает согласованность **документа** с policy и матрицей. Он не означает работающую БД, созданные test accounts, выполненный START/READ-A или пройденные A01–A112. Следующий возможный блок — подробные сценарии сбоев и сверки, только по отдельному поручению; код, SQL и миграции по-прежнему не начинаются.


## 9. C04-E01–E08 — исходный результат и атомарность

Дополнение принятого блока 2 C04. Это восемь документальных ожиданий, не новые продуктовые коды, записи в БД или пройденные A-ID. Символические receipt IDs E01/E02/E06 ниже обозначают будущие серверные UUID. Каждый новый допустимый ключ сохраняет по одной строке command_keys, command_receipts и command_receipt_details (CMD); точный повтор не добавляет ни одной. Во всех строках дельта FIN/start audit/outbox от самого C04 равна нулю. Действующий полный user-вход и собственное ownership предполагаются; сценарии гостя/claim и точные FK блока 3 пока предложения.

C04-E01–E06 образуют последовательность одного нового изолированного draft по S01 (Polymarket, fixed, B=200, F=20, p=10%, d=15%). Время ниже UTC; TTL семь суток от действительного изменения ввода. result_last_saved_at/result_expires_at относятся к вводу, не к времени создания нового unchanged/rejected receipt. Все неупомянутые поля формы и доступ остаются прежними. fieldErrors сохраняются в details исходного ответа; точные безопасные параметры DTO ещё требуют H02.
