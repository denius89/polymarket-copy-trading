# Границы транзакций и порядок записи первого сценария

30.10.2026 · По поручению владельца: первый документальный блок для C04, C05, C06 и claim. Baseline актуальной main — `f72f1e81c31bae95952cc82ee59650b9f304e98f` (PR №180). **Принятые гарантии сведены в карту сохранения; реализация и испытания не выполнены.** C04, включая last_input_receipt_id, повторно не открывается. Новых таблиц, колонок, кодов, SQL, миграций или продуктовых операций нет.

TX00/TX04/TX05/TX06/TXCL/TXR ниже — метки документа, не новые команды, таблицы или имена процедур. «Порядок записи» означает зависимости между действиями внутри одного неделимого сохранения. Это не исполняемый порядок INSERT и не требование публиковать промежуточные строки. Циклы обязательных FK замыкаются до commit; обязательные ссылки не становятся nullable ради удобства вставки.

Сохраняется принятый общий порядок ресурсов: policy/catalog/control → principal/identity/access/login/assignment → command/claim key → user/staff slot → draft/ownership → session/финансовые записи/audit/outbox. Ненужные группы пропускаются, внутри группы используется стабильный полный ключ. Для claim «claim key» — защита единственного результата по environment/draft, **не** строка command_keys. C05 не получает ключ команды. Конкретные режимы блокировок, способ защиты отсутствующего claim и полная таблица пар конкурирующих обработчиков относятся к следующему блоку; новая техника здесь не выбирается.

Предварительный поиск ID нужен только для определения набора ресурсов. После защиты заново проверяется, что это актуальные и разрешённые ссылки. Если набор изменился, нельзя захватывать раннюю группу после поздней или молча использовать старое чтение. Одна блокировка родителя не освежает устаревший Serializable-снимок; значимое изменение детей меняет guard, конфликт обрабатывается по TXR. Порядок locks не определяет порядок причин отказа T03.

## 2. TX00 — общая граница исполнения

| Этап | Что требуется | Что не становится сохранённым результатом |
| --- | --- | --- |
| До предметной транзакции | Строгая форма запроса/версия, UTF-8 и размеры, отсутствие неизвестных/повторных полей, разрешённый media type; доверенные environment/actor и защита запроса | Неверный транспорт, недействующий вход, отсутствие доступа, скрытая/чужая цель, ранний rate limit не создают CMD/review/claim/FIN |
| Подготовка попытки | Одно выделенное соединение; короткая Serializable-транзакция; необходимые guards/ссылки в принятом порядке | Предварительная авторизация не заменяет текущую проверку внутри защищённой операции |
| Допуск | Текущий вход или guest proof и принадлежность цели; затем восстановление прежнего результата либо новое исполнение | ID, FK, email, clientCommandId и исторический ownership сами не дают права |
| Непосредственно перед предметной записью | После ожиданий проверить действительность login/proof, применимые сроки и актуальность защищённого контекста; now ≥ expires_at означает истечение | Время начала запроса не сохраняет истёкшее право. Непрочитанные controls/повреждение не становятся удобным предметным отказом |
| Закрытие транзакции | Локальные ограничения, scoped unique/FK, разрешённые переходы и межстрочная полнота от родителей и детей; затем подтверждённый commit | Нет публикации key-only, половины claim/START или успешного ответа до commit |
| После commit | Ответ разрешённому читателю с исходными фактами; только текущие безопасные проекции пересобираются | Потеря HTTP-ответа не откатывает данные. RequestId/nextAction/разрешённые ссылки/restrictedGroups не переписывают receipt |

Новые C04/C06 различают **право определить свою цель** и **право сейчас изменить её**: собственный used/expired draft после допуска к ключу даёт окончательный предметный отказ, а не ранний access denied ради отсутствия receipt. При отзыве текущего доступа результат не раскрывается. Для C05 отказ в законном создании review не заменяется сохранённым отрицательным review. Для claim сохраняется только подтверждённая однократная передача; нового вида долговечного отказа claim нет.

Все четыре операции имеют уже принятые 5 секунд с начала первой серверной попытки, включая соединение/ожидания/паузы, и до трёх попыток всего только при доказанном serialization/deadlock rollback. Бюджет монотонный; прикладные моменты — серверное UTC с миллисекундной точностью. Детали исходов — TXR. Это не распространяет этот бюджет на Auth, Q05/Q06 или worker.

Внешний Auth-провайдер, почта и API площадок не включаются в локальную транзакцию Shadow. Здесь используется доказанный текущий Auth-контекст; полный вход, OTP/MFA, logout и внешние side effects не добавляются в CMD. Возможная разрешённая фиксация foreground-активности login следует H01 и не продлевает draft TTL; в предметных дельтах ниже она не заявлена как новый эффект этих четырёх операций.

## 3. TX04 — C04, сохранение ввода вместе с окончательным результатом

### 3.1. Чтение и допуск

Нужны постоянная область user/guest до создания draft; для update — доступный setup_drafts и его текущая draft_ownerships; существующие command_keys/command_receipts/details либо защита отсутствующего ключа. Для вычисления fieldErrors используются достоверные правила точной карты, защищённые в ранней группе ресурсов. Каталог/venue/trader проверяются по применимым ссылкам; это не проверка разрешения START. Точный replay не требует заново вычислять ошибки или проверять новые торговые правила.

1. Проверить текущий доступ, разрешить исходный scope и проверенные target refs. Исходный key определяется environment/realm/постоянным actor/типом C04/clientCommandId; create/update не разделяют эту область.
2. Если найден завершённый key, сравнить fingerprint по сохранённой канонизации и исходному actor. Совпадает — возвратить исходный результат по TXR; иной payload — KEY_REUSE_CONFLICT без замены результата. Не переходить из replay в новое сохранение.
3. Для нового update после допуска к ключу проверить used → expiry → expectedDraftVersion; только затем сравнить **весь** сохраняемый ввод. Достоверно установленные причины упорядочиваются по T03. Create не получает expected version/фиктивную target-пару.
4. Для нового успеха вычислить безопасные fieldErrors по точной карте. Короткий невалидный числовой raw допускает succeeded, но не создаёт effective settings. Raw NULL/пустая строка/пробелы/«20»/«20.00» не склеиваются.

### 3.2. Неделимые наборы и зависимость записи

| Ветка | Что связывается внутри одной транзакции | Состояние после подтверждённого commit |
| --- | --- | --- |
| Create | Собственные ID draft/первичной ownership/key/receipt заранее согласованы; draft ↔ ownership и current pointer; полный ввод/version1/моменты; key ↔ succeeded receipt + details; last_input_receipt_id → этот created | +1 draft, +1 ownership, по +1 key/receipt/details; TTL 7 дней от сохранения |
| Updated | Защищённый target и ожидаемая version; новый key/receipt/details; изменение полного ввода, version+1, last_saved_at/expires_at и last_input_receipt_id → новый updated | По +1 key/receipt/details и одна согласованная правка draft; исторические receipts неизменны |
| Новый unchanged | Новый key/receipt/details с исходными draft/ownership/version/моментами и своими fieldErrors | По +1 key/receipt/details; draft/raw/version/TTL/last_input_receipt_id без изменений. Это не нулевая дельта команды |
| Допущенный предметный отказ | Key с разрешённым target update, rejected receipt и полными details; обе группы успешного result пусты | По +1 key/receipt/details; draft/ownership без изменений. Create rejection не создаёт пустой draft |
| Exact replay | Только доступ, исходный key/fingerprint и поддерживаемый целый результат | +0 предметных записей; прежние changeKind/version/моменты/errors даже после следующих правок/used/expiry |

До commit проверяются key↔receipt, ровно одни details, тип C04, принадлежность target/result и допустимый переход ввода. last_input_receipt_id ссылается только на свой succeeded created/updated с текущей version и моментами. Новый unchanged не становится источником Q03. Исторический result не привязан FK к будущей изменяемой version draft; после claim его ownership вправе остаться guest.

У succeeded reason_data = {}; response_data содержит обязательный fieldErrors, включая пустой массив. У rejected reason_data содержит reasons с основной причиной первой, response_data = {}; исходные ошибки/пояснения не пересчитываются при повторе. Нет полной истории raw каждой правки, review, funding, session, start audit или outbox от C04.

При подтверждённом rollback все новые строки и правка draft этой попытки отсутствуют. Если ошибка произошла после изменения raw, но до receipt/details, отдельно «спасти ввод» запрещено. Unknown не означает rollback; порядок восстановления — TXR.

**Связи TX04:** R004, R012, R013, R015, R016, R017, R018, R019, R038, R039, R040, R041, R042, R043, R044, R045; A15, A19, A23, A28, A29, A35, A46, A54, A55, A56, A57, A58, A59, A98, A100, A101, A103, A106, A110. Общие правила TX00/TXR добавляются по применимости. Примеры C04-E01–E16/J05–J09; сбои F05/F06/F17/F21/F22; I16/I21.

## 4. TX05 — C05, согласованная неизменяемая проверка

| Этап | Чтение / запись и требуемый результат |
| --- | --- |
| Защитить источники | Актуальные policy/controls, выбранные catalog source/trader/revision, current Auth/ownership, существующий user slot/его отсутствие, draft/version. Предварительные ID перепроверяются; отсутствие выбранного trader не превращается в «трейдер отключён» |
| Проверить право создать review | Доступный актуальный draft и expectedDraftVersion, применимые сроки/used/current ownership. Нельзя создавать review по недоступному/устаревшему вводу. Недействующий user login не становится guest; technical/read failure не становится negative review |
| Составить результат | Точная копия raw/version/ownership; policy/trader refs и guards; нормализованные значения либо **все** normalized NULL; слот и срок. Для guest: not_applicable, requires_authentication=true, allowed_to_start=false. Для user: достоверные absent либо present+generation |
| Сохранить | Ровно +1 setup_reviews с reasons/fieldErrors/warnings, checked_at и expires_at=checked_at+10 минут; проверить типизированную полноту/принадлежность/точность до commit |
| Выдать | Только после commit показать конкретный reviewId и его результат. HTTP 200 допустим при allowed_to_start=false; это не permission на C06 |

Валидные числа при занятом слоте/недоступном трейдере могут оставаться нормализованными в отрицательном review. При невалидной числовой нормализации нельзя сохранить частично действующий набор. Основная причина и порядок fieldErrors — T02/T03 и точная карта; C05 не копирует ошибки C04 как текущую числовую проверку и не меняет источник ошибок Q03.

C05 **не создаёт** slot, command_keys/receipt/details, claim, session/settings/funding/journal/snapshot, audit или outbox. Не меняет draft/raw/version/TTL/last_input_receipt_id. Несколько reviews допустимы, предыдущий не переписывается; изменение исходного контекста после commit не исправляет review на месте. C06 вновь проверяет контекст и сроки.

Rollback: +0 reviews этой попытки. Unknown: review мог сохраниться; прекратить автоматический повтор, не объявлять его отсутствующим или настройки неверными. Пользователь может явно повторить C05 и получить **новый** review; прежний возможный результат остаётся историей. Для start нужен конкретный полученный и показанный review. Обычного key/Q05 для C05 нет.

**Связи TX05:** R003, R004, R006, R020, R021, R022, R023, R024, R025, R026, R027, R029, R043; A02, A03, A07, A08, A17, A19, A23, A28, A32, A36, A40, A44, A47, A49, A60, A62, A96, A99, A100, A103. S01–S16/N01–N22/J01–J04; F07/F22/F23; BASE-READY/I01. Числовая проверка не закрывает Auth/M02.

## 5. TX06 — C06, один полный запуск

### 5.1. Допуск и порядок формирования

| Этап | Действие и обязательная граница |
| --- | --- |
| Исходные ссылки | Разрешить конкретный immutable review и его draft/ownership/catalog/policy, текущий user/login. Для новой команды защитить controls и доступ в общем порядке; для replay новые controls не переоценивают прежний результат |
| Командный ключ | Постоянная user-область C06 и исходный fingerprint; существующий целый receipt → TXR. Новый ключ резервируется в той же транзакции, не отдельным pending |
| Слот и draft | Защитить свой slot(environment,user_id,paper), без venue; при отсутствии — уникальное резервирование. Затем защитить draft/ownership; сверить source review, версии, used/expiry и ожидаемое состояние слота. Абсолютное отсутствие и существующий свободный slot различаются |
| Итоговый допуск | Проверить полную принадлежность/актуальность review, controls/trader revision, current login, слот/блокеры; после ожиданий заново сроки draft/review/login непосредственно перед session. Все применимые достоверные причины — по T03, не по порядку locks |
| Кандидат START | Согласовать IDs и ссылки полного комплекта §5.2, рассчитать точные суммы и календарный deadline по сохранённым zone/algorithm/tzdb. Нельзя дополнять отсутствующие обязательные данные вымышленными defaults |
| Публикация | Собрать комплект и замкнуть pointers/циклы, затем проверить полноту/суммы/источники/guards до commit. Успешный ответ с исходными IDs/версиями — только после подтверждения commit |

C06 принимает намерение, не готовые деньги из браузера. Настройки — из проверенного immutable review, без молчаливого пересчёта под другую policy. При stale требуется новая проверка и отдельное намерение. Если одновременно обнаружено несколько предметных причин, сохраняется порядок DRAFT_USED → DRAFT_EXPIRED → VERSION_CONFLICT → SESSION_NOT_SETTLED → CURRENT_SESSION_EXISTS → CAPABILITY_UNAVAILABLE → REVIEW_EXPIRED → REVIEW_STALE → SETUP_INVALID. Техническую неизвестность нельзя вставить в этот список.

### 5.2. Полный комплект успешного commit

| Состав | Дельта / связи |
| --- | --- |
| command_keys, command_receipts, command_receipt_details | По +1; user/C06/succeeded, обязательные result_session_id/result_settings_revision_id и исходные result_snapshot_version/result_session_version; reason_data={}, response_data={} |
| paper_sessions | +1; свой user/slot/venue, started_from_draft_id/review_id/ownership_id, start_receipt_id; неизменный started_at/deadline/zone/algorithm/tzdb; начальные active/copying_not_connected |
| settings_revisions | +1 sequence1, previous=NULL; свой C06/actor/session, точная копия эффективных настроек review/policy |
| funding_flows, journals | По +1 initial; взаимные ссылки своей session/receipt, сумма B в своей unit, journal sequence1 |
| journal_entries | Ровно +2: paper_cash +B и virtual_funding_source −B; line1/line2, та же unit/session/journal, точная сумма 0 |
| session_snapshots | +1 version1, EMPTY/synthetic/no_trade_data; initial funding/free/equity=B, остальные суммы0/1, trade/position/order counts0; свои settings1/ledger1 и session version |
| Current pointers | Session указывает на свои settings/ledger/snapshot1; slot → эту session; новый slot сразу generation1 занятого состояния. У ранее существующего свободного slot смена pointer увеличивает generation на1 |
| setup_drafts | used_at/used_by_session_id вместе; исходные raw/version/last_saved_at/expires_at/last_input_receipt_id сохранены. Отмечен использованным только source draft |
| audit_events | +1 paper_session.started/succeeded с исходным login/actor/receipt/session/snapshot1; audit_authorizations не добавляются для user start |
| outbox_events | +1 исходное событие для зарегистрированного consumer с исходными версиями. Consumer receipt пока +0; worker не участвует в commit START |

На стороне каждого затронутого родителя и детей требуется полнота R037: нет session без обязательного ребёнка, journal без двух entries или key без final receipt/details. Все условные C06-ссылки обязательны и типизированы; C04/rejected receipt не могут заменить successful C06. Взаимные FK и поддерживающие unique сохраняют environment/user/session/источники. Исторические source draft/review уникальны навсегда, даже если будущая операция когда-либо освободит slot.

### 5.3. Отказ, откат и граница после запуска

Допущенный окончательный отказ: по +1 key/rejected receipt/details, без новой session/финансов/used draft/start audit/outbox. Если достигнуто резервирование нового slot, допустима ровно принятая дельта: +1 свободный slot generation1 с NULL pointer **вместе с отказом**. Если резервирования не было — slot +0. Ранее существующий slot от отказа не меняется. Свободный slot после отказа требует нового review перед новым намерением; старое absent не используется повторно как актуальное.

При подтверждённом rollback отсутствует весь новый комплект **и** резервирование slot этой попытки; прежние draft/slot/версии восстановлены. При unknown нельзя обещать ни отсутствие session, ни наличие одного только отказа: сначала TXR.

После успешного commit worker лишь доставляет локальное событие с дедупликацией; не создаёт деньги/снимок/допуск задним числом. Exact replay не создаёт новый audit/outbox/funding и возвращает исходные версии даже после допустимой публикации следующего snapshot. Q04/Q06 читают текущее состояние отдельно; полный Q06 требует текущего staff-доступа и собственного audit/evidence. Владелец 1 и владелец 2 равноправны, но не получают обход этих правил.

## 6. TXCL — claim, однократная передача своего guest draft

| Этап | Действие и неделимый результат |
| --- | --- |
| Вход и поиск результата | Полный текущий user-вход; разрешённый поиск исходного claim через защищённый контекст. Если передача завершена этому user, вернуть прежний результат без новых строк; действительность закрытого guest proof для восстановления успеха не требуется |
| Допуск нового claim | Только после подтверждённого незавершения: действующий guest proof именно этого draft, текущая guest ownership и применимые guards/доступ. DraftId сам не доказательство; чужой результат не раскрывается |
| Защита единственности | Единственный claim по environment/draft; защита отсутствующего результата и общий порядок ресурсов. Проверить актуальные draft/current ownership и отсутствие уже совершённой передачи; сохранённая история не переназначается |
| Формирование передачи | +1 user draft_ownerships с previous guest ownership и своим claim_receipt_id; +1 draft_claim_receipts с actor_user_id/previous/claimed; draft.current_ownership_id → claimed и служебный updated_at |
| Закрытие гостевого допуска и аудит | Старое доказательство больше не допускает **этот** draft и его C04-результаты; +1 setup_draft.claimed/succeeded audit с текущим user/login, draft и claim receipt. Цикл ownership↔claim и audit обязателен до commit |
| Ответ | После commit возвращается подтверждённая передача. Затем отдельное чтение актуального draft; для запуска отдельный новый user C05. Нет автоматического C06 |

Исходная guest ownership и guest reviews неизменны. Raw/version/last_saved_at/expires_at/last_input_receipt_id не меняются; claim не оживляет истёкший ввод и не превращает guest review в user review. Не создаются обычные command_keys/receipts/details, slot, session, финансовые записи или outbox. Прекращение guest-допуска к этому draft не означает глобального отзыва независимых drafts того же guest context.

Закрытие доступа должно следовать из атомарно сохранённого состояния владения и проверяться всеми путями чтения/записи. Удаление cookie в потерянном HTTP-ответе не обеспечивает эту гарантию. Внешний Auth не объявляется откатившимся вместе с Shadow; конкретный защищённый recovery-протокол/адаптер H01 остаётся зависимостью, дополнительная внешняя таблица или колонка отзыва здесь не придумывается.

При подтверждённом rollback новая ownership/claim/audit и смена pointer отсутствуют; старый доступ определяется действующими Auth-условиями, а не обещанием восстановить внешнюю сессию. При unknown сначала защищённое восстановление того же claim; нельзя создать второй ownership, заменяющий draft, перенести его другому user или использовать Q05 как recovery claim.

После claim user читает прежний C04 по доказанной цепочке: succeeded через result ownership, rejected update через проверенный target ownership; actor/key не переносятся. Rejected create без draft не получает фиктивную цепочку. Право читать прежний guest receipt не даёт права исполнить отсутствующий guest key. last_input_receipt_id вправе указывать на исторический guest C04, что не ослабляет current-access проверку.

**Связи TXCL:** R012, R013, R014, R016, R017, R019, R024, R038, R044, R046, R069, R070; A02, A23, A26, A28, A29, A35, A55, A100, A103, A106, A107, A110. C04-E09–E16/J07; F06/F05/F17/F19. Эти связи проверяют цепочку, но не объявляют полноценный Auth-протокол испытанным.

## 7. TXR — откат, повтор и неизвестный исход

| Наблюдение | C04/C06 | C05 | Claim |
| --- | --- | --- | --- |
| Ранний отказ до предметного допуска | Нового CMD нет, старый результат не меняется | Review нет | Передачи/claim receipt нет |
| Подтверждённый предметный результат | Success либо durable rejected со всеми details | Новый immutable review, включая allowed=false; отказ в исполнении C05 не является review | Целая successful передача; обычного rejected CMD нет |
| Serialization/deadlock с доказанным rollback | Полный повтор всех проверок с прежним key/payload в общем бюджете | Повтор всей попытки в бюджете, предыдущая попытка доказанно откатилась | Повтор по тому же защищённому контексту в бюджете |
| Unique conflict | Отдельный разбор и свежее авторизованное чтение; не универсальный business rejection/retry | Не объявлять любой unique повторяемым конфликтом | Сверить свой уже совершённый claim; не передавать другому user |
| Constraint/format/программная неисправность | При подтверждённом откате новых записей нет; не маскировать под допустимый отказ или автоматический retry | Не создавать отрицательный review | Не создавать successful receipt без передачи |
| Ответ commit потерян / отмена не доказана | Исход неизвестен; прежний key/payload, Q05 или разрешённый replay, без нового ключа | Автоповтор прекращается; явная новая проверка может создать ещё один review | Сначала защищённый поиск исходного claim, без второго владения/draft |
| Отсутствие результата при первом чтении | Не доказательство отката/свободного ключа; Q05 pending — наблюдение, не сохранённый статус | Q05 не применяется | Q05 не применяется |
| Повреждённый/неизвестный формат или недоступное хранилище | Техническая недоступность, не pending/пустые details/новый key | Не считать настройки неверными | Не считать передачу несостоявшейся |

Свежая сверка выполняется на основном хранилище в новой транзакции, не в старом Serializable-снимке и не по отстающей реплике. Наличие целого результата проверяется вместе с обязательными связями и текущим доступом. Если результат не установлен, остаётся неизвестность; нельзя принять таймаут, закрытие соединения, отсутствие строки или исчерпанные попытки за доказанный rollback.

При подтверждённом rollback с исчерпанным бюджетом — техническая недоступность, без сохранённого отказа. Для C04/C06 следующее обращение сохраняет исходное намерение/ключ. Паузы 50–150 мс входят в 5 секунд; новая попытка не начинается при недостаточном остатке. Ограничение ожиданий/отмена драйвером и отсутствие позднего commit ещё требуют испытаний.

Окончательный rejected C04/C06 остаётся прежним после исчезновения причины. Его чтение через Q05 имеет HTTP 200; это не succeeded. Точный replay сохраняет исходный статус успеха/отказа и факты, но текущий requestId/доступ/навигация вычисляются для данного обращения. После утраты доступа выдача закрывается без изменения истории. Новый ключ — только отдельное явное допустимое намерение после разрешения неизвестности, не способ обойти отказ.

После восстановления старой копии отсутствие более позднего receipt/claim не доказывает незавершение в исходной системе. Барьер restore и сверка ключей/владения/финансов/отзывов сохраняются; текущий блок не разрешает открывать команды или worker.
