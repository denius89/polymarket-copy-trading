## 1. Общие правила

Команда меняет состояние, чтение возвращает разрешённые данные. UserId/role из тела не дают полномочий: actor определяется серверным входом. Среда и paper/test область задаются сервером; браузер не может включить live, заменить fixture-контекст на реальные данные или передать чужой userId.

Для сохранения черновика и запуска: commandId/idempotency key, expected resource version, correlationId; для start также reviewId и expectedSlotGeneration. Предложение: commandId создаётся клиентом до отправки и является ключом команды; Q05 ищет его в области текущего actor, даже если ответ с серверным receiptId потерян. Сервер считает hash значимых полей запроса и возвращает устойчивый receipt. Две одинаковые команды дают один результат, противоречивое повторение ключа — конфликт. При истёкшем входе сначала 401/повторный вход, затем восстановление **того же** ключа; ключ не заменяет авторизацию.

Статус 202 не означает завершение операции. Для start предпочтителен синхронный ответ 201 после commit, а неизвестный сетевой итог проверяется чтением receipt. Фоновой «доставкой» события нельзя второй раз создать initial funding. Числовые значения — точные decimal-строки с проверяемым шагом/диапазоном, не float; имя ошибки стабильно, подпись локализуется RU/EN. Локаль не участвует в денежном расчёте и не разделяет session slot.

После успешного C06 used draft закрыт для новых сохранений и остаётся для разрешённого просмотра; дальнейшая настройка требует другого draft, без обхода одной текущей сессии. Коды/credentials C02 не попадают в обычные CommandReceipt/requestHash журналы. Семантика повторной сетевой проверки auth определяется одноразовой транзакцией провайдера и восстановлением собственного входа; нельзя повторно обменять использованный код на новую независимую сессию. TTL, link-binding и защита от перебора остаются обязательным auth-решением до реализации, а не обещанием этого документа.

Если обязательный снимок доступной сессии отсутствует/повреждён — «Данные сессии временно недоступны» и техническая диагностика, без нулей/автоматического EMPTY и без удаления исходных записей. Проверка прав предшествует раскрытию состояния; обычное чтение не запускает ремонт. Точный код/HTTP-ответ и процедура восстановления ещё проектируются.

Минимальное действие администратора в срезе — **просмотр**, не команда «исправить баланс», ручной start от имени пользователя или редактирование базы. Отдельный вход сотрудника через выбранный staff identity механизм — обязательная предпосылка Q06, не пользовательский email-login с добавленным role. Приглашения/смена назначений в первом срезе не разрабатываются; назначения для проверки создаются в изолированной test-среде, а реальные получатели и безопасная выдача доступа согласуются отдельно.

## 4. Переходы после входа

Применяется [ADR-0048](../../decisions/0048_unified_registration_and_first_entry.md):

1. Есть текущая активная/paused сессия **или** остатки/сверка, мешающие новой → показать её фактическое состояние, сохранить подготовленный draft. Не возобновлять торговлю из-за входа.
2. Препятствий нет и свой draft восстановлен → продолжить достигнутый шаг, после auth заново review; запуск отдельной кнопкой.
3. Новый аккаунт без draft → каталог. Завершённая сессия без блокирующих остатков → главная с итогом и выбором трейдера.
4. Draft на другом устройстве фактически не найден → пояснение и выбор возврата/новой настройки. Не обещать перенос, которого нет.

Пример с историей открывается в отдельном example-контексте, никогда через C06. Смена языка и Back не создают команды запуска.

## 5. Отказы и восстановление

28.10.2026 · Приняты принципы [ADR-0064, раздел 10](../../decisions/0064_first_session_database_contract.md): стабильный код причины и безопасные поясняющие данные сохраняются отдельно от RU/EN текста. Конкретные написания кодов/DTO в таблице ниже пока предложения, не новый согласованный словарь. Публичные причины не раскрывают чужой ресурс или сырые внутренние ошибки.

Для нового C06 после ожидания необходимых блокировок и непосредственно перед созданием сессии заново проверить сроки по текущему серверному времени; время отправки/приёма до ожидания не сохраняет допуск. При подтверждённом откате из-за конфликта одновременных изменений допускаются максимум три автоматические попытки всего с прежними key/payload и полной повторной проверкой. Проверенный бизнес-отказ не запускает следующую попытку. После третьего подтверждённого отката — временная недоступность без записи окончательного бизнес-отказа. Неизвестный commit сначала выясняется через исходный key/receipt, не трактуется как безопасный откат; результат успешного ключа не исполняется заново. Общий бюджет и паузы приняты в ADR-0064, раздел 17; принцип измерения/остатка принят в разделе 18, реализацию таймаутов и технический список повторяемых ошибок ещё определить.


Принято в [ADR-0064, раздел 17](../../decisions/0064_first_session_database_contract.md): C06 имеет общий бюджет автоматических попыток 5 секунд, включая ожидание БД и случайные паузы 50–150 мс после подтверждённого отката из-за конфликта. Всего максимум три попытки; каждый повтор не получает новые 5 секунд. После исчерпания бюджета следующая попытка не начинается. Если время закончилось во время сохранения и исход не установлен, интерфейс показывает «Уточняем результат запуска»; C06/Q05 восстанавливают результат прежнего ключа при действующей авторизации. Сохранённая сессия возвращается та же, без второго funding. Истечение времени/отсутствующий receipt не доказывают откат. Это состояние выяснения команды, не новое состояние сессии и не окончательный бизнес-отказ. При подтверждённом откате после исчерпания бюджета — временная недоступность. Бюджет попыток не обещает установить неизвестный исход за 5 секунд; механизм/точные DTO и HTTP ещё проектируются.

Принято в [ADR-0064, раздел 18](../../decisions/0064_first_session_database_contract.md): монотонный таймер C06 начинается с серверной обработки до ожидания БД, не меняется при переводе часов и не сбрасывается между попытками. Каждое ожидание БД ограничивается актуальным остатком 5 секунд: прошло 4 секунды → максимум 1 секунда следующего ожидания. После подтверждённого конфликтного отката выбранная пауза, не помещающаяся в остаток, завершает повторы временной недоступностью, без сокращения паузы ради новой попытки и без durable бизнес-отказа. После состоявшейся паузы бюджет проверяется заново. UTC-сроки допуска проверяются отдельно; неизвестный исход сохранения всё ещё требует выяснения по прежнему ключу. Реализация таймера/отмены ожиданий и согласование с транспортом открыты.

Принято в [ADR-0064, раздел 19](../../decisions/0064_first_session_database_contract.md): всё тело C06 ограничено 65 536 байтами полного JSON в UTF-8 до разбора, включая имена/значения/пробелы. Первый стенд принимает только несжатое тело по разделу 20. Условие измерения после распаковки остаётся для возможного отдельно согласованного расширения. Превышение отклоняется без обрезания, создания session/funding и потери сохранённого draft. В журнал ошибки попадают только факт превышения, серверное время, идентификатор запроса и безопасная причина; тело/фрагменты не сохраняются. Предел 16 КиБ на дополнительное JSON-поле остаётся отдельным. Ошибка текущей передачи не отменяет прежний receipt и не доказывает откат другой передачи той же команды. Точный HTTP/код и реализация проверки/диагностики ещё проектируются.

Принято в [ADR-0064, раздел 20](../../decisions/0064_first_session_database_contract.md): C06 отклоняет повторяющиеся имена полей в одном объекте даже при одинаковых значениях, без выбора первого/последнего. Проверяется каждый объект. Максимум 8 уровней объектов/массивов с корневым объектом на уровне 1; каждый вложенный контейнер добавляет уровень, скалярное значение — нет. Уровень 9 отклоняется без обрезания. Первый стенд принимает только несжатый JSON; сжатие отклоняется с понятной причиной. При этих отказах новые session/funding не создаются, сохранённый draft/прежний receipt не меняются. Точные коды/HTTP, parser и транспортная обработка ещё проектируются.

Принято в [ADR-0064, раздел 21](../../decisions/0064_first_session_database_contract.md): форматы SetupReview, SettingsRevision, SessionSnapshot и CommandReceipt версионируются независимо и описываются в [общем реестре](data-model.md#16-единый-реестр-форматов-записей) для бэкенда/БД. Если затронутая операция встретила неизвестную серверу версию, она сообщает временную недоступность и фиксирует техническую причину; запись сохраняется без изменений и не читается как другая версия. Неизвестный формат receipt не означает отсутствующий key и не разрешает новый start/funding. Авторизация обязательна; начальные обозначения v1 приняты в разделе 22, конкретные DTO/HTTP ещё проектируются.

Принято в [ADR-0064, раздел 22](../../decisions/0064_first_session_database_contract.md): каждый из четырёх типов начинает с v1, формат определяется вместе с типом записи. Изменение полей/смысла/правил чтения требует новой версии затронутого типа; редакционная опечатка без изменения контракта — нет. Обновление сервера допускается только после проверки чтения всех форматов, уже имеющихся в сохранённой истории. Это условие будущего выпуска; декодеры/проверки не реализованы и новый API-контракт этим не объявлен.

Принято в [ADR-0064, раздел 23](../../decisions/0064_first_session_database_contract.md): при возврате предыдущая версия сервера должна читать все уже сохранённые форматы, включая появившиеся после обновления; иначе возврат блокируется с сохранением данных. Возврат программы не запускает автоматическое восстановление старой БД. Проверка чтения перед обновлением/возвратом выполняется на изолированной копии базы тестового стенда с записью результата, без изменения основной базы. Это правила будущего допуска; технический регламент ещё проектируется, новые пользовательские/административные команды не добавляются.

Принято в [ADR-0064, раздел 24](../../decisions/0064_first_session_database_contract.md): отчёт совместимости фиксирует точную версию сервера/схемы БД, ID и дату копии, найденные форматы и результат чтения каждого. Изменение версии сервера, схемы или набора форматов требует новой проверки; старый отчёт остаётся историческим. Каждый прогон получает отдельный неизменяемый отчёт с собственным ID, исправление подтверждается новым прогоном. Эти правила не добавляют команды управления отчётами в первый пользовательский/административный API.

Принято в [ADR-0064, раздел 25](../../decisions/0064_first_session_database_contract.md): перед подтверждением совместимости форматы четырёх типов определяются по фактическим записям изолированной копии и сверяются с реестром; неизвестный формат отражается в отчёте и блокирует подтверждение. Тип без записей получает «Нет данных для проверки», не успешное чтение. На первом стенде читаются все сохранённые записи четырёх типов; ошибка хотя бы одной блокирует подтверждение. Это отдельная проверка совместимости, не изменение поведения обычного Q04/Q05/Q06 и не новый API обхода всей БД.

Принят [блок 1, ADR-0064, раздел 26](../../decisions/0064_first_session_database_contract.md): recordSchemaVersion — текстовая метка v1; n/d первого пустого запуска до 64 цифр на компонент без знака, исходный числовой ввод draft до 64 символов. Переполнение счётчиков останавливает изменение технической ошибкой без сброса. Ограничения тела C06 (64 КиБ, 8 уровней, без дубликатов/сжатия) применяются и к C04; ошибка оставляет прежнее сохранение целым. Дополнительный JSON измеряется отдельным компактным UTF-8 представлением по data-model; полный входящий запрос по-прежнему учитывает исходные пробелы. В диагностике проблемной записи — тип/ID/формат/безопасный код, без полного содержимого.

| Ситуация | Предлагаемый ответ | Что делает интерфейс |
| --- | --- | --- |
| Нет действующего входа | 401 AUTH_REQUIRED / AUTH_EXPIRED | Вход и восстановление своего намерения; без автоматического start |
| Чужой/несуществующий ресурс | Одинаковый внешний 404 | Никаких сумм, email, признака существования; staff без доступа к функции — 403, без раскрытия объекта |
| Число вне диапазона/шага, fixed больше P/D | 422 FIELD_INVALID с безопасными field reasons | Сохранить введённое; не округлять/не уменьшать/не заменять режим |
| Review/draft/policy/catalog/control/slot изменились | 409 REVIEW_STALE / VERSION_CONFLICT | Обновить review и показать изменения; отдельное подтверждение нового намерения |
| Уже есть текущая или блокирующая сессия | 409 CURRENT_SESSION_EXISTS / SESSION_NOT_SETTLED | Открыть собственную текущую сессию с причиной, draft сохранить |
| Тот же ключ, другое содержимое | 409 KEY_REUSE_CONFLICT | Не выполнять; восстановить исходный receipt либо явно начать новое намерение после review |
| Истёкший review | 409 REVIEW_EXPIRED | Повторить review, без потери формы; не обходить проверку новым start |
| Нет пригодного источника/включённого режима | 409 CAPABILITY_UNAVAILABLE | Показать честную недоступность; тестовая среда не становится реальным источником |
| Почта/БД временно недоступны | 503 SERVICE_UNAVAILABLE; auth без раскрытия аккаунта | Не сообщать об успехе; сохранить безопасный контекст, проверить исходный receipt после восстановления |
| Ограничение попыток | 429 RATE_LIMITED с разрешённым retryAfter | Понятный RU/EN текст, draft остаётся; точные пороги до реализации |
| Ответ start потерян после commit | Сетевая неопределённость, не «сессия не создана» | Q05/тот же ключ → существующий успех; не добавлять виртуальные деньги оптимистично |

Успешное чтение не означает актуальность следующей команды: start снова проверяет право и версии. Cookies — Secure/HttpOnly, защита CSRF для изменений, запрет сервисных секретов и постоянных bearer-токенов в URL/localStorage. Доставка одноразового link credential — отдельный auth-контракт: короткий срок, привязка, отсутствие утечки в логи/referrer, очистка адреса после обмена; реализацию и параметры выбрать до кода. Ошибки не содержат сырые сообщения БД/провайдера.

Принят [блок 2, ADR-0064, раздел 27](../../decisions/0064_first_session_database_contract.md): C04, claim, C05 и полный C06 имеют отдельные атомарные границы; критические операции используют Serializable и общий порядок блокировок из [data-model, раздел 22](data-model.md). Отзыв доступа/изменение controls участвует в том же порядке. Для Q06 актуальные права, целый snapshot и audit выдачи согласуются одной транзакцией, ответ после commit. Циклические связи и полнота/баланс проверяются до commit. Ранее согласованные повторы/5 секунд C06 не расширяются на остальные API автоматически; unknown commit не является бизнес-отказом.


## 6. Принятый протокол сбоев и восстановления

[ADR-0064 §28](../../decisions/0064_first_session_database_contract.md), [data-model §23](data-model.md). Потерянный ответ C06 → «Уточняем результат», Q05/повтор исходного ключа с текущей авторизацией. Отсутствие receipt в первом чтении не доказывает rollback; новый ключ автоматически не создаётся. При unknown Auth/claim сервер выясняет подтверждённую identity и прежний результат, не верит клиентскому статусу входа и не создаёт второго владельца draft.

Pending в Q05 — состояние выяснения/обработки запроса, не долговечный pending CommandReceipt. Committed/rejected требуют сохранённого окончательного результата. Нельзя вернуть «не выполнялось» по отстающему кэшу или старой восстановленной копии. Несовместимый/повреждённый receipt означает техническую недоступность, не разрешение повторного исполнения.

Служебные события доставляются с временным захватом и защитой consumerName/eventId. Локальный эффект и отметка обработки атомарны. Временные ошибки: всего 5 попыток с паузами 1/5/30/120 секунд; затем needs_review без удаления. Неизвестный формат сразу needs_review. Этот бюджет не меняет 3 попытки/5 секунд C06. Сбой worker не отменяет успешный receipt запуска.

Restore не открывает API/worker автоматически: сначала изолированная проверка целостности, актуальных доступов и команд после точки копии. Если последние изменения или dedup не восстановлены, запуск закрыт. Повреждённые данные не заменяются нулями; очистка отдельная после проверенной копии, с сохранением обязательной истории и защиты старых команд.
