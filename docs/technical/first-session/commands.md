# Команды и чтения первого сценария

27.10.2026 · Часть [проекта T0](README.md). **Предлагаемый контракт, без работающих endpoints и OpenAPI-кода.** Пути уточняют предложение раздела 14 [117](../../117_user_interface_technical_specification_2026-10-09.md); не задают новый пользовательский сценарий.

Уточнение 27.10.2026: [ADR-0063](../../decisions/0063_supabase_user_auth_provider.md) принимает числовые ограничения email-кодов. Для C01/C02/C03 действуют 6 цифр, 10 минут, resend 60 секунд, 5 ошибок с паузой попытки 15 минут, 5 писем/15 минут и 10/час на адрес, последний выданный код. Это требования к будущему API, не уже работающие ограничения. Сроки login/OTP/MFA не смешиваются; [профиль входа 30/7 дней](auth-policy.md#4-срок-пользовательского-входа-предложение) принят с возможностью изменить сроки позже; обычные изменения применяются только к новым полным входам; существующие сохраняют свою политику до истечения/отзыва.

Уточнение 27.10.2026: несколько независимых пользовательских входов и обычный logout только текущего login-сеанса приняты. C07 не отзывает остальные устройства; административный reset TOTP — отдельный маршрут со всеми старыми входами. При изменении SDK нельзя молча использовать global logout вместо принятого local.

Уточнение 27.10.2026: срок доступности незавершённой настройки 7 дней после сохранения изменений принят. C04/Q03 не продлевают его одинаковым повторным сохранением/чтением; C05/C06 проверяют expiry draft/review, при истечении объясняют новый шаг без скрытого запуска. Аккаунт/сессия/финансовая история и durable receipts от TTL draft не удаляются.

28.10.2026 · [ADR-0064](../../decisions/0064_first_session_database_contract.md) принимает логические правила хранения/конкуренции; названия маршрутов и точные DTO всё ещё проектные. Область ключа — environment + actor realm + постоянный actorId + commandType + key, без loginId. Окончательные бизнес-отказы сохраняются; технический/неизвестный исход требует выяснить результат исходного ключа. Одинаковый key/payload возвращает прежний успех/отказ после новой проверки доступа. C04 допускает несколько независимых draft пользователя, без автоматического слияния: новая вкладка не получает права перезаписать чужую версию. Продолжение auth связано с конкретным draft. C05 хранит собственную неизменяемую копию значений и проверенный номер draft; история всех правок формы не хранится. C06 отмечает использованным только свой draft внутри commit. Expired draft/review остаются физически в синтетическом полигоне до плановой очистки, но недоступны для продолжения/запуска. Q06 проверяет актуальное Assignment независимо от роли в старом login.

Внутреннее хранение процентов (целые сотые процентного пункта) не меняет молча внешний decimal-string контракт формы: единицы и точное преобразование фиксируются в общей версии DTO до реализации. Ни представление 320, ни его преобразование в 3,2% не обходят шаг ADR-0058.

Дополнение после PR №136, 28.10.2026: [ADR-0064, раздел 7](../../decisions/0064_first_session_database_contract.md) фиксирует однократный claim с закрытием старого guest-доступа, DraftOwnership и TraderRevision, обязательный audit перед административной выдачей, компактную защиту старого command key и базовые типы. Собственный resource ID — серверный UUID v4; clientCommandId — UUID v4 клиента до отправки и единственный логический key в своей actor/type/environment области. Возможный служебный digest этого ID не образует другого пространства ключей. Даты передаются UTC с Z с точностью до миллисекунды; exact n/d и числовые version/sequence/generation — строками при любом размере. Окончательная schemaVersion/имена DTO ещё совместно уточняются. Внешние provider/venue ID сохраняют свой формат и область.

При claim запрос подтверждённого продолжения передаёт доказательство владения безопасным способом: полный вход и действующий guest-допуск проверяются сервером. Атомарно создаются account DraftOwnership, новый currentOwnershipId, закрытие guest-доступа и факт результата. Повтор тем же аккаунтом восстанавливает итог, другой аккаунт не получает draft/признак его существования. Исторический guest review ссылается на прежнее владение и не используется для запуска; C05 создаёт новую проверку. Это контракт, точный маршрут/секреты/ключ повторного claim и защита гонок ещё требуют реализации.

Q06 согласует актуальное Assignment, целую версию snapshot и запись «Данные разрешены к выдаче» (actor/assignment, session/snapshot, server time/request ID). Ответ с защищёнными данными только после сохранения события; отказ audit-записи закрывает выдачу с безопасной ошибкой/повтором. Событие не равно доказанному просмотру человеком. После будущей разрешённой очистки подробного receipt Q05 сообщает недоступность подробностей явно; компактное ядро scope/key/fingerprint/outcome/result ID не даёт повторно исполнить команду. Конкретные error codes/DTO этой ветки ещё проектируются; HTTP 404 неизвестного key не подменяет известный архивный итог.

28.10.2026 · [ADR-0064, раздел 9](../../decisions/0064_first_session_database_contract.md): единая миллисекундная точность серверных моментов; draft/review/login уже недействительны при равенстве серверного времени сроку истечения. Версии/последовательности/generation передаются строками даже для "1"; числовой порядок сохраняется. Истечение не превращает повтор ранее завершённой команды в новый запуск: доступ к прежнему результату требует текущей авторизации, а receipts сохраняются. Повторная проверка сроков после ожидания непосредственно перед созданием сессии принята в ADR-0064, раздел 10; функция времени и реализация ещё требуют проверки.

Единое правило измерения сериализованного UTF-8 ещё закрепить; это не лимит целого запроса. C06 отклоняет неизвестные поля поддерживаемого формата с понятной безопасной причиной, сохраняя существующий draft и не создавая session/funding. Молча отбрасывать неизвестную настройку запрещено. SetupReview, SettingsRevision, SessionSnapshot и CommandReceipt получают серверное обозначение формата записи отдельно от version/sequence; реестр/точные имена и его отображение в DTO ещё проектируются.

28.10.2026 · [ADR-0064, раздел 14](../../decisions/0064_first_session_database_contract.md): состояние draft вычисляется на сервере: использованный при наличии согласованного факта start, иначе истёкший при serverNow >= expiresAt, иначе редактируемый. Отдельный изменяемый флаг expiry не хранится; использованный не превращается в истёкший по прежнему сроку. Состояние не заменяет ownership/валидацию настроек. C06 сохраняет обязательную неизменяемую ссылку session.startedFromReviewId на подтверждённый review; точные DTO/коды ещё проектируются.

Завершение сессии не разрешает повторное использование пары. Точный повтор прежней команды возвращает receipt; новый key не обходит уникальность. Удаление использованного draft/review/SettingsRevision при существующих ссылках запрещено, без каскадного стирания истории; очистка отдельно.

28.10.2026 · [ADR-0064, раздел 16](../../decisions/0064_first_session_database_contract.md): C06 создаёт snapshot 1 и обязательную session.currentSnapshotVersion=1 атомарно. Q04/Q06 выбирают снимок по этой ссылке, не по максимальному времени. Новая версия и переход указателя сохраняются вместе; переход назад запрещён, повтор текущей версии ничего не меняет. Snapshot.asOf — время данных для клиента/админки; createdAt — отдельное время создания записи для технической проверки, не замена asOf. Точные DTO/механизм обновления ещё проектируются.

## 1. Общие правила

Команда меняет состояние, чтение возвращает разрешённые данные. UserId/role из тела не дают полномочий: actor определяется серверным входом. Среда и paper/test область задаются сервером; браузер не может включить live, заменить fixture-контекст на реальные данные или передать чужой userId.

Для сохранения черновика и запуска: commandId/idempotency key, expected resource version, correlationId; для start также reviewId и expectedSlotGeneration. Предложение: commandId создаётся клиентом до отправки и является ключом команды; Q05 ищет его в области текущего actor, даже если ответ с серверным receiptId потерян. Сервер считает hash значимых полей запроса и возвращает устойчивый receipt. Две одинаковые команды дают один результат, противоречивое повторение ключа — конфликт. При истёкшем входе сначала 401/повторный вход, затем восстановление **того же** ключа; ключ не заменяет авторизацию.

Статус 202 не означает завершение операции. Для start предпочтителен синхронный ответ 201 после commit, а неизвестный сетевой итог проверяется чтением receipt. Фоновой «доставкой» события нельзя второй раз создать initial funding. Числовые значения — точные decimal-строки с проверяемым шагом/диапазоном, не float; имя ошибки стабильно, подпись локализуется RU/EN. Локаль не участвует в денежном расчёте и не разделяет session slot.

28.10.2026 · [ADR-0064, раздел 13](../../decisions/0064_first_session_database_contract.md): новый C04 с устаревшим expectedDraftVersion отклоняется даже при совпадении данных. Для актуального доступного draft точное совпадение полей не повышает version/expiry; строки "20" и "20.00" различаются и успешная правка повышает version. Нормализация точного денежного значения происходит отдельно при review. После успешного C06 used draft закрыт для новых сохранений и остаётся для разрешённого просмотра; дальнейшая настройка требует другого draft, без обхода одной текущей сессии. Точный повтор выполненной команды возвращает прежний receipt после проверки доступа и не изменяет draft/session.

При запуске отправляются только выбранный способ размера и проверенная конфигурация из review, а не неактивные поля fixed+percent. Канонический requestHash учитывает значения/версии и review, но не пользовательские RU/EN подписи. Повтор того же ключа с другим review/параметрами — KEY_REUSE_CONFLICT; новое намерение после новой проверки получает новый ключ.

Коды/credentials C02 не попадают в обычные CommandReceipt/requestHash журналы. Семантика повторной сетевой проверки auth определяется одноразовой транзакцией провайдера и восстановлением собственного входа; нельзя повторно обменять использованный код на новую независимую сессию. TTL, link-binding и защита от перебора остаются обязательным auth-решением до реализации, а не обещанием этого документа.

28.10.2026 · [ADR-0064, раздел 12](../../decisions/0064_first_session_database_contract.md): Q04/Q06 возвращают существующий снимок с прежними version/asOf; административная запись о выдаче отдельна. Просмотр не создаёт новую версию и не подменяет asOf временем ответа. Минимальное действие администратора в срезе — **просмотр**, не команда «исправить баланс», ручной start от имени пользователя или редактирование базы. Отдельный вход сотрудника через выбранный staff identity механизм — обязательная предпосылка Q06, не пользовательский email-login с добавленным role. Приглашения/смена назначений в первом срезе не разрабатываются; назначения для проверки создаются в изолированной test-среде, а реальные получатели и безопасная выдача доступа согласуются отдельно.

## 4. Переходы после входа

Применяется [ADR-0048](../../decisions/0048_unified_registration_and_first_entry.md):

1. Есть текущая активная/paused сессия **или** остатки/сверка, мешающие новой → показать её фактическое состояние, сохранить подготовленный draft. Не возобновлять торговлю из-за входа.
2. Препятствий нет и свой draft восстановлен → продолжить достигнутый шаг, после auth заново review; запуск отдельной кнопкой.
3. Новый аккаунт без draft → каталог. Завершённая сессия без блокирующих остатков → главная с итогом и выбором трейдера.
4. Draft на другом устройстве фактически не найден → пояснение и выбор возврата/новой настройки. Не обещать перенос, которого нет.

Пример с историей открывается в отдельном example-контексте, никогда через C06. Смена языка и Back не создают команды запуска.

## 5. Отказы и восстановление

28.10.2026 · Приняты принципы [ADR-0064, раздел 10](../../decisions/0064_first_session_database_contract.md): стабильный код причины и безопасные поясняющие данные сохраняются отдельно от RU/EN текста. Конкретные написания кодов/DTO в таблице ниже пока предложения, не новый согласованный словарь. Публичные причины не раскрывают чужой ресурс или сырые внутренние ошибки.

Для нового C06 после ожидания необходимых блокировок и непосредственно перед созданием сессии заново проверить сроки по текущему серверному времени; время отправки/приёма до ожидания не сохраняет допуск. При подтверждённом откате из-за конфликта одновременных изменений допускаются максимум три автоматические попытки всего с прежними key/payload и полной повторной проверкой. Проверенный бизнес-отказ не запускает следующую попытку. После третьего подтверждённого отката — временная недоступность без записи окончательного бизнес-отказа. Неизвестный commit сначала выясняется через исходный key/receipt, не трактуется как безопасный откат; результат успешного ключа не исполняется заново. Общий бюджет и паузы приняты в ADR-0064, раздел 17; измерение времени, согласование таймаутов и технический список повторяемых ошибок ещё определить.


Принято в [ADR-0064, раздел 17](../../decisions/0064_first_session_database_contract.md): C06 имеет общий бюджет автоматических попыток 5 секунд, включая ожидание БД и случайные паузы 50–150 мс после подтверждённого отката из-за конфликта. Всего максимум три попытки; каждый повтор не получает новые 5 секунд. После исчерпания бюджета следующая попытка не начинается. Если время закончилось во время сохранения и исход не установлен, интерфейс показывает «Уточняем результат запуска»; C06/Q05 восстанавливают результат прежнего ключа при действующей авторизации. Сохранённая сессия возвращается та же, без второго funding. Истечение времени/отсутствующий receipt не доказывают откат. Это состояние выяснения команды, не новое состояние сессии и не окончательный бизнес-отказ. При подтверждённом откате после исчерпания бюджета — временная недоступность. Бюджет попыток не обещает установить неизвестный исход за 5 секунд; механизм/точные DTO и HTTP ещё проектируются.

| Ситуация | Предлагаемый ответ | Что делает интерфейс |
| --- | --- | --- |
| Нет действующего входа | 401 AUTH_REQUIRED / AUTH_EXPIRED | Вход и восстановление своего намерения; без автоматического start |
| Чужой/несуществующий ресурс | Одинаковый внешний 404 | Никаких сумм, email, признака существования; staff без доступа к функции — 403, без раскрытия объекта |
| Число вне диапазона/шага, fixed больше P/D | 422 FIELD_INVALID с безопасными field reasons | Сохранить введённое; не округлять/не уменьшать/не заменять режим |
| Review/draft/policy/catalog/control/slot изменились | 409 REVIEW_STALE / VERSION_CONFLICT | Обновить review и показать изменения; отдельное подтверждение нового намерения |
| Уже есть текущая или блокирующая сессия | 409 CURRENT_SESSION_EXISTS / SESSION_NOT_SETTLED | Открыть собственную текущую сессию с причиной, draft сохранить |
| Тот же ключ, другое содержимое | 409 KEY_REUSE_CONFLICT | Не выполнять; восстановить исходный receipt либо явно начать новое намерение после review |
| Истёкший review | 409 REVIEW_EXPIRED | Повторить review, без потери формы; не обходить проверку новым start |
| Нет пригодного источника/включённого режима | 409 CAPABILITY_UNAVAILABLE | Показать честную недоступность; тестовая среда не становится реальным источником |
| Почта/БД временно недоступны | 503 SERVICE_UNAVAILABLE; auth без раскрытия аккаунта | Не сообщать об успехе; сохранить безопасный контекст, проверить исходный receipt после восстановления |
| Ограничение попыток | 429 RATE_LIMITED с разрешённым retryAfter | Понятный RU/EN текст, draft остаётся; точные пороги до реализации |
| Ответ start потерян после commit | Сетевая неопределённость, не «сессия не создана» | Q05/тот же ключ → существующий успех; не добавлять виртуальные деньги оптимистично |

Успешное чтение не означает актуальность следующей команды: start снова проверяет право и версии. Cookies — Secure/HttpOnly, защита CSRF для изменений, запрет сервисных секретов и постоянных bearer-токенов в URL/localStorage. Доставка одноразового link credential — отдельный auth-контракт: короткий срок, привязка, отсутствие утечки в логи/referrer, очистка адреса после обмена; реализацию и параметры выбрать до кода. Ошибки не содержат сырые сообщения БД/провайдера.
