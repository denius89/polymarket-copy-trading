## 2. Режимы защиты

| Метка | Проектируемый механизм | Граница |
| --- | --- | --- |
| S | Совместимая строковая блокировка чтения изменяемого guard/состояния; для PostgreSQL — row mode FOR SHARE | Несколько читателей совместимы; writer должен конфликтовать с ними. Обычное MVCC-чтение или FOR KEY SHARE не заменяет защиту изменяемого допуска |
| X | Строковая блокировка намерения изменить; консервативный исходный режим PostgreSQL FOR UPDATE | Брать сразу для известного writer, даже если после проверки получится unchanged/отказ; не повышать S→X поздно. Более слабый режим — только отдельное обоснование совместимости всех FK/guards |
| U | Уникальное резервирование отсутствующего key/slot внутри текущей транзакции | Обязательная scoped уникальность проверяет конкурирующие вставки; не откладывать арбитраж до commit. Отложенные FK/полнота при этом замыкают весь комплект до commit |
| G | Исключительная advisory-блокировка **уровня транзакции** для одного claim scope | Защищает отсутствие claim до записи; не постоянная строка и не session-level lock. Не заменяет unique/FK, доступ или защиту draft |
| H | Чтение неизменяемого объекта по точному scope/ID/формату | Исторические review/revision/policy/receipt/details/ownership не получают X для обычного чтения; current pointers и доступ защищаются отдельно |
| P | Чтение отсутствия в Serializable с контролем предикатных зависимостей | Не блокировка несуществующей строки и не reservation. C05 может запомнить отсутствие, C06 обязан отдельно защитить право создать slot |

S/X — именно строковые режимы, не одноимённые табличные блокировки. Они удерживаются до завершения предметной транзакции. Изменяемый guard и защищаемые им дочерние факты публикуются вместе с увеличением guard; блокировать неизменившегося родителя после изменения детей недостаточно.

Техническая сверка, 30.10.2026: документация PostgreSQL 17 подтверждает конфликты row modes, автоматическое освобождение transaction-level advisory lock и риск deadlock. Advisory-протокол обязателен для участвующих writers, сама БД не навязывает его всем произвольным запросам. Это основание выбора механизма, не проверка адаптера. [Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html).

Serializable не обновляет уже полученный снимок из-за ожидания lock. Предикатные зависимости позволяют обнаруживать несовместимые исполнения, но не дают права считать отсутствие строк заблокированным. Уникальный конфликт возможен и требует отдельного разбора. Техническое основание: [Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html). Все дальнейшие правила повторов остаются принятым контрактом проекта.

## 3. Единый порядок ресурсов

| Ранг | Порядок внутри группы для рассматриваемых операций | Режим и повторная проверка |
| --- | --- | --- |
| G1 · Политика/каталог/controls | paper_controls → catalog_sources → traders → login_policy_controls; последний ресурс нужен только если операция действительно зависит от его current pointer | S у потребителя, X у publisher; immutable paper_policy_versions/trader_revisions — H. Login использует закреплённую policy, её новая публикация не меняет старые сроки |
| G2 · Principal/identity/доступ/login | users → user_auth_identities → auth_sessions. Доверенный guest-контекст и его изменяемые guards относятся к группе доступа по будущему H01-адаптеру | S для разрешения действия; X сразу, если этот путь действительно меняет guard/login, включая разрешённый foreground touch. Нельзя после G5 возвращаться за X login |
| G3 · Команда или claim | C04/C06: полный scoped key; claim: G по environment/draft, затем H существующего claim receipt | Новый CMD — U; immutable завершённый CMD — H с текущим доступом. Claim не вставляется в command_keys. В одном запросе этого среза не захватываются и CMD, и claim guard ради новой второй операции |
| G4 · Слот | user_session_slots по environment/user_id/paper | C05: S существующего либо P отсутствия; C06: X существующего либо U нового. Venue не часть ключа. C04/claim группу пропускают |
| G5 · Черновик/владение | setup_drafts → связанные draft_ownerships | Новый update C04, C06, claim — X draft; C05 и разрешённое чтение прежнего C04 — S draft; ownership — H. Create пишет собственный новый draft/ownership, но конкурентный create уже защищён G3 |
| G6 · Сессия и её комплект | paper_sessions → settings_revisions → funding_flows → journals → journal_entries → session_snapshots → audit_events → outbox_events | Текущий изменяемый session, определяющий блокер, — S; разрешённый writer current state — X. Новый START пишет собственный полный комплект. Неизменяемые дети — H при чтении |

Внутри каждого вида ресурса сортировка по полному типизированному ключу: environment, применимый realm/type, затем постоянные IDs; сравнение детерминированное, не локализованный текст/created_at. Для UUID — одинаковый порядок значений во всех обработчиках. Не смешивать отсутствующее значение с пустой строкой. Конкретное кодирование ключей закрепляется в одном адаптере; два обработчика не выбирают разные порядки.

Это порядок **явной защиты**, не порядок всех вставок. Например, claim receipt может записываться после проверки draft, когда его G уже удерживается с G3; session/settings/snapshot имеют циклические отложенные ссылки. Неявные FK/unique locks всё равно участвуют в реальном графе ожиданий и проверяются отдельно, включая parent completeness и конкурентные writers.

### 3.1. Предварительное обнаружение ссылок

Сначала разрешённо определить кандидатов controls/principal/key/slot/draft/session по запросу и точным историческим ссылкам, затем защищать их по рангам. Предварительный результат не даёт права раскрытия или записи. Под защитой проверить, что все фактически используемые ссылки входят в защищённый набор и scope совпадает.

Если после G5 обнаружилась другая нужная G1/G2/G3/G4-ссылка, нельзя захватывать её задним числом, продолжать по неподтверждённому ресурсу или превращать техническую невозможность проверки в business rejection. Подтверждённый serialization/deadlock обрабатывается по §7. Для иной несовместимости набора — полный подтверждённый откат и технический результат без самовольного расширения автоматических retry; уже достоверно установленный предметный отказ сохраняется только по T03/T14 при полном допуске.

В частности, C04 update сверяет target ownership после защиты draft; claim мог сменить её со времени предварительного чтения. Предварительная guest target-пара не разрешает сохранить CMD после утраты права. Тот же принцип относится к post-claim поиску старого результата и slot/current session.

### 3.2. Где нет глобальной очереди

Чтение одних controls не ставит всех пользователей в одну X-очередь: S совместимы. Независимые draft и slot не получают общий X пользователя только ради удобства. Реальная правка user guard или разрешённая активность одного login могут дать локальный конфликт G2 — это не глобальный lock. Фактические планы/SSI/индексные и FK-конфликты ещё требуют измерений; независимость по модели не обещает отсутствие любых ожиданий в СУБД.

«Текущий доступ» в G2 включает S guards и проверку сроков; если H01 разрешает этому запросу foreground touch, X login выбирается заранее. Здесь не расширяется список foreground-действий и не проектируется реальный Auth-adapter. При истечении/отзыве нет продления, превращающего недействующий вход в действующий.

Для известного claim можно читать неизменяемый результат, но весь путь восстановления должен доказать текущего получателя и цепочку. Консервативный профиль выше сохраняет тот же G и X draft, что и новый claim, чтобы не строить отдельную гонку «проверили отсутствие → решили передать». Завершённый claim не требует повторной действительности закрытого guest proof; неизвестность не разрешает новый claim.

Для C05 порядок строк таблицы не означает запись review в финансовые таблицы G6. Это собственный неизменяемый результат после всех нужных проверок; CMD/slot/session от C05 не создаются.

## 5. Отсутствующие key, slot и claim

### 5.1. C04/C06 key

Полный scope — environment/realm/постоянный actor/command_type/clientCommandId. User и guest уникальности раздельны, create/update C04 делят одну область. В G3 заранее согласованы key ID и final receipt ID, U выполняется внутри той же транзакции; обязательный receipt FK отложен до полного результата. Между ними нет commit/pending/lease команды.

Победитель либо сохраняет весь результат и его предметную дельту, либо полностью откатывается. Ожидавший не читает старый снимок как доказательство отсутствия результата; после конфликта — подтверждённый откат и свежая авторизованная сверка основного хранилища. Известный другой payload — KEY_REUSE_CONFLICT, старый результат неизменен. Частичный key/details/неподдерживаемый формат — неисправность, не свободный key.

### 5.2. User slot

C05 читает существующий slot под S или фиксирует достоверное для своей Serializable-проверки отсутствие P. Он не резервирует slot. При перекрывающихся C05/C06 допустимо, что review сериализуется до появления slot; это не обещание удержать отсутствие до будущего запуска. C06 всегда проверяет заново expected absent/present/generation.

Новый C06 резервирует отсутствующий slot через U в G4. Собственная вставка, выполненная именно для исходного absent, не объявляется чужим изменением review; чужая уже сохранённая строка делает прежнее absent устаревшим, даже если она свободна. Конкурентную невидимую строку нельзя признать собственной: конфликт разбирается после отката свежим чтением.

У нового успешного START slot сразу generation1 занятого состояния. При допущенном окончательном отказе после собственного резервирования возможен свободный generation1 вместе с rejected CMD. При техническом rollback нового slot нет. Новый review перед следующим намерением должен увидеть present/generation1; ноль не кодирует отсутствие. Слот не удаляется/не освобождается от timeout/logout/STOPPED/ошибки чтения.

### 5.3. Claim guard — принятое уточнение этого блока

Владелец явно выбрал **временную блокировку по черновику на время транзакции**, без новой таблицы. В проекте это исключительный transaction-level advisory guard G в группе G3. Логическая идентичность: отдельное пространство claim + environment + draftId. Получатель user, loginId, guest context, clientCommandId и площадка не разделяют этот guard: два претендента на один draft должны встретиться на одном ресурсе.

Все paths первого claim и его восстановления берут один и тот же guard, после текущего user-доступа и до slot/draft ресурсов. Claim не получает обычного CMD. После G — поиск своего завершённого результата; при допустимом новом исполнении — X draft в G5, текущий guest proof/ownership и unique(environment,draft_id) claim receipt, затем полный CLAIM-OK с audit. Переход current ownership закрывает старый guest-доступ независимо от доставки cookie/HTTP.

Guard освобождается окончанием транзакции, а не ответом HTTP или возвратом соединения в pool. Session-level advisory locks не используются. Вложенный откат/ошибка не должны выпускать защиту и затем продолжать часть операции: применяется полный откат и новый допустимый путь по §7. Обрыв клиента не доказательство освобождения server transaction.

Захват G не освежает Serializable-снимок. Если другой claim успел сохраниться, а snapshot ещё не видит receipt, нельзя доверять этому отсутствию: защита и проверка актуального draft должна выявить изменившееся владение/конфликт; завершение/получатель выясняются свежим авторизованным чтением. До этого нет ни новой передачи, ни вывода «успех отсутствует».

Точная функция отображения логического claim scope в ограниченный advisory key — зависимость адаптера до реализации, с одной версией для всех одновременно работающих обработчиков. Возможная коллизия должна давать лишь лишнее ожидание, никогда общий доступ/общую идентичность; результат всегда ищется по полным реальным ключам. Одновременная смена отображения без совместимости запрещена: один draft не должен получить два независимых guards. В этом срезе один claim за транзакцию, batch claim не вводится.

G не заменяет unique/FK/полноту от родителя, X draft или права runtime. Некорректный обходчик без G должен всё равно упереться в предметные ограничения, но не считается участником доказанного протокола конкуренции. Конкретные DB-роли/закрытые процедуры и все испытания остаются H05/M03.

## 7. Ожидания и завершение попытки

Один бюджет 5 секунд/до трёх попыток, включая первую, получение соединения, locks, работу и паузы 50–150 мс; правила взяты из T05/T12/H05. Ожидание G claim входит в тот же бюджет, не отдельный дополнительный таймер. Время ожидания ограничивается остатком. Пауза не сокращается, чтобы втиснуть лишнюю попытку; текущие часы сроков и монотонный бюджет различаются.

- Только доказанный serialization/deadlock rollback даёт автоматический полный повтор. Перечитать guards/ссылки/сроки; C04/C06 сохраняют исходные key/payload. Сервисный restart не сбрасывает намерение.
- Unique violation после соперника — отдельное свежее чтение на primary после подтверждённого отката. Не использовать недействующую транзакцию или невидимость в прежнем снимке; не переименовывать unique в serialization ради retry.
- Lock timeout/отмена запроса сами по себе не бизнес-отказ. Подтвердить исход текущей транзакции; при доказанном rollback вне разрешённых retry вернуть technical, при unknown сохранить неопределённость. Не добавлять rejected из обработчика ошибки драйвера.
- Не освобождать часть locks через savepoint и не коммитить «остаток» START/claim/C04. При ошибке целостности откатывается весь неделимый набор TX. Соединение с неустановленным состоянием не возвращается как исправное в pool до разрешения/закрытия по будущему адаптеру.
- Unknown C04/C06 — исходный key; неизвестный claim — исходный защищённый контекст и тот же G scope; C05 — прекращение автоповтора, возможность новой **явной** проверки. Auth/claim не добавляются в Q05.

Наличие/отсутствие advisory lock в диагностике не является результатом claim. Источник истины — полный committed claim/ownership/audit и текущий доступ. Аналогично отсутствие lock/receipt после restore старой копии не доказывает, что эффект никогда не происходил; барьер восстановления остаётся.

## 8. Как позже проверить этот проект

Каждый прогон имеет две независимые DB-транзакции на отдельных соединениях, известный BASE и разрешённые паузы в стенде. Один прогон — одна заданная гонка. Будущие trace должны показывать: исходный scope без секретов, номер попытки, порядок запрошенных/полученных групп и режимов, наблюдавшиеся guards/версии, моменты ожиданий, класс ошибки, подтверждение commit/rollback либо unknown и финальные дельты TX. Trace не содержит raw-body, guest secret, cookies, OTP, токенов или личных email.

Для каждой пары: A удерживает нужный ресурс → B доходит до конкурирующей точки → зафиксировать ожидание/допустимый конфликт → завершить A выбранным исходом → сверить B свежим разрешённым способом. Затем поменять очередность. Отдельно проверять подтверждённые retry и потерю ответа commit. Нельзя объявить успех по одной последовательной отправке двух HTTP-запросов или по конечному count без IDs/версий/источников.

Обязательные специальные проверки: два отсутствующих key; absent slot двух площадок; два claim разных user на отсутствующем результате; ожидание G при старом Serializable-снимке; S→X не возникает поздно; одинаковый advisory mapping у всех обработчиков; коллизия guard не даёт доступа; конец транзакции освобождает G; FK/unique locks не обходят весь порядок; parent без children откатывается; несовпадение предварительных refs; исчерпание времени/expiry; старый replay после новой записи.

NEG требует достижения проверяемого ограничения, BAD/READ-FAULT — отдельные уровни из M03. Изолированные средства остановки/инъекции ошибок, точные DB-привилегии, полное H01-доказательство, будущие lifecycle формы M02 и evidence M05 ещё нужны. Это **план доказательств**, не описание созданного тестового кода/стенда или выполненных испытаний.
