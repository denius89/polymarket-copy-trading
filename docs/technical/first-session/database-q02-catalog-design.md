## 2. Точная карта Trader из существующих колонок

Один объект используется в trader карточки и в каждом items списка. V=venues, S=catalog_sources, T=traders, R=trader_revisions, P=paper_controls. Все ссылки включают environment и свою venue/source/trader; R выбирается по T.current_revision_id, а не max(created_at). Источники ниже — отражение уже принятых API-форм, не новые колонки.

| venueId | T.venue_id, совпадает с V.id и S.venue_id |

Курсор и источник его доверия ещё блоки2–3, не готовое поле БД.

## 3. Блок 1 на выбор: явная видимость в двух существующих таблицах

**Рекомендация, ещё не принято:** добавить по обязательному boolean read_visible в catalog_sources и traders. Это два новых проектируемых поля, число34 таблиц не меняется. Никакого SQL/изменения реальной БД здесь нет.

| Поле | Предлагаемый смысл |
| --- | --- |
| catalog_sources.read_visible | Источник опубликован для Q02 в своей среде/площадке; false скрывает все его карточки |
| traders.read_visible | Конкретный trader опубликован для Q02; действует только при опубликованном источнике |

Разрешённая карточка Q02 требует одновременно серверно разрешённого контекста чтения/источника и обоих true. Флаги не заменяют авторизацию; ID/env/source из клиента не дают полномочий. Нет нового клиентского фильтра visible, нового API-поля или режима «покажи скрытых». Параметры персонализации и новые роли/списки доступа не вводятся: применяется уже принятый guest/user допуск к разрешённому каталогу.

У нового источника/трейдера при доверенной подготовке предполагается явное false; публикация true — только после подготовки полного проверенного источника/current revision. NULL, отсутствие значения или неизвестность не считаются false/пустым результатом для повреждённой обязательной записи. Старые синтетические S-наборы при будущей подготовке получат явно подтверждённые true для своих SRC/T; не массовый runtime-backfill и не предположение, что все существующие строки автоматически открыты.

Видимость для Q02 и start-допуск независимы. Сочетание read_visible=true/start_enabled=false (или start_allowed=false) — корректная видимая карточка с unavailable причиной. False видимости скрывает Q02-карточку независимо от start-флага. Из read_visible=true нельзя вывести право C04/C05/C06/торговлю; из скрытия нельзя вывести удаление draft/review/старой сессии/проводок. Действующие проверки доступа и запуска этих операций сохраняются; новый reasonCode/сброс/обход либо новая политика исторического доступа этим полем не вводятся.

Точный путь видимости в остальных операциях должен быть сверен с уже принятыми access/version проверками при следующей детализации публикации: это не повторное открытие C04. Не объявлять одни flags полным защищённым H01-протоколом и не выдавать новый publisher/admin endpoint.

### 3.1. Сохранение публикации

Новая revision публикуется только полным существующим комплектом R + T.current_revision_id + T.version + S.version, как уже принято. Если эта же операция меняет read_visible, изменение входит в её транзакцию. Нельзя сначала показать ссылку, затем дописать обязательные данные. Не вводится staged revision без прежнего полного current-цикла: скрытый trader тоже должен удовлетворять физическим FK/полноте.

Предлагаемое дополнение к guards:

- Изменение S.read_visible повышает S.version вместе с флагом, не переписывая revisions/trader identities.
- Изменение T.read_visible повышает T.version и S.version вместе. Номер не сбрасывается; false→true→false не возвращает прежние версии. При отсутствии изменения флага не изображать его новую публикацию.
- Несколько затронутых полей одной публикации дают согласованные новые положительные guards по действующему протоколу; не вводится произвольное число повышений на поле. Исторические номера review/R не меняются.
- Новые источник/trader/current revision создаются по прежним scoped unique/FK и полноте; начальные версии и итоговые guard values фиксирует будущий manifest подготовки. Смена venue/sourceEnvironment/dataOrigin/external identity не маскируется обновлением флага.
- Управляет доверенный publisher/процедура подготовки, не обычный Q02 или клиентский запрос. Права writer и происхождение публикации ещё требуют механизма/доказательств; роль owner по имени не даёт прямого DML, владелец 1 и владелец 2 равноправны.

Это определяет атомарные факты публикации, но **не закрывает обнаружение изменения всего набора**: новый/убранный из разрешённого набора источник нельзя заметить одним guard ранее выбранного источника. Курсор должен учитывать разрешённый набор целиком, paper guard и применимую видимость, включая доверенное серверное изменение доступа. Устройство этого контроля остаётся блоком2; конкретный hash/новый aggregate guard сейчас не выбран.

### 7.1. Что считается одним состоянием

| Часть | Доверенный источник / смысл |
| --- | --- |
| Контекст | Серверная environment, постоянная venue, версия формы чтения; применимый проверенный guest/user доступ. Параметры клиента не выбирают environment/source scope |
| Область чтения | Серверно определённый набор допустимых источников **до** фильтра read_visible и доверенная версия правил, определяющих этот набор. Скрытие по флагу не удаляет источник из внутреннего набора контроля |
| Общий paper-допуск | Свой paper_controls.id/version/start_enabled; отсутствующий/неизвестный обязательный guard не default |
| Источники | Полный отсортированный набор разрешённых source IDs со своей venue, version/read_visible/start_enabled; не только source первой/текущей страницы |
| Трейдеры | Внутри этих sources полный набор trader IDs, version/current_revision_id/read_visible/start_allowed. Current revision принадлежит своему T/S/V; неизменяемые сведения определяются её ID и revision, а видимые обязательные поля должны быть пригодны к выдаче |
| Позиция обхода | Последний traderId и эффективный limit связываются с тем же состоянием в cursor; не входят в само содержимое каталога и не являются версией источника |

Отпечаток вычисляется по однозначно упорядоченному полному состоянию, не по items страницы, времени чтения, max(updated_at) или сумме версий. Повышение source guard уже защищает изменения дочерних данных; полный набор и указатели позволяют явно связать его с областью обхода. Формат канонизации/алгоритм отпечатка/аутентификация cursor — блок 3. Нет новой сохраняемой hash-колонки, raw manifest в API или разрешения отдавать внутренние/закрытые IDs клиенту.

Разрешённые, но скрытые по флагам строки участвуют во внутреннем контроле изменений; их карточки/поля не выдаются. Источники вне серверно разрешённой области не подмешиваются в отпечаток и не раскрываются через специальный ответ. Невалидный обязательный источник, необходимый для доказательства состояния, не пропускается ради успешного списка; читать недоступные детали скрытых карточек для их выдачи не требуется.

### 7.2. Граница одного чтения

Один запрос списка Q02 использует одно соединение основного хранилища и один короткий Serializable-снимок для состояния/карточек/наличия следующей страницы. Не собирать controls, items и fingerprint из разных транзакций или отстающих реплик. Запросы внутри снимка могут быть отдельными; согласованность определяется общей границей, а не количеством запросов. Технический профиль не разрешает внутренние повторы: прежние 5s включают все ожидания и чтения.

Текущий допуск проверяется для каждого HTTP-запроса. Разрешение из старого cursor не заменяет H01. Если для него нужны изменяемые guards, защита и проверка сроков выполняются по действующему порядку G1→G2, с повторной проверкой после ожидания; чтение не оживляет login. Устаревший снимок не «освежается» после ожидания. Конкретная привязка внешнего guest/user proof и версии области к согласованному наблюдению остаётся обязательной частью H01, а не обещанием одного уровня изоляции.

Внутри согласованного разрешённого состояния Q02:

1. Проверяет форму/контекст и подлинность cursor по будущему блоку 3. Недействующий user не превращается в guest.
2. Устанавливает полный набор и отпечаток; для продолжения сравнивает с исходным, **до выдачи** страницы. Нет достоверного сравнения — техническая ошибка, не CATALOG_CHANGED.
3. Выбирает разрешённые карточки с обоими read_visible=true, по traderId строго после позиции cursor, в принятом порядке UUID. Получает до limit и проверяет наличие следующей карточки в том же снимке; дополнительная карточка не отдаётся как часть items.
4. Формирует полные 17 полей каждого Trader; nextCursor только при доказанном продолжении. Последняя страница вправе иметь ровно limit. Пустая первая страница имеет []/null только после достоверного чтения. Порча не превращается в пустоту или молча пропущенную карточку.
5. Завершает чтение и выдаёт ответ в бюджете. No-store и текущие requestId/навигация сохраняются. Q02 не создаёт CommandReceipt/Q05, draft/review/session/финансы или Q06 audit.

Публикация, завершённая до нового снимка, должна быть видна ему. Перекрывающаяся публикация может логически следовать за чтением: полная прежняя страница допустима, даже если HTTP приходит позже commit публикации. Это не удержание каталога неизменным до доставки ответа. Следующее продолжение сравнивает новое состояние и при установленном изменении возвращает409. Не держать транзакцию/блокировки между HTTP-страницами.

Одиночная карточка Q02 использует согласованное чтение своего разрешённого S/T/current R/P и текущего доступа, но не требует cursor/полного обхода других источников. Достоверно скрытая либо отсутствующая карточка после надлежащего допуска даёт одинаковый404; непригодный обязательный источник видимой карточки — техническую ошибку. Другой скрытый трейдер не подставляется в ответ и не служит fallback.

### 7.3. Публикация, ABA и стык с командами

- Новая revision, current pointer, затронутые guards и видимость публикуются одним полным commit по R021/R022. При доказанном rollback нет частичного нового состояния. Результат записи, чей commit неизвестен, устанавливает доверенный publisher; Q02 не ремонтирует запись.
- Добавление trader обнаруживается полным набором и повышением source guard, включая изменения за пределами текущей страницы. Новый разрешённый source обнаруживается составом source-набора. Видимость false→true→false обнаруживается сохранённым увеличением guards даже при прежних boolean.
- В этом протоколе нет удаления и повторного создания catalog identity ради возврата старого набора/номеров. Вывод из публикации выполняется флагом, история остаётся. Будущие purge/restore/смена разрешённой области обязаны исключить повторное использование старого состояния доверия; это отдельная зависимость, не разрешение на удаление.
- Для серверной области доступа недостаточно хеша текущего списка IDs: удаление и возвращение разрешения не должно незаметно восстановить прежний токен. H01 должен дать доверенную, не переиспользуемую версию области и согласованный протокол её изменения. Это не произвольно выбранная users.version, не staff authorization_version, не timestamp и не новый параметр клиента. До определения источника/атомарной привязки этой версии механизм нельзя считать полностью специфицированным или доказанным.
- Повышенные S/T guards учитываются существующими C05/C06-проверками актуальности. Старый review не переписывается, C04 replay не пересчитывается, claim и последний источник ошибок не меняются. Из read_visible нельзя вывести новый самостоятельный business-reason отказа C04/C05/C06; текущие правила доступа/версий остаются источником решения. CATALOG_CHANGED используется только чтением каталога, не сохраняется в command/review.

### 7.4. Различимые исходы и повтор

| Условие | Принятый внешний смысл |
| --- | --- |
| Тот же разрешённый контекст, достоверно то же состояние и тот же cursor/limit | Та же items-страница; новая диагностика/navigation допустимы. Q02 не выполняет внутренний retry |
| Подлинный пригодный cursor, доступ сохранён, состояние достоверно изменилось | 409 CATALOG_CHANGED; один reasonDetails с code CATALOG_CHANGED/params={}, select_trader с проверенным venueId; без items/nextCursor |

Порядок независимых ранних transport/Auth-защит и конкретные ключи курсора здесь не додумываются.

## 9. Заключительный блок на согласование: точный cursor v1

02.11.2026 · Baseline main `e6e6d8a8b7e97c507f6e35c0be95f2f3714c6d3d` (PR №193). **Предложение; блок 3 ещё не принят.** Блоки1–2/ADR-0064 §§50–51 остаются согласованными. Содержание §§9–11 не выдаётся за уже действующий codec, новые таблицы/поля или выполненное испытание.

### 9.1. Выбор и граница доверия

Рекомендуется шифрованный cursor с проверкой подлинности: **XChaCha20-Poly1305**, канонический JSON JCS, отпечаток состояния SHA-256 и внешняя base64url без padding. Клиент не выбирает алгоритм/ключ/источник данных. Нет собственного шифра, шифрования браузером или использования пароля/login cookie как ключа.

Альтернатива — подписанный читаемый cursor с отдельной минимизацией всех открытых полей; такая подпись сама по себе не скрывает внутренние привязки/отпечатки. Для принятого непрозрачного cursor рекомендуется первый вариант. Выбор библиотеки/TypeScript binding, конкретной версии, secret store и production key-management не выполнен; совместимость нужна до реализации.

Cursor — переносимая позиция чтения, **не полномочие**. До выдачи нужны текущий H01 и свежая проверка разрешённого состояния. Независимые ключи для среды и назначения Q02; нельзя переиспользовать ключи Auth, command fingerprint, кошелька или другого протокола. В Git/БД Shadow/логах/аналитике не сохраняются ключи, полный cursor, plaintext и внутренний manifest; для диагностики достаточно requestId и безопасной категории отказа. Владелец 1 и владелец 2 равноправны; role не даёт прямого доступа к ключам.

### 9.2. Однозначное состояние до хеширования

JCS по RFC8785 применяется к UTF-8 закрытых объектов ниже. Дубликаты ключей/неизвестные поля/null/неправильные типы запрещены. Unicode не нормализуется; некорректный Unicode не заменяется символом-заглушкой. Собственные UUID кодируются канонической строчной строкой с дефисами; UUID v4 проверяется отдельно. Положительные версии — десятичные строки в пределах bigint, не JSON number; boolean — только true/false. Единственное число payload — limit1–50, точно представимое целое. Состояние не содержит денег/времени запроса/навигации.

Определения доменно разделённых значений (везде SHA-256 точных байтов UTF-8 JCS, результат — ровно64 строчные hex-цифры, без префикса):

| Значение | Канонический вход |
| --- | --- |
| environmentBinding | Массив ровно из двух строк: shadow.q02.environment.v1, доверенный environment |
| readerBinding | Массив ровно из четырёх строк: shadow.q02.reader.v1, environmentBinding, realm guest либо user, защищённый readContextId H01 |
| catalogFingerprint | Полный объект Manifest ниже; включает собственный purpose shadow.q02.catalog-state.v1 |

ReadContextId — непустая непротиворечивая строка доверенного контекста читателя, не bearer proof/email/клиентский userId. Её источник/стабильность при входе/замене входа определяет H01; codec не выбирает сам users.version либо guest scope C04. **Изменяемая версия разрешений не входит в readerBinding:** она входит в Manifest.scopeRevision, чтобы изменение каталога/области при сохранённом контексте не превращалось в400 вместо409.

| Закрытый объект | Ровно эти поля и источники |
| --- | --- |
| Manifest | purpose="shadow.q02.catalog-state.v1"; environmentBinding; readerBinding; venueId=V.id; venueCode=V.code; scopeRevision=непустая непрозрачная строка доверенной версии области H01; paperControl=Paper; sources=Source[] |
| Paper | id=P.id; version=P.version как PositiveVersion; startEnabled=P.start_enabled |
| Source | sourceId=S.id; venueId=S.venue_id; version=S.version; readVisible=S.read_visible; startEnabled=S.start_enabled; traders=TraderState[] |
| TraderState | traderId=T.id; version=T.version; currentRevisionId=T.current_revision_id; currentRevision=R.revision как PositiveVersion; readVisible=T.read_visible; startAllowed=T.start_allowed |

Sources содержит весь серверно разрешённый набор **до** флагов видимости, сортируется по sourceId. Внутри каждого source traders содержит полный его набор, сортируется по traderId. Порядок UUID — порядок16 байтов значения от старшего к младшему; одинаковые canonical строки дают тот же порядок. Дубли IDs/чужие FK/неположительные guards/неполный current-цикл не сортируются/схлопываются в удобный manifest, а дают техническую недоступность. Sources=[] и traders=[] допустимы только как достоверные пустые наборы; обязательный Paper/H01 не исчезает.

Внутри manifest допустимы metadata скрытых строк, но они не выходят в API. RevisionID и номер связывают неизменяемые поля карточки; source/identity-поля не разрешено менять без прежних правил. Fingerprint не является независимой проверкой произвольной правдоподобной порчи БД: нарушение immutable writer/данных требует прежних механизмов R и сверки, не объявляется автоматически обнаруженным хешем. Целый manifest не помещается в cursor и не ограничивается размером одной страницы. Если его нельзя достоверно прочитать/канонизировать в общем бюджете, ответ503; нельзя хешировать только прочитанный префикс.

### 9.3. Точный закрытый plaintext cursor

В plaintext ровно восемь обязательных полей; сериализация JCS/UTF-8 без BOM. Полей issuedAt/expiresAt/TTL/алгоритма/произвольных claims нет.

| Поле | Тип / источник |
| --- | --- |
| requestSchemaVersion | Строка v1 |
| environmentBinding | 64 lowercase hex из §9.2; сравнивается с текущей серверной environment |
| readerBinding | 64 lowercase hex из защищённого текущего H01; чужой или иной контекст не принимает cursor |
| venueId | UUID v4 разрешённой V.id |
| venueCode | polymarket либо limitless, ровно текущий запрос/venue |

### 9.4. Точные байты оболочки и предел

Предлагается codec с локальным именем q02-cursor-v1; это не новый runtime reasonCode/record_schema_version и не изменение реестра v4. У версии фиксированный алгоритм, поля alg нет.

| Порядок байтов после base64url decode | Длина / значение |
| --- | --- |
| formatVersion | 1 байт, значение01 hex |
| keyId | 16 байт непрозрачного публичного идентификатора ключа, не UUID ресурса и не URL secret store |
| nonce | 24 байта нового криптографически случайного nonce для каждого шифрования |
| ciphertext | Зашифрованные точные JCS-байты plaintext §9.3, длина равна длине plaintext |
| authenticationTag | 16 байт, полный tag без усечения |

AEAD additional authenticated data — точные ASCII-байты строки shadow.q02.cursor.v1, затем один нулевой байт, затем formatVersion и16 байтов keyId. Ключ —32 байта. Nonce не секретен, но его нельзя намеренно повторять с тем же ключом, выводить из requestId/time/statehash или получать из слабого генератора. Шифрование выполняет проверенная библиотека; ручная сборка Poly1305/ChaCha не разрешена этим документом. При недоступном генераторе/ключе нельзя выдавать неподписанный cursor или усекать tag.

Вся оболочка кодируется один раз base64url RFC4648 §5 без padding, точек/пробелов/переводов строк. При чтении проверяются принятый предел2048 ASCII, алфавит, полный расход входа, допустимые остаточные биты; повторное каноническое кодирование должно дать ту же строку. Декодер не игнорирует символы и не выполняет повторный URL/base64 decode. Параметр query обрабатывается по обычному однократному транспортному разбору, не собственным «починяющим» декодером.

Восемь полей фиксированного профиля дают ограниченный размер независимо от числа трейдеров. Документальный подсчёт длины восьми ASCII-полей даёт 425–427 байт plaintext; с оболочкой 482–484 байт, после base64url 643–646 символов. Это расчёт спецификации, не запуск codec/шифрования; wire-предел2048 не расширяется. Неразрешённый размер/структура клиентского cursor —400. Невозможность доверенного writer сформировать соответствующий профиль —503 без cursor, не «последняя страница» с null. До успешной AEAD-проверки plaintext не разбирается и не используется для поиска данных.

### 9.5. Ключи, отсутствие TTL и смена версии

Ключевой набор — отдельная доверенная конфигурация со своим контролем целостности/свежести и непереиспользуемыми keyId; не новая таблица Shadow и не публичный endpoint. Для каждого окружения/назначения ровно один ключ выдачи; прежние могут быть только для проверки/расшифрования, отозванные — запрещены. Это внутренние статусы key-management, не новые коды реестра проекта.

Плановая смена: сначала все readers получают новый допустимый ключ, затем issuer начинает использовать его; прежний остаётся для чтения старых курсоров. Смена ключа/nonce не меняет Manifest и не означает CATALOG_CHANGED. Повтор того же запроса при прежнем состоянии даёт ту же items-страницу, но байты nextCursor могут отличаться. Текущая диагностика/navigation также не immutable receipt.

TTL курсора не вводится. Поэтому нельзя автоматически удалять прежние проверочные ключи через выдуманный срок и называть это совместимой ротацией. Их плановый вывод требует отдельно согласованной политики совместимости; до неё они сохраняются для проверки. При подтверждённом отзыве, в том числе компрометации, курсоры этого keyId непригодны400; текущий доступ всё равно обязателен, причину/наличие ключа клиенту не раскрывают. Отзыв должен действовать на всех readers; неопределённая свежесть/состояние key store —503, не fallback к старой локальной копии.

Незнакомый keyId даёт400 только если доступен полный актуальный авторитетный набор, подтверждающий отсутствие. Если известный ключ недоступен, набор неполон/его свежесть неизвестна или verifier сломан —503. Не перебирать произвольные ключи/внешние URI из cursor и не отличать tag-failure от известного отзыва в деталях ответа.

Новая версия codec требует отдельного формата/совместимого развёртывания readers до writers. Не менять правила v1 задним числом; неизвестная formatVersion —400 для текущего поддерживаемого протокола. Restore не возвращает отозванные ключи/старую версию области доверия: протокол восстановления ключевого набора и scopeRevision остаётся H01/H06. Авторизация/keys не выводятся из одного успешного backup БД.

### 9.6. Порядок проверки и исходы

После применимых ранних transport/Auth-защит (их общий приоритет остаётся H01) применяются такие зависимости:

1. Ограничить форму/длину; разобрать только ограниченную оболочку и локальный keyId.
2. Установить актуальный key status; достоверно неизвестный/отозванный →400, неизвестность самой проверки →503.
3. Проверить AEAD целиком до использования plaintext. Доказанная подмена →400; сбой криптографического компонента →503.
4. Проверить ровно8 полей, типы, canonical JCS и текущие environment/reader/venue/limit. Несовпадение контекста/параметров →400; недействующий текущий вход/право →прежний access/hidden ответ, не400 вместо проверки доступа.
5. По принятому §7 прочитать согласованное состояние с текущим разрешением. ScopeRevision неизвестна →503; доступ утрачен →access/hidden; подтверждённое отличие fingerprint →409 CATALOG_CHANGED.
6. Только при совпавшем состоянии выбрать страницу. Позиция должна соответствовать существующему разрешённому lastTraderId этого состояния и иметь последующие элементы: корректный issuer не выдаёт cursor на конец. Если достоверное целостное состояние подтверждено, неподходящая позиция — непригодный cursor400, с безопасной внутренней диагностикой возможного дефекта issuer; не пустая страница. Если позицию нельзя проверить из-за сбоя/порчи данных — технический503, не доказанная непригодность cursor. Новый code не вводится.

400 остаётся общим INVALID_REQUEST без раскрытия plaintext/keyId/получателя;409 сохраняет ровно один reasonDetails CATALOG_CHANGED/params={} и безопасный select_trader/venueId, без items/nextCursor;503 — неизвестность/непригодность по прежним категориям. Q05/CMD/сохранённый rejection для этих чтений не создаются. Нет внутреннего повтора, автоматического нового cursor/обхода при ошибке, обновления C04 или пересчёта исторических fieldErrors.
