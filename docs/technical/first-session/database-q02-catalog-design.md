## 1. Принятые границы и найденный пробел

Источники актуальной main доступны: [формы API §14](backend-api-forms-addendum.md), [передача DB-API-10 §9](backend-database-change-list.md), [физический каталог §§2–7](database-physical-catalog-review.md), [реестр v4](backend-code-registry.md), [T09 чтения](backend-contracts.md), [R020–R022](database-constraint-register.md). Они задают формы и правила; этот документ не изменяет их по дате своего появления.

Уже принято:

- Карточка по venueCode/traderId и список по одной venue. Guest/user читают разрешённый каталог, environment/источники задаёт сервер. Неполный/недействующий user-контекст не превращается в guest для обхода действующего H01.
- Сортировка traderId по возрастанию, limit по умолчанию20, диапазон1–50; непрозрачный cursor base64url без padding длиной≤2048 ASCII. Нет offset/поиска/score/клиентской сортировки/only-available.
- Видимые карточки с запрещённым запуском остаются в списке с startAvailability=false. Скрытая/отсутствующая/чужая venue карточка даёт одинаковый404. Ошибка чтения или порча обязательного источника не пустой список.
- Все поля страницы согласованы; конец только nextCursor=null. Изменение проверяемого состояния разрешённого каталога между страницами →409 CATALOG_CHANGED; неверный cursor→400 INVALID_REQUEST; неизвестность чтения→503; потеря доступа не маскируется409. Старый draft/выбор не стираются.
- Q02:5s, без внутренних автоматических повторов, no-store. Чтение не создаёт draft/review/session/CommandReceipt/audit Q06 и не открывает загрузку fixture через публичный API.

Источники всех17 верхних полей Trader уже существуют (§2). Но catalog_sources.start_enabled и traders.start_allowed определяют допуск запуска, а не публикацию для чтения. В физических таблицах нет отдельного принятого признака видимости; внешний контракт требует отличать скрытое от видимого start-disabled. Не следует молча назначать start_enabled роль такого признака.

## 2. Точная карта Trader из существующих колонок

Один объект используется в trader карточки и в каждом items списка. V=venues, S=catalog_sources, T=traders, R=trader_revisions, P=paper_controls. Все ссылки включают environment и свою venue/source/trader; R выбирается по T.current_revision_id, а не max(created_at). Источники ниже — отражение уже принятых API-форм, не новые колонки.

| Поле Trader | Колонка / преобразование |
| --- | --- |
| traderId | T.id |
| venueId | T.venue_id, совпадает с V.id и S.venue_id |
| catalogSourceId | T.catalog_source_id, совпадает с S.id и R.catalog_source_id |
| venueCode | V.code; polymarket/limitless; совпадает с path/query |
| externalTraderId | T.external_trader_id — непустой ID своего источника, не новая нормализация адреса |
| displayName | R.displayed_name, не V.display_name и не имя иной revision |
| traderRevisionId | R.id = T.current_revision_id |
| traderRevision | R.revision → положительная целочисленная строка |
| dataOrigin | R.data_origin, согласованный с S; synthetic первого стенда |
| sourceRef | R.source_ref — безопасный сохранённый источник revision; не S.source_ref как замена и не автоматически разрешённая внешняя ссылка |
| observedAt | R.observed_at → UTC с миллисекундами; fixture не становится наблюдением live-рынка |
| revisionCreatedAt | R.created_at → UTC с миллисекундами |
| catalogVersionAtCreation | R.catalog_version_at_creation → положительная строка; исторический номер не переписывается |
| catalogVersion | S.version → текущая положительная строка именно источника; не V.version и не будущий общий номер обхода |
| traderControlVersion | T.version → текущая положительная строка |
| paperControlVersion | P.version своей environment/mode=paper → текущая положительная строка |
| startAvailability.available | Вычисляется по достоверным P.start_enabled, S.start_enabled и T.start_allowed из согласованного состояния |
| startAvailability.capabilityReasonCode | При true — null; иначе первый применимый известный запрет PAPER_START_DISABLED → CATALOG_SOURCE_DISABLED → TRADER_START_DISABLED |

StartAvailability — ровно два ключа, не новая колонка JSON. Остальные16 верхних полей не null; лишних полей/денег/счётчиков/score нет. Исторический catalogVersionAtCreation вправе отличаться от текущего catalogVersion. Неизвестная версия/неполный current-цикл/отсутствующий обязательный control не подменяется default или удобным известным запретом; после надлежащего доступа действует техническая ошибка по принятому контракту.

Current revision в Q02 и историческая revision в review/settings/session имеют разное назначение. Новая карточка не переписывает исторические имена/источники сессии. C04 по-прежнему принимает только venueId/traderId своей формы и сохраняет исходный ввод/результат по прежнему контракту, без клиентских guards/полного Trader.

Корни ответов и параметры остаются точными формами §14 бэкенда: карточка trader/nextAction/nextActionParams; список venueCode/items/nextCursor/nextAction/nextActionParams. RequestId/correlation только текущая диагностика; при отсутствии безопасной цели nextAction=null/params={}, произвольный draft не выбирается. Курсор и источник его доверия ещё блоки2–3, не готовое поле БД.

## 3. Блок 1 на выбор: явная видимость в двух существующих таблицах

**Рекомендация, ещё не принято:** добавить по обязательному boolean read_visible в catalog_sources и traders. Это два новых проектируемых поля, число34 таблиц не меняется. Никакого SQL/изменения реальной БД здесь нет.

| Поле | Предлагаемый смысл |
| --- | --- |
| catalog_sources.read_visible | Источник опубликован для Q02 в своей среде/площадке; false скрывает все его карточки |
| traders.read_visible | Конкретный trader опубликован для Q02; действует только при опубликованном источнике |

Разрешённая карточка Q02 требует одновременно серверно разрешённого контекста чтения/источника и обоих true. Флаги не заменяют авторизацию; ID/env/source из клиента не дают полномочий. Нет нового клиентского фильтра visible, нового API-поля или режима «покажи скрытых». Параметры персонализации и новые роли/списки доступа не вводятся: применяется уже принятый guest/user допуск к разрешённому каталогу.

У нового источника/трейдера при доверенной подготовке предполагается явное false; публикация true — только после подготовки полного проверенного источника/current revision. NULL, отсутствие значения или неизвестность не считаются false/пустым результатом для повреждённой обязательной записи. Старые синтетические S-наборы при будущей подготовке получат явно подтверждённые true для своих SRC/T; не массовый runtime-backfill и не предположение, что все существующие строки автоматически открыты.

Видимость для Q02 и start-допуск независимы. Сочетание read_visible=true/start_enabled=false (или start_allowed=false) — корректная видимая карточка с unavailable причиной. False видимости скрывает Q02-карточку независимо от start-флага. Из read_visible=true нельзя вывести право C04/C05/C06/торговлю; из скрытия нельзя вывести удаление draft/review/старой сессии/проводок. Действующие проверки доступа и запуска этих операций сохраняются; новый reasonCode/сброс/обход либо новая политика исторического доступа этим полем не вводятся.

Точный путь видимости в остальных операциях должен быть сверен с уже принятыми access/version проверками при следующей детализации публикации: это не повторное открытие C04. Не объявлять одни flags полным защищённым H01-протоколом и не выдавать новый publisher/admin endpoint.

### 3.1. Сохранение публикации

Новая revision публикуется только полным существующим комплектом R + T.current_revision_id + T.version + S.version, как уже принято. Если эта же операция меняет read_visible, изменение входит в её транзакцию. Нельзя сначала показать ссылку, затем дописать обязательные данные. Не вводится staged revision без прежнего полного current-цикла: скрытый trader тоже должен удовлетворять физическим FK/полноте.

Предлагаемое дополнение к guards:

- Изменение S.read_visible повышает S.version вместе с флагом, не переписывая revisions/trader identities.
- Изменение T.read_visible повышает T.version и S.version вместе. Номер не сбрасывается; false→true→false не возвращает прежние версии. При отсутствии изменения флага не изображать его новую публикацию.
- Несколько затронутых полей одной публикации дают согласованные новые положительные guards по действующему протоколу; не вводится произвольное число повышений на поле. Исторические номера review/R не меняются.
- Новые источник/trader/current revision создаются по прежним scoped unique/FK и полноте; начальные версии и итоговые guard values фиксирует будущий manifest подготовки. Смена venue/sourceEnvironment/dataOrigin/external identity не маскируется обновлением флага.
- Управляет доверенный publisher/процедура подготовки, не обычный Q02 или клиентский запрос. Права writer и происхождение публикации ещё требуют механизма/доказательств; роль owner по имени не даёт прямого DML, владелец 1 и владелец 2 равноправны.

Это определяет атомарные факты публикации, но **не закрывает обнаружение изменения всего набора**: новый/убранный из разрешённого набора источник нельзя заметить одним guard ранее выбранного источника. Курсор должен учитывать разрешённый набор целиком, paper guard и применимую видимость, включая доверенное серверное изменение доступа. Устройство этого контроля остаётся блоком2; конкретный hash/новый aggregate guard сейчас не выбран.

### 3.2. Альтернатива и вопрос

| Вариант | Последствие |
| --- | --- |
| Рекомендация: read_visible в существующих source/trader | Видимость хранится рядом с идентичностью и атомарно меняется с существующими guards; два явных поля и без новой таблицы |
| Версионированный внешний manifest видимости | Меньше колонок, но нужен отдельно доказанный атомарный протокол сопоставления manifest с БД/guards на каждом чтении и смене конфигурации; разрыв публикации нельзя скрыть кэшем |

**Принять ли блок1 целиком: точную карту источников и отдельные read_visible у источника и трейдера, с атомарной сменой соответствующих guards?** Это новый физический выбор, поэтому до ответа поля/ограничения не вносятся в принятую физическую спецификацию. Использовать start_enabled вместо видимости не вариант: это смешивает уже различённые внешним контрактом состояния.
