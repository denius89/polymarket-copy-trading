# Передача из чата бэкенда в чат БД — изменения H01–H06 и C04

29.10.2026 · Подготовлено по прямому поручению владельца. **Согласованные решения бэкенда**, а не новое предложение продуктовых правил: [единый пакет](backend-design.md), [ADR-0065](../../decisions/0065_first_session_backend_contract.md). Baseline main 1452fc36fc02b530fa0fe33cd99805d3251ab8f3. Сообщение в другой чат автоматически не отправлялось.

Нужно отразить решения в существующих документах БД и критериях их проверки. Код, SQL, миграции, аккаунты, установка и deploy не поручены. Все 34 ранее принятые таблицы/инварианты остаются исходной опорой; расширение C04 оформляется явно, без ослабления C06. Историческое принятие ADR-0064 §33 не переписывается как будто оно уже содержало этот вариант.

## 1. Обязательное изменение M01 — C04

Пробел подтверждён в [матрице M01](database-integrity-matrix.md): команды/acceptance требуют устойчивый результат C04, а физический command_keys ограничен user/C06; succeeded receipt требует session/settings/snapshot. Гостевой C04 и результат draft туда не помещаются.

Принято расширить существующие command_keys/command_receipts/command_receipt_details с условной полнотой по команде. Одного добавления C04 к enum недостаточно.

| ID | Требуемое документальное изменение | Проверяемое постусловие |
| --- | --- | --- |
| DB-C04-01 | Описать взаимоисключающие user/guest actor-варианты ключа; постоянный guest context создаётся Auth-адаптером до первого C04 | Потеря ответа create не создаёт другой draft; ID без proof не даёт доступа; scope не зависит от login |
| DB-C04-02 | Область unique: environment + realm + постоянный actorId + C04/C06 + clientCommandId; создать точные колонки/условия/индексы без nullable-лазеек | Один ключ не резервируется несколько раз из-за NULL; user/guest и среды не смешиваются |
| DB-C04-03 | Закрепить create/update как намерение C04 в fingerprint, target и expected version | Тот же ключ с другим draft/операцией/полями конфликтует, не меняет старый результат |
| DB-C04-04 | Описать успешный C04 core: draftId, ownershipId, draftVersion, changeKind, lastSavedAt, expiresAt; fieldErrors в типизированных details | Восстанавливается исходный результат после следующей правки, без хранения полной истории raw |
| DB-C04-05 | Описать rejected C04, допустимые исходные target/ownership refs и безопасные details, включая create без созданного draft | Отказ не требует фиктивного draft/session и не раскрывает чужое владение |
| DB-C04-06 | Атомарный C04: key + окончательный receipt/details + изменение draft/ownership при create | Нет commit с изменением без результата или key без окончательного receipt |
| DB-C04-07 | Новый unchanged C04 сохраняет результат, но не меняет version/lastSavedAt/expiry; stale version проверяется до равенства | Exact replay отличается от новой no-op команды; одинаковые данные с устаревшей версией конфликтуют |
| DB-C04-08 | Q05/путь восстановления: guest до claim, user после claim через подтверждённую цепочку | Старый proof закрыт; новый владелец читает прежний результат без переноса/повторного исполнения ключа |
| DB-C04-09 | Сохранить все C06 mandatory result/FK/обратные ссылки и полноту initial пакета | C04 receipt не может удовлетворить ссылки session/settings/funding/journal/start audit/outbox |
| DB-C04-10 | Уточнить компактное ядро/retention C04, включая historical ownership и version результата | Expiry/used/новый login не удаляют защиту повторов; нет каскадного разрушения evidence |

Точные новые имена колонок, условные FK/unique и связь guest context с ownership ещё не утверждены физическим описанием. Это работа данного списка, а не скрытая готовая миграция. Не назначать фиктивного user для guest и не делать обязательные связи C06 необязательными ради общей формы.

Для DB-C04-08 требуется доказать авторизацию по текущему владельцу + конкретной цепочке claim + исходному историческому ownership/result. Один переданный draftId/clientCommandId или совпадение email недостаточны. Поиск исходного guest create до получения draftId опирается на действующий серверный guest context и ключ.

### Дельты C04 для будущей матрицы

| Случай | Ожидаемая дельта |
| --- | --- |
| Новый create | Один draft и первоначальное ownership + один key/receipt/details |
| Новый update с изменением | Один key/receipt/details, изменение своего draft/version/TTL; без новой истории raw |
| Новый unchanged | Один key/receipt/details; draft/version/TTL прежние |
| Точный повтор | Новых key/receipt/details и изменений draft нет |
| Новый окончательный business rejection после допуска к ключу | Один rejected key/receipt/details; draft неизменен |
| Ранний invalid/access denied | Предметных записей нет; безопасная диагностика отдельно |
| Подтверждённый rollback | Комплекта именно этой операции нет; независимый commit конкурента не отменяется |
| Unknown commit | Дельта не объявляется нулевой до выяснения исходного ключа |

Во всех C04 случаях новых FIN, start audit/outbox нет. Текущий реестр не добавляет guest C04 в user/staff-only audit_events.

### Обязательные варианты проверки C04

Потеря ответа create; два одновременных одинаковых ключа; разные payload одного ключа; пара новых ключей с одной expectedVersion; повтор после version+1; новый stale no-op; 20→20.00; invalid raw; истечение/used; новый login; гонка claim↔C04 в обоих порядках; закрытие guest proof; восстановление user по claim; чужая среда/ownership; подстановка C04 receipt в C06; поломка details; backup до сохранения. Связать с A54–A57/A98/A100–A107/A110–A112 и F05/F06/F17/F19, не объявляя их пройденными.

## 5. Критерий завершения сверки

- Каждый DB-C04 пункт имеет точные поля/связи/nullable-условия/уникальность и безопасный путь чтения.
- Нет C04 результата без устойчивого actor scope; нет C06, ссылающегося на C04 receipt.
- Исторический результат, текущий draft и авторизация после claim различены.
- Нет скрытого pending, повторного funding, склеивания grants, переименования истории или UI-only защиты.
- Все DTO/коды и физические ограничения согласованы; неизвестные/неприменимые значения не получают defaults.
- По H01–H06 отдельно перечислены непроверенные компоненты/форматы/сбои/restore.
- Обновлённые документы проходят редакционные проверки; DB/API/Auth проверки остаются «запланировано».

## 6. Готовый текст для передачи в чат БД

В чате бэкенда приняты H01–H06 и закрытые реестры. Прочитай backend-design.md, затем backend-contracts.md, backend-code-registry.md, backend-auth-access.md, backend-operations.md и этот список изменений. Сейчас только документы, без SQL/кода/миграций/аккаунтов/deploy.

Нужно явно отразить принятое дополнение C04 в физических документах: user/guest scope до создания draft; key/receipt/details в одной транзакции; отдельный успешный результат draft; unchanged и exact replay; безопасный результат после claim; сохранение строгой полноты всех C06-связей. DB-C04-01–10 и дельты выше задают проверяемый объём. Не заменять расширение enum ослаблением C06.

Сверь H02/H03 коды/форматы/whole-grant evidence, параметры H04 и решения H05/H06 с матрицей M01–M05. Сохрани продуктовые правила, исходные A01–A112 и исторические принятия ADR-0064. Принятое решение не равно применённой или испытанной схеме. Используй обозначения «владелец 1» и «владелец 2».
