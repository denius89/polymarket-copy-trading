## 1. Обязательное изменение M01 — C04

Исходный пробел [M01](database-integrity-matrix.md) — user/C06-only ключ и обязательный session-result — уже частично устранён в документах. На актуальном baseline [блоки C04 1–2](database-c04-addendum.md) приняты: user/guest XOR, scoped уникальности, guest_context_id ownership, исходные result-поля C04/details, атомарность и last_input_receipt_id. Блок 3 (target/post-claim/типизированные FK) предложен, не принят; заключительная сверка H02–H06 ещё впереди. M01 не закрыт целиком. Таблица DB-C04-01–10 ниже сохраняет исходный объём передачи, не отменяет уже принятые части.

Принято расширить существующие command_keys/command_receipts/command_receipt_details с условной полнотой по команде. Одного добавления C04 к enum недостаточно.

| --- | --- | --- |
| DB-C04-01 | Описать взаимоисключающие user/guest actor-варианты ключа; постоянный guest context создаётся Auth-адаптером до первого C04 | Потеря ответа create не создаёт другой draft; ID без proof не даёт доступа; scope не зависит от login |
| DB-C04-02 | Область unique: environment + realm + постоянный actorId + C04/C06 + clientCommandId; создать точные колонки/условия/индексы без nullable-лазеек | Один ключ не резервируется несколько раз из-за NULL; user/guest и среды не смешиваются |
| DB-C04-03 | Закрепить create/update как намерение C04 в fingerprint, target и expected version | Тот же ключ с другим draft/операцией/полями конфликтует, не меняет старый результат |
| DB-C04-04 | Описать успешный C04 core: draftId, ownershipId, draftVersion, changeKind, lastSavedAt, expiresAt; fieldErrors в типизированных details | Восстанавливается исходный результат после следующей правки, без хранения полной истории raw |

| DB-C04-10 | Уточнить компактное ядро/retention C04, включая historical ownership и version результата | Expiry/used/новый login не удаляют защиту повторов; нет каскадного разрушения evidence |

Статус по DB-C04-01/02 и result/атомарности DB-C04-04–07/10 обновлён блоками 1–2. Точные target refs и типизированные FK/post-claim поиск DB-C04-03/05/08/09 ещё согласуются блоком 3. Не перечёркивать принятые колонки/unique/last_input_receipt_id общей пометкой «всё ещё открыто». Не назначать фиктивного user для guest и не делать обязательные связи C06 необязательными ради общей формы.

Для DB-C04-08 требуется доказать авторизацию по текущему владельцу + конкретной цепочке claim + исходному историческому ownership/result. Один переданный draftId/clientCommandId или совпадение email недостаточны. Поиск исходного guest create до получения draftId опирается на действующий серверный guest context и ключ.

### Дельты C04 для будущей матрицы

| Случай | Ожидаемая дельта |
| --- | --- |
| Новый create | Один draft и первоначальное ownership + один key/receipt/details; last_input_receipt_id указывает на created result |
| Новый update с изменением | Один key/receipt/details, изменение draft/version/TTL и last_input_receipt_id; без новой истории raw |
| Новый unchanged | Один key/receipt/details; draft/version/TTL/last_input_receipt_id прежние |
| Точный повтор | Новых key/receipt/details и изменений draft нет |
| Новый окончательный business rejection после допуска к ключу | Один rejected key/receipt/details; draft неизменен |
| Ранний invalid/access denied | Предметных записей нет; безопасная диагностика отдельно |
| Подтверждённый rollback | Комплекта именно этой операции нет; независимый commit конкурента не отменяется |
| Unknown commit | Дельта не объявляется нулевой до выяснения исходного ключа |

Во всех C04 случаях новых FIN, start audit/outbox нет. Текущий реестр не добавляет guest C04 в user/staff-only audit_events.

### Обязательные варианты проверки C04

Потеря ответа create; два одновременных одинаковых ключа; разные payload одного ключа; пара новых ключей с одной expectedVersion; повтор после version+1; новый stale no-op; 20→20.00; invalid raw; истечение/used; новый login; гонка claim↔C04 в обоих порядках; закрытие guest proof; восстановление user по claim; чужая среда/ownership; подстановка C04 receipt в C06; поломка details; backup до сохранения. Связать с A54–A57/A98/A100–A107/A110–A112 и F05/F06/F17/F19, не объявляя их пройденными.

## 5. Критерий завершения сверки

- Каждый DB-C04 пункт имеет точные поля/связи/nullable-условия/уникальность и безопасный путь чтения.
- Нет C04 результата без устойчивого actor scope; нет C06, ссылающегося на C04 receipt.
- Исторический результат, текущий draft и авторизация после claim различены.
- Нет скрытого pending, повторного funding, склеивания grants, переименования истории или UI-only защиты.
- Все DTO/коды и физические ограничения согласованы; неизвестные/неприменимые значения не получают defaults.
- По H01–H06 отдельно перечислены непроверенные компоненты/форматы/сбои/restore.
- Обновлённые документы проходят редакционные проверки; DB/API/Auth проверки остаются «запланировано».

### Точки полевой сверки, не скрытые решения

- Физический reason_data — объект с пустым объектом при отсутствии; API reasonDetails — список. Нужны точные схема/отображение и известные поля safe params без произвольного содержимого. FieldErrors исходного C04 не пересчитываются.
- Last_input_receipt_id не меняется при новом unchanged. Для Q03 после смены policy отдельно обозначить происхождение ошибок, не выдавая историю за новую проверку; это не повод переписать прежний receipt.
- Новые requestId/nextAction/разрешённые ссылки и restrictedGroups принадлежат текущей выдаче; неизменяемые причины/числа результата остаются в истории. Если ссылка больше не разрешена, текущая проекция не раскрывает её и не изменяет БД.
- C01–C03/claim/C07 unknown требуют собственного защищённого H01-протокола. Автоматическое помещение их в Q05 или обычный CommandReceipt запрещено текущей областью контракта.
- На baseline блок 3 C04 остаётся предложением; новые discriminator/target FK не считать принятыми только от данного handoff.

### Проверочные дополнения, пока без исполнения

Сопоставить с существующими A01–A112/S/N/K/F01–F24; добавлять документальные подкейсы, не переписывать прежний ожидаемый финансовый результат:

1. Raw comma/dot/leading zeros/trailing zeros; invalid syntax vs invalid wire type; no rounding; одна ошибка на поле и независимые ошибки нескольких полей.
2. Несколько причин C05/C06, известный receipt после used/expiry/смены policy, technical read error вместо вымышленного business refusal.
3. Rejected, затем исчезновение препятствия: тот же key по-прежнему rejected, новое явное намерение проходит актуальную проверку.
4. Lost C04 response/version5 после version6; отсутствие обновления pointer при unchanged; Q05 pending/503/неизвестный формат; 30-секундное окно не очищает key.
5. C05 неизвестный commit и явный новый review; claim lost response после закрытия guest proof; другой user не читает результат.
6. Q06 group denied/null/zero/повреждение/audit failure; repeat HTTP даёт собственный audit, но прежний snapshot/version/asOf.
7. C07 late retry/ответ после нового login, Auth C02 неизвестный итог, C01/C03 повтор доставки запроса без повторного письма; неполный Auth не создаёт полный прикладной вход.
8. HTTP 200 отрицательного review/чтения rejected, повтор201, разные requestId при одном clientCommandId/receiptId; no-store и безопасная диагностика.

Результаты этой задачи — документальная сверка и передача. Испытания перечисленных случаев, реализация парсера/DTO/ограничений/Auth/восстановления не выполнены.
