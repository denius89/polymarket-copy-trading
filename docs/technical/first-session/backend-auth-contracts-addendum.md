## 2. Общие формы, время и порядок проверок

Во всех точных формах перечисление полей закрыто: неизвестные/дублирующиеся ключи, пропущенные обязательные, неверные типы/enum/NULL запрещены. Идентификаторы новых контекстов, операций, login/challenge — UUIDv4; версия запроса — строка v1. Время — UTC Z, ровно три знака миллисекунд. requestId и correlationId остаются диагностикой из API-дополнения, а не ключами операции.

Auth POST: до **8192 исходных байт**, глубина контейнеров до **8**, корень-объект считается первым. Несжатый UTF-8 JSON; application/json с необязательным charset=UTF-8, Content-Encoding отсутствует или identity. Нет BOM, невалидного UTF-8, непарных Unicode-surrogates, повторных ключей после декодирования escapes, comments/trailing commas/data, coercion или обрезания. Размер проверяется по фактическим байтам. Глубина разбирается после допустимости media. Для claim и прежних C04/C05/C06 сохраняется **65536 байт**, не 8192. GET не допускает непустого тела; только перечисленные query, без дублей после percent-decoding.

Порядок: размер → media → структура/диагностика → Origin/CSRF → подтверждение личности/контекста → доступ к цели → transport rate limit → запись операции/её целостность → совпадение намерения → сохранённый результат → условия нового исполнения. Техническая невозможность останавливает достигнутую стадию; не подменяет более ранний уже определённый отказ. Повреждённая запись — технический отказ до сравнения payload. Известный другой payload — KEY_REUSE_CONFLICT. Transport quota учитывает разрешённые повторы; бизнес-паузы OTP/TOTP применяются только к новому исполнению после поиска результата.

Ошибка без результата: корень ровно reasonCode, reasonDetails, nextAction, nextActionParams. reasonDetails — ровно один объект code/params, code=reasonCode, params={}. При nextAction=null параметры строго {}. Нет receipt/result/claim/review/fieldErrors/observedAt, если они не предусмотрены отдельной успешной формой. Коды 400 INVALID_REQUEST, 413 REQUEST_TOO_LARGE, 415 UNSUPPORTED_MEDIA_TYPE, 401 AUTH_REQUIRED/AUTH_EXPIRED/AUTH_REVOKED, 403 ACCESS_DENIED, 404 RESOURCE_NOT_FOUND, 409 KEY_REUSE_CONFLICT, 429 RATE_LIMITED, 503 SERVICE_UNAVAILABLE/RECORD_UNAVAILABLE сохраняются. Отозванное и истёкшее подтверждение даёт AUTH_REVOKED, если оба факта доказаны. Скрытый объект не раскрывается подробностями.

Новые принятые 409-коды: AUTH_CONTEXT_STATE_CONFLICT; AUTH_COOKIE_RECOVERY_NOT_APPLICABLE; AUTH_COOKIE_RECOVERY_CLOSED. [Реестр](backend-code-registry.md) получает документальное издание v5; четыре immutable recordSchemaVersion=v1 не меняются. Auth commandType и result.kind ниже не становятся кодами команд Shadow или значениями audit_events.

Все ответы защищённых чтений/результатов — Cache-Control: no-store. Общие nextAction/params остаются из API-дополнения. Для 429 — retry_later; retryAt только достоверный и безопасный. В контекстных операциях не выдаётся retryAt за границей срока контекста; тогда параметры {}. Разрыв соединения не является полученным JSON.

## 3. Идентичность, cookie и вкладки

authContextId — серверная идентичность попытки, не секрет. authOperationId создаётся клиентом до явного действия, сохраняется при повторах. Область: environment + user Auth-context + commandType + operation ID. Новое явное действие — новый ID; другой payload того же ID — конфликт. OTP/секреты не помещаются в обычные fingerprints/журналы. Как безопасно сравнивать секретную часть намерения, ещё требуется описать для адаптера.

UI и API — один HTTPS origin. Для подготовительных/изменяющих Auth POST обязательны точный настроенный Origin, JSON и единственный X-Shadow-Auth-Request: 1. Missing/null/wrong Origin или неоднозначный защитный заголовок — 403 без эффекта/cookie. Sec-Fetch-Site, если есть, должен быть same-origin; отсутствие не отменяет других проверок. Cross-origin CORS не открывается.

| Cookie | Свойства и выбор |
| --- | --- |
| __Host-shadow-authctx-<authContextId> | Случайный секрет ≥256 бит; Secure/HttpOnly/SameSite=Strict/Path=/, без Domain; session cookie без Max-Age/Expires. Серверный срок контекста обязателен |
| __Host-shadow-user-login-<loginId> | Отдельная cookie полного user login, общие защищённые атрибуты; выбранный login задаёт X-Shadow-Login-Id |
| __Host-shadow-staff-login-<loginId> | Отдельная staff cookie; никогда не заменяет user cookie |
| __Host-shadow-logoutctx-<logoutContextId> | Защищённые атрибуты; фиксированный Expires контекста выхода |
| __Host-shadow-claimctx-<claimContextId> | Случайный секрет ≥256 бит, защищённые атрибуты; фиксированный срок контекста claim |

ID выбирает конкретную cookie, но не подтверждает её. Нельзя выбрать первую/последнюю подходящую cookie. Неверный/дублирующий X-Shadow-Login-Id — 400. Поздняя выдача/очистка cookie A не изменяет B; серверный отзыв сильнее сохранившейся cookie. Provider refresh не меняет loginId и не продлевает абсолютный срок. Точные параметры persistent full-login cookie остаются §16: принятые сроки доступа не равны автоматически браузерному Expires.

После успешного Q01 разрешён несекретный localStorage-указатель ровно version=v1, realm=user, loginId. Каждая вкладка удерживает свой выбор; общий указатель — лишь кандидат при новом открытии. До подтверждения Q01 персональный кэш не показывается. Нет указателя — экран входа, не перебор cookie и не новый endpoint списка аккаунтов. Другие открытые вкладки автоматически не переключаются на новый login. Запоздалые ответы сопоставляются с исходными login/запросом/выбором. Pending logout не превращается в восстановленный кабинет. Недоступный Q01 не означает logout; пользовательские и служебные контуры раздельны.

## 4. Выдача и чтение Auth-контекста

POST /api/auth/contexts: без query; body ровно requestSchemaVersion. HTTP201: корень authContext, observedAt, nextAction=null, nextActionParams={}; выдаёт отдельную cookie. GET /api/auth/contexts/:authContextId: только requestSchemaVersion=v1 в query, без тела, proof контекста; HTTP200 с той же оболочкой. GET не выдаёт cookie и не продлевает сроки.

authContext содержит ровно перечисленные поля:

| Поле | Правило |
| --- | --- |
| authContextId | UUIDv4 |
| stage | ready / email_verification / totp_verification / totp_enrollment / completed |
| accessConfirmed | false в ответе создания; true после доказанного GET; это не полный login |
| createdAt, expiresAt | Неизменяемые; expiresAt=createdAt+30 минут |
| emailCodeIssuedAt, emailCodeExpiresAt, currentEmailChallengeId | Обязательные nullable: заполняются в email_verification, в том числе для истёкшего текущего кода; иначе null |
| currentTotpChallengeId, totpChallengeIssuedAt, totpChallengeExpiresAt | Обязательные nullable: только в totp_verification, включая истёкший challenge; иначе null |
| loginCookieRecoveryDeadlineAt | null до полного входа; затем min(completedAt+5 минут, context.expiresAt), верхняя граница, а не право восстановления |

Для totp_verification/enrollment nextAction соответственно complete_totp/enroll_totp с authContextId; иначе null/{}. Нет email/userId/роли/секретов. Unknown источник времён не подменяется null. Completed — историческое состояние, актуальный login проверяет Q01.

До C01 клиент подтверждает созданный контекст GET; сервер при действии всегда перепроверяет proof. Потеря ответа создания до C01: если ID/proof есть — GET; иначе явный новый пустой контекст. После C01 потеря proof не доказывает отсутствие отправки или входа; публичный ID/email proof не заменяют, новый вход подчинён прежним лимитам.

30 минут фиксированы, чтения/resend/ошибки срок не продлевают; now≥expiresAt закрывает действия и чтение Auth-истории этим proof. Полный login живёт по отдельной политике. Отсутствие proof — 401; несовпадение proof/скрытый контекст — 404; доказанное истечение — 401; неустановимое состояние — 503.

## 5. C01/C02/C03: точные формы и email

Во всех трёх — proof контекста, принятые POST-защиты, нет query. По 10 секунд, без автоматического повторения отправки/потребления подтверждения.

| Команда / маршрут | Точные поля тела |
| --- | --- |
| C01 · POST /api/auth/request | requestSchemaVersion, commandType=C01, authContextId, authOperationId, email, locale=ru/en |
| C03 · POST /api/auth/resend | requestSchemaVersion, commandType=C03, authContextId, authOperationId, expectedChallengeId, locale=ru/en |
| C02 · POST /api/auth/verify | requestSchemaVersion, commandType=C02, authContextId, authOperationId, challengeId, code |

Code — строка ровно шести ASCII-цифр, не число. Неверная форма — 400 без увеличения счётчика неверных кодов. C03 не принимает email. Locale выбирает письмо, не меняет профиль.

Email: исходная строка ≤512 UTF-8 байт; удалить только крайние U+0020. Только ASCII, после обрезки ≤254 байт, local 1…64, ровно один @. Local dot-atom: буквы/цифры и !#$%&'*+-/=?^_`{|}~, точки не в начале/конце/подряд. Domain: ≥2 labels, каждая 1…63, буквы/цифры/дефис без краевых дефисов; нет конечной точки. Нет display-name, quoted local, comments, bracket IP literal, Unicode или исправления NFC. ASCII punycode допускается по тем же правилам без преобразования Unicode. Весь адрес переводится в ASCII lower-case по принятой продуктовой норме; точки и +suffix сохраняются, аккаунты не объединяются. Синтаксис не доказывает доставку или владение адресом.

Первый допущенный C01 до возможного внешнего эффекта связывает нормализованный email с контекстом; unknown сохраняет связь. Повтор сравнивает исходные raw email и locale, даже если иной raw нормализуется так же. Другой адрес — новый явный контекст. Новый C01 после принятой первичной отправки — 409 AUTH_CONTEXT_STATE_CONFLICT; resend только C03.

C01/C03 подтверждённое принятие отправки: HTTP202, оболочка операции §7 со status=resolved. Result ровно kind=email_dispatch_accepted, acceptedAt, challengeId, resendNotBeforeAt. Последнее — историческая нижняя граница новой отправки с учётом известных ограничений, не гарантия будущего допуска и не срок кода. Email-код 10 минут, resend≥60 секунд, максимум5 отправок/15 минут и10/час на адрес; пять неверных проверок в семье затем15 минут. Resend счётчики не сбрасывает. Последний подтверждённо выпущенный код заменяет прежний; unknown отправки не объявляет замену.

C03: сначала replay; новое действие требует текущего expectedChallengeId и email-stage. Истёкший код не запрещает resend внутри живого контекста. Два новых C03 по одному expected не отправляют два письма: первый меняет challenge, второй конфликтует. Stale →409 AUTH_CONTEXT_STATE_CONFLICT, если не сработала более ранняя429; unknown конкурирующей операции →503 без новой отправки.

C02: replay прежде текущих stage/challenge. Чужой/неизвестный challenge —404; заменённый/неверный stage —409 AUTH_CONTEXT_STATE_CONFLICT; истёкший текущий email-code —401 AUTH_VERIFICATION_FAILED без счётчика. Неверный действующий код —401, один учёт на операцию; пятая ошибка задаёт retry_later с15-минутной паузой, последующие запросы429. Неизвестность503 не неверный код. Сохранённый отрицательный результат — verification_rejected; GET его выдаёт200.

Email подтверждён, но нужен TOTP/enrollment: HTTP200 оболочка операции, result auth_step_required, nextAction complete_totp/enroll_totp с authContextId. Полный вход — completion §7. C02/C03 сериализуются: C02 первой закрывает resend; C03 первой делает старый challenge непригодным. Unknown блокирует зависимое действие; два C02 с новыми IDs не создают два login.

## 6. Проверка TOTP при входе и обновление challenge

POST /api/auth/totp/verify: body ровно requestSchemaVersion, commandType=AUTH_TOTP_VERIFY, authContextId, authOperationId, challengeId, code. Нет factorId/email/userId/времени клиента. Поиск результата, proof и POST-защиты как выше. Бюджет10 секунд, без автоматического повторного потребления кода. Успех — completion §7; GET операции и POST cookie-recovery допускают этот commandType.

Принят профиль user-totp-login-v1: RFC6238, HMAC-SHA1, 6 цифр, шаг30 секунд, T0=Unix epoch; серверный текущий шаг ±1, без расширения/обучения смещения. Профиль закреплён за версией фактора. Время — момент проверки сервером, не поступления запроса. Недоверенные часы →503 без счётчика. Использованные time steps учитываются по версии фактора между устройствами; при совпадении кода с несколькими допустимыми шагами отмечаются все, наличие уже использованного среди совпавших означает отказ. Это не вечный запрет шестизначной строки. Совместимость адаптера с точной защитой ещё не доказана.

Неверный/повторно использованный допустимо сформированный код —401 AUTH_VERIFICATION_FAILED, счётчик один раз на операцию. Пять подряд неверных после подтверждённого email →15 минут паузы по пользователю между устройствами; успешная проверка завершает серию, после паузы возможна новая. Другие действующие login не отзываются. Pause429 применяется к новой проверке/renew; replay известного результата не повторяет код. Foreign challenge404; неверный stage/заменённый/истёкший TOTP challenge409 без проверки кода; истёкший контекст401.

TOTP challenge живёт min(5 минут от выдачи, context.expiresAt). Result auth_step_required для totp_verification содержит ровно kind, stage, challengeId, challengeIssuedAt, challengeExpiresAt. Для totp_enrollment приняты kind/stage; подробный DTO подключения остаётся §16. Чтения/ошибки/смена30-секундного кода срок challenge не продлевают. C02 replay возвращает исходный challenge, не новый.

POST /api/auth/totp/challenges/renew: body ровно requestSchemaVersion, commandType=AUTH_TOTP_CHALLENGE_RENEW, authContextId, authOperationId, expectedChallengeId. Только явное обновление истёкшего текущего challenge при том же действующем факторе, живом контексте, без активной паузы/неизвестной проверки. Result ровно kind=totp_challenge_renewed, replacedChallengeId, challengeId, challengeIssuedAt, challengeExpiresAt; новый срок5 минут с прежней границей контекста. HTTP200 оболочка операции; nextAction=complete_totp при текущем допуске, иначе null. GET результата поддерживает тип, cookie-recovery — нет.

Renew не сбрасывает ошибки/паузы/использованные steps. Challenge, pointer и результат должны сохраняться восстановимо согласованно. Два новых renew одного expected дают один результат и конфликт второго; точный replay возвращает историю до новых условий. Бюджет5 секунд/одна попытка;3 допущенных запроса/60 секунд по environment+доказанный user+назначение renew, между контекстами/устройствами. Unknown →GET прежней операции, без нового ID/автоPOST.

## 7. Результат Auth-операции, completion и Q01

GET /api/auth/contexts/:authContextId/operations/:authOperationId: query ровно requestSchemaVersion=v1 и commandType (C01/C02/C03/AUTH_TOTP_VERIFY/AUTH_TOTP_CHALLENGE_RENEW), без тела; требует proof того же контекста, не email/код. Не выдаёт cookie, не выполняет действие, не продлевает контекст.

Оболочка содержит ровно operationRef, status, result, resolvedAt, observedAt, nextAction, nextActionParams. OperationRef ровно authContextId, authOperationId, commandType. HTTP200/status=resolved с закрытым result; HTTP202/status=unresolved с result=null и resolvedAt=null. ResolvedAt — неизменяемое время окончательной фиксации, не время внешнего эффекта; observedAt — текущее чтение. При недоступности/повреждении503, не202. Отсутствие результата в разрешённом поиске не доказывает откат. В GET nextAction=null/params={} всегда.

Закрытые result: email_dispatch_accepted (§5); auth_step_required (§§5–6); login_completed ровно kind и completion; verification_rejected ровно kind и reasonCode=AUTH_VERIFICATION_FAILED; totp_challenge_renewed (§6). Новые ветки TOTP-management/staff сюда автоматически не добавлены.

Прямой полный вход HTTP200: корень ровно completion, observedAt, nextAction=null, nextActionParams={}. Completion ровно authContextId, authOperationId, loginId, realm=user, completedAt. ID операции принадлежит фактически завершившей вход C02 или AUTH_TOTP_VERIFY. Replay сохраняет completion; не оживляет login.

Q01 сохраняет принятый JSON authenticated/user/navigation, а успешный ответ добавляет заголовок **X-Shadow-Login-Id с проверенным login**, не слепой echo. Клиент открывает персональный доступ только после200/authenticated=true/совпадения ожидаемого login и актуального запроса. Первый успешный Q01 надёжно фиксирует использование cookie в Auth и закрывает её recovery-window; этот технический эффект не является foreground-активностью, автоматически не продлевает idle. Контракт фиксации требует проверки реализации.

Результаты/Auth-история первого стенда автоматически не архивируются и не очищаются; окончание контекста закрывает его proof, не объявляет неизвестную операцию отменённой. Короткоживущие секреты не становятся бессрочной историей; их хранение/удаление отдельно §16.

## 8. Восстановление cookie полного user login

POST /api/auth/contexts/:authContextId/operations/:authOperationId/login-cookie: без query, body ровно requestSchemaVersion и commandType=C02 либо AUTH_TOTP_VERIFY. Требуются proof исходного Auth-контекста и POST-защиты, не полный login-cookie. LoginId в body не принимается.

Нужен подтверждённый login_completed, актуально допустимые user/login/context, воспроизводимый исходный cookie-секрет, открытое окно до min(completedAt+5 минут, context.expiresAt) и отсутствие успешного Q01. На границе окно закрыто. Первое успешное Q01 закрывает раньше, но не переписывает исторический deadline. Все способы повторной выдачи cookie, включая replay завершения, подчинены тому же окну.

HTTP200: тот же completion, текущее observedAt и null/{} navigation; выдаётся та же cookie с тем же секретом, без rotation/нового login. Подготовительный proof не заменяется секретом полного входа. Короткое защищённое recovery-хранение секрета и его уничтожение ещё требуют механизма.

409 AUTH_COOKIE_RECOVERY_NOT_APPLICABLE — известный результат не login_completed; 409 AUTH_COOKIE_RECOVERY_CLOSED — окно/Q01 закрыли восстановление. 401/403/404/429 по общим правилам;503 для unknown/непригодных данных. Ошибки не имеют Set-Cookie/completion;202 не используется. После потерянного POST сначала Q01: cookie могла дойти; автоматического нового POST нет. Если окно закрыто, имеющаяся cookie ещё может быть действительна; утраченная требует нового явного полного входа.

Бюджет5 секунд/одна попытка,3 допущенных запроса за скользящие60 секунд по environment+Auth-context+назначение восстановления. Повторы и последующие ошибки считаются после допуска; отклонённая ограничителем попытка окно не продлевает; недоступный счётчик503.

## 9. Logout: подготовка, C07, чтение и продолжение

POST /api/auth/logout-contexts: body только requestSchemaVersion, без query; X-Shadow-Login-Id и доказательство исходного login. Допустимо криптографически проверенное прежнее credential уже истёкшего/отозванного login только для выхода; это не полный доступ. Нет доказательства — не204; невозможность проверки503. Подготовка не отзывает login.

HTTP201: корень logoutContext, observedAt, nextAction=null, nextActionParams={}. LogoutContext ровно logoutContextId, loginId, realm=user, createdAt, expiresAt. Срок **15 минут** фиксирован; выдаётся отдельная cookie §3. Отзыв целевого login не уничтожает право ограниченного восстановления выхода; самостоятельный отзыв самого контекста возможен по безопасности.

C07 POST /api/auth/logout: body ровно requestSchemaVersion, commandType=C07, logoutContextId, authOperationId. Цель берётся из proof контекста. X-Shadow-Login-Id не нужен; если есть, должен совпадать с целью, иначе400. Не наследовать автоматически login B, используемый для подготовки продолжения выхода A. POST-защиты обязательны. Бюджет5 секунд/одна попытка; отдельный числовой лимит C07 не принят.

HTTP204 без тела только после доказанного отзыва/истечения/недействительности целевого login. Удаляется только его cookie; logout-context сохраняется до своего срока. Повтор исходной операции подтверждает тот же итог, другой payload409. Unknown не204. Другие login, user/staff realm, черновики и paper-сессии не изменяются.

GET /api/auth/logout-contexts/:logoutContextId/operations/:authOperationId: query только requestSchemaVersion, proof logout-контекста. Корень ровно operationRef, status, confirmedAt, observedAt, nextAction=null, nextActionParams={}. Ref ровно logoutContextId, authOperationId, loginId, commandType=C07. HTTP200/status=completed/confirmedAt задан;202/status=unresolved/confirmedAt=null только при доверенном чтении;503 если прочитать нельзя. GET не отзывает/не выдаёт cookie, отсутствие записи не подтверждает завершение.

Подготовка:5 секунд/одна попытка;3 допущенных запроса/60 секунд на environment+realm+целевой login. Чтение:5 секунд/одна попытка;30/60 секунд на целевой login между контекстами/вкладками. Разрешён опрос сразу, затем на2/5/10/20/30 секундах, максимум один in-flight, пропущенные моменты не догоняются. Hidden/final/access error останавливают;429 учитывается; после30 секунд — ручное действие.

POST /api/auth/logout-contexts/continue: body ровно requestSchemaVersion, sourceLogoutContextId, authorizationMode=original_login/current_user. Обязательный X-Shadow-Login-Id выбирает доказательство: original_login — исходное проверяемое credential даже после expiry/revoke; current_user — действующий полный login того же постоянного пользователя и среды плюс серверная связь исходного контекста с целью. Старый logout-proof не нужен, публичный ID/email недостаточен; между режимами нет fallback. HTTP201 прежняя оболочка, но logoutContext дополнительно содержит sourceLogoutContextId. Новая cookie/контекст15 минут, новый явный C07 с новым ID, старую операцию/результат не переносит и не переписывает. Успех нового выхода доказывает недействительность цели сейчас, не исход старого запроса. Login B как доказательство не отзывается. Бюджет5 секунд и общий с обычной подготовкой лимит3/60 на целевой login. Потеря ответа подготовки не разрешает угадывать ID/автоlogout.

## 10. Привязка продолжения и её разрешение после Q01

Намерение continuation — ровно один из объектов: kind=default; либо kind=setup_draft и draftId. Нет URL/redirect, user/role, settings, review. Один неизменяемый binding на Auth-context; отсутствие означает default, не удаление локального ввода.

POST /api/auth/contexts/:authContextId/continuation: без query; body ровно requestSchemaVersion, continuation; proof контекста и POST-защиты. Setup_draft: если X-Shadow-Login-Id есть, проверяется выбранный user; иначе нужен guest proof. Неудачный user не становится guest. Нет claim/edit/start. HTTP201 при создании/200 при точном повторе; корень continuationBinding, observedAt, nextAction=null, nextActionParams={}. Binding ровно authContextId, continuation, createdAt. Другой binding409 AUTH_CONTEXT_STATE_CONFLICT; authOperationId не нужен. Конкурентные идентичные запросы создают один binding, разные — один успех/один конфликт.

GET того же пути: query только requestSchemaVersion; доказанный контекст, текущая проверка доступа к ссылке draft. HTTP200 та же оболочка; binding=null только при достоверном отсутствии записи, не для denied/ошибки. Чтение не редактирует/не продлевает. Потерянный POST →GET; совпало — продолжить, другой — конфликт, доказанный null — явный повтор исходного POST,503 — unknown. В фоне бесконечно не опрашивать; допустим один восстановительный GET.

Нет PATCH/DELETE. Пользователь может отказаться от прежнего автоматического продолжения и после Q01 выбрать другой draft обычным действием с повторной проверкой доступа/claim. Старый binding не переписывается и не должен переигрывать явный новый выбор. До завершения входа возможен явный новый Auth-context, но pending операции в него не переносятся. Чтение/привязка не продлевают30 минут Auth-context и TTL draft.

GET /api/auth/contexts/:authContextId/continuation/resolution: query только requestSchemaVersion; X-Shadow-Login-Id обязателен, действующие cookie этого login и исходного Auth-context. Login должен совпадать с завершившим этот контекст; другой login того же user не подставляется. Для ветки гостевого draft требуется proof его доступа. HTTP200: корень ровно authContextId, loginId, observedAt, nextAction, nextActionParams. Не копирует binding/settings/review/user/snapshot.

Порядок решения: препятствующая session →view_session/view_summary с sessionId, draft сохраняется; иначе доступный свой draft →continue_setup/review_setup с draftId; гостевой →recover_setup с доступным draftId и явным подтверждением claim; default/отсутствие binding →обычный путь по текущему состоянию, в том числе select_trader с разрешёнными необязательными draftId/venueId. Если дошли до draft и он скрыт —404, не молчаливый каталог. Истёкший/used draft — прежние предметные правила. Непрочитанное/повреждённое не200/null. Незавершённый full Auth →409 AUTH_CONTEXT_STATE_CONFLICT. Остальные отказы по §2.

Решение читается согласованно, но не является разрешением будущей команды. Нет автоматических claim/C04/C05/C06. Клиент применяет ответ только к исходному запросу/login/context и неизменившемуся намерению. После expiry Auth-context путь закрыт, но действующий полный login может открыть доступный draft обычным путём без нового входа ради binding.

Бюджеты POST/оба GET —5 секунд/одна попытка. POST3/60; два GET вместе30/60 по environment+Auth-context, между вкладками. Transport quota учитывает допущенные повторы/последующие ошибки, rejected rate не продлевает окно; проверка ограничителя недоступна →503.

## 11. Claim: подтверждение, выполнение и восстановление

Явное действие «перенести настройки в этот аккаунт» связывает черновик с выбранным полным login после Q01. Вход/чтение продолжения не выполняют claim. Context подтверждает намерение, не резервирует владение и не заменяет текущую авторизацию. Локальные несохранённые правки не входят в claim.

POST /api/auth/claim-contexts: без query; body ровно requestSchemaVersion, draftId. X-Shadow-Login-Id, полный user и текущий guest proof, POST-защиты. Сервер определяет получателя и исходное владение; user/ownership/settings в body запрещены. HTTP201: корень claimContext, observedAt, nextAction=null, nextActionParams={}. ClaimContext ровно claimContextId, draftId, previousOwnershipId, actorUserId, loginId, createdAt, expiresAt. Срок **10 минут** фиксирован, отдельная cookie §3. Не зависит от оставшегося времени предварительного Auth-context; действительность full login проверяется отдельно.

GET /api/auth/claim-contexts/:claimContextId: query только requestSchemaVersion; cookie контекста и действующий исходный login. HTTP200 та же оболочка с текущим observedAt; GET не восстанавливает cookie/не продлевает и не является поиском результата claim. На now≥expiresAt закрыт. Потеря ответа подготовки до claim: GET при сохранённых ID/proof, иначе явная новая подготовка безопасна; после отправленного unknown claim этот путь не обход неизвестности.

**POST /api/demo/drafts/:draftId/claim сохраняется. Body только requestSchemaVersion.** Нет authOperationId/clientCommandId/expectedDraftVersion. Прежнее предложение добавить ID операции исправлено до принятия итогового блока: dedup определяется исходным claim receipt и уникальностью передачи draft, а не новой командной областью.

Первое исполнение требует X-Shadow-Login-Id, X-Shadow-Claim-Context-Id, соответствующие cookie, гостевой доступ и POST-защиты. Draft/исходное ownership/user/login сверяются с контекстом. После структуры/актуального полного user/разрешённого доступа/rate сначала ищется исходный claim. Подтверждённая передача этому user возвращает прежний результат без живого старого guest/context proof, даже под новым действительным login того же user. Для нового исполнения нужны действующие исходные подтверждения. Чужой результат скрыт. Unknown сначала выясняется; другой контекст/получатель не обходит его.

HTTP200 сохраняет оболочку claim,nextAction,nextActionParams и шесть полей claim: claimReceiptId,draftId,previousOwnershipId,claimedOwnershipId,actorUserId,completedAt. Исходные поля неизменны, navigation текущая. Передача/новое ownership/смена current pointer/закрытие прежнего доступа/claim receipt/обязательный audit сохраняют принятую атомарную границу и общий draft guard. После — Q03 с сохранением локальных правок, при необходимости C04 и новый user C05, отдельный C06. Исторический guest review запуск не разрешает.

GET /api/demo/drafts/:draftId/claim: query только requestSchemaVersion, без тела, полный выбранный user. HTTP200 — та же успешная claim-оболочка по доказанной цепочке получателя, без старого гостевого proof. HTTP202 при доказанной области поиска и пока неустановленном окончательном исходе: корень ровно status=unresolved, observedAt, nextAction=null, nextActionParams={}; claim отсутствует. Нет разрешённого основания/чужой результат404, недействующий текущий login401, техническая недоступность503, повреждение RECORD_UNAVAILABLE. Нет CommandReceipt/Q05.

**Принятое позднейшее расширение восстановления:** для ограниченного GET результата допускается истёкший/утраченный claim-cookie, если X-Shadow-Claim-Context-Id указывает исходный контекст, серверная запись надёжно связывает его с тем же постоянным user, средой и draft, а текущий полный login доказан (может быть новым). Это даёт только чтение исхода, не guest/settings/право исполнить. Ранее требовавшийся живой proof для такого202 заменён только этой явно принятой веткой. Публичного ID без доказанного user/серверной связи недостаточно. GET самого контекста после expiry остаётся закрыт.

Ни202, ни отсутствие receipt, ни expiry не доказывают rollback. Новый действующий контекст для нового исполнения возможен лишь после надёжного доказательства, что прежняя передача не завершилась и уже не может завершиться, с заново проверенными условиями. Как это доказать между Auth и БД — открытый стык, не обещание готового механизма. Смена аккаунта не перенаправляет отправленный claim. Пока исход неизвестен, нельзя предложить передачу другому получателю; поздний ответ не переключает UI на исходный аккаунт.

Подготовка5 секунд/одна попытка; POST claim5 секунд/до3 попыток только после доказанного serialization/deadlock rollback с прежними50–150мс паузами внутри бюджета; оба GET5 секунд/одна попытка. Раздельные лимиты3 подготовки/3 POST/30 суммарных GET за60 секунд по environment+постоянный user+draft, общие для устройств/контекстов. Внутренние rollback-попытки не новые HTTP-запросы. История/связь контекста не удаляется при expiry cookie; секрет в открытом виде для восстановления результата не нужен.

## 12. Подключение, отключение и сброс пользовательского TOTP

Здесь принят поведенческий пакет, **не полный закрытый DTO/набор маршрутов**. Отдельные Auth-result виды, transport поля, безопасная выдача/повтор секрета и свежий email для конкретного назначения ещё требуют формы по §16; C01–C03 с закрытыми телами не расширяются молча.

### Подключение

Добровольное в настройках: действующий full login и **свежее подтверждение email для этой операции**. После административного сброса: подтверждённый email и доверенное серверное требование enrollment, без полного доступа до нового TOTP. Клиент режим восстановления/получателя не назначает; enrollment не заменяет существующий действующий фактор.

Отдельный защищённый контекст на10 минут, не дольше исходного подтверждающего контекста; связан с user, основанием, исходным login либо ограниченным Auth-context и одной подготовленной версией фактора. До проверки кода фактор не активен. Принятый профиль TOTP сохраняется. QR/секрет выдаются только защищённым путём, не в логи/обычный исторический result. Повтор подготовки той же операции не создаёт новый секрет; неизвестность сначала восстанавливается.

Отдельный счётчик enrollment по user между контекстами/устройствами: пять неверных кодов →15 минут; новый секрет/контекст не сбрасывает. Ошибка структуры/technical failure не неверный код. Истёкший подготовленный секрет активировать нельзя; новую подготовку при unknown подтверждения не начинать до выяснения. Два подтверждения не создают два активных фактора/login; сброс/отзыв/смена версии делают прежний контекст непригодным.

При добровольном подключении **существующие входы сохраняются** с прежними сроками, не продлеваются; последующие новые входы требуют TOTP. После admin reset старые входы отозваны, полный новый login только после подтверждённого enrollment и затем Q01. Успех выдаётся после доказанной активации и обязательности фактора, не по одному успешному HTTP внешнего вызова.

### Добровольное отключение

Свежий email и действующий TOTP привязаны к цели отключения, не заимствуются из входа/enrollment. Контекст10 минут без продления связан с user, выбранным login, версией фактора и назначением. До начала явное предупреждение о закрытии всех входов; этапы: начало →email →TOTP →исполнение подтверждённого отключения. Сервер задаёт получателя/фактор. TOTP проверяется после email.

Отдельный счётчик отключения5/15 по user, общий для контекстов/устройств. Прежние email-числа сохраняются, отправки этой цели включаются в общие адресные ограничения. Успех означает отключение фактора и отзыв всех прежних входов; следующий новый вход по email, обязательного enrollment нет. Paper-сессия/бюджет/история не меняются.

### Административный сброс и общее исполнение

Обращение не разрешение сброса. Нужны полный staff login, явное право, одобренное решение с обращением/user/версией фактора и свежее служебное подтверждение этой версии. Изменение цели/фактора/решения требует нового подтверждения. **Проверка принадлежности аккаунта, состав согласующих и конкретное право ещё не выбраны**; Owner по имени не заменяет их. Владелец 1/владелец 2 равноправны.

С начала исполнения admin reset прежние входы закрываются. Перед изменением фактора обе процедуры устанавливают серверное ограничение, исключающее полный доступ по прежним подтверждениям; новый конкурентный login проверяет актуальное состояние перед выдачей. После reset email разрешает только восстановление до нового TOTP. Частичный внешний Auth/DB итог сохраняет ограничение до сверки, не объявляется одной внешней транзакцией.

У каждой операции один ID/защищённый контекст; бюджет исполнения10 секунд, без автоматического повторного внешнего изменения с unknown. Повтор возвращает исходный результат, не потребляет OTP заново, не отзывает новые законные login после завершения. Потерянный ответ →чтение исходной операции. После отзыва login её proof может давать только чтение собственного результата, не кабинет; один ID недостаточен. Expiry не отменяет начатое изменение. Полный протокол чтения/истечения ещё требует DTO/механизма.

Аудит: инициатор, назначение, исходная версия фактора, подтверждённые этапы/результат; для reset обращение/решение. Секреты не журналируются. Новые имена прикладных audit-kind не назначены этим текстом. Уведомление отделено от изменения защиты: сбой письма не повторяет reset/disable; принятие отправки не доставка, её статус отдельно. Paper-сессия/бюджет/история сохраняются.

## 13. Служебный вход, права и восстановление владельцев

Сохраняются [auth-policy §§12–18](auth-policy.md): два разных равноправных Owner; passkeys с обязательной user verification разрешены для синтетического полигона; это не изменение будущих денежных правил. Staff Auth отделён от user; email совпадение не создаёт identity/роль. 8 часов absolute/30 минут idle, один текущий login на человека; фон/refresh/действия коллеги срок не продлевают. Обычный Q06 не требует второго Owner; два подтверждения только для предусмотренных действий.

Принят отдельный защищённый staff-context на **10 минут** без продления. Каждый WebAuthn challenge — **5 минут**, не дольше контекста, связан с environment/context/purpose и проверяемыми origin/RP ID. Подтверждение входа не применяется к registration/recovery/чужому approval. Full login только после проверки credential, user verification, identity/principal и текущего назначения; отмена/неудача не отзывает прежний login.

Попытка завершения имеет неизменяемый ID; replay восстанавливает, не создаёт login. Новый login/отзыв прежнего/смена staff slot должны иметь согласованный итог. Конкурентные успехи оставляют один login по серверному порядку завершения. После cookie отдельное чтение подтверждает текущий staff login; исторический success может уже быть superseded. Late ответы не переключают выбор/не чистят новый cookie/не оживляют отозванный login. User Q01 и его точный cookie-recovery автоматически staff не обслуживают; формы ещё §16.

Каждая выдача проверяет текущие полные grants, не роль из cookie/старый audit. Нет сборки разрешения из неполных разных grants. Q06 сохраняет группы/обязательный audit и принятый DB-API-09. Новое право пользовательского MFA reset этим не выдаётся. Bootstrap двух владельцев доверенный, не публичная регистрация или произвольный staffId; личные email/секреты в пакет не включаются.

Один владелец потерял доступ: его личный offline recovery code, свежее подтверждение другого действующим passkey и доказательство нового ключа. Оба потеряли: два личных кода разных существующих владельцев, два новых ключа и два подтверждения одной версии общей операции. Один код/два кода одного человека/два новых ключа без исходных доказательств недостаточны.

Подтверждения привязаны к составу участников/новых ключей/версии. Изменение состава требует новых согласий. Принятый recovery code расходуется один раз, replay восстанавливает ту же процедуру. Частичный результат не даёт админку. Unknown не разрешает вторую замену. После подтверждённого восстановления старые credentials/login соответствующего участника или пары отозваны; новый обычный вход новым ключом и действующее назначение обязательны. Recovery не снимает блокировки и не возвращает отозванные права. Нет email-обхода/инфраструктурного доступа или повторного исполнения прежних команд.

Пять минут — срок отдельного криптографического подтверждения, не всей человеческой процедуры восстановления пары. Срок всей процедуры, число/формат/выдача/защита резервных кодов, точная проверка коллеги и staff DTO ещё не закрыты. Уведомления и журнал без секретов, paper-сессии/бюджеты/история неизменны.
