## 1. Граница набора и правила счёта

Обозначения вида count/phase/refs в карточках — сокращённая запись ожидаемого состояния; точные имена колонок и разрешённые значения задаёт физическая карта, а API-поля — принятый реестр.

AS01–AS28 — карточки этого документа, не новые A-критерии, таблицы или коды API. В каждой заданы исходный факт, действие/порядок, ожидаемый срез строк и запрет. Это спецификации будущих наборов; неподтверждённая внешняя предпосылка обозначается явно. Наличие синтетического login/подписи в описании не доказывает реальный Auth, криптографию или готовность маршрута.

Используются прежние уровни: **срез** — выбранные связанные записи внутри будущей полной BASE; **SEM** — заданный внешний факт для проверки решения, не наблюдение provider; **NEG** — будущая попытка нарушить одно ограничение при включённой защите; **BAD** — уже повреждённая изолированная копия; **READ-FAULT** — ошибка чтения без заявления о физической порче. Не создавать BAD рабочим endpoint, не выключать рабочие constraints, не считать отклонённую NEG допустимой BASE. Все виды сейчас только описаны.

Каждая AS — независимая дочерняя копия своего исходного состояния. Исключение — явно названные последовательности/replay внутри карточки; они сохраняют исходные IDs и историю. Удаление старых результатов/steps/attempts ради повторного использования ключа запрещено. Настоящие email/OTP/cookie/seed/ключи/provider evidence не помещаются в документ. В будущем реальные параметры только отдельной изолированной среды по отдельному поручению; этот документ не разрешает сетевые вызовы, создание аккаунтов или запуск worker.

**Числа в AS относятся к указанному срезу**, например «AC05=1 для O1» или «+1 window нового L2». Это не total таблицы во всей БД. Не названные ancestors/служебные записи не считаются нулём. Формула общего manifest: сохранённый исходный count каждой таблицы + все перечисленные предметные и служебные дельты. Неизвестное значение отмечается «зависимость», а не 0. Полный manifest должен содержать все 73 таблицы и закрытую карту IDs/ссылок до будущей загрузки; карточки с незакрытым обязательным полем не объявляются готовыми fixtures.

| Сопровождение карточки | Что обязательно учитывать сверх выделенного среза |
| --- | --- |
| Исходные родители | Свои user/staff/identity/login-policy/security, contexts/operations/results, каталог/ownership и обязательные children по матрице. Реальный список и counts фиксируются в manifest; чужой/фиктивный parent недопустим |
| Transport quota | Для каждого допущенного HTTP запроса — полный набор обязательных AC13/14. Replay HTTP может расходовать новый quota token; отсутствие новой AC04/AC05 не означает нулевую дельту всей БД. Внутренняя обработка того же admission не расходует quota второй раз |
| Auth audit | Требуемые AC32/33 по виду действия и полным grants, отдельно от Shadow audit. Отсутствующий в D02 точный variant не заменяется свободным JSON или автоматическим count 0 |
| Witness | Для защищённого изменения — подтверждённый внешний intent, AC34 и полный declared AC35 в одной локальной T с эффектом. Повтор чтения старого результата не новый эффект. Точный список roots/closure для Q01, erasure, admission и служебных исключений остаётся зависимым от U01/D02 |
| Внешние факты | Provider outcome, совпавшие TOTP steps, свежесть checkpoint, доказанный drain и ключевой статус — отдельно от собственных FK. В SEM они предпосылки, а не созданные свидетельства D03 |

Точная безопасная форма payload/enum/stage/purpose берётся из принятого контракта или будущей согласованной D02-дельты. Символическое «исход отказа» не вводит новое имя result.kind. Общие identity/realm/environment/immutable/NULL правила исходной карты действуют и для не повторённых здесь полей. Никакие rows не получают автоматический TTL/DELETE.

## 2. Общие символы, время и предметные опоры

| Символ | Документальный смысл |
| --- | --- |
| E-AS / E-OTHER | Разные синтетические среды, выбираемые доверенным descriptor, не клиентом. Они обозначают разные изолированные копии, а не переключение environment в рабочей БД |
| U1 / U2; I1 / I2 | Разные обычные пользователи и принадлежащие им user identities. Не реальные аккаунты, не совпадающие staff principals |
| владелец 1 / владелец 2; S1 / S2 | Два разных равноправных staff principals с личными identities/credentials/assignments. Номера не задают старшинство |
| G1 / C1 / O1 / R1 / CH1 | Guest context / контекст своей процедуры / Auth operation / её immutable result / свой challenge. В каждой независимой AS эти символы имеют свой scope |
| L1 / L2; W1 / X1 | Два полных login одного указанного actor, окно и временный cipher исходной cookie L1. Привязки полного login/verifier ещё зависят от U01/D02 |
| D1 / OG1 / OU1 / CR1 | Draft, его первоначальный guest ownership, последующий user ownership и единственный Shadow claim receipt. Не AC05 и не новый клиентский claim key |
| F1 / V1 / CASE1 / AP1 / AP2 | Версия TOTP factor; версия решения; security case; approvals разных staff. UUID/текст символа не доказательство допуска |
| T0 | `2026-11-02T10:00:00.000Z`; фиксированный документальный UTC, не фактическое время выполнения |

Собственные IDs будущего набора — серверные UUIDv4 с неизменной картой символов; здесь не приведены literal UUID, bearer или вычисленные криптографические теги. Placeholder digest/key/ref не является валидным proof. Точные bytes/формат/decoder обязательны до загрузки; отсутствующий D02-профиль не заполняется произвольно.

Для AS08–AS11 контекст C1 создан в 09:50, expires_at=10:20; полный user login завершён в T0, поэтому recovery deadline=min(10:05,10:20)=10:05. User absolute expiry=`2026-12-02T10:00:00.000Z`, last_user_activity_at=T0; без новой разрешённой активности idle-предел=`2026-11-09T10:00:00.000Z`. Для staff, завершившего вход в T0, absolute expiry18:00, idle-предел 10:30. Это разные часы; Q01 не сдвигает idle. На любой границе now≥expiry уже истечение. Сроки конкретной AS приоритетнее этой общей опоры.

Две площадки — Polymarket и Limitless. Финансовый bridge AS02/AS14 использует прежние S01–S04: B=200/1, fixed F=20/1 либо percent q=300, p=1000,d=1500. Auth/claim не создают paper_session/funding/journal и не превращают баланс в ноль: если финансы отсутствуют, строк нет; если существовали, суммы/версии неизменны. Новый C06 не выполняется этим набором. Четыре сочетания площадка×fixed/percent — независимые копии, не четыре запуска на одном пользователе.

## 3. Guest, намерение, TOTP и quota

### AS01. Guest существует до draft

**Дано:** в срезе G1 — AC03(kind=guest, realm=guest, created_at=T0, expires_at=`2026-11-09T10:00:00.000Z`) и ровно один AC06 своего purpose. User/staff/login/identity/draft/case refs в G1 — NULL; digest присутствует, erased_at=NULL. Для G1 ещё нет setup_drafts/ownership/CMD.

**Ожидание:** чтение гостевого контекста не создаёт draft, login или command receipt. Разрешённый refresh в 10:01 сохраняет тот же G1/proof; применяется только принятый refresh-профиль. Повтор уже завершённого refresh не продлевает срок снова. При подтверждённом refresh в 10:01 и прежнем меньшем expiry новый expires_at=`2026-11-09T10:01:00.000Z`: max прежнего срока и confirmedRefreshAt+7d по API §7. Refresh не продлевает draft/review и не равен GET.

**NEG:** добавить user_id в guest либо заменить digest другим proof при replay — нарушение варианта/истории; чтение чужого G1 не раскрывает его. **Связь:** AC03/06, B05; MAP01/08; DA01/08 в части proof/history; R002/007/069/070, A02/A23/A25/A35. Полный guest API payload/quota/audit требует D02; это срез, не полностью созданный bootstrap.

### AS02. C04 действительно меняет ввод, no-op и replay — нет

**Дано:** независимая исходная копия AS01 без выполнения refresh, затем в 11:00 C04 created создаёт D1(version 1, last_input_receipt_id=K1-result, expiry=`2026-11-09T11:00:00.000Z`), OG1 и прежний полный C04 key/receipt/details. Guest expiry атомарно становится max(10:00 9 ноября,11:00 9 ноября)=11:00 9 ноября. Для выбранного D1 counts draft 1/guest ownership 1/C04 key 1/receipt 1/details 1, полных login/claim/session/funding 0.

**Ветки:** в 11:01 настоящий updated по expectedVersion 1 даёт version 2, новый input receipt и draft/guest expiry=`2026-11-09T11:01:00.000Z`. В 11:02 exact replay этой операции сохраняет counts/времена предметного комплекта. Новый key с expectedVersion 2 и тем же вводом даёт собственные key/receipt/details(+1 каждого), unchanged/version 2 без продления. ExpectedVersion1 с тем же вводом — устаревшая версия, не unchanged; исход фиксируется по принятому C04 без изменения D1/G1. Короткий нечисловой raw при настоящем C04 updated продлевает по тому же правилу, не даёт права start.

**NEG:** сохранить новую expiry G1 без полного C04 комплекта либо продлить replay/no-op. Все предметные записи реальной правки откатываются вместе при доказанном rollback; transport quota отдельно. **Связь:** AC03, B05; MAP01/07/08; R017/018, A54–A57/A100/A103; прежние C04-E. Повторить документально для S01–S04, суммы не пересчитывать.

### AS03. Точный повтор окончательного результата

**Дано:** O1(namespace=context, context=C1, action своей проверки, client_operation_id=K1, phase=resolved, result_id=R1), ровно один AC05(R1, operation=O1, kind=verification_rejected, reasonCode=AUTH_VERIFICATION_FAILED) и предусмотренный AC08 сравнения секретного намерения. **Ожидание:** равное намерение даёт прежний R1 и его времена; в срезе O1/R1 counts остаются 1/1, steps/login не добавляются и failure counter не увеличивается повторно. Успешный GET сохранённого verification_rejected имеет HTTP200; исходный прямой отказ401 остаётся отказом, не новым успехом проверки. Текущий requestId/nextAction/доступ проверяются заново. Иной secret либо иной raw input с тем же K1 не перезаписывает O1/R1. Отдельное правило сравнения C01: два raw email, дающие одинаковый canonical email, не автоматически одинаковое намерение; email не добавляется в payload выбранной verification-операции O1. Новый HTTP может расходовать quota — это не новая operation.

**BAD/READ-FAULT:** missing AC05 при resolved или недоступный comparison key — техническая недоступность, не unresolved/успех/новый key. **Связь:** AC04/05/08/12, B01/B02; MAP01/07/08, DA01/04/10; R007/008/045/070, A21/A29/A100/A107. ### AS05. Все совпавшие TOTP steps, разные устройства

**Дано:** F1 своего U1 с принятым профилем 30s/Unix epoch; проверка в T0, current step=59787120, допустимы 59787119–59787121. ### AS07. Скользящая quota отдельно от результата

### AS24. Auth audit и прежний Q06 audit не смешиваются

**Дано:** текущее полномочие владельца 1 подтверждать reset case/V1 и matching approval operation. Для выбранного действия подтверждения reset (точное имя audit-kind — D02) ожидается один AC32 с case/version/staff/login и достаточный AC33 полного соответствующего grant. В минимальном срезе одного такого действия — event 1/evidence 1; остальные события процедуры отдельно, это не общий total всего reset. Complete reset должен иметь evidence обоих независимых подтверждений и исполнения по D02, а не автоматически этот один child.

**NEG:** parent требует evidence, но его 0; доказательство от владельца 2 при actor S1; grant составлен из частей разных assignments; system_actor_ref вместе с человеческим actor. Всё отклоняется как неполный/чужой вариант. Auth event не заменяет существующий Shadow audit.

**Отдельная связь с пользовательской сессией:** при наличии прежней BASE-START разрешённый Q06 с четырьмя группами добавляет 1 shadow.audit_events и 4 shadow.audit_authorizations. Два независимых разрешённых чтения владельцем 1 и владельцем 2 —2 и 8; финансовые строки/суммы прежние. Если audit не сохранился, защищённая выдача не разрешена. Это условный expected, не выполненный запрос. **Связь:** AC32/33 +Shadow audit, B13; MAP01/07, DA11/12; R046–048/054/055/069, A24/A37/A100/A103/A104. Точный Auth audit whitelist остаётся D02.

## 7. Witness, стирание, уведомления и повреждения

### AS25. Local commit есть, witness ack потерян

**Дано:** AC34(WB1,state=intent_registered,epoch 7,intent_sequence=41) после подтверждённого внешнего intent. Для выбранного эффекта закрытый manifest заранее перечисляет все необходимые typed AC35 targets; их количество=N. **N не подставлено произвольно:** точный closure/root-состав некоторых Auth эффектов зависит от U01/D02. Ни один неизвестный target не скрывается за count 1.

**Ожидание локального commit:** бизнес-факт/исходный result, ровно N объявленных AC35 и AC34.local_committed_at/state сохраняются вместе. После потери внешнего confirmed ack результат остаётся исходным; разрешённое чтение свежего primary с текущим доступом восстанавливает его. Нового receipt/login/claim/funding из-за missing ack нет. После доказанного ack меняется только разрешённая отметка AC34, не исходный outcome. Intent_sequence41 не новый command key.

**NEG/BAD:** N−1 или лишний не объявленный target, другой actor/environment, пустой parent после эффекта; old backup без WB1 не доказательство rollback. Прогон не готов, пока N/перечень не закрыт. **Связь:** AC34/35 +конкретный effect, B13; MAP01/06/07, DA09/11; R045/062/066/070, A29/A34/A100/A103/A106/A107/A111.

### AS26. Законное стирание не уничтожает историю; backup не возвращает доступ

**Дано:** после доказанного закрытия W1 имеется X1 с историческими owner/key/format/reveal refs и допустимый erasure. В принятой 73 после стирания nonce/ciphertext/tag все NULL, erased_at задан законным фактом; count AC07 остаётся 1. AC05 R1, AC16 W1 и login сохранены. Аналогично AC06/08/09/22/24 стирают только разрешённые соответствующими путями verifier поля, не результаты/refs.

**Ожидание:** уже действительный login может пройти предусмотренный current read, но erased secret не восстанавливается из нового случайного значения. Raw proof/OTP/seed/cookie не появляются в audit/result/witness. Для восстановленной старой копии, где cipher ещё присутствует и окно открыто, внешняя актуальность/отзывы неизвестны: допуск закрыт до независимой сверки, copy не считается новым разрешением.

**BAD:** частично пустой cipher без marker, пропавший source result либо стирание единственного proof до закрытия нужного исполнительного пути — повреждение/нарушение, не разрешённое отсутствие. **U01-граница:** D01-U предлагает иной режим сохранения nonce; он не переносится в этот пример принятой 73. Продолжение: [карта истории/стирания](database-auth-history-erasure.md) подготовлена 03.11.2026; реальное удаление backup/WAL и политика ключей остаются эксплуатационными зависимостями. **Связь:** AC05–09/16/22–24/32/35, B03/B04/B10/B13; MAP08, DA02/03/08/09/12; R007/059/066/067/070, A25/A29/A34/A107/A111.

### AS27. Уведомление неизвестно, reset уже завершён

**Дано:** исходный security result R-sec цел, для выбранных purpose/получателя есть один AC36(J1), один AC37(ATT1,attempt_number=1,seal/performer, outcome=uncertain), current_attempt=ATT1. Факт reset/factor change не uncertain из-за одного письма; неизвестна только отправка.

**Ожидание:** не создаётся ATT2 либо новый J2 с тем же source/purpose/recipient ради слепой повторной отправки; count jobs 1/attempts 1 в этом срезе. Исходный R-sec/factor/login revocations не повторяются и не переписываются. Лишь доказанный not_sent либо отдельно принятая безопасная политика может разрешить следующий attempt; число retries H04 не переносится. Доказанное принятие отправки сохраняет свой однократный outcome, не доказательство прочтения письма.

**NEG:** current_attempt другой job, второй recipient-вариант одновременно, таймаут как not_sent_proven без основания, worker пишет финансовые таблицы. **Связь:** AC36/37 +AC05, B14; MAP01/05/07, DA11; R007/045/062/068/070, A25/A29/A100/A103/A107. Реальных писем/worker/интеграции нет.

### AS28. Один дефект — один отдельный дочерний срез

Эта карточка задаёт семейство независимых NEG/BAD/READ-FAULT, а не одну составную порчу. Положительная опора — соответствующая AS с закрытыми обязательными зависимостями; её нет — вариант остаётся заблокированным для будущего исполнения, а не строится на заведомо неполном seed.

| Отклонение | Исходная опора / ожидаемый запрет |
| --- | --- |
| Cross-environment/realm/actor/purpose | Один FK AC03/05/09/16/19/20/28/33 заменён чужим при сохранённых остальных полях; scoped связь/полнота отвергает, нет утечки чужого объекта |
| Незаконный NULL/лишний вариант | Guest получает user_id; cipher имеет только tag; AC35 имеет две targets; event human+system. Ни nullable FK, ни JSON не обходят XOR/mandatory поля |
| Parent без child | Resolved O1 без R1; login без window; manifest с 1 handle; set с 9 codes; audit без evidence; batch без полного N. Весь локальный кандидат должен отклониться, не только ошибочная строка |
| Duplicate/подмена истории | Второй result O1; повтор step F1/k; второй claim receipt D1; UPDATE старого payload/target/approval valid_until. Старый исход сохраняется |
| Законная пустота против corruption | Consent без AC19 до POST; default binding с NULL draft; пустой PM-B membership; законно erased X1 допустимы по варианту. Missing обязательного parent/current/result или недоступный reader — технический отказ, не этот вариант |
| Несовместимый decoder | Неизвестный формат одного Auth result, иной согласованный subtype не поддержан читателем; нет автоматического v1/default и повторного эффекта. Новая версия формата в продукт не вводится |

**Разделение доказательств:** NEG должен дойти до целевого ограничения, не упасть раньше из-за permissions/недостающего постороннего FK. BAD проверяет уже нарушенное хранение только в изолированной копии. READ-FAULT подтверждает обработку чтения, не работу DB constraints. Ни один из этих опытов не выполнен. **Связь:** все AC01–AC37 через свою AS/матрицу; MAP01/07/08, DA01–DA12 по выбранному дефекту; R001/002/007/008/009/068/069/070, A19/A23/A40/A100/A103/A110.
