## 1. Что уже принято и где настоящий пробел

Источники: [передача БД §10](backend-database-change-list.md), [формы API §16](backend-api-forms-addendum.md), [Auth и доступ §5–6](backend-auth-access.md), [физическая спецификация §4/§6](database-physical-operations-access.md), [закрытый реестр H03 §8](backend-code-registry.md), [продуктовый контракт прав](../../design/admin/staff-access-2026-10-18/contract.md).

Маршрут — GET /api/admin/users/:userId/sessions/current. Полный отдельный staff-вход, актуальные права и обязательный аудит до выдачи уже требуются. При достоверном отсутствии current session внешний ответ — HTTP 200, session=null, restrictedGroups=[], текущие nextAction/nextActionParams. При отсутствии безопасной цели навигация null/{}. Это отсутствие текущей сессии, не всей истории. Нет создания slot/session/snapshot/funding и нет выбора старой session вместо current.

Отсутствующий или скрытый target user даёт одинаковый404 без признака существования. Ошибка чтения/повреждённый pointer не превращаются в отсутствие; сбой аудита закрывает ответ. Пустой restrictedGroups не доказывает наличие всех прав. Эти правила не предлагаются повторно.

Пробел состоит из трёх связанных частей:

1. Какое конкретное право допускает раскрытие отсутствия у target user, когда venue сессии нет.
2. Как хранить этот факт и разрешающее evidence без обязательных ссылок на несуществующие session/snapshot. Нынешний admin_session.read_authorized требует обе реальные ссылки.
3. Как согласовать чтение/аудит с C06, отзывом и заменой login. Само чтение отсутствующего slot не означает его блокировки.

Здесь на согласование вынесена только часть 1. Части 2–3 не получают молчаливого решения. C04/last_input_receipt_id, карта ошибок, строгий C06 и история ADR-0064 сохраняются.

## 2. Блок 1: рекомендуемое отдельное право

**Предложение:** завести один явно различимый тип данных для факта отсутствия текущей paper-сессии у указанного пользователя. Кандидат имени — user.current_session_absence. Это новый внутренний код права, не новая группа session, не API-поле, не роль и не audit event_kind.

| Часть одной разрешающей строки | Предлагаемое значение / проверка |
| --- | --- |
| environment | Точная текущая среда запроса и target user |
| action_code | read |
| section_code | ADM-03 — сессии |
| data_type_code | user.current_session_absence — кандидат нового кода |
| product_mode | paper |
| venue_scope / venue_id | Только all / NULL; отсутствие устанавливается для общего межплощадочного current slot |
| assignment / principal | Действующее назначение текущего staff principal, полный актуальный grant set |
| Время и guards | Действующий полный login/identity/staff slot, срок назначения, актуальные authorization/assignment версии, повторная проверка после ожидания |

Нужна одна целая достаточная строка. Два назначения one (Polymarket и Limitless), даже вместе охватывающие обе сегодняшние площадки, не заменяют all. Нельзя соединить action/section/data type одного grant с областью другого. Кандидат нового сочетания one не публикуется как допустимый вариант этого права; наличие любых прежних venue-ограниченных grants не открывает отсутствие.

Это право относится к точному target userId маршрута в своей среде. Оно разрешает ограниченное раскрытие: пользователь доступен этой проверке, а текущей paper-сессии у него достоверно нет. При отсутствии дополнительных принятых ограничителей target это право действует на любого target user в своей среде — не следует скрыто обещать индивидуальный список разрешённых пользователей, которого в текущем grant нет. Возможность узнавать этот минимальный факт — осознанная граница предлагаемого права.

Право не даёт поиск/перечень пользователей, профиль, email, адреса, VIP, баланс, историю сессий, экспорт или запуск. Оно не выдаёт userContext: при session=null этого объекта нет. Предлагается не требовать дополнительно user.minimal_context: это прежняя группа существующей session с иным содержанием. Если current session существует, действует прежняя проверка session.summary и остальных групп её конкретной venue; новое право отсутствие не подменяет её и само не позволяет выдать или подтвердить наличие скрытой session.

Право только на session.summary (даже all), только user.minimal_context, действующий staff login или название роли owner не предполагают нового права автоматически. После согласования доверенная версия полной роли owner должна материализовать одинаковое право для владельца 1 и владельца 2; фактических назначений/аккаунтов здесь нет. Опубликованные immutable grants не дописываются: потребуются новый полный набор и атомарная смена current set/guards по прежнему протоколу. Это не новая роль и не ограничение равноправия владельцев.

Если несколько целых grants достаточны, предлагается сохранить уже принятый детерминированный выбор: assignmentId, затем grantId по возрастанию. Источник должен попасть в обязательное evidence новой ветки; способ хранения/точная условная полнота ещё часть 2. Одно решение о праве не разрешает выдавать200 без согласованного и сохранённого аудита.

## 3. Альтернатива и причина рекомендации

| Вариант | Последствие |
| --- | --- |
| Рекомендуемый: отдельный user.current_session_absence с read/ADM-03/paper/all | Позволяет отдельно назначать и доказывать право на минимальный факт; не переопределяет существующие группы. Требует одного явного расширения закрытого реестра и доверенной конфигурации owner |
| Использовать прежний session.summary с all для отсутствия | Меньше новых кодов, но действующее право на сведения о существующей session получает новый смысл раскрытия target user без session/venue. Это тоже изменение контракта доступа, а не бесплатное следствие старого grant |

Не рекомендуется выводить all из объединения venue-ограниченных строк или считать [] разрешением. Выбор самостоятельного права делает новую границу явной и оставляет прежний просмотр session без изменений. Вопрос на согласование: **принять ли блок 1 целиком — отдельное право user.current_session_absence, read/ADM-03/paper, только venue_scope=all, без автоматического наследования из старых grants?**

Это документальные условия будущих проверок, все **«не выполнялось»**. NA — локальные номера этого предложения, не новые A/R/API-коды. Выдача200 во всех строках дополнительно требует ещё не выбранных физического аудита и протокола согласованности.

| Вариант | Ожидаемая граница |
| --- | --- |
| NA01 · Полный staff, целое новое право all, свой environment, target существует, current достоверно отсутствует | Допуск к новой ветке;200/null/[] только после обязательного audit/evidence, никакой финансовой дельты |
| NA02 · Есть только прежние summary/settings/financial/user.minimal grants | Новое право не выведено из старых; отсутствие не раскрывается |
| NA03 · Только одна площадка либо две отдельные one-строки | Межплощадочное отсутствие не раскрывается; нельзя выбрать произвольную venue для обхода |
| NA04 · Пользователь отсутствует либо скрыт от этого staff | Одинаковый404 RESOURCE_NOT_FOUND, без session=null/существования/имени; диагностические детали не раскрывают цель |
| NA05 · Неактуальное назначение, другая среда, истёкший/заменённый login | Нет успешной выдачи по старому grant; ответ Auth/скрытия определяется принятыми контекстами, не новым кодом этого проекта |
| NA06 · Новое право есть, current session существует, прежних summary-прав на её venue нет | Не200/null, не раскрытие session; скрытый объект — общий404. Новое право не открывает существующую карточку |
| NA07 · Current session существует и прежний достаточный scope есть | Прежний Q06 с обязательной summary, разрешёнными группами и строгими session/snapshot audit-ссылками; новый grant отсутствия не обязателен |
| NA08 · Владелец 1 и владелец 2 с равными актуальными назначениями | Одинаковая граница допуска, разные principals/login/requestId и независимые записи аудита; роль по имени не bypass |
| NA09 · Повреждённый указатель или чтение не завершилось | Не факт отсутствия; после надлежащего допуска технический ответ по принятым правилам, без исправления данных |
| NA10 · Audit/evidence не сохранены либо commit неизвестен | Нет успешного ответа с данными; неизвестный commit не означает доказанный rollback/нулевую дельту. Повтор HTTP — новая проверка, не ordinary CommandReceipt |

NA02/NA03 при доказанном полном staff-входе скрывают target одинаковым404, как NA04; не вводят отдельный ответ, позволяющий отличить существующего пользователя. При технической неопределённости прав/данных нельзя объявлять установленный отказ или отсутствие. Приоритет независимых ранних Auth/защит остаётся H01. Проверки существующей session и новой ветки должны исключать утечки через связанные сведения; конкретные время/нагрузка/rate guards требуют будущей реализации, не считаются доказанными одинаковым HTTP.

## 7. Принятие блока 1 — право на отсутствие

02.11.2026 · Владелец принял §2 целиком, включая имя user.current_session_absence и комбинацию read/ADM-03/paper/all, запрет one/склейки, отсутствие наследования из старых grants и минимальный предел раскрытия target user. Новое право само не открывает существующую session, профиль, поиск, историю, деньги или экспорт. Дополнительный user.minimal_context для ветки отсутствия не требуется. Владелец 1 и владелец 2 получают одинаковую проекцию через доверенную конфигурацию полной роли owner, а не по названию роли; аккаунты/назначения не созданы.

Право и условие all отражены в [реестре v3 §12](backend-code-registry.md), [H03 §8](backend-auth-access.md), [физическом дополнении §13](database-physical-operations-access.md) и [ADR-0064 §47](../../decisions/0064_first_session_database_contract.md). Связи R055/R069/A23/A24 и NA01–NA10 сохраняются. Выбор достаточного целого grant — assignmentId, затем grantId; опубликованный набор не дописывается. Реестр v3 не добавляет audit-kind или новое authorized_data_code в audit_authorizations до принятия блока 2.

Статусы: право **согласовано и отражено в документах**, применение в реальной БД/доступе **не проверено испытаниями**. Ни metadata реестра, ни этот факт принятия не разрешают выдачу без обязательного аудита. DB-API-09 частично закрыт только по праву; §§6.2–6.4 остаются следующими задачами.

## 8. Блок 2 — предложение типизированного аудита отсутствия

**Статус: предлагается, ещё не принято.** Рекомендация — новый event_kind в существующем audit_events и доказательство в существующем audit_authorizations. Число прикладных таблиц остаётся 34, но состав полей и закрытые варианты потребуют явного расширения. Не использовать старый admin_session.read_authorized с обнулёнными обязательными ссылками.

### 8.1. Событие и три предлагаемые колонки

Кандидат event_kind — admin_session.current_absence_authorized, outcome_code=authorized, собственная первая event_schema_version=v1. Это факт разрешённой подготовки ответа об отсутствии, не доставки/просмотра и не пожизненного отсутствия сессии. Режим paper задан смыслом этого event_kind; live и future modes им не описываются.

| Колонка audit_events | Тип / условие предлагаемого нового варианта |
| --- | --- |
| target_user_id — новая | uuid, обязательно для нового kind; FK (environment,target_user_id) → users(environment,id). Цель не actor_staff_id и не user из произвольного JSON |
| slot_observation — новая | text, обязательно: absent либо present_free; not_applicable/occupied/unknown запрещены |
| observed_slot_generation — новая | bigint: NULL только при absent; положительное целое обязательно при present_free |
| id / environment | Существующий серверный UUID v4 / точная среда, прежний PK |
| actor_realm / actor_staff_id / actor_user_id | staff / обязательно / NULL, прежние FK/условия actor |
| actor_login_id / actor_authorization_version | Обязательны; login того же staff/realm/environment и исторический положительный guard |
| request_id / occurred_at | Обязательны; текущий server requestId и момент проверенного наблюдения. Не ключ команды, не timestamp доставки/commit |
| event_kind / event_schema_version / outcome_code | Новый kind / v1 / authorized, только это сочетание |
| session_id / snapshot_version | Оба строго NULL именно у нового kind; отсутствие не заменяется нулём или фиктивным snapshot |
| command_receipt_id / claim_receipt_id / draft_id | Все строго NULL; обычная команда/claim не создаются |
| safe_context | Ровно {}; цели/слот/разрешение не прячутся в нетипизированном JSON |

Absent означает доказанное отсутствие строки user_session_slots для target/environment/paper. Present_free означает существующую строку с current_session_id=NULL и записанным поколением. Это внутренние значения аудита, не изменение C05/C06 expectedSlot и не новые поля ответа200/null/[]. Поколение — историческое наблюдение, не FK на изменяемое текущее generation. Slot ищется по уникальному environment/user/paper; отдельный slot_id в новом audit не предлагается. Никакого создания slot ради записи аудита.

Все три новые колонки у прежних event_kind строго NULL. Их отсутствие у старой истории не требует выдумывать наблюдения задним числом. Семантические варианты старых событий/ссылок сохраняются:

| Вариант | Обязательная прежняя полнота |
| --- | --- |
| paper_session.started | User actor, успешный C06 receipt, draft/session/snapshot и весь строгий START; новый audit не удовлетворяет этой полноте |
| setup_draft.claimed | Прежний user/claim/draft комплект; никаких session/snapshot и новых target/observation полей |
| admin_session.read_authorized | Staff actor, реальные session_id/snapshot_version с прежним составным FK и достаточное evidence каждой выданной группы |
| Новый current_absence_authorized | Staff actor, реальный target user, полное наблюдение absent либо present_free, ровно одно достаточное evidence права отсутствия; session/snapshot и command refs NULL |

Предлагается дополнительно unique(environment,request_id) для объединения двух Q06 audit-kind. Так одна HTTP-передача не сохраняет одновременно «сессия показана» и «сессии нет». Прежние unique по kind/command/claim сохраняются. Новая HTTP-передача получает новый requestId и собственный audit; технический повтор не даёт права повторно сохранить то же событие. Политика обычного чтения без внутренних повторов не меняется.

### 8.2. Evidence и атомарная полнота

Предлагается разрешить для audit_authorizations нового kind ровно authorized_data_code=user.current_session_absence. Это отдельное расширение поля доказательства; принятие grant-кода в блоке 1 само его не включало. Старый read_authorized допускает только прежние четыре группы и не удовлетворяется этим новым code.

Ровно одна строка evidence выбранного достаточного grant: прежние audit_event_id/assignment_id/grant_id/assignment_version; FK на свою неизменяемую строку своего assignment/environment, назначение того же staff actor. Проверяются весь read/ADM-03/user.current_session_absence/paper/all, venue_id=NULL, current set/guard/срок и положительная историческая assignment_version. При нескольких достаточных grants — принятый выбор по assignmentId/grantId, без склейки.

Событие и evidence сохраняются целиком одной транзакцией вместе с доказанным согласованным чтением и текущим допуском. До commit требуется проверка от родителя: у нового события ровно одна правильная строка, а не только проверка существующих детей; event без evidence/лишний или чужой evidence не допускаются. Нельзя сослаться на evidence прежнего запроса. Неизменяемость истории/FK и запрет каскадного удаления старых оснований доступа сохраняются.

Предлагаемая дельта подтверждённой выдачи: +1 audit_events/+1 audit_authorizations, +0 command keys/receipts, slot/session/settings/финансы/start audit/outbox. Это не утверждение, что служебные механизмы Auth никогда ничего не обновляют. Сбой любой части закрывает весь ответ. При доказанном rollback новых audit/evidence нет; неизвестный commit не доказывает их отсутствие. После потери ответа новый запрос заново проверяет актуальные данные/права и сохраняет собственное событие: не восстанавливает прежний факт отсутствия как текущий и не использует Q05.

### 8.3. Ограничения, будущие проверки и открытая часть

NA01–NA16 — локальные ожидаемые случаи, не новые критерии A113+. Основные связи: R046/R047/R048/R055/R063/R069; A23/A24/A30/A52/A53/A100/A103/A104; E02/E07/E09/E10/E12. I20/CC18/AP16 не объявляются закрывшими новую ветку. Эталоны отрицательной записи, повреждённой копии и модели отказа чтения должны быть раздельны.

Блок 2 не доказывает отсутствие сессии одним FK/кодом audit: это требует следующего протокола чтения. Конкуренция с C06, защита отсутствующей строки, точка наблюдения/проверка после ожидания и гонки revoke/login replacement остаются **блоком 3**; конкретный lock/guard сейчас не выбирается. Сведения event должны происходить из той же согласованной операции, а не двух отдельных чтений.

После принятия потребуются отдельное издание реестра для нового kind/observation/authorized_data_code, дополнения физических ограничений/FK/уникальности/полноты и карты чтения/evidence. Версия v1 нового события не делает его понятным старому декодеру; неизвестные kind/вариант должны закрываться. Проверка поддержки исторических и новых событий, публикации набора прав и совместимого возврата остаётся зависимостью H02/H03/M05, не объявлена выполненной. Сейчас реестр v3 содержит только принятое право блока 1.

Альтернатива — отдельная таблица отсутствия и отдельные доказательства; она добавляет самостоятельный журнал и дублирует общие actor/login/request связи. Рекомендуется типизированный новый kind с тремя колонками и отдельными условиями в существующих audit-таблицах: каждый вариант остаётся строгим. **Вопрос блока 2: принять ли это хранение целиком — новый kind, target/наблюдение слота, один полный grant-evidence, взаимное исключение двух Q06-исходов и сохранение строгих старых связей?**

## 9. Принятие блока 2 — аудит отсутствия

02.11.2026 · Владелец явно принял §8 целиком: «Да, отдельный вид события в существующем журнале». Приняты event_kind=admin_session.current_absence_authorized/outcome=authorized/event_schema_version=v1; новые target_user_id/slot_observation/observed_slot_generation; conditional absent/present_free; ровно одно evidence user.current_session_absence; уникальность requestId между обоими Q06-видами; строгие старые ссылки и атомарная полнота. Это принятие заменяет статус предложения в §8, не переписывая его содержание.

Отражение: [реестр v4 §13](backend-code-registry.md), [физическая спецификация §14](database-physical-operations-access.md), [R §16](database-constraint-register.md), [ADR-0064 §48](../../decisions/0064_first_session_database_contract.md), дополнения API-карты/матрицы/примеров/сбоев/evidence. Число таблиц остаётся 34; появились три проектируемые колонки и строгий новый вариант, а не созданная БД/миграция.

Статусы блоков 1–2: **согласовано и отражено в документах; не проверено испытаниями**. NA01–NA16 не выполнялись. Обязательность audit не означает доказанной согласованности источника: блок 3 ещё должен выбрать защиту отсутствующего слота и обе очередности C06/revoke/login replacement, точку наблюдения и порядок guards. До этого DB-API-09 не объявляется закрытым. Никакого изменения C04/last_input_receipt_id/карты ошибок/строгого C06.
