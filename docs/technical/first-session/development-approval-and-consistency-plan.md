# Единый пакет решений перед разработкой и план сквозной сверки

04.11.2026 · **V00 перешёл к разрешённому исполнению.** [Прямые сообщения владельца](../../CURRENT_AUTHORIZATIONS.md) разрешают проверочный код/SQL, тестовые PostgreSQL/сети Oracle, развёртывание, D03-07 и согласованный внешний backup/restore. [Текущий профиль и доказательства](v00-oci/README.md). Условия AP-01–06 сохраняются; неизвестные доступы/получатели не назначаются автоматически. Ниже сохранена история пакета до этих разрешений.

03.11.2026 · **AP-01–06 приняты владельцем с Oracle вместо Mac. На 03.11 разрешались только сквозная проверка и отчёт; последующие разрешения V00 приведены выше.**

На этапе планирования 03.11 выбран отдельный сервер Oracle; его наличие и доступы тогда ещё не были подтверждены. Текущая фактическая конфигурация и отдельно незакрытые квоты/доступы описаны в пакете V00. Личный Mac не является обязательной частью стенда.

Основание: поручение сначала согласовать оставшиеся вопросы, затем проверить согласованность админки, БД, бэкенда, пользовательского интерфейса, скора и API обеих площадок. Документальный baseline: `b9bc3490ebb421cabdc94bb9b6374e85d95c68f2` / PR №219. Первоначальный пакет сохранён PR №220–221; принятие AP-01–06 зафиксировано последующим ответом владельца: «Да, остальные пункты согласуем» и поручением провести сквозную проверку «Пока без кода». Принятие рамок не означает прохождения испытаний или разрешения их запуска.

## 1. Порядок работы

1. Собрать и принять конкретные оставшиеся решения; не переоткрывать действующие ADR и D02/v6.
2. Выполнить документальную и визуальную сквозную сверку по матрице раздела 5. Каждому расхождению назначить источник правила, исполнителя и критерий закрытия.
3. Устранить противоречия первого среза. Изменение продукта, расходов или безопасности вернуть владельцу; обычные уточнения внутри принятого правила закрыть самостоятельно.
4. Предъявить конкретный профиль ограниченного V00 по D04: среда, разрешённые действия, строки испытаний, доступы, хранение результатов, бюджет. Только затем запускать разрешённое испытание.
5. По его доказательствам переходить к следующему срезу. Результат одного теста не разрешает автоматически V01–V07, публичный запуск или live.

Общее пожелание «всё утвердить» задаёт цель согласования, но не утверждает ещё не показанные варианты. Уже принятую автономность чатов сохраняем: никаких вопросов «продолжать?» внутри разрешённого этапа.

## 3. Принятый пакет ближайших решений

AP-01–06 приняты как рамки будущего V00, с размещением на Oracle и отказом от Mac. На дату подготовки пакета 03.11 фактические сервер, доступы, хранитель/проверяющий, внешнее хранилище и совместимость компонентов ещё не были назначены/проверены; текущие результаты и остаток — в пакете V00. Историческое поручение 03.11 ограничивалось документальной/визуальной сверкой; отдельное разрешение исполнения V00 от 04.11 зафиксировано в CURRENT_AUTHORIZATIONS.

| ID | Рекомендация | Последствие и граница |
| --- | --- | --- |
| AP-01 | Первый V00 — изолированный стенд на отдельном сервере Oracle, с закрытым доступом к служебным компонентам. Mac для стенда исключён явным решением владельца. Разрешаемый будущий объём: проверочный код, тестовые SQL/миграции, установка проверенных зависимостей и отдельная тестовая БД | Рабочие базы не затрагиваются. Это проверка основы, а не разработка всего сервиса; до развёртывания нужен конкретный серверный профиль, доступы и проверка доступной ёмкости |
| AP-02 | Только искусственные аккаунты и данные; почта во внутренний тестовый приёмник стенда. Внешняя сеть нужна для официальных компонентов и документации | Без реальных писем, облачных Auth/почтовых сервисов, рабочих торговых ключей, торговых запросов и реальных денег. Инфраструктурные доступы Oracle назначаются отдельно. Реальные read-only источники площадок позже по отдельному профилю |
| AP-03 | Дополнительные платные расходы первого V00 — 0. Ограничения ресурсов и объёма прогонов агент выбирает после проверки доступной ёмкости | Новый платёж требует одного конкретного решения с причиной; подбор бесплатных компонентов не выносится владельцу по одному |
| AP-04 | Сначала проверить self-hosted Supabase Auth + PostgreSQL на D03-04/05: неизвестный исход операции Auth и точный учёт TOTP. Затем независимые проверки утверждённого профиля V00 | При несовместимости предъявить конкретный контрпример и варианты. Не заменять провайдера и не ослаблять принятые гарантии молча. Версии из D03 — кандидаты до проверки источников |
| AP-05 | Результаты и тестовые ключи — раздельно, вне восстанавливаемой БД; в публичный Git только очищенный отчёт. Для внешнего evidence/backup/witness — отдельное защищённое хранилище вне сервера стенда; личный Mac не требуется | До зависимого прогона назначить реальные место, хранителя, проверяющего и получателей через закрытую процедуру. Папка на том же диске не доказывает защиту от потери сервера; роль Owner не даёт автоматически инфраструктурных прав |
| AP-06 | Перед открытием восстановленного стенда: оператор готовит доказательства, отдельный проверяющий сверяет, оба владельца подтверждают одну версию отчёта, назначенный хранитель выполняет открытие | Это принятая процедура инфраструктуры; реальные исполнители ещё не назначены. Неподтверждённые исходы сохраняют запрет зависимых действий. RPO/RTO сначала измеряются; обещания времени восстановления не выдумываются |

AP-05/AP-06 задают принятую модель ответственности, но не назначают доступы неизвестным людям или устройствам. Фактические назначения и доступность носителя остаются обязательными полями профиля среды. Независимые изолированные проверки не требуют заранее объявлять внешний backup успешным.

Рутинная подготовка агента: точный состав компонентов и проверка источников, ресурсные лимиты, синтетические ID и состояния, ожидаемые результаты, наборы отказов и конкурентных действий, формат manifest и очищенный отчёт. Эти технические детали не превращать в новую серию продуктовых согласований.

## 4. Полный видимый остаток более поздних этапов

Принятие AP-01–06 не закрывает перечисленные ниже пункты. Рекомендации по публичному скору/live и прочие варианты раздела 4 не утверждены этим ответом автоматически. Сейчас можно согласовать направление, но окончательный выбор требует указанных данных. Перечисленные зависимости не блокируют независимые изолированные проверки V00. Конкретные witness/evidence, ключи, права и резервирование должны быть готовы до соответствующих зависимых операций и приёмки первого стенда. Публичный доступ сам по себе не определяет эту границу; см. D03-12/13 и D04 §3.

| Когда понадобится | Что осталось выбрать или доказать | Рекомендация и ответственный |
| --- | --- | --- |
| Реальные пользователи | Почтовая доставка, условия провайдера, реальные адреса/доступы; сроки хранения по классам данных и порядок удаления | Бэкенд/БД готовят конкретный пакет перед открытой регистрацией; не считать тестовый SMTP настоящей доставкой |
| Защищённые операции/восстановление; позднее общий доступ | Назначенные инфраструктурные доступы, внешние evidence/backup/ключи нужны до зависимых испытаний. Конкретный публичный сервер/сеть — перед развёртыванием | БД/бэкенд готовят профиль и проверяют сроки восстановления; Oracle остаётся ранее выбранным серверным направлением. Не переносить зависимости V00 на момент публичного запуска |
| Аварийное восстановление владельцев | Потерян необходимый резервный код и нет рабочего входа: хранители, защищённый канал, независимая проверка личности | Админка/безопасность готовят регламент. До принятия рекомендуем сохранять блокировку, а не добавлять обход в БД |
| Расширенная админка | Приглашения, произвольные шаблоны прав, дополнительные операционные команды | Админка/бэкенд отделяют шире согласованный дизайн от точного первого реализуемого набора; новые полномочия требуют решения |
| Публичный скор | Формулы компонентов, нормализация, подходящие действия по площадкам, критерии полезности и стандарт сравнения | Чат скора предъявляет проверенное сравнение с базовым вариантом без ранжирования. Не утверждать численные параметры без доказательств |
| Устаревший скор | Поведение после потери актуальности источника | Предлагается показывать статус без числа, сохранить ручной поиск и существующие сессии. Это не разрешение исполнять сделки на устаревших рыночных данных; отдельные проверки исполнения сохраняются |
| Paper по реальным сигналам | Полнота действий лидера, задержки/пропуски, комиссии/округление, пригодность книги и профилей каждой площадки | API/скор проверяют отдельно; неизвестные расходы не равны нулю. Если открытых данных мало — владельцу выбор ограниченного охвата или партнёрского доступа |
| Реальные сделки | Кошелёк/подписант, точные scopes, отзыв, расходы, доступ проекта к каждой площадке, географические и договорные ограничения | Turnkey/Privy и другие варианты остаются отложенной идеей. Выбрать после актуального подтверждения возможностей. Никакого автоматического допуска live из успешного paper |

Исходные API-материалы — датированные срезы; свежая адресная проверка 03.11 и расхождения зафиксированы в [X13–X15](../../qa/cross-layer-2026-11-03/README.md). Исходные пакеты: [Polymarket](../../api/polymarket/README.md), [Limitless](../../api/limitless/README.md), [аудит допуска 19.10](../../137_profile_activation_audit_2026-10-19.md). ## 5. Матрица сквозной сверки

Сверка выполнена 03.11.2026 по main d04a796: [охват, согласованные связи и 15 открытых пунктов](../../qa/cross-layer-2026-11-03/README.md). Документы сопоставлены с адресно прочитанными живыми узлами Figma и актуальными официальными API-страницами. Полного Present-прохода и поведенческих испытаний не было. X01–X10 требуют синхронизации первого среза; X11–X15 относятся к будущему скору/API. Найденное не объявлено исправленным.

| Цепочка | Что должно совпасть | Ведущий / встречная проверка |
| --- | --- | --- |
| Вход → Auth → БД → пользователь/сотрудник | Сроки входов, MFA, несколько устройств, отзыв, восстановление, ошибки и доступный следующий шаг; UI не обещает неподдержанный маршрут | Бэкенд / БД + UX + админка |
| Каталог → площадка → трейдер → выбор | Venue/account IDs, происхождение и ревизия источника, доступность запуска; синтетика видима, чужая площадка не подставляется | API / БД + UX |
| Настройки → сохранение → проверка → запуск | Фиксированная сумма/% (3% по умолчанию), лимиты, расходы, часовой пояс, срок демо и версия подтверждённых условий. В первом срезе проверяем настройки/пустой запуск; исполнение сделок — поздний этап | Бэкенд / БД + UX |
| Повтор/таймаут → БД → UI/админка | Одна операция не создаёт второй результат; неизвестный исход явно отображён, проверяется, не превращается в успешный или нулевой | БД / бэкенд + оба интерфейса |
| Пользовательская сессия → административное чтение | Один sessionId, snapshotVersion и asOf; одинаковые суммы/статусы/причины, корректные права и обязательный аудит Q06 | Админка / БД + UX |
| Данные площадки → скор → публикация → каталог | Происхождение, время доступности, пригодность, методика и версия публикации; нет смешения версий и ручного назначения балла; неизвестное/устаревшее не маскируется | Скор / API + БД + админка + UX |
| API каждой площадки → нормализация → копирование | Покупки/продажи, повторы действий лидера, min/tick/lot, комиссии, резервы, freshness и correction; Polymarket/Limitless имеют отдельные доказательства | API / бэкенд + БД + скор |
| Восстановление → Auth/БД → интерфейсы | Старые права и входы не оживают; неизвестные исходы не повторяются; затронутые действия закрыты до сверки | БД / бэкенд + админка |
| Mobile/desktop × RU/EN | Одинаковый смысл состояний, действий и отказов, видимые переходы и отсутствие расхождений с контрактом | UX / бэкенд + админка |

Входы для визуального прохода: [карта клиента](../../design/client/sitemap.md), [карта админки](../../design/admin/sitemap.md), [старт Figma](https://www.figma.com/design/lxPP2um7FvIbt02K8eeH4T?node-id=3-2). Перед проверкой фиксировать фактические node IDs/дату просмотра и свежий Git SHA; старый снимок не заменяет текущий экран.

Для каждого найденного расхождения записать: ID, сценарий/этап, принятое правило и ссылку, затронутый экран/команду/таблицу/профиль, фактическое несовпадение, влияние, исполнителя, предлагаемое исправление, необходимость решения владельца и доказательство закрытия. Не придумывать отсутствующие поля или конечные состояния ради заполнения матрицы.

Критерий завершения документальной сверки: у первого среза нет необъяснённых противоречий или неотмеченных зависимостей; каждое обещанное действие имеет серверный контракт, хранение, отказ и соответствующее представление. Поздние части имеют явные границы и перечень открытого. Это допускает подготовку разрешённого испытания, но не означает, что runtime уже работает.

## 6. Как фиксируем согласование и продолжаем без лишних вопросов

- Ответ владельца связываем с конкретными AP-IDs и версиями источников; частичное принятие не расширяется на соседние строки.
- Ведущий общий чат сохраняет решение здесь и в соответствующем ADR/профильном документе; меняет текущий указатель PROJECT_STATE/ROADMAP. Тематические чаты получают короткую дельту, без пересылки всей истории.
- После согласования документального пакета чаты сами проводят назначенную сверку и исправляют обычные несовпадения внутри принятого правила. Общий результат — один реестр, а не шесть конфликтующих списков.
- Перед исполнением отдельное поручение по [D04 §2](backend-first-session-d04-handoff.md) должно охватывать конкретный профиль V00. Для текущих согласованных участков V00 это поручение уже дано 04.11; для нового объёма действует та же проверка полномочий. Не запрашивать повторное разрешение на уже названные действия.
