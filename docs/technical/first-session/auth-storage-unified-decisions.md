- точные reset grants/Auth audit для D02, прежний P-RESET и равноправие владельца 1 и владельца 2.

Подтверждение документации не означает реально созданные таблицы/права или прохождение испытаний. Реестр остаётся v5 до полного D02.

## U01. Точная физическая дельта к принятой карте73

**Рекомендация:** принять единую уточнённую карту42 Auth +36 Shadow =78 собственных таблиц вместо параллельных описаний37 и18. Это дельта **+5 самостоятельных таблиц**, не сумма обеих карт:

| Добавление | Почему отдельный факт необходим |
| --- | --- |
| AC38 login_cookie_credentials | Постоянный verifier исходной полной cookie действует независимо от стираемого recovery cipher; временный AC06 context proof его не заменяет |
| AC39 operation_dispatches | История запечатанного внешнего вызова и доказательств его исхода отделена от единственного локального результата; timeout не позволяет незаметно назначить нового исполнителя |
| AC40 claim_attempts | До3 разрешённых внутренних rollback-попыток внутри одного принятого AC19 и исходного5s бюджета; не новые HTTP исполнения/consents |
| AC41 reconciliation_runs | Самостоятельный факт fence/inventory/drain/проверки/разрешения открытия среды |
| AC42 reconciliation_items | Неизменяемое доказательство исхода конкретного claim admission либо внешнего dispatch внутри сверки |

**Устранение дублей:** subject/email/claim consent остаются в AC03 с once-bound typed полями; full completion — в AC05 с обратной полнотой login/context; секреты — в AC07. Отдельные subject_bindings/email_bindings/claim_consents/login_completions/cookie_recovery_secrets из D01-A не создаются. Поля seal/performer/provider outcome переходят из AC04 в AC39; AC04 хранит ссылку current_dispatch, а не копию факта.

**Изменения к принятой структуре, требующие именно этого согласия:**

- Добавляются typed ссылки и deferred полнота login/result/credential/window/secret; source/authorization/target различаются. AC03 получает staff identity/current WebAuthn challenge, обязательные email-binding refs, created epoch/access-confirmed. Нормализованный email хранится зашифрованно в AC07, raw сравнение — AC08, вместо plaintext в AC03.
- Для AC28 снимается UNIQUE(case_version,staff): иначе после истечения5min нельзя вновь подтвердить ту же версию неизменяемой записью. Уникальны operation/challenge; execution закрепляет конкретные два свежих approvals разных владельцев. Ни правило двух владельцев, ни срок свежести не меняются.
- Gate/AC41/42 и AC34/35 получают точные ссылки/full change-set/drain evidence; approved глобальный fence/witness не заменяются другим принципом. PK AC01 оставлен по каталогу БД, а не варианту D01-A.
- Для AC04 nonsecret history выбран предел16384 bytes, AC05 result65536 и AC32 audit16384/depth8; raw registration attestation в history не сохраняется. Это явное сужение общего65536 для operation payload, а не скрытый wire-limit. Новый guest-draft-proof-v1 из D01-A §7.1 становится точным предложенным HMAC-отображением B1-D2; proof-purpose/key separation сохраняется.
- Уточняется один lock-порядок схемы §6. AC04 переносится из хвоста G2 в Auth-ветвь G3 рядом с AC39; все существующие parents берутся раньше. Claim AC19/40 остаются G3 после прежнего draft advisory guard. Q01/recovery/eraser используют window→secret. Реальный граф с FK/unique locks ещё должен быть испытан.

**Что специально сохранено:** UNIQUE(environment,consent) AC19, один HTTP-исполнитель на consent, до3 внутренних attempts, прежний claim receipt/guard. Предложение D01-A о нескольких executions одного consent отклонено при сведении с принятой основой. Повтор POST не выдаёт нового permit/бюджета; после доказанного закрытия старого допуска для нового исполнения требуется новое явное согласие по текущим правилам, а неизвестность запрещает обход новым consent.

**Цена:** пять таблиц и дополнительные обязательные связи/writers. До вашего подтверждения принятый каталог —73,78 только проект. Поля и полнота подробно перечислены в [схеме §§2–8](auth-storage-unified.md); provider/evidence/test-control не включены в это число.

## U02. Отдельный предел запроса регистрации WebAuthn

**Рекомендация:** принять только для WebAuthn registration POST предел65536 bytes, с clientDataJSON≤4096 и attestationObject≤32768 bytes. Authentication assertion и остальные Auth POST остаются8192/depth8. Более крупный body нужен для attestation, а не для расширения обычных запросов/истории.

Это явно предложенное transport-исключение [API-проекта §§1/6](backend-review-api-spec.md), не принятие P05 сроков заново. Полная форма request/response и закрытые action/result/purpose должны быть отражены в D02. Storage65536 не является автоматическим разрешением wire65536. Пока исключение не принято и не отражено, маршрут нельзя объявлять полностью согласованным.

## U03. Внешнее подтверждение получено, но полный login уже нельзя выдать

**Рекомендация:** принять отдельный окончательный результат «подтверждение выполнено, вход не выдан», когда внешний эффект доказан, локальный full login ещё не создан и current context/security-допуск закрыт. AC39 сохраняет внешний факт, AC05 — законный финальный исход без login/cookie. Это не неверный OTP и не бессрочная неизвестность после доказанной финализации.

Сейчас предлагается подтвердить **семантику**, предложенное имя для D02 — auth_completion_not_issued. Оно ещё не включено в закрытый реестр. Точные DTO/закрытые причины/прямой HTTP-ответ/исторический GET оформляются следующим документальным шагом; это не повод выдумать публичный result заранее. Current-access проверки сохраняются: сохранённый результат не даёт права прочитать его после утраты допуска.

Таймаут без доказанного provider outcome не даёт этого результата. Уже созданный и затем отозванный login сохраняет исходный успешный completion и текущий отзыв. Внешний factor-reset/уведомление не подменяются этим login-only результатом. До согласия и точной D02-формы стык ASC18 остаётся открытым; известный внешний факт можно хранить, но новый публичный ответ ещё не принят.
