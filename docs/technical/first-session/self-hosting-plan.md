# Самостоятельное размещение: рекомендация для Shadow

27.10.2026 · **Проект T0, без кода и развёртывания.** Владелец поручил двигаться по рекомендации после сравнения собственного Supabase и PostgreSQL + Better Auth. Следующий результат — конкретизация самостоятельного размещения. Рекомендованный основной кандидат — **self-hosted Supabase Auth + собственная PostgreSQL**; выбор состава/версий/сервера и готовность ещё не подтверждены. Это не поручение автоматически устанавливать полный BaaS или менять принятые денежные правила.

Baseline: main `f0a196034adf8f04ad1d2a7927f509af96f95de1`. [Первый сценарий](README.md), [команды](commands.md), [данные](data-model.md), [26 критериев](acceptance.md) сохраняются. В этой задаче сравнивалась документация, не работающий стенд.

## 1. Почему этот кандидат первым

| Вариант | Подтверждено документацией | Что проверить / вывод |
| --- | --- | --- |
| Supabase на нашем сервере | Официальное самостоятельное размещение, email OTP/link, серверный TOTP и уровни проверки входа | Сохраняет принятый механизм входа. Самостоятельно настраиваем AAL enforcement, cookies/отзыв, limits, recovery, backups. Основной кандидат для дальнейшего проекта, не готовая система |
| PostgreSQL + Better Auth в приложении | PostgreSQL, email OTP и TOTP/backup codes существуют | По документации passwordless email OTP/magic link **не требуют 2FA по умолчанию**. Нужен дополнительный проверенный серверный переход до полного входа. Резервный кандидат, если основной окажется неудобен по эксплуатации; не принимаем дополнительную интеграцию молча |

Это инженерный выбор ради соответствия текущему сценарию, не вывод о сравнительной безопасности всех библиотек. Отдельные OTP/MFA функции не доказывают весь маршрут. Владелец отдельно принял добровольное подключение TOTP для paper и его обязательную проверку при новом входе после подключения; восстановление при утрате — через администраторов, решение о сбросе за ними; сроки/отключение и технический регламент ещё не утверждены.

## 2. Предлагаемая компоновка

- **Backend Shadow** выполняет команды, права, session slot, финансовый учёт и общий snapshot клиента/админки. Браузер не получает прямое изменение финансовых таблиц через сгенерированный API Supabase.
- **Supabase Auth** подтверждает пользователя/второй фактор и ведёт auth-состояние. Финансовые user/session IDs наши; auth subject связывается с ними, но не заменяет их. Включённая 2FA проверяется сервером по текущему фактору/уровню и правилам отзыва, а не лишь перенаправлением UI.
- **PostgreSQL** хранит auth и прикладные данные с разными схемами/учётными записями и минимальными правами. Точный вариант одного кластера или отдельных БД определить перед миграциями. Auth-сервис не получает произвольную запись в финансовый ledger; миграции auth не должны менять прикладные ограничения.
- **Пограничный HTTPS/gateway** даёт только нужные маршруты входа/API. PostgreSQL, служебная панель и административные ключи не публичны. Конкретный состав gateway/API/панели выбирается по закреплённой версии, а не копируется как незакрытый quickstart.
- **SMTP** остаётся отдельной зависимостью. Amazon SES исключён; Mailgun/профильный поставщик не принят. Письма на внутреннем стенде можно перехватывать тестовым транспортом; это не доказывает доставку пользователям.
- **Копии и наблюдение** обслуживаем сами: зашифрованная копия вне основного узла, проверяемое восстановление и сверка, сигналы сбоев/свободного диска/задержек. Нужны ответственный за обслуживание и согласованные допустимые потеря данных/время восстановления.

Не подключаем функции, файлы, Realtime/Storage и прочие компоненты ради наличия в Supabase. Их исключение допустимо только после проверки зависимостей конкретного состава. Сам backend остаётся модульным TypeScript по ADR-0062. Staff/Owner вход и независимые подтверждения из админки не заменяются пользовательским TOTP.

## 3. Что собственное размещение меняет

Открытый Auth-компонент имеет MIT-лицензию; официальная документация допускает самостоятельное размещение. Это отдельный способ эксплуатации от использования облачной платформы. Не требуется предполагать, что один облачный аккаунт Supabase является местом хранения всей финансовой истории.

Перед реализацией зафиксировать версии/лицензии **всех** выбранных компонентов и условия реально используемых услуг. Self-hosting не считать ни автоматическим переносом cloud AUP на весь локальный код, ни гарантией отсутствия любых ограничений. Хостер, SMTP, домен, площадки и применимое право остаются отдельными зависимостями. Внешние платные/API-функции Supabase этим проектом не подключаются.

Самостоятельно отвечаем за обновления, защиту, восстановление и доступность; готовые managed backups/SLA не возникают от установки Docker. Локальный Supabase CLI development stack не публикуется как production deployment.

## 4. Очередь до первого стенда

1. **Зафиксировать вариант размещения и эксплуатацию:** собственный Auth/PostgreSQL, компоненты/версии, хостер/регион/ресурсы/условия, кто обслуживает, где копии, целевые recovery limits. Сервер не куплен и не проверен. Ранее упомянутый ARM 4 ядра/24 GB/200 GB — кандидат test, совместимость образов/диск/IO/доступность ещё проверить; это не утверждение production capacity.
2. **Закончить политику входа:** добровольное подключение TOTP и обязательная проверка при новом входе приняты; остаются enrollment/отключение, потеря устройства, email/link, сроки/попытки/resend и входная сессия. Числа email-кодов из [auth-policy](auth-policy.md) теперь приняты; сроки входа 30/7 дней с возможностью изменения теперь также приняты; закрытие старых входов после reset MFA и новый TOTP до полного доступа приняты; применение обычных изменений срока только к новым полным входам принято; публикация политики и прочие параметры ещё требуют решения. Supabase native recovery codes не обещаются; владелец принял восстановление через администраторов вместо требуемого запасного аутентификатора. До реализации остаются регламент, назначения, проверки и последствия сброса.
3. **Согласовать внешний SMTP** и доставку только запрошенных служебных писем по полному описанию Shadow. Пока нет согласованного поставщика/плана, не оплачиваем и не рассылаем.
4. **Отдельное поручение реализации** — после решений выбрать минимальный состав и воспроизводимую конфигурацию dev/test. До него не писать Docker Compose/SQL/код и не входить на серверы. Существующий запрет писать код сохраняется.
5. **Проверка реализованного входа:** email→MFA, невозможность обхода прямым API/старым token/другим браузером, resend с общим budget, recovery/отзыв, restart и restore. Затем первый T1/T2 срез и его A01–A26 на настоящей БД. Потребуются дополнительные MFA сценарии; они пока не выполнены.

Ничего не устанавливалось; проект не обещает нулевой риск, успешную доставку, достаточную производительность или готовность к live.
