## Откуда продолжаем

Все четыре блока логической модели первого сценария приняты. [Итоговая схема](database-final-review.md), [ADR-0064 §29](../../decisions/0064_first_session_database_contract.md). Согласование не открываем заново и продуктовые правила самостоятельно не меняем. Первый сценарий прежний: вход → трейдер → настройки → проверка → пустая демо-сессия → просмотр той же сессии в админке.

**Бэкенда пока нет; его проектирование и разработка будут в другом чате.** Здесь работаем над БД и требованиями к её использованию. Общие документы — источник согласованной семантики, а не доказательство существующего API или выбранного Auth-компонента.

## Порядок работы

| Шаг | Работа в чате БД | Проверяемый результат |
| --- | --- | --- |
| 1. Проект физической схемы | Разложить принятую логическую модель на таблицы, колонки, типы, обязательность и связи. Каждую запись связать с принятой сущностью/правилом | Документ структуры БД без SQL и миграций; зависимые от будущего бэкенда места явно обозначены |
| 2. Ограничения и минимальные индексы | Описать PK/FK/unique/check, составные проверки владельца/среды/сессии, неизменяемость и необходимые отложенные проверки. Для индексов указать обслуживаемое ограничение или чтение | Матрица того, что запрещает сама БД, и минимальный план индексов; эффективность не объявлять проверенной без будущих query plans |
| 3. Пакет требований бэкенду | Свести границы транзакций, порядок блокировок, защиту отсутствующих ключей/слотов, idempotency, audit/outbox и требования к сохранению/чтению | Один связный документ передачи для отдельного чата бэкенда со ссылками на общие контракты; без самостоятельной разработки серверных обработчиков |
| 4. Зависимости и границы ответственности | Выделить решения, зависящие от устройства Auth, точной формы будущих запросов/ответов и доступа серверных компонентов к БД | Краткий список зависимостей с указанием, что требуется от чата бэкенда. Не заменять отсутствующие решения предположениями |

Шаги выполняются в этом порядке; выявленные зависимости фиксируются сразу. Независимую часть схемы можно продолжать без ожидания всех ответов от бэкенда. Обычные технические детали оформляются в рамках принятого контракта, без новой цепочки микровопросов. Реальный конфликт с продуктовым правилом выносится отдельно.

## Что здесь не начинаем

- Не проектируем за другой чат механизм входа, API-маршруты и серверные обработчики; документируем только требования и зависимости БД.
- Не пишем код приложения, SQL, миграции или конфигурацию развёртывания; не создаём БД/сервер и не применяем изменения к средам.
- Не объявляем плановые A01–A112 выполненными тестами; фактические проверки БД/API, гонок и restore относятся к будущей реализации.
- Не пишем автоматически в другой чат и не отправляем пакет коллеге: готовим документ для передачи владельцем, если отдельного поручения на отправку нет.
