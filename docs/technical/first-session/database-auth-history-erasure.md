## 1. Четыре разных срока и факт стирания

| Понятие | Что означает | Что из него не следует |
| --- | --- | --- |
| Срок допуска | До какого момента конкретные context/login/challenge/approval разрешают действие с текущими правами | Что строка/результат должны исчезнуть в этот момент |
| Срок выдачи секрета | До какого момента можно повторно выдать исходные bytes через разрешённый путь | Что вся история доступна по публичному ID или cookie действительна только это время |
| Срок использования verifier/comparison | Пока соответствующий proof/сравнение нужны разрешённым исполнительным путям | Что любой digest можно стереть по общему таймеру контекста, включая доказательство старого login для logout |
| Срок хранения истории/копий/ключей | Отдельная политика для конкретного класса данных и его зависимостей | Что 5 минут окна, 7 дней guest или семь backup-копий являются общим TTL истории |
| `erased_at` | Подтверждённый факт допустимого стирания предусмотренных полей в текущем хранилище | Что erase уже случился ровно в deadline либо все WAL/backup/provider/browser копии уничтожены |

На границе `now >= deadline` новое использование по этому сроку закрыто независимо от работы фонового процесса. Проверяется достоверное время и нужные текущие guards; недоверенные часы не дают разрешения. Поздний worker не продлевает доступ. Историческое approval/challenge/result сохраняет исходные времена; чтение не делает его свежим.

M04 первого стенда **не разрешает автоматический архив/удаление истории**. Это действующее ограничение текущего этапа, а не новая политика бессрочного хранения персональных данных. Узкое стирание секретных полей по принятой карте разрешено документально отдельно от удаления строк. Будущий общий архив/очистка потребует отдельного совместимого проекта с родителями, dedup, результатами, аудитом и копиями.

## 5. Документальный контракт eraser

Это детализация узкого writer, уже принятого в физической карте §5. **Не новый endpoint, daemon, расписание или физический порядок locks.** Для всех выбранных записей сохраняются прежние environment/purpose/actor связи и guard-протокол. U01 `window→secret` и перенос рангов не объявляются уже принятым новым порядком.

1. Выбрать только предусмотренный класс поля/его источник и достоверно проверить срок/отзыв/подтверждённое закрытие. Expiry строки не разрешает стирать другой класс данных. Для AC06/08/09/22/24 нужны закрытые соответствующие исполнительные proof-пути; при неустановленном исходе сверка сохраняет факты и не даёт нового исполнения.
2. Повторно проверить условия под принятой защитой от конкурентной выдачи/consume/refresh. Нельзя прочитать старую expiry гостя, дождаться продления C04 и затем стереть живой proof. Полный граф внутренних locks/closure остаётся будущей проверкой D03, не обещанием этого документа.
3. Сохранить допустимое очищение полей и marker **одной локальной транзакцией**, без промежуточного допустимого частично пустого cipher. Для AC07 по принятой73 все nonce/ciphertext/tag становятся NULL вместе; owner/key/format/reveal_until остаются. Для verifier очищается только его разрешённое поле; metadata/history не переписываются.
4. Сохранить обязательное сопровождение по действующему audit/witness контракту. Точный список typed targets и decoder должен быть закрыт U01/D02 до реализации; новый event-kind или универсальный JSON для erase здесь не добавлен. Повтор уже подтверждённого erase не ставит новое «первое» время и не восстанавливает bytes.
5. Подтвердить исход фиксации. Потеря commit-ответа означает необходимость чтения того же состояния; ни «стёрто», ни «не стёрто» не угадываются. До/после логической границы выдача определяется сроком/допуском, а не оптимистическим успехом eraser. Внешний witness ack не переписывает локальный исход.

Неизвестность внешнего эффекта **не продлевает срок выдачи секрета**. После закрытия пути нельзя удержанием/восстановлением secret обосновать повторную отправку. Для сверки используются разрешённые несекретные source/provider refs и доказательства; если их ещё недостаточно, фиксируется зависимость, а не новый срок хранения. Там, где условие безопасного erase ещё не доказано, документ не назначает новый крайний срок физического удаления и не заявляет выполненное стирание.

Успешный Q01 должен атомарно зафиксировать предусмотренное закрытие окна до выдачи защищённого ответа; idle прежний. Законное стирание временного cipher обязательно по принятому пути, но точные расширенные связи/порядок Q01+eraser из D01-U не импортируются до U01. Доставленный позже ранее подготовленный recovery-ответ содержит прежние bytes, не новую выдачу после закрытия. Стирание live-row не отзывает уже выданную cookie: отзыв проверяется по current login/security/slot.

## 6. Ключи, внешние копии и restore

При restore выбранной старой копии AS26 новый deadline не вычисляется от времени восстановления. Сначала изоляция/закрытый допуск, затем независимая сверка по принятому P03/P04/H06, и только доказанное разрешение открытия. No-effect нельзя вывести из отсутствующей старой строки; missing result при сохранённом ownership/login — отдельная проблема полноты. C06 финансы/receipt/slot и прежние revoke/claim/сcope связи проверяются целиком по существующему плану, не чинятся eraser автоматически.
