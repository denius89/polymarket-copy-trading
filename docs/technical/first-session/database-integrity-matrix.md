Baseline актуальной main: `6b13eefe4146afb15427f03d7e97aca1a71d5c48`. Все строки ниже имеют статус **«запланировано; не выполнено»**. Матрица не меняет критерии приёмки, состав 34 таблиц и продуктовые правила; SQL, код тестов/приложения, миграции, тестовые аккаунты и БД не создавались.

## 1. Как читать и проверять

Каждый A-ID ниже соответствует ровно одному исходному пункту acceptance.md; сокращённый сценарий не отменяет варианты его полной формулировки. Варианты успеха/отказа/сбоя разделены внутри строки. «+1» — изменение числа записей относительно снимка **перед данной операцией**, в полном scope environment/actor/resource/key. Это не общий размер таблицы. Изменения независимой конкурентной транзакции учитываются отдельно и не объявляются частичным результатом откатившейся операции.

Число строк само по себе недостаточно: сравниваются полные IDs/FK, владелец/среда/venue, версии, сохранённые исходные значения и деньги. Перед тестом фиксируются существующие записи, затем после подтверждённого исхода — дельта и неизменность прежних записей. Для unknown commit нельзя требовать нулевую дельту до выяснения исхода. Для rollback сравнивается новая свежая транзакция после подтверждённого отката, не старый Serializable-снимок.

Уровни доказательства: **БД** — фактические записи/ограничения; **API** — запрос, безопасный ответ и связь с данными; **Auth** — проверенный провайдер/полный вход/отзыв; **UI** — клиент и админка, локали/устройства; **ОПС** — изолированная копия, совместимость, таймеры/доставка/restore. План содержит требуемые уровни, не утверждение их прохождения. H01–H06 определены в сводной передаче; H05 нужен для всех физических испытаний БД даже там, где строка отдельно называет лишь специальную зависимость.

Для каждой будущей проверки нужны: A-ID и вариант, версия приложения/схемы/формата, безопасная конфигурация и IDs, исходное состояние, действие/точка сбоя/порядок конкурентов, подтверждённый исход транзакции, дельта записей, результат независимой проверки и статус. Не сохранять bearer, OTP, passkey/recovery-секреты или полное содержимое проблемной записи. Неподтверждённое, неисполняемое или частично выполненное не отмечается «пройдено».

## 3. Эталонные дельты операций

Эти обозначения используются в A-строках. Полнота/принадлежность обязательны в дополнение к количеству. Считаются только committed записи после разрешения исхода; служебные недолговечные резервирования до commit не являются отдельным результатом.

| Профиль | Ожидаемое сохранение | Что не должно меняться |
| --- | --- | --- |
| START | +1 paper_sessions, +1 settings_revisions(sequence=1), +1 funding_flows(initial), +1 journals(sequence=1), **+2 journal_entries**, +1 session_snapshots(version=1); +1 каждой из трёх CMD; +1 start audit_events; +1 outbox_events для зарегистрированного consumer. Slot: +1 generation=1 при первоначальном отсутствии либо обновление свободного существующего pointer и generation+1. Исходный draft получает used_at/used_by_session_id; обязательные ссылки замкнуты | REVIEW/ownership/catalog/policy неизменны; другие drafts/сессии не меняются. Нет новых consumer receipts до обработки, audit_authorizations для start не добавляются. Draft.version и TTL ввода не повышаются служебной отметкой used |
| REJECT | Для нового авторизованного C06 с окончательным предметным отказом после допуска к scoped key: +1 key, +1 rejected receipt, +1 details. Созданный при достигнутом резервировании пустой slot может сохраниться ровно по правилу блока 3: generation=1/current=NULL | FIN +0, start audit/outbox +0, draft не помечается used. Существующий slot не освобождается/не переназначается. Отдельный безопасный audit отказа зависит от согласованного типа события H02; не требовать его как start audit |
| INVALID | Отказ входного формата/транспорта или доступа **до исполнения C06**, без права на финансовую запись | FIN/CMD/start audit/outbox +0, прежний draft и прежний receipt целы. Допустима безопасная техническая диагностика вне финансового результата; её точный sink — H02/H05 |
| ROLLBACK | После подтверждённого отката весь комплект именно этой операции отсутствует; прежние строки/ссылки/версии восстановлены | Нет committed key без receipt, частичного funding/журнала, использованного draft без session или нового slot от откатившегося старта. Внешний Auth не объявляется откатившимся вместе с Shadow |
| REPLAY | Тот же scoped key/payload после новой проверки доступа возвращает прежние receipt/result IDs/версии | CMD/FIN/start audit/outbox +0; slot generation и used draft не меняются. Другой payload не перезаписывает core. Новый login допустим, новый ключ автоматически не создаётся |
| CLAIM-OK | +1 user draft_ownerships и +1 draft_claim_receipts; current_ownership_id переключён, old guest handle больше не допускает доступ; пары previous/claim замкнуты | Исходная guest ownership и прежний guest REVIEW неизменны; raw/version/TTL draft не переписываются передачей; FIN/CMD C06 +0. Audit claim — по закрытому событию H02, не денежный receipt |
| SAVE | Новый draft: +1 setup_drafts и +1 начальная ownership, version=1. Содержательная правка доступного draft: update одной строки, version+1, новое last_saved_at/7-дневный expiry. Актуальный no-op: дельта 0 | Нет FIN/REVIEW автоматически. Stale/used/expired/невалидный транспорт не изменяют прежний draft. Durable повтор C04 требует закрыть зависимость M01 (§7), его нельзя считать обеспеченным C06-таблицами |
| REVIEW-OK | +1 неизменяемый setup_reviews с копией версии/ownership/raw/выбранных нормализованных параметров, policy/trader/guards/наблюдения slot, checked_at и expiry+10 минут | FIN/CMD/SLOT +0. Предметно неверная настройка может дать review с normalization_valid=false, всеми normalized NULL и allowed=false; ошибка формата/хранилища не создаёт ложный успешный review. Точное различение ответов — H02 |
| READ-U | Чтение текущей своей session по current snapshot pointer; FIN/CMD/SLOT/REVIEW +0 | Session/snapshot version, as_of/created_at и деньги неизменны. Подтверждённая foreground-активность может обновить **свой** auth_sessions по H01; «read» не означает отсутствие любых служебных записей |
| READ-A | Один целый разрешённый snapshot; +1 audit_events выдачи на request_id и достаточный набор audit_authorizations (≥1, точное число по использованным grants/группам данных) | FIN/CMD/SLOT +0, пользовательский login не продлевается. Staff foreground может обновить его auth_sessions. Без сохранённого audit/evidence ответ с данными не отправляется |
| WORKER | Для нового локального эффекта +1 consumer_event_receipts на env/consumer/event, обновление доставки outbox; повтор при уже сохранённом receipt только завершает доставку | FIN/CMD/start audit +0, immutable event ID/ресурс/payload прежние. Lease/attempt/version — изменяемые служебные поля, не новый запуск |

**Денежный независимый ориентир первого запуска:** B200, p10%, d15% → settings B=200/1, p=1000, d=1500, P=20/1, D=30/1; fixed F=20/1, q=NULL **либо** percent q=300, F-пара NULL. Funding=200/1; journal cash=+200/1, source=−200/1; free/equity/initialFunding=200/1; reserve/positionCost/positionValue/tradingResult=0/1, все торговые счётчики=0. Для B300: P=30/1, D=45/1, cash/free/equity/funding=300/1. Сравнение делается с этими заранее указанными значениями и противоположностью пары, не повторным вызовом того же builder. Funding не суммируется с cash вторично; source не вычитается из пользовательского equity.

## 6. Границы полноты и доказательств

- A01–A112 сохранены как требования. 112 сопоставленных строк означают полноту **документального отображения ID**, не 112 пройденных тестов и не доказанный охват всех рисков.
- Каждый финансовый START сверяется по всем новым/изменённым записям профиля, не только по session count. REJECT имеет собственный durable outcome, но не финансовые дети. INVALID/ROLLBACK/unknown не подменяют его.
- Для гонки фиксируются обе допустимые очередности и постусловия; проверки не требуют случайно выбранного победителя. Утверждение «всё откатилось» относится к проигравшей транзакции, а не к независимому commit конкурента.
- Выполненный SQL constraint test не доказывает правильность HTTP, UI, Auth или отзыва провайдера. Нулевой FIN не доказывает отсутствие утечки чужих данных. Отчёт по форматам не доказывает актуальность прав после backup.
- Четыре основных формата проверяются по фактическим данным и всем строкам; core command_keys и details проверяются как обязательные связи receipt. Собственные event_schema_version и Auth-контракты дополнительно требуют своих H02/H01 проверок.
- Для финансового критического пути нужен отдельный проход fixed/percent и Polymarket/Limitless; UI-варианты RU/EN/mobile/desktop — по A10. Не требуется бесцельный полный декартов перебор всех границ на всех экранах.
- На этом этапе не создаются синтетические аккаунты, SQL fixtures, наборы recovery-кодов или исполняемые тесты. Конкретные воспроизводимые наборы данных и подробные карточки сбоев — следующие возможные документальные блоки по отдельному поручению.
