## 1. Разделение источников и trust boundaries

Один PostgreSQL-кластер с раздельными правами: прикладной Shadow, существующий provider Auth, собственная служебная область auth_control. Supabase Auth остаётся принятым user provider. Его user/session/factor refs не подменяются браузерными UUID; служебные права не возникают из provider metadata. Staff WebAuthn исполняется отдельным adapter. Closed Auth-controller получает provider ответы и управляет разрешением Shadow, но не пишет финансовый ledger.

Проект auth_control хранит локальный допуск/версии/результаты, на которые может опереться одна транзакция Shadow. Это не копирование всей БД провайдера. Результат внешней операции и локальный commit не объявляются атомарными. Только подтверждённый provider исход и соответствующие локальные security guards разрешают полный login. Неясное состояние provider закрывает затронутое действие; его нельзя оформить как неверный код/пустой результат.

Все управляющие provider endpoints закрыты от браузера/публичной сети. Единственные штатные writers проходят controller; служебный внештатный доступ сначала закрывает environment gate, затем выполняет сверку и публикует новые guards. Асинхронный webhook не считается достаточной гарантией мгновенного отзыва. Компрометация provider/DB administrator остаётся за пределами доказательства обычных API-прав и требует восстановления по §7.

## 2. Предлагаемый закрытый каталог хранения

Ниже **логические группы записи**, не обещание «ровно10 новых таблиц». БД должна отразить точные physical constraints отдельной дельтой и подтвердить, что ни один generic JSON не заменяет обязательную связь/enum/тип.

| principal_security | environment,realm,principalId,securityVersion,state=active/transition/blocked,transitionRef | Auth-controller; полный допуск/финальные Auth шаги; изменения повышают связанные guards |
| contexts | environment,kind,id,subjectRef?,selectedLoginRef?,sourceContextRef?,targetDraftRef?,previousOwnershipRef?,proofDigestKeyId/proofDigest,stage,created/expires/revoked,version,executionClosedAt? | Только контекстные процедуры; proof-проверки и scoped result recovery |
| operations | environment,contextId,action,operationId,nonSecretCanonicalPayload,secretComparisonRef?,phase=admitted/dispatched/resolved/uncertain,providerRequestRef?,resultRef?,admittedEpoch,dispatchSealAt? | Единственный action handler/reconciler; собственный результат при текущем proof; уникальность полного scope |

Contexts kinds разделяют user_auth,guest,mfa,mfa_result,logout,user_claim,staff_auth,staff_logout,staff_registration,staff_recovery,staff_recovery_codes. У каждого закрытый допустимый набор nullable refs; например user_claim требует user/login/draft/previous ownership одной среды, guest не получает userId, staff-recovery не превращается в user-auth. Cross-environment FK и enum checks обязательны, незнакомый kind не декодируется как ближайший. Recovery pair — версия объединённой процедуры в recovery/bootstrap/audit, не третий субъект и не новое право.

Contexts сохраняются после истечения для доказанной истории/claim recovery; secret material имеет отдельный срок. Изменяемые stage/version не переписывают прежний result. Body/cookies/OTP/assertion целиком в audit/history не пишутся. Временная копия MFA seed для выдачи QR и выдача резервных кодов — отдельные зашифрованные записи с жёсткими readers и физическим удалением ciphertext по окончании принятого окна после подтверждённой сохранности несекретного результата. Действующий фактор у provider имеет собственное защищённое хранение; уничтожение временной копии выдачи не удаляет активный фактор.

## 3. Идемпотентность и внешний Auth

До внешнего вызова: проверить текущий proof/target/HTTP quota; под X operation-context создать или прочитать scoped operations; другой несекретный payload409; сохранённый result восстановить. Первый исполнитель фиксирует dispatchSeal в самостоятельной короткой транзакции, после чего только он имеет право сделать один внешний вызов. Crash между seal и сетью оставляет неопределённость, а не право другому worker повторить отправку. Ошибка подключения до доказанного неотправления может разрешить отдельный явно записанный safe retry; timeout/5xx сами этого не доказывают.

После подтверждённого provider response локальный finalizer одной транзакцией сохраняет result и допустимые guards/login/counters. Crash после provider effect до result →reconciler читает точный provider_request_ref/подтверждённый audit/outcome. Если выбранный provider не даёт корреляцию достаточной силы, операция остаётся uncertain и пользователь получает ограниченное восстановление; нельзя обещать exactly-once письма или успешное восстановление всех сбоев. **Это блокирующая проверка адаптера**, а не пробел, заполненный вторым HTTP-вызовом. При отсутствии нужной возможности придётся отдельно согласовать узкое расширение адаптера, не менять продуктовые правила.

Для secrets нельзя хранить обычный SHA256 шестизначного OTP. Проект: отдельный keyed HMAC-SHA256 над domain/environment/context/action/operationId и length-prefixed secret bytes; ключ purpose-specific, вне БД; сравнение constant-time. Значение хранится в закрытой secretComparison записи только для срока допустимого повтора, не в обычном fingerprint/receipt/log. Для WebAuthn replay сравнивается канонический hash публичных assertion bytes, server challenge связан с operation; raw assertion не нужен в обычной истории. HMAC сам по себе не защищает при компрометации и ключа, и БД; хранение/ротация разделены §7.

TOTP profile requires точные использованные steps; provider success без информации/контроля нужного набора steps недостаточен для обещания принятого ±1/одноразовости. Пин версии Supabase не закрывает это требование. Adapter обязан показать проверяемое соответствие либо закрыть данный маршрут до исправления. Same factorVersion использованные steps разделяются по субъекту/фактору, не по цели/login; неверные счётчики остаются отдельными по принятым назначениям.

## 4. Локальный допуск, Q01 и cookie races

Provider credential сначала проверяется закрытым adapter, затем в предметной транзакции проверяются local environment/principal/identity/login guards, сроки и staff slot. Не использовать TTL-кэш allow для обхода текущей проверки. Внешняя проверка не выполняется под долгими SQL locks. Неизвестность проверяемой внешней identity до допуска503; известный отзыв401. Полный trusted mapping provider/subject/realm/environment → local principal неизменяем по совпадению email.

Completion создаёт local login и cookie_recovery row с source result/secret/deadline. Q01/current staff берёт X на этой recovery row сразу в правильной группе допуска (без позднего S→X), проверяет login/cookie, фиксирует firstConfirmedAt/closedAt в том же commit перед200. Restore берёт ту же X, затем проверяет current login/deadline/firstConfirmedAt и формирует тот же cookie secret. Порядок определяет: restore первым может подготовить допустимый ответ до последующего Q01; Q01 первым закрывает новую выдачу. Уже подготовленный HTTP может прийти позже — не обещаем отозвать сетевой ответ. Секрет/имя не меняются, поздняя cookie не оживляет отозванный local login.

Server idempotency результата не привязана к requestId; requestId текущего чтения отличается. Нельзя ставить Set-Cookie после ошибочного guard или для другого выбранного login. Контекстные cookie ограничиваются per-ID именами и explicit selectors. Общий/browser storage указатель не authority. Cookie header parser отклоняет дубли точного имени; resource lookup никогда не выбирает первый подходящий cookie.

## 5. Guest и protected selector Q02

Guest-context до draft хранится в auth_control.contexts. Proof — HMAC-SHA256 с domain shadow.guest.proof.v1 + length-prefixed environment + UUID bytes + secret, отдельный keyId. Это proof общего контекста, **не подстановка существующего draft-bound digest**. При C04 create в той же транзакции связываются существующий guest actor и новый ownership; draft-bound proof, если сохраняется физической моделью, выводится/проверяется отдельным purpose и не открывает другие drafts. Claim закрывает прежний доступ только к переданному draft, не общий guest каталог и независимые drafts. TTL/refresh/потеря ответа заданы API §7; C04 extends guest validity и draft expiry согласованно, без изменения last_input_receipt_id semantics.

Предлагаемый selector: закрытая immutable configuration `catalog-binding-v1` с точными ключами environment,realm=guest/user,venueId → единственный readScopeId,sourceRef,policyVersion. Для первого синтетического среза нет персональных overrides/новых ролей: все доказанные readers одного realm/venue используют одно явно опубликованное разрешённое основание. ReadScope не берётся из cursor, клиента, первой строки БД или name. Неизвестная комбинация без разрешения скрыта; повреждённая/неопубликованная обязательная конфигурация503.

Binding хранится в предлагаемом auth_control каталоге current binding + immutable versions. Publisher доверенный, environment/sourceRef подписаны и имеют контрольную сумму. Публикация выбирает существующие q02_read_scopes своей venue, подтверждает membership/sourceRef и обновляет current binding/guard атомарно. Это физическая дельта H01, не третья незаметная таблица каталога Shadow. Два существующих scope-хранилища не заменяют binding/доступ.

Точный порядок Q02: предварительно прочитать candidate binding только как locator; открыть primary Serializable; G1 S все candidate scope родители в стабильном порядке; G2 S binding/current policy guard и доказанный reader access; проверить, что candidate id/version/sourceRef всё ещё совпадают. Затем membership+sources/traders/revisions и весь manifest/страница в том же снимке, с прежним5s/одной попыткой. Изменение guard после snapshot или mismatch не лечить чтением «новой первой строки»: транзакцию завершить техническим503; следующая явная попытка получает новый snapshot. На свежем допуске изменённая разрешённая область против cursor →409 CATALOG_CHANGED, потерянный допуск →403/hidden404, а не409.

Binding writer берёт X старых и новых scope parents в G1, затем X binding в G2, обновляет version/current/sourceRef целиком. Source membership writer сначала тот же G1 scope X; account/guest revoke обновляет соответствующий G2 parent; только полные ключи, без возврата из G2 за G1. Если изменившийся mapping указывает новые G1, writer определяет полный набор до lock и при несовпадении откатывает, а не повышает locks. Истёкшие права перепроверяются после ожидания; чтение Q02 не продлевает user idle автоматически.

## 6. Claim: guard, неизвестность и отсутствие позднего исполнения

Сохраняется **transaction-level advisory guard**, без новой постоянной таблицы guard на draft. Предлагаемая точная функция `claim-guard-v1`: SHA256 от ASCII `shadow.claim.guard.v1`, байта00, uint32BE длины UTF-8 environment, его bytes,16 UUID bytes draft. Первые8 bytes трактуются как signed64 big-endian для одного advisory key. Коллизия даёт только дополнительное ожидание; поиск/access/unique всегда используют полные environment/draft. Ни user, ни consent/context/login не входят в guard. Все одновременно работающие handlers используют одну версию; смена только при закрытом admission и drain, либо отдельный доказанный совместимый протокол.

До G3 проверяются G1/G2/current full user; после G3 сохраняется прежний G4/G5/G6 порядок. Unique(environment,draft_id), исторический claim receipt, full CLAIM-OK/audit не заменены advisory lock. SQL-подключение одно на транзакцию; savepoint release/отмена клиента не доказательство полного rollback. Один claim за транзакцию; session advisory locks запрещены.

Новый consent не создаёт нового пространства исполнения. POST сначала разрешённо ищет существующий receipt, как принято. Consent действует только как доказательство целей/выбранного login. Если результат неизвестен, история source consent/dispatch отмечает unresolved; GET200 по цепочке возвращает факт, GET202 — только доказанную область, не разрешение записи. API не обещает по отсутствию строки отличить «ещё не начиналось» от «ещё может завершиться».

**Конкретный консервативный путь, если receipt отсутствует, а старое исполнение могло остаться в полёте:** сначала закрыть admission изменяющих запросов этой среды в auth_control.environment_gate и увеличить epoch под X (раньше G1). Все mutating handlers до бизнес-работы берут S gate и проверяют исходный admittedEpoch; новые запросы пока закрыты. Дождаться завершения/доказанного прекращения всех старых DB transactions и provider dispatch этого claim-пути; controller не имеет очереди автоматического возобновления claim. Старые отложенные handlers с прежним epoch не могут начать после открытия. В отдельном свежем primary snapshot с прежним G3 и текущими правами проверить receipt/ownership/fullness; старый source consent закрыть для исполнения. Только после успешной сверки gate открывается новой версией и допускается новое явное подтверждение. Если drain/epoch/result не доказаны, gate/затронутая операция остаются закрытыми. Это редкая административная сверка, не действие «повторить» из UI.

Gate — предлагаемый общий Auth control, **не новый claim guard**, локальная атомарность claim остаётся прежней. Этот способ намеренно ограничивает доступность на синтетическом стенде ради доказанного отсутствия позднего writer; его влияние на остальные операции коллега должен оценить явно. Получение advisory lock в старом Serializable snapshot само по себе не доказывает свежесть отсутствия; в указанной последовательности snapshot создаётся только после drain/fence, не «обновляется» ожиданием lock.

## 7. Ключи, restore и независимый источник свежести

Key purposes раздельны: guest proof,context proof,secret comparison,short-lived encryption,Q02 cursor,offline recovery code,evidence signing. Key material не в app DB/Git; рабочие secrets выдаются через root-owned read-only файловые дескрипторы закрытым процессам, filesystem0400/service account, без env dumps. Для AEAD — проверенная библиотека/уникальный CSPRNG nonce, full tag; plaintext никогда не аудит. Public keyId/version не permission. Key catalog подписан, состояния active/read_only/revoked. Старый decrypt разрешён только по текущему status и purpose; revoked никогда не оживляется из backup.

Независимый witness — защищённый журнал на отдельном Mac/носителе вне восстанавливаемой БД. Вариант размещения/права конкретизирован в [операционном проекте](backend-review-operations.md). Запись journal: sequence,previousHash,environment,epoch,eventKind,operationRef,nonSecretDigest,state=intent/confirmed/uncertain,recordedAt,signature. Секреты/OTP/seed/персональные адреса не включаются. Fresh signed head хранится отдельно от backup и сверяется при старте/restore; rollback head не принимается только по локальному счётчику.

Для security/permission/key/scope публикации и сохраняемых command outcomes writer сначала регистрирует witness intent, затем локальную транзакцию, затем confirmed witness с доказательством локального commit. Отказ witness до intent запрещает новое изменение; после DB commit отсутствие confirmed означает неизвестность до сверки, не rollback. Согласованность восстанавливается по intent + WAL/local fact, а не повторным исполнением. Письмо/внешний Auth эффект с lost outcome остаётся отдельной uncertain записью. Это двухсторонний журнал сверки, не обещанная распределённая транзакция.

Влияние witness на принятую5s/10s задержку — release-block измерения. В этом проекте его недоступность закрывает новые защищённые изменения, а не снижает сохранность ради ответа200. Read-only пути допускаются лишь при доказанном текущем environment epoch/key status; старое permissive cached state не восстанавливает отозванный доступ. Нет свидетельств непокрытого промежутка после backup — соответствующие функции остаются закрытыми, даже если локальные R/A проверки зелёные.

Restore: изолированная копия+WAL →сверка external head/intents/credentials/revokes/scopes/receipts/claim/slots/финансов/outbox →новый environment epoch и новые browser context/login proofs (старые отозваны) →перевыпуск scope IDs либо доказанная непрерывность их id/version по witness →подписанный reconcile report →отдельное разрешение открыть gate. Отозванные факторы, подтверждения и ключи не возвращаются. Потеря средств восстановления не даёт универсального входа по email; действия остаются закрытыми. Новые scope IDs без атомарного protected selector не решают rollback самостоятельно.

## 8. Права записи и физическая передача

Предлагаемые технические роли: shadow_api_exec,shadow_worker_exec,shadow_auth_exec,shadow_catalog_publish,shadow_access_publish,shadow_schema_owner,shadow_backup,shadow_verifier. Это service accounts, не продуктовые роли владельцев. Runtime не owner/superuser/BYPASSRLS, не может отключать triggers/FK или выполнять arbitrary DML. Только узкие процедуры и разрешённые read projections; Q06 всегда через audit-bound выдачу. Schema executor используется только отдельным поручением миграции, не runtime connection pool.

Procedure owners NOLOGIN, фиксированный search_path без пользовательских схем; все аргументы scoped/typed, проверка environment/proof маппинга до writes. RLS — дополнительная граница, не замена родительским guards/unique/deferred completeness. Catalog/access publishers меняют полный набор+version/guard одной транзакцией, не роль в токене.
