## Два этапа и их граница

**A. Одноразовый E2E.** Новая физическая DB-only копия создаётся и проверяется внутри Oracle, без выгрузки незашифрованной базы на Mac. Auth, Mailpit, gateway и Node этой копии используют только её БД и собственные адреса сервисов. До старта проверить фактические DSN всех служб, mounts, порты и отсутствие связи с постоянной внутренней сетью. Не разрешать перенесённому outbox отправлять внешние письма. Вход получают штатные Auth endpoints, а не setup-fixture.sql или импорт cookie. Доступен только синтетический каталог. Включение тестового профиля в копии — явная операторская процедура с manifest и marker, не скрытая startup-миграция. Если используется существующий 008, его применение к копии должно быть отдельно показано и допущено; текущий пакет его не исполняет.

**Изоляция браузера обязательна:** cookies не разделяются по порту. Для E2E нужен отдельный browser profile/storage partition без импорта cookie постоянного полигона; не открывать 18443 и 18444 в одном профиле. В копии создавать новые auth context/login IDs; после безопасного evidence удалить её браузерный профиль. Один другой порт не изолирует `__Host-` cookies.

Для одновременного сохранения постоянного UI предлагается отдельный origin `https://localhost:18444` и SSH-проброс непосредственно к приватному Docker IP шлюза копии (порт8443 внутри её сети). Это ещё предлагаемая топология: до запуска сверить configurability origin/Host/Auth/Cookie/TLS с backend. Не публиковать Node/PostgreSQL/Auth/Mailpit и не заменять текущий launcher. На Oracle host ports не публикуются вообще; только локальный SSH listener на Mac. Новый системный сервис и публичные правила firewall не нужны. Открытие этого origin не доказывает успешный E2E.

**B. Постоянный полигон.** После A — отдельный точный пакет: текущая зашифрованная резервная копия и проверка восстановления, миграции/ACL, seed/gate/008, новые runtime ключи и LOGIN, compose/static change, restart, браузерная проверка, порядок выключения paper без удаления истории. Постоянная активация 008 не входит в сейчас выполняемую подготовку. Если требуется новый допуск, отправить в административный чат один готовый пакет с hashes, дельтой, проверками и восстановлением.

## Gateway: обязательная проверка границ

1. Точный allowlist методов и путей `/api/traders`, карточки, drafts (POST/GET/PATCH), validate, sessions, current, по ID и commands. Auth и static остаются на существующем launcher. Неизвестные методы/пути закрыты; абсолютный request target, дубли Host, Transfer-Encoding и неоднозначный Content-Length не обходят проверку.
2. Публичные `/__polygon__/…` и прежние `/__v00__/…` возвращают 404. Поддельные X-Forwarded/actor headers не дают identity. Клиентские internal deadline/body/proof удаляются или отвергаются до формирования доверенного запроса.
3. HMAC: domain `shadow.polygon.ingress.v1` + NUL, uint32BE длины method/raw target/body SHA256/deadline. Ключ отдельный от credential/cursor, приватный mount. Не логировать proof/cookie/body с OTP.
4. Общий deadline5s фиксируется на первом входе запроса до body/ожидания. Проверить медленное тело, задержку до Node, последовательный Q01→mapping, уже истёкший бюджет, timeout backend, отсутствие нового 5s на proxy. Непрошедший proof не должен вызывать SQL.
5. Ошибка product mapping после успешного Q01 даёт технический отказ без подмены userId; подтверждённые Auth-изменения не откатываются вымышленно. С выключенным paper gate — прежнее поведение Auth.
6. Неверный Origin, поддельный/чужой login, отсутствие cookie и чужой draft/session/command закрыты. Реальная cookie выдаётся C02, HttpOnly/secure сохраняются. До запуска сверить точную схему selected login header и Cookie forwarding.

## Завершение и остановка

Не считать PASS только по HTTP200 или изображению экрана. Нужны точные pins, полный браузерный маршрут, gateway negatives, наблюдение БД и cleanup. При расхождении остановить затронутую команду, сохранить безопасное evidence и исправить новый source pin; ожидания не ослаблять.

Удаление временной копии выполняется только по созданному scope/labels и совпавшим mounts. Затем отдельное чтение подтверждает отсутствие контейнеров/тома/временных каталогов и SSH-туннеля копии; постоянный Auth/UI и отсутствие paper schema должны совпасть с preflight. Ошибка cleanup блокирует отметку завершения. Unknown-COMMIT, staff/passkey, P04, реальные площадки/кошельки и торговля не становятся PASS по этому E2E.


Подготовительный source bundle: `tools/v00-polygon-gateway/SHA256SUMS` (6 файлов), 25 локальных тестов. Следующий API-кандидат `7d02f9fdf9d141d0937d4053d0cf8f61d874eb86` дополнительно сохраняет CATALOG_CHANGED409 navigation; он вычитан БД, но не относится к историческому Oracle46/46 на fb14cf0. ### Фактическая инвентаризация без изменений · 05.11

Чтением Oracle подтверждены: все пять служб постоянного `shadow-polygon` находятся только в `shadow-polygon_lab` (`internal=true`), host port bindings пусты. Auth подключается к `db:5432/shadow_v00` ролью `v00_auth`; в отдельной копии должны быть собственные DB/Auth/Mailpit и те же DNS aliases только её внутренней сети. У Mailpit пересылка SMTP relay не настроена. Ни одна служба нового профиля не присоединяется к постоянной сети.

У app и otp-template видны `/var/lib/postgresql/data` из базового образа, но это собственные разные anonymous volumes, не том `shadow-polygon_db-data` постоянной PostgreSQL. Не интерпретировать одно совпадение Destination как общий PGDATA. При сборке новой копии отключить ненужные унаследованные writable volumes либо учитывать их в scoped cleanup; Node/Gateway не должны монтировать настоящий PGDATA. Private configs копируются и перепривязываются только внутри Oracle, без вывода паролей/ключей/OTP в отчёт.

Точный тестовый порядок после допуска нового пакета: свежая физическая копия → проверка base backup → изолированный PostgreSQL и HBA по фактическим адресам служб → paper001–007 → dedicated LOGIN без memberships → явный `008-operator-activate.sql` только в disposable DB с переменными role/tzdb → собственные Auth/Mailpit/gateway/Node без fixture_auth → реальные новые C01/C02/Q01 → E01–E08 → отдельное наблюдение и cleanup. 008 в этом порядке пока лишь предложен, не выполнялся.
