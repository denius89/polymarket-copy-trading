## 1. Единые типы и транспорт

U — канонический UUIDv4, V — положительная десятичная строка в пределах signed bigint, T — UTC Z/миллисекунды. Все поля обязательны, если явно не названы nullable/вариантными. Все перечисления закрыты; нет произвольных пользовательских сообщений. Body всех новых Auth/guest POST: до8192 байт/глубина8, JSON/Origin/X-Shadow-Auth-Request:1 и правила разбора PR №199. Только WebAuthn registration ответ требует явно отдельного предела65536 байт, поскольку attestationObject может не поместиться в8192; это отдельная предлагаемая transport-дельта, не молчаливое изменение Auth-профиля. Authentication assertion остаётся8192. Все GET без тела, query ровно requestSchemaVersion=v1, если не оговорено иное. POST без query. No-store/отсутствие секретов в URL/логах обязательны.

Каждое body включает requestSchemaVersion=v1; далее таблицы перечисляют только остальные поля. Action задаёт маршрут, не поле commandType. Новые операции имеют operationId:U, область environment/контекст/action/operationId. Повтор с другими полями409 KEY_REUSE_CONFLICT, exact replay до условий нового исполнения при действующем допуске. Транспортный rate применяется до replay. Секретная часть сравнивается только закрытым механизмом [storage §3](backend-review-mechanisms.md).

Новый OperationReply имеет ровно operationRef,status,result,resolvedAt,observedAt,nextAction,nextActionParams; ref ровно contextId,operationId,action. GET результата200/resolved либо202/unresolved с result=null/resolvedAt=null. Для GET navigation всегда null/{}. Прямое выполнение неизвестного исхода503, не202/unresolved. Email accepted202 — сохранённый resolved результат отправки, не ожидание завершения. No result при ошибке; четырёхполевой error-конверт PR №199 сохраняется. Во всех операциях сначала proof/current access, затем replay/состояние; ID не proof.

Названия action/result этого проекта не добавлены в принятый реестр v5 до итогового принятия; их полный кандидатный перечень задают таблицы ниже. Новых reasonCode не требуется: INVALID_REQUEST, AUTH_REQUIRED/EXPIRED/REVOKED/VERIFICATION_FAILED, ACCESS_DENIED, RESOURCE_NOT_FOUND, AUTH_CONTEXT_STATE_CONFLICT, KEY_REUSE_CONFLICT, RATE_LIMITED, SERVICE_UNAVAILABLE, RECORD_UNAVAILABLE, два принятых cookie-recovery кода используются только в своих смыслах. Неизвестный формат серверной записи —503, клиентского запроса —400.

## 2. User MFA-management: контекст и свежий email

Других полей нет. Purpose не позволяет клиенту создать режим recovery: отсутствие серверного основания409. Enroll при действующем факторе409; disable без фактора409; reenroll с невыполненным admin reset409.

Ответ201: ровно mfaContext,observedAt,nextAction=null,nextActionParams={}. ## 3. Подготовка и подтверждение фактора

POST .../factor: body operationId; action=factor_prepare; только enroll/reenroll после email. Result200 ровно kind=mfa_factor_prepared,factorVersion,challengeId,challengeIssuedAt,challengeExpiresAt. Одна подготовленная версия на контекст, challenge5 минут в его пределах. Повтор не выпускает другой seed. Подготовленный фактор не допускается для обычного входа до подтверждения. Серверное состояние provider factor сверяется до успеха.

POST .../factor/secret: body operationId,factorVersion; action=factor_secret. Ответ200 ровно contextId,factorVersion,totpUri,secretExpiresAt,observedAt. TotpUri — сформированный сервером URI otpauth из подготовленного seed; клиент рисует QR локально, не отправляет URI внешнему генератору. Выдача только исходному подтверждённому контексту до его expiry/активации/отзыва. Ограниченная зашифрованная recovery-копия позволяет повтор исходного чтения; исторический GET операции возвращает только kind=mfa_secret_accessed,factorVersion,accessedAt, без URI/seed. После закрытия выдачи —409 AUTH_CONTEXT_STATE_CONFLICT, а не повторная подготовка фактора. Оба варианта ответа явно различаются, байтового replay секрета после закрытия не обещаем.

POST .../confirm: body operationId,challengeId,code; action=mfa_confirm. Сначала replay, затем pause/stage/current factor/challenge/expiry/code. Однократные steps разделяются по factor version и учитываются между login/management целями; нельзя повторно потребить код, использованный в другом назначении. Email-подтверждение привязано именно к этой операции. Для enrollment и disable приняты отдельные по user5 ошибок/15 минут; формат/technical failures не ошибки кода. Принятый профиль TOTP сохраняется.

| Purpose | Result подтверждённого200 | Последствия |
| --- | --- | --- |
| enroll | kind=mfa_enabled,factorVersion,completedAt | Старые login сохраняют прежние сроки; следующий новый вход требует TOTP |
| disable | kind=mfa_disabled,previousFactorVersion,completedAt | Фактор отключён и прежние login отозваны; полная выдача закрыта, следующий новый вход email-only |
| reenroll | kind=mfa_reenrolled,factorVersion,completedAt,login | Login ровно loginId,realm=user,completedAt,cookieRecoveryDeadlineAt; новый полный вход после подтверждённой активации |

Login.completedAt совпадает со временем полного нового входа, не обязательно со временем промежуточного provider action; cookieRecoveryDeadlineAt=min(login.completedAt+5min,context.expiresAt). Completion этого API не подставляется в старую форму C02: это собственный новый result. GET /api/auth/mfa/contexts/:contextId/operations/:operationId с query дополнительно action из таблиц — OperationReply; reenroll возвращает ту же историческую login-группу без cookie. POST того же пути /login-cookie, body requestSchemaVersion и action=mfa_confirm, выдаёт200 ровно login,observedAt,nextAction=null,nextActionParams={} и исходную cookie по тем же5min/first-Q01 условиям. Полный вход проверяется прежним Q01 с проверенным login header. Типы C01–C03 GET автоматически не расширяются.

После disable ограниченный proof этого контекста даёт только собственный результат до expiresAt; произвольный отозванный login не доказательство. После утраты/expiry proof результат можно читать новым полным login того же user по доказанной серверной связи, без выполнения. Если unknown disable не даёт завершить новый вход, отдельный путь чтения через заново подтверждённый email в recovery-only контексте предоставляет только outcome этой операции; сервер проверяет user identity и исходный context, не принимает email строку за proof. Точный маршрут POST /api/auth/mfa/result-contexts: body sourceContextId,authContextId; второй — действующий email-proven restricted контекст. Ответ201 ровно resultContextId,sourceContextId,createdAt,expiresAt,observedAt; proof-cookie __Host-shadow-mfaresult-<id>,10min в пределах authContext. GET /api/auth/mfa/result-contexts/:id/operations/:operationId с action=mfa_confirm только читает OperationReply. Не выдаёт cookie полного login, не снимает security transition. Provider-неопределённость503 либо202 результата, без нового изменения фактора.

## 4. Административный сброс пользовательского TOTP

Политика P-RESET предложена владельцу отдельным вопросом; до ответа **не принята**: свежий email пользователя + независимый заранее подтверждённый канал + два разных владельца, подтвердившие одну версию решения. Если независимого основания нет — сброс запрещён; паспортные документы не собираются. Контакт, впервые названный в обращении, не независимое основание. Человеческая проверка не криптографическое доказательство; остаточный риск социальной инженерии явно проверяет коллега. Никакой новый reset-grant сейчас не опубликован.

POST /api/auth/mfa/reset-requests: body authContextId,operationId. Нужен email-proven restricted context, где требуется утраченный TOTP; запрос не сбрасывает фактор. Ответ201/повтор200: resetRequestId,createdAt,observedAt,nextAction=null,nextActionParams={}. Внешний статус запроса не раскрывает staff/контакты или внутренние доказательства. GET /api/auth/mfa/reset-requests/:id при том же proof: resetRequestId,status=requested/under_review/completed/rejected,observedAt; это не полный login и не право reenroll до подтверждённого reset.

Staff POST /api/admin/auth/mfa-reset/cases: body operationId,resetRequestId,reasonCode=lost_authenticator,verificationEvidenceId:U; full staff+предлагаемое отдельное действие mfa_reset_review. Evidence ссылается на закрытый immutable документ проверки, не содержит секреты в API. Case: caseId,userId,factorVersion,decisionVersion,verificationEvidenceId,requiredApprovals=2,approvedBy:[staffId],status=collecting/authorized/executing/completed/rejected,createdAt,expiresAt,completedAt:T|null. Case живёт24h; отдельное passkey подтверждение5min, финальные обе approval не старше5min на начало выполнения. Это новые кандидатные сроки, вынесенные в общий review.

POST /api/admin/auth/mfa-reset/cases/:id/approval-options: body operationId,decisionVersion; ответ WebAuthn options §5, challenge связан с case/version/user/factor/evidence. POST .../approve: operationId,decisionVersion,challengeId,assertion; собственное approval не заменяет другого владельца. POST .../execute: operationId,decisionVersion; нужны актуальные reset-execute право и обе свежие approval, неизменная версия фактора; срок/отзыв перепроверяются при исполнении. Result200 ровно kind=mfa_reset_completed,caseId,userId,previousFactorVersion,completedAt. OperationReply GET /api/admin/auth/mfa-reset/cases/:id/operations/:operationId с action=case_create/approval_options/approve/reset_execute; current staff rights обязательны, старое approval не разрешает чтение.

До подтверждённого исполнения все прежние user login блокируются по принятому security-transition протоколу; дальнейший email даёт только обязательное reenroll. Неуспешное письмо не повторяет reset. Audit kinds-кандидаты: auth.mfa_reset_requested/reviewed/approved/completed; scopes и exact DB payload задаёт физическая дельта, они не подменяют существующий Q06-audit. Человеческое решение не прикрепляет рабочие proof/OTP к case.

## 5. Staff WebAuthn: точный профиль и формы

Основа — отдельный staff realm,10min context/5min challenge,8h/30min login, один активный login на principal. Кандидат технического профиля: WebAuthn L3, residentKey=required,userVerification=required, attestation=none; COSE ES256(-7) и RS256(-257) в порядке предпочтения. Синхронизированный passkey допустим на полигоне, две его копии не два независимых владельца. Origin/RP ID читаются из подписанного environment descriptor, браузер не задаёт их. Эти параметры — проект для проверки двух устройств, не доказанная совместимость.

POST /api/admin/auth/contexts: body только version. Ответ201: staffContext,observedAt,nextAction=null,nextActionParams={}. StaffContext ровно contextId,stage=ready/challenge/completed,createdAt,expiresAt,challengeId:U|null,challengeExpiresAt:T|null. Cookie __Host-shadow-staffctx-<id>, proof≥256bit, Strict/HttpOnly/Secure/Path=/, Expires fixed. GET того же context path/query v1 возвращает200; не выдаёт cookie.

POST /api/admin/auth/contexts/:id/options: body operationId; action=login_options. Новый challenge допускается при отсутствии unresolved verify и истечении предыдущего; replay возвращает старый. Результат200: kind=staff_authentication_options,challengeId,challengeExpiresAt,publicKey. PublicKey ровно challenge:base64url(32 bytes),rpId:string,timeout:integer ms<=300000,userVerification=required,allowCredentials:[]; пустой массив использует discoverable credential без публичного поиска staff по email.

POST .../verify: body operationId,challengeId,assertion; action=staff_login. Assertion ровно id,rawId,type=public-key,response,clientExtensionResults={}; id=canonical base64url(rawId), rawId декодируется в1…1023 bytes. Response ровно clientDataJSON,authenticatorData,signature,userHandle (nullable base64url). Base64url без padding, canonical decode/reencode; clientDataJSON<=4096 bytes, authenticatorData<=2048, signature<=1024, userHandle<=64. Общий body-limit8192 сильнее суммы отдельных максимумов. ClientDataJSON проверяет type=webauthn.get, точные challenge/origin; crossOrigin допускается только отсутствующий/false, topOrigin отсутствует. COSE/public key читается из доверенной записи credential, не из assertion. Credential.active, userHandle↔principal, UV/UP, RP hash, sign counter/backup flags проверяет библиотека; zero/synced counter не отключает одноразовый server challenge. Неизвестное extension поле не принимается молча.

Успех200: корень completion,observedAt,nextAction=null,nextActionParams={}; completion ровно contextId,operationId,loginId,realm=staff,completedAt. До результата атомарно сменить staff slot и отозвать прежний login; поздний replay не меняет слот снова. GET .../operations/:operationId?requestSchemaVersion=v1&action=login_options/staff_login — OperationReply. Results: options выше; kind=staff_login_completed,completion; kind=verification_rejected,reasonCode=AUTH_VERIFICATION_FAILED. Нет user C02 или пользовательского completion в этом namespace.

GET /api/admin/me?requestSchemaVersion=v1: full staff cookie + X-Shadow-Login-Id; ответ200 ровно authenticated=true,staff={staffId:U},observedAt,nextAction=null,nextActionParams={}; успешный проверенный X-Shadow-Login-Id. Не выдаёт роль/все grants или клиентские данные. Первое успешное чтение закрывает5min staff cookie recovery. POST /api/admin/auth/contexts/:id/operations/:operationId/login-cookie с action=staff_login использует тот же исходный proof и окно min(5min,contextExpiry); возвращает completion-envelope и ту же cookie, current staff/slot обязателен. Старый slot не восстанавливается. Это явный отдельный проект staff recovery, не автоматическое применение user endpoint.

Staff logout использует маршруты /api/admin/auth/logout-contexts, /api/admin/auth/logout, /api/admin/auth/logout-contexts/:id/operations/:op и /api/admin/auth/logout-contexts/continue. Формы строго как user logout PR №199 с realm=staff, staff proof/principal вместо user; authorizationMode=original_login/current_staff (не current_user). Cookies __Host-shadow-stafflogoutctx-<id>; исходный staff login цель, новый staff login того же principal только доказательство продолжения, прежние15min/5s/3 и30 запросов сохранены. Ни одно user credential здесь не подходит.

## 6. Первичная регистрация и восстановление владельцев

Bootstrap разрешается только по закрытому подписанному manifest: environment,bootstrapVersion,два существующих staffId с двумя независимыми enrollment handles,точный RP/origin,approvedGrantsHash,expiresAt. Каждый handle —256bit секрет, передаётся отдельным согласованным каналом, хранится HMAC-digest, однократен/24h. Публичного bootstrap enable нет. Проверка реальных двух людей делается до выдачи по доверенной процедуре; UUID/два браузера не доказывают этого. Infra-оператор и право публикации manifest отдельно от Owner-роли. Без назначенных реальных участников bootstrap не выполняется.

POST /api/admin/auth/bootstrap/contexts: body bootstrapHandle (секрет только body),operationId; ответ201 ограниченный registrationContext {contextId,purpose=bootstrap,createdAt,expiresAt}. Cookie __Host-shadow-staffreg-<id>,10min. POST .../:id/options body operationId: result kind=staff_registration_options,challengeId,challengeExpiresAt,publicKey. PublicKey ровно challenge,rp={id,name=Shadow},user={id:opaque64byteMax,name:opaqueHandle,displayName:обезличенное обозначение},pubKeyCredParams:[{type=public-key,alg=-7},{type=public-key,alg=-257}],timeout=300000,attestation=none,authenticatorSelection={residentKey=required,userVerification=required},excludeCredentials:[{type=public-key,id}]. Credential IDs берутся только этого staff. Никакого личного email в RP/user displayName.

POST .../:id/verify: body operationId,challengeId,credential. Credential ровно id,rawId,type=public-key,response={clientDataJSON,attestationObject},clientExtensionResults={}; canonical base64url, id/rawId равны; clientDataJSON<=4096,attestationObject<=32768 bytes, общий лимит65536, Cose key/flags проверяет адаптер. Result200 kind=staff_credential_registered,credentialRef:U,completedAt; это не login. Однократное принятие handle, запись credential/userHandle, полномочия manifest и результат согласуются по storage-протоколу. Затем новый обычный staff login.

Recovery codes-кандидат:10 личных кодов по160 случайных бит в base32 uppercase без padding,32 символа; визуальные дефисы через8 символов разрешены только UI, API принимает32 A–Z/2–7. Хранятся HMAC с отдельным purpose/key, не plaintext. Подтверждённая сервером новая выдача после свежего staff passkey подтверждения атомарно отзывает старый набор; клиенту предлагается сохранить новый. Подтверждение интерфейса не возвращает старый набор и не является границей отзыва. Ограниченная зашифрованная выдача5min позволяет повтор при потере ответа; после истечения новый просмотр невозможен. Сам код при успешном допуске расходуется атомарно с собственным recovery result, никогда не логируется.

POST /api/admin/auth/recovery/contexts: body operationId,recoveryHandle:U,recoveryCode; handle выдан вместе с кодами и лишь выбирает principal. Cookie __Host-shadow-staffrecovery-<contextId>, ограниченный контекст24h, без админки. Ответ201/повтор200 ровно recoveryContext={contextId,subjectStaffId,requestVersion:V,status=limited/awaiting_approvals/committing/completed/expired,createdAt,expiresAt},observedAt. Неверные code/handle дают одинаковый AUTH_VERIFICATION_FAILED без раскрытия аккаунта;5 неверных/15min по доказуемому handle и ограничение источника, не блокировать живой staff login чужими запросами. Точные внешние anti-abuse пороги — §8.

Регистрация нового ключа в recovery использует те же /options и /verify формы под /api/admin/auth/recovery/contexts/:id/credentials, но credential остаётся ограниченным. Другой owner подтверждает tuple subjectStaffId/contextId/requestVersion/newCredentialRef через fresh passkey5min и текущие права. Для двух потерянных owners POST /api/admin/auth/recovery/pairs с body operationId,firstContextId,secondContextId требует proofs обоих ограниченных contexts, двух разных principals; создаёт pairId/version и объединяет точные два credential refs. Обе стороны подтверждают один tuple своими новыми ограниченными ключами, не произвольным полем approved=true.

POST recovery context либо pair /approval-options и /approve: version,operationId и assertion/challengeId для approve; schemas §5. POST /complete: operationId,requestVersion; result kind=staff_recovery_completed,recoveryId,requestVersion,completedAt. Два owner-grant/ключа в pair становятся пригодны только после общего завершения; никакого частичного full login. Старые ключи/login отозваны, затем обычный вход. GET /operations/:op с action выдаёт только статус своей процедуры, secret-free; без proofs/действующих прав доступ закрыт. Expiry24h закрывает новые подтверждения, но не откатывает committing. Изменение ключа/участника повышает version и сбрасывает все approval. Fresh approval5min ограничивает начало complete; потеря ответа не требует повторно тратить код.

## 7. Постоянный guest до draft и email-link

Guest не user Auth-context. POST /api/guest/contexts: body только version, Origin/header/JSON; не создаёт draft/CMD. Ответ201 ровно guestContext={guestContextId:U,createdAt,expiresAt,accessConfirmed=false},observedAt,nextAction=null,nextActionParams={}. Cookie __Host-shadow-guestctx-<id>,256bit proof, Secure/HttpOnly/Strict/Path=/, Max-Age=2592000 (30 дней браузерного хранения, не30 дней доступа). Server expiry исходно7 дней; доказанная C04-правка продлевает его как минимум до собственного draft.expiresAt в той же локальной транзакции. Это отдельный проект lifecycle гостя, не продление draft чтением.

GET /api/guest/contexts/:id требует cookie, возвращает ту же форму с accessConfirmed=true и текущим expiry. X-Shadow-Guest-Context-Id выбирает proof для guest Q02/C04; наличие X-Shadow-Login-Id выбирает user и при неуспехе не даёт fallback в guest. Перед первым C04 требуется подтверждённый guest GET. Чистый Q02 не создаёт постоянную business запись. Guest ID — прежний actor_guest_context_id, сохраняется при обновлении proof/кнопке языка.

POST /api/guest/contexts/:id/refresh: body operationId; только живой proof, тот же секрет/ID, без rotation; result kind=guest_context_refreshed,guestContextId,expiresAt=confirmedRefreshAt+7d. Exact replay сохраняет expiry, не продлевает. C04 срок может быть больше — max прежнего и нового. Cookie30 дней от текущей выдачи, поэтому запоздалый короткий server expiry не укорачивает серверное право; сервер всегда проверяет актуальный expiry. Limits3/60 на контекст. Expiry/loss не восстанавливаются по публичному ID; уже claimed результат user читает через прежнюю цепочку. До первого C04 при потере create-response можно явно создать новый пустой guest; после unknown C04 новый guest не заменяет исходный scope. Сам refresh не меняет draft/review TTL/ошибки/ключи. Отзыв guest запрещает новый guest-доступ, но не удаляет историю и независимое user владение.

Email-link — альтернативная передача того же email challenge C01/C03, без новой отправки/счётчиков. GET ссылки ничего не потребляет и не входит. Link token≥256bit, привязан к purpose/context/challenge и тому же10min сроку; secret только во fragment, не query, landing имеет no-referrer/no-store/без сторонних скриптов. Браузер после явного действия передаёт token POST /api/auth/email-link/verify: body authContextId,authOperationId,challengeId,token; исходный context proof обязателен, action отдельный AUTH_EMAIL_LINK_VERIFY с теми же результатами C02. На другом устройстве без proof предлагается обычный новый вход, token не переносит контекст/claim. Потребление ссылки или кода закрывает оба способа challenge атомарно; TOTP не обходится. Добавление этого Auth-only типа/результатов в реестр — отдельная явная дельта этого проекта.

## 8. Бюджеты, лимиты, активность и cookie

Существующие принятые числа не переопределяются. Для новых management/staff операций: чтение и подготовка5s/одна попытка; внешнее подтверждение/изменение Auth10s без автоматического неизвестного повтора. HTTP limits отдельно: context/options/secret/preparation3/60s по environment+доказанный principal+purpose; confirm/approve/execute10/60s по тому же scope; GET30/60s; счётчики TOTP/email более строгие и не заменяются HTTP rate. Для неизвестного staff/guest bootstrap до доказанной личности —20 preparations/15min на сеть источника (IPv4 /32, IPv6 /64) плюс глобальный1000/15min на среду; IP не доказательство личности. Доверенный ingress определяет адрес, клиентский X-Forwarded-For не принимается. Эти пороги — кандидатные настройки полигона, не измеренная ёмкость.

Full login cookie Expires=исходный absolute expiresAt (user30d/staff8h), без продления refresh. Idle только серверный. Для выбранного login cookie не переименовывается при refresh; поздний replay не создаёт новый deadline. Контекстные proof cookies имеют свои fixed expiry, удаление только выбранного имени. На выдачу нового контекста ограничение8 одновременно живых contexts каждого purpose на подтверждённого principal; превышение429, живые pending не вытесняются. Для анонимных контекстов браузерный лимит8 только дополнительная защита, не заменяет сетевой rate; чужие cookie не вычищаются. Лимит не ограничивает принятые независимые user login и не отзывает их.

Foreground не определяется одним флагом клиента. POST /api/auth/activity-contexts, body routeCode из закрытого списка user_catalog/user_setup/user_review/user_session либо staff_session_view и targetId:U|null; соответствующий действующий login и доступ к цели, ответ201 activityContextId/expiresAt=now+30s/observedAt. Одноразовый серверный билет в X-Shadow-Activity-Id допускается ровно одному последующему разрешённому Q02/Q03/C05/Q04 либо Q06 соответственно; форма прежних query/body не меняется. C04 с изменением/C06, инициированные пользователем, могут touch в своей транзакции без билета. Автопросмотр/Q01/refresh/poll/observer не touch. Staff Q06 касается только staff idle, не target user. Билет не доказывает физическое присутствие человека: он ограничивает серверно принятый набор интерактивных действий; клиентский запуск остаётся trust boundary, отдельно отмеченной в threat review. Нельзя обещать защиту от автоматизации действующим авторизованным браузером. Прямой доступ к provider endpoints вне backend/ingress закрыт, включая самостоятельный email/TOTP/refresh/disable и публичную регистрацию staff.

## 9. Проверка точности и границы

Для всех новых proof-cookie в этом проекте, где параметры не повторены рядом с маршрутом: Secure/HttpOnly/SameSite=Strict/Path=/, без Domain; Expires равен expiresAt собственного контекста. Каждый proof проверяется вместе с типом контекста и средой. Одинаковый UUID в другом namespace не допускается.

Уточнение маршрутов §6: одиночное восстановление использует `/api/admin/auth/recovery/contexts/:id/approval-options`, `/approve`, `/complete` и `/operations/:operationId`; парное — те же суффиксы под `/api/admin/auth/recovery/pairs/:id`. Везде поле версии называется requestVersion; сокращённое «version» в описании означает только requestSchemaVersion=v1 плюс requestVersion:V. Pair creation возвращает201 ровно pairId:U,requestVersion:V,firstContextId:U,secondContextId:U,createdAt:T,expiresAt:T,observedAt:T; expiry=min(expiry обоих контекстов). Approval-options возвращает200 kind=staff_recovery_approval_options,challengeId:U,challengeExpiresAt:T,publicKey по §5. Approve возвращает200 kind=staff_recovery_approved,recoveryId:U,requestVersion:V,approverStaffId:U,approvedAt:T. Исторический GET — OperationReply с action=recovery_options/recovery_approve/recovery_complete; для пары нужны оба ограниченных proof, для одиночного — исходный proof либо текущий staff-допуск подтверждающего второго владельца. Право второго владельца ограничено своей approval, не выдачей чужого recovery-code.

Выдача резервного набора §6: POST `/api/admin/auth/recovery-code-contexts` с operationId, полный staff login; ответ201 contextId,createdAt,expiresAt,observedAt (10min), cookie `__Host-shadow-staffcodes-<contextId>`. POST `/:id/options` с operationId выдаёт kind=recovery_code_options,challengeId,challengeExpiresAt,publicKey по §5. POST `/:id/issue` с operationId,challengeId,assertion требует свежий passkey, не offline code; ответ200 ровно contextId,recoveryHandle:U,setVersion:V,codes:[ровно10 строк],issuedAt:T,secretExpiresAt:T,observedAt:T. Выдача нового набора/отзыв старого и несекретный результат атомарны; повтор исходного issue возвращает тот же набор только в5min окне и при живом proof, затем409 AUTH_CONTEXT_STATE_CONFLICT. GET `/:id/operations/:operationId` с action=recovery_code_options/recovery_code_issue — OperationReply, результат issue только kind=recovery_codes_issued,recoveryHandle,setVersion,issuedAt,secretExpiresAt, без codes. Все `/:id` здесь относятся к `/api/admin/auth/recovery-code-contexts/:id`. Будущий registry delta включает эти purpose/action/result явно.

Предлагаемые новые числовые сроки/лимиты, policy P-RESET, WebAuthn registration transport65536, гостевой lifecycle и activity-ticket — явно выделенные проектные решения. Они не проставлены задним числом как принятые в PR №199. Исторические v1 формы остаются прежними; при принятии этого пакета издание реестра должно добавиться отдельно, с перечислением новых action/result/purpose/аudit-kind, а не переписать v5.

Коллеге проверить каждый маршрут на форму proof/отсутствие утечек/replay/expiry/unknown и согласование с [storage](backend-review-mechanisms.md). Спецификация закрывает предложение по форме, но не доказывает enforcement/совместимость выбранных библиотек. Все будущие испытания — «не выполнялось».
