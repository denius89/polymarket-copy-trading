# Первый рабочий сценарий Shadow: проект до кода

Текущая конкретизация 27.10.2026: [проект самостоятельного размещения](self-hosting-plan.md). Основной рекомендованный кандидат — Supabase Auth и PostgreSQL на нашем сервере; Better Auth остаётся вариантом сравнения. Состав, обслуживание, SMTP и политика MFA ещё требуют решений. Код/миграции/развёртывание не поручены; облачный и самостоятельный Supabase различаются.

27.10.2026 · **Проект документов T0, без реализации.** Три решения приняты в [ADR-0062](../../decisions/0062_paper_first_modular_backend_and_first_slice.md). Таблицы, маршруты и технические механизмы ниже — предложения для реализации, не созданные БД/API.

Baseline: main `04f5981583b369a77a2c66ac6a8b6efce8b732ad` (PR №99). Локальные источники прочитаны 27.10.2026; Figma и API площадок в этой задаче заново не проверялись.

Уточнение 27.10.2026 после PR №100: **Supabase Auth согласован** в [ADR-0063](../../decisions/0063_supabase_user_auth_provider.md). Запрошена Google 2FA; предварительное понимание — Google Authenticator/TOTP. [Почта, параметры кодов и MFA](auth-policy.md) описаны отдельно: Amazon SES отклонён владельцем; Mailgun — следующий кандидат с проверкой допуска. Режим MFA принят: добровольное подключение для paper и обязательный второй фактор при новом входе после него. Восстановление при потере аутентификатора — через администраторов, которые решают, как выполнить сброс. Несколько устройств и обычный выход только из текущего login приняты. Числа email-кодов приняты; срок входа 30 дней / 7 дней без использования принят с возможностью изменения только для новых полных входов; последствия сброса 2FA приняты (старые входы закрыть, новый TOTP до полного доступа); технический регламент восстановления ещё открыт. Прочитаны официальные документы провайдеров; аккаунты и настройки не менялись.

**Допуск поставщиков остаётся открытым:** в Supabase AUP обнаружено ограничение unregulated gambling/wagering; пригодность Shadow не подтверждена. Выбор провайдера принят, но подключение/публичный запуск не допущены одним этим решением. [Подробности и варианты](auth-policy.md#0-пригодность-для-shadow-важнее-географии).

## Что согласовано простыми словами

- Первый рабочий выпуск использует виртуальные деньги.
- Делаем один серверный проект с отдельными модулями и общей PostgreSQL, без обязательного разбиения на микросервисы.
- Сначала пользователь входит, выбирает трейдера, задаёт fixed или %, проверяет настройки и отдельно запускает демо. Сотрудник с подходящим доступом видит **ту же сессию** в админке.

Это первый небольшой результат внутри выпуска. Пока он не умеет копировать сделки; после него идут учёт/копирование, данные площадок, жизненный цикл, административные операции и итоговая приёмка по [139](../../139_shadow_technical_implementation_plan_2026-10-27.md). Согласованный дизайн админки v1 не сокращается и не пересобирается.

## Граница первого среза

Входит: единый email-вход/регистрация, гостевой черновик и его возврат после входа, минимальный каталог/профиль с происхождением данных, fixed/% и числовая политика, review, один пустой paper-start, восстановление после reload, административное чтение и серверные права, журнал, устойчивый результат команды. RU/EN и mobile/desktop относятся к одному поведению.

Не входит: BUY/SELL, отмена, резервы реальных заявок, автоматический скор/ранжирование, изменение бюджета активной сессии, pause/stop/reset и полный отчёт, служебные переводы, приглашения/конструктор ролей, интеграция Telegram, деплой и live. Их контракты не подменяются заглушками «успешно». Текущая сессия с блокирующими остатками должна распознаваться при входе/попытке запуска даже до реализации управляющих команд.

Для внутренней приёмки — отдельный test-контекст с подписанным synthetic trader на каждой из двух площадок. Подготовленный пример — отдельный read-only контекст, не создающий пользовательскую сессию. Пригодность реального источника для paper не следует из учебного каталога: все профили ADR-0059 остаются выключенными до T4. Пользователь не должен видеть обещание работающего копирования, если сборщик не включён.

Разрешение создания test-сессии задаётся конфигурацией изолированной среды; оно не включается параметром браузера и не служит fallback при отказе реального источника. У test-сессии явно показаны происхождение данных и отсутствие подключённого копирования; lifecycle «активна» сам по себе не разрешает BUY.

| Решение | Предлагаемое направление | Кто/когда |
| --- | --- | --- |

| Защита входа и хранение | Одноразовость, общий счётчик попыток при resend, ограничение отправки/проверки; отдельные сроки кода, входа, черновика, review и receipt | Email OTP и срок login 30/7 приняты; срок draft 7 дней принят; срок review 10 минут принят; распознавание email принято; срок receipt, детали enforcement и удаления персональных данных ещё открыты |
| Сотрудник первого среза | Только разрешённый просмотр сессии по существующим назначениям v1; отдельная staff-аутентификация | Срок входа 8 часов / 30 минут без активности и один активный рабочий вход приняты. | Тестовый стенд | Изолированный dev/test без live-ключей и исходящих денежных команд | Размещение/бюджет/доступы согласовать отдельно; бесплатный Oracle ARM — кандидат, не выбранный или проверенный ресурс |
| Библиотеки и доставка обновлений | TypeScript/PostgreSQL приняты; конкретный web/API/DB stack, миграции и механизм обновления выбрать по совместимости | Техническое обоснование до T1, без нового продуктового согласования каждого пакета; актуальные версии проверить при выборе |

Не нужно заново обсуждать B/F/q/p/d, 3%, одну текущую сессию и строгий финал. Продакшен-схема частичных продаж, отчётность, recovery владельцев и score блокируют свои последующие этапы, а не написание этого проекта документов.

<a id="следующий-вопрос-исходная-зона-сессии"></a>

## Исходная зона сессии: принято

27.10.2026 · **Принято владельцем:** часовой пояс устройства с возможностью изменить до запуска. [ADR-0019](../../decisions/0019_daily_buy_limit_resets_at_session_local_midnight.md) уже задаёт полночь и закреплённую IANA-зону. Сейчас выбирается только способ её определения до запуска, не новое правило сброса лимита.

Принято: предложить именованную зону устройства, **показать её на проверке настроек вместе с временем обновления дневного лимита**, дать изменить до запуска и подтвердить запуском. Например: «Часовой пояс: Варшава (Europe/Warsaw). Дневной лимит обновляется в 00:00 по этому поясу». Не показывать один постоянный UTC-offset вместо зоны. Если определить/проверить зону не удалось — попросить выбрать, не подставлять скрытый UTC или географию по площадке.

При запуске сервер проверяет допустимую зону и сохраняет её в paper-сессии. После старта она фиксирована: поездка, другой браузер/телефон, язык и обычный повторный вход не меняют дневной интервал. После строгого завершения/сверки для новой сессии можно выбрать актуальную зону. Перенос незавершённых резервов через полночь сохраняется по ADR-0020; смена зоны не создаёт повторного лимита.

Это дополнение к review до реализации, не уже выполненная правка Figma/кода. Технические проверки: unknown/invalid zone, draft с другой зоной устройства после входа, смена пояса до подтверждения, одна зона на всех устройствах, DST/ближайшая местная полночь. Источник достоверного времени fills и пограничные случаи расчёта срока оценки остаются отдельными gates; сроки login/draft считаются отдельно и не становятся местными календарными сутками.

<a id="следующий-вопрос-срок-подтверждения-настроек"></a>

## Срок подтверждения настроек: принято

27.10.2026 · **Принято владельцем:** «Да, согласуем 10 минут». Экран проверки настроек (review) действителен 10 минут с момента серверной проверки. По истечении показать «Проверка настроек устарела. Проверьте условия ещё раз», сохранить введённые параметры и предложить обновить проверку. Обновление не запускает сессию: пользователь снова видит актуальные условия и отдельно нажимает «Запустить демо».

Изменение параметров, зоны или значимых условий требует новой проверки и до истечения 10 минут; сервер при запуске повторно проверяет актуальность и доступ. Чтение экрана не продлевает срок. Если запуск уже завершён, потерянный ответ восстанавливается по прежнему ключу команды/receipt: истечение review не превращает успех в новый запуск. Это срок готовности подтверждения, не TTL черновика, сессии или финансовой истории. Точная реализация и проверки границы/гонок остаются до кода.

<a id="следующий-вопрос-точная-граница-14-дней"></a>

## Точная граница 14 дней: принято

Правила email, попыток TOTP и добровольного отключения MFA приняты в [политике входа](auth-policy.md). 27.10.2026 · **Принято владельцем:** «Да, согласуем такой отсчёт 14 дней». Период оценки заканчивается через 14 календарных дней после запуска, в то же местное время сохранённой зоны сессии. Например, запуск 27 октября в 16:30 → граница 10 ноября в 16:30 в той же зоне. Неполный первый день не считать целым; поездка/другой телефон не меняют границу. Это календарный расчёт, не обязательно 14 × 24 часа при переходе DST.

При запуске вычислить и показать точную дату/время окончания и зону. Для редкого отсутствующего местного времени при переходе часов техническое предложение — первый допустимый момент после разрыва; для повторяющегося времени — первое вхождение. Сохранить вычисленный UTC deadline и использованную зону/правила расчёта, не пересчитывать незаметно уже начатую оценку. Эти пограничные правила тоже пока предложение и требуют тестов выбранной библиотеки.

На границе действует уже принятый ADR-0050: новые BUY/увеличения запрещены, остатки BUY запрашиваются к отмене с подтверждением, сокращения копируемых позиций продолжаются; нет принудительной продажи или освобождения unknown-резерва. История/обязательства сохраняются по ADR-0051/0052. Закрывается период оценки, не обязательно вся сессия. Точное правило времени исполнения и поздних fills остаётся отдельным контрактом; правило 7 календарных дней для достаточности этим решением не переопределяется. Код/Figma и фактические таймеры не менялись.

<a id="следующий-вопрос-пауза-и-срок-оценки"></a>

## Пауза и срок оценки: принято

27.10.2026 · **Принято владельцем:** «Да, согласуем паузу без продления срока». Пользовательская пауза не останавливает отсчёт 14 календарных дней и не переносит показанную дату окончания оценки. До подтверждения паузы и в состоянии паузы показывать это явно вместе с датой окончания. При возобновлении использовать оставшееся время, не создавать новую сессию или новый бюджет; пропущенные во время паузы BUY задним числом не исполнять. Это уточнение календарного срока, не изменение принятого действия Pause: новые позиции/увеличения запрещены, сокращения и защитные закрытия продолжаются.

На исходной границе действуют ADR-0050/0051: период оценки завершён, новые BUY запрещены, обработка существующих обязательств продолжается. Если достаточности нет — «Недостаточно данных», без выдуманной оценки. Отключение входа/закрытие браузера и технические простои не объявляются пользовательской паузой; отдельные правила качества данных/инцидентов не приняты этим решением. Код, таймеры и Figma не менялись.

<a id="следующий-вопрос-почта-первого-закрытого-стенда"></a>

## Почта первого закрытого стенда: принято

[Сроки staff-входа и один активный вход](auth-policy.md#13-одновременные-входы-в-админку-принято) приняты. 27.10.2026 · **Принято владельцем:** «Да, согласуем тестовый почтовый ящик для первых внутренних проверок». Для первых внутренних тестов подключить к Auth локальный тестовый SMTP-приёмник без пересылки наружу. Он принимает письма в изолированном dev/test и позволяет уполномоченному тестировщику увидеть код, проверить срок, одноразовость, resend и пройти вход. Только синтетические тестовые аккаунты/адреса; реальные пользователи и их почтовые коды в этот режим не допускаются.

Просмотр тестовой почты доступен только разрешённой команде в закрытом контуре, без публичного интерфейса и без OTP в репозитории, общих логах или демонстрационных материалах. Исходящая внешняя доставка выключена. Сам способ входа не обходится: команда читает письмо из тестового приёмника и вводит обычный код, а не получает универсальный код/скрытую кнопку авторизации.

Это временный способ разработки, не выбранный сервис рассылки, не доказательство доставки/антиспама/допуска поставщика и не разрешение публичного запуска. Реальный SMTP, домен, ограничения поставщика, расходы и доставка остаются отдельным gate до испытаний с внешней почтой и реальными пользователями. Конкретный приёмник/версия и сетевое ограничение подлежат технической проверке до подключения; ничего не установлено и не отправлено.

## Следующий вопрос: доступ к первому общему стенду

27.10.2026 · **Предложение, ещё не принято:** первый общий dev/test-стенд доступен только явно приглашённой команде через защищённую частную сеть/VPN, без открытого публичного входа по ссылке. Каждый человек получает свой отзывной доступ, без общего пароля/универсальной ссылки. После сетевого допуска пользователь всё равно проходит вход в приложение, а сотрудник — принятую staff-аутентификацию и проверку назначений; VPN не выдаёт роли и не заменяет ключи.

Тестовая почта, БД, служебные панели и админка не публикуются в интернет. Сетевой доступ к стенду не означает прямого доступа к БД/тестовой почте/серверу: эти возможности только у отдельно допущенных исполнителей. Для внешней демонстрации позже отдельно определить состав, защиту и данные. Существующие ссылки Figma/документация и правила будущего публичного продукта не меняются.

Конкретное решение VPN, его условия/регион/стоимость, список участников, размещение сервера и процедура восстановления доступа остаются до подключения. Это граница первого закрытого стенда, не покупка, развёртывание или фактическая выдача сетевых прав. Проверить отсутствие публичных обходных адресов/портов, независимый отзыв каждого участника и сохранение авторизации приложения.

## Как принять первый результат

Один пользователь запускает демо с B=$200; клиент и разрешённая админка показывают один sessionId, одну версию настроек и один snapshot: свободно $200, резерв $0, позиции $0. Повтор, две вкладки и обрыв связи не создают вторую сессию или финансирование. Чужой пользователь и сотрудник без назначения ничего не узнают об этой сессии. Всё это должно быть подтверждено реализованным приложением и настоящей БД, а не макетами.

Текущая проверка пакета: прослежены ADR/числовые примеры, взаимные ссылки, граница полномочий и сценарии сбоев; выполняются проверки репозитория. Критерии приложения пока **не выполнены**, потому что код по поручению не пишется.
