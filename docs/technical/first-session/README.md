# Первый рабочий сценарий Shadow: проект до кода

27.10.2026 · **Проект документов T0, без реализации.** Три решения приняты в [ADR-0062](../../decisions/0062_paper_first_modular_backend_and_first_slice.md). Таблицы, маршруты и технические механизмы ниже — предложения для реализации, не созданные БД/API.

Baseline: main `04f5981583b369a77a2c66ac6a8b6efce8b732ad` (PR №99). Локальные источники прочитаны 27.10.2026; Figma и API площадок в этой задаче заново не проверялись.

## Что согласовано простыми словами

- Первый рабочий выпуск использует виртуальные деньги.
- Делаем один серверный проект с отдельными модулями и общей PostgreSQL, без обязательного разбиения на микросервисы.
- Сначала пользователь входит, выбирает трейдера, задаёт fixed или %, проверяет настройки и отдельно запускает демо. Сотрудник с подходящим доступом видит **ту же сессию** в админке.

Это первый небольшой результат внутри выпуска. Пока он не умеет копировать сделки; после него идут учёт/копирование, данные площадок, жизненный цикл, административные операции и итоговая приёмка по [139](../../139_shadow_technical_implementation_plan_2026-10-27.md). Согласованный дизайн админки v1 не сокращается и не пересобирается.

## Граница первого среза

Входит: единый email-вход/регистрация, гостевой черновик и его возврат после входа, минимальный каталог/профиль с происхождением данных, fixed/% и числовая политика, review, один пустой paper-start, восстановление после reload, административное чтение и серверные права, журнал, устойчивый результат команды. RU/EN и mobile/desktop относятся к одному поведению.

Не входит: BUY/SELL, отмена, резервы реальных заявок, автоматический скор/ранжирование, изменение бюджета активной сессии, pause/stop/reset и полный отчёт, служебные переводы, приглашения/конструктор ролей, интеграция Telegram, деплой и live. Их контракты не подменяются заглушками «успешно». Текущая сессия с блокирующими остатками должна распознаваться при входе/попытке запуска даже до реализации управляющих команд.

Для внутренней приёмки — отдельный test-контекст с подписанным synthetic trader на каждой из двух площадок. Подготовленный пример — отдельный read-only контекст, не создающий пользовательскую сессию. Пригодность реального источника для paper не следует из учебного каталога: все профили ADR-0059 остаются выключенными до T4. Пользователь не должен видеть обещание работающего копирования, если сборщик не включён.

Разрешение создания test-сессии задаётся конфигурацией изолированной среды; оно не включается параметром браузера и не служит fallback при отказе реального источника. У test-сессии явно показаны происхождение данных и отсутствие подключённого копирования; lifecycle «активна» сам по себе не разрешает BUY.

## Что осталось выбрать до кода соответствующей части

| Решение | Предлагаемое направление | Кто/когда |
| --- | --- | --- |
| Вход пользователя | Passwordless код + сохранённая возможность одноразовой ссылки; защищённая cookie, серверный выход/отзыв | Подготовить выбор провайдера/почты, стоимость и ограничения; владелец согласует сервис/расходы, технические параметры безопасности фиксируются до T1 |
| Защита входа и хранение | Одноразовость, общий счётчик попыток при resend, ограничение отправки/проверки; отдельные сроки кода, входа, черновика, review и receipt | Конкретные TTL/cooldown/лимиты, email canonicalization и срок удаления персональных данных — открыты; без них auth/draft не принимаются |
| Сотрудник первого среза | Только разрешённый просмотр сессии по существующим назначениям v1; отдельная staff-аутентификация | Владелец определяет людей и области доступа; способ входа/ключи и отзыв — до включения admin API. Учебный role picker запрещён как реальная авторизация |
| Тестовый стенд | Изолированный dev/test без live-ключей и исходящих денежных команд | Размещение/бюджет/доступы согласовать отдельно; бесплатный Oracle ARM — кандидат, не выбранный или проверенный ресурс |
| Библиотеки и доставка обновлений | TypeScript/PostgreSQL приняты; конкретный web/API/DB stack, миграции и механизм обновления выбрать по совместимости | Техническое обоснование до T1, без нового продуктового согласования каждого пакета; актуальные версии проверить при выборе |
| Время сессии | Хранить UTC и закреплённую IANA-зону, показывать её при проверке | Правило местной полуночи принято; выбор/подтверждение исходной зоны и точная граница 14 дней ещё требуют определения до включения зависимого поведения. В тестах зона/clock задаются явно, скрытый UTC-default запрещён |

Не нужно заново обсуждать B/F/q/p/d, 3%, одну текущую сессию и строгий финал. Продакшен-схема частичных продаж, отчётность, recovery владельцев и score блокируют свои последующие этапы, а не написание этого проекта документов.

## Как принять первый результат

Один пользователь запускает демо с B=$200; клиент и разрешённая админка показывают один sessionId, одну версию настроек и один snapshot: свободно $200, резерв $0, позиции $0. Повтор, две вкладки и обрыв связи не создают вторую сессию или финансирование. Чужой пользователь и сотрудник без назначения ничего не узнают об этой сессии. Всё это должно быть подтверждено реализованным приложением и настоящей БД, а не макетами.

Текущая проверка пакета: прослежены ADR/числовые примеры, взаимные ссылки, граница полномочий и сценарии сбоев; выполняются проверки репозитория. Критерии приложения пока **не выполнены**, потому что код по поручению не пишется.
