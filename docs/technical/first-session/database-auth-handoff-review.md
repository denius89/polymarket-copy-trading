## 3. Две обязательные границы согласованности

### Q01 и восстановление cookie

Принятое правило бэкенда: первый успешный Q01 надёжно закрывает окно повторной выдачи исходной cookie. Это отдельный служебный факт Auth, не foreground-активность, не новый login и не изменение бумажной сессии. JSON Q01 прежний, заголовок X-Shadow-Login-Id содержит проверенный login. Исторический recovery deadline не переписывается закрытием окна.

Будущий протокол должен показать обе очередности Q01/recovery, сроки и отзыв, а также потерю ответа/неизвестную фиксацию. Если результат обязательной фиксации не установлен, нельзя обещать успешное защищённое чтение с заведомо неизвестным закрытием окна. Это требование к механизму, не объявление готовой распределённой транзакции. Поздняя доставка уже разрешённой cookie не должна оживлять отозванный login; строгий порядок выдачи/закрытия должен определить Auth-адаптер. Одного last_user_activity_at недостаточно, и продление idle ради фиксации запрещено.

### Claim после утраты proof и неизвестного исполнения

Разделяются три факта: (1) действительность proof для **нового исполнения**; (2) серверная историческая связь consent, разрешающая ограниченное **чтение исхода**; (3) завершённый неизменяемый результат передачи. Expiry закрывает (1), но само по себе не удаляет (2)/(3). Новый полный login того же постоянного user допустим для принятого чтения исхода; GET самого claim-context имеет другой допуск и срок.

Наличие результата даёт HTTP200 по проверенной цепочке. Доверенная область поиска без окончательного исхода даёт202 только по принятому Auth-допуску, не по знанию draftId. Недоступность источника503, повреждение RECORD_UNAVAILABLE, чужая цель скрыта. Новый consent не становится вторым ключом dedup; текущий receipt/unique сохраняются.

Для нового исполнения после unknown отдельно нужно исключить позднее завершение прежнего. Даже если временный guard сейчас свободен, ранее допущенный запрос мог ещё не достичь его. Поэтому чтение пустого receipt под guard без протокола допуска/завершения не доказывает отсутствие будущего эффекта. Рекомендуется сперва документировать жизненный цикл всех исполнителей, способ закрытия прежнего допуска и проверяемый барьер перед новым; выбор места хранения и механизма — BA-G06, не решён этим ответом. Лимиты/срок consent не заменяют этот барьер. C04, его ключи и строгий C06 не затрагиваются.

Для каждого факта нужны постоянный ключ, trusted writer/reader, срок допуска отдельно от хранения, уникальность, атомарная граница, revoke/unknown/restore и безопасное хранение/удаление секретов. Начать с этой карты до выбора конкретных новых таблиц и их числа.

Это предложение очереди, не утверждение новой физической схемы. Недостающие DTO/guest/selector и право admin reset должен закрыть бэкенд; новые сущности или изменения допуска согласовываются отдельно. Владелец 1 и владелец 2 равноправны. История ADR-0064, принятия C04/карты ошибок и гарантии C06 сохранены. Отправка сообщения бэкенду не выполняется автоматически; реализация/SQL/миграции/испытания отдельным поручением.
