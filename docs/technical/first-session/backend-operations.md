# Доставка, ограничения БД, время и восстановление — H04–H06

29.10.2026 · **Блок принят целиком**, включая параметры worker, кандидатов компонентов и дополнение копирования журналом WAL. Часть [пакета бэкенда](backend-design.md). Системы не устанавливались, SQL/миграции не созданы, испытания не выполнялись. Сохраняются [data-model §22–23](data-model.md), [физическая схема](database-backend-handoff.md) и [self-hosting plan](self-hosting-plan.md).

## 1. H04: локальная доставка

Отдельный worker, один зарегистрированный paper_start_observer. Эффект — подтвердить наблюдение исходного старта; не создаёт session/funding/snapshot и не отправляет email/Telegram/торговую команду. C06 отвечает после собственного commit, не ожидая worker.

| Параметр | Принятое начальное значение |
| --- | --- |
| Проверка пустой очереди | Раз в 1 секунду |
| Параллельность одного worker | Одно событие |
| Lease | 30 секунд |
| Продление lease | Отключено для этого короткого локального потребителя |
| Общий бюджет обработки после захвата | 5 секунд, включая ожидания БД |
| Одно ожидание блокировки | До 1 секунды и не более оставшегося общего бюджета |
| Общий предел попыток | 5 |
| Паузы после неудач 1–4 | 1 / 5 / 30 / 120 секунд |

Lease и допуск определяются серверным временем БД; бюджет процесса монотонный. Это отдельный бюджет от 3 попыток/5 секунд C06. Числа — настройки проекта для проверки на стенде, не измеренная производительность.

### Обработка

1. Короткая транзакция захватывает доступное событие, увеличивает attempt_count и сохраняет новый token/lease_until. Попытка существует после успешного сохранения захвата; падение после него расходует попытку.
2. Проверяются event type/format/consumer и исходные receipt/session/snapshot refs, среда и версии. Позднее событие не требует сделать исторический snapshot снова текущим.
3. В транзакции эффекта блокируется outbox и сверяется существующий consumer receipt.
4. Совпадающий сохранённый receipt имеет приоритет: восстановление только завершает служебную доставку, без повторного эффекта.
5. Иначе проверяются текущий token/срок, сохраняется observed и processed вместе. Перед завершающим изменением проверка token/срока повторяется; блокировка удерживается до commit.

Действующий lock сам по себе не заменяет token/expiry и dedup. Просроченный обработчик не вправе завершать новую попытку или записывать last_error поверх неё. Unknown commit сначала выясняется по consumer receipt. Повреждённый receipt не считается отсутствующим.

Временный подтверждённый сбой → retry_wait по принятой паузе. При expiry пауза начинается не раньше lease_until. Пятая неудача/постоянная ошибка/неизвестный формат → needs_review без удаления. Но уже существующий согласованный receipt имеет приоритет и после пятого захвата: доведение служебного состояния до processed не является шестым эффектом. Needs_review не разрешает ручное переисполнение без отдельного разбора.

Scope/связи — outbox_events и consumer_event_receipts, без новой очереди/таблицы. При восстановлении из backup worker закрыт до §5, старые leases не перезапускаются автоматически.

### Проверка

Два worker; crash после claim и до/после commit; потерянный ответ; истёкший token; timeout на блокировке; пятая попытка с существующим/отсутствующим receipt; неверные refs/format/consumer. Во всех случаях FIN/CMD/start audit не растут от observer. Сверять не только количество, но scope/IDs/версии и отсутствие повторного эффекта. Основа A108–A109.

## 2. H05: компоненты и точная арифметика

Исходные **кандидаты для проверки**: PostgreSQL 17.11 и node-postgres pg 8.23.1. Поддерживаемая ветка PostgreSQL и выпуск драйвера подтверждены документацией 29.10.2026; совместимость с точной сборкой self-hosted Supabase Auth/Node.js/целевой архитектурой не испытана. Перед реализацией закрепить весь состав, зависимости, версии/хеши образов и проверить вместе. Наличие документа о версиях не разрешает установку.

| Область | Решение |
| --- | --- |
| Прикладные суммы | BigInt и сокращённые дроби, без промежуточного Number/float |
| Драйвер | Явное чтение/запись numeric и bigint строками; UUID/даты/JSON проверяются своим контрактом |
| DB numeric | Без округляющего scale; проверки конечности, целочисленности, знака, длины и сокращённости |
| Предел 64 цифры | Для сохраняемой пары; промежуточный результат может быть шире |
| Проценты | Сотые п.п. в БД, exact преобразование; не долларовый float |
| Version/sequence/generation | Внутри транзакции, без отдельного неоткатываемого sequence |
| Транзакция | Одно выделенное соединение от начала до окончания, не независимые pool.query |
| Unknown result | Свежая транзакция основного хранилища; не старый Serializable-снимок/отстающая реплика |

B110/p7 даёт P77/10; UI rounding не участвует. Проверка ошибки не округляет F до доступного лимита, не подставляет B200, не вводит минимум $5 для percent. Суммы начального ledger signed по счёту, бюджет положителен.

### Уровни ограничений

| Механизм | Ответственность |
| --- | --- |
| Тип/NOT NULL/CHECK/unique/FK | Локальные значения, допустимые варианты, scoped уникальность и составная принадлежность |
| Отложенные проверки до commit | Обязательная полнота, циклические ссылки, ровно две сбалансированные entries, snapshot↔settings/ledger, достаточно Q06 evidence |
| Разрешённые процедуры записи | Порядок locks, актуальный допуск/guards, разрешённые переходы, запрет редактирования опубликованной истории |

Проверки полноты запускаются также от родителя без детей. Нельзя проверять журнал только при вставке entry: иначе пустой journal прошёл бы. Обновление/удаление/дописание immutable истории закрыто рабочими правами и ограничениями. Точные triggers/FK/процедуры пока не написаны.

Критические C04, claim, C05, C06, staff-login replacement, Q06 и конкурирующие изменения guards используют Serializable. Сохраняется порядок: policy/catalog/control → principal/identity/access/login/assignment → command/claim key → user/staff slot → draft/ownership → session/финансовые записи/audit/outbox. Внутри группы полный стабильный ключ. Изменения детей повышают родительский guard; скрытые unique/FK locks требуют испытаний.

C06 автоматически повторяет только подтверждённые serialization failure/deadlock rollback в принятом бюджете. Unique violation разбирается отдельно свежим чтением; constraint bug не маскируется как retryable. Потеря связи при commit не означает rollback. Правила C06 не переносятся автоматически на прочие API.

### Роли БД

| Служебная роль | Граница доступа |
| --- | --- |
| Shadow API | Разрешённые операции и чтения, без произвольного DML таблиц |
| Worker | Захват/завершение событий, минимальное чтение исходных фактов |
| Auth | Собственное хранилище, без записи в финансовый ledger Shadow |
| Schema executor | Отдельная учётная запись для изменений схемы; не runtime API/worker |
| Backup | Отдельные полномочия выбранного физического копирования |
| Copy verifier | Изолированное чтение копии, без доступа к рабочей системе |

Runtime не владеет таблицами и не может отключать ограничения. Q06 проходит путь, согласующий данные и аудит, без обходного raw read. Проверка actor по полному входу остаётся доверенной границей сервера; DB FK не доказывает MFA. Конкретные имена ролей, privileges и процедуры уточняются при реализации, не новые продуктовые роли.

### Проверки

Использовать [S01–S16/N01–N22/K01–K07](database-synthetic-examples.md), затем полноту всех связей/циклов, A100–A107, гонки обоих допустимых порядков, минимальные роли и сбои около commit. Независимо сверять проводки/снимок и количество/IDs/guards. Query plans — scoped key, current slot, Q06 и due outbox на реалистичной истории; новые индексы только по проверенному запросу/ограничению.

M02: будущие блокирующие состояния — управляемая изолированная копия, без новой торговой функциональности. M03: последующая полная публикация/повреждение snapshot — отдельный тестовый путь/копия, без рабочей команды «сломать FK» или «освободить слот». Проверки репозитория не являются этими испытаниями.

## 3. H06: время

Кандидат для календарного расчёта — Temporal через @js-temporal/polyfill 0.5.1; upstream помечает выпуск prerelease. Его допуск требует отдельных календарных испытаний. Закрепляются Node.js, библиотека, ICU/фактическая tzdb и образ; нельзя считать версию базы зон известной по часам Mac или по одному имени библиотеки.

Алгоритм paper-evaluation-deadline-v1:

1. Серверный startedAt переводится в закреплённую IANA-зону.
2. К местной дате прибавляются 14 календарных дней, местное время сохраняется.
3. Единственное существующее время используется прямо; при повторе выбирается первое вхождение; при пропуске — первый существующий момент после пропуска.
4. Сохраняются UTC deadline, зона, версия алгоритма и фактическая timezone_database_version. Чтение, поездка, повтор команды или новая tzdb их не пересчитывают.

Стандартный Temporal compatible не заменяет правило gap: при переходе 02:00→03:00 целевые 02:30 могут стать 03:30, а принятое правило требует 03:00. Это отдельная ветвь алгоритма, без скрытой смены продукта.

Испытания: обычная дата, overlap, gap, получасовой переход, пропущенная календарная дата, UTC, граница миллисекунд, одинаковое повторное чтение после обновления tzdb. Ожидаемые значения фиксируются независимо от проверяемого builder. Если версия tzdb/зона не установлена достоверно, новый расчёт не выдаётся за доказанный.

Login/draft/review/lease проверяются по актуальному серверному времени БД после ожиданий; время начала транзакции не заменяет текущий момент. Общие бюджеты — монотонные. Конкретная дисциплина часов/таймаутов должна выдержать испытания; сохранённые даты только миллисекундной точности.

## 4. Совместимость и доказательства M05

Перед обновлением или возвратом сервера на изолированной согласованной копии выполняется **полный** обход всех сохранённых review/settings/snapshot/receipt. Реестр сверяется с фактически найденными форматами. Неизвестный формат/ошибка любой записи/незавершённый обход блокируют подтверждение. Для отсутствующего типа — «нет данных для проверки», не успех; отдельный synthetic test декодера не подменяет обход копии.

| Состав неизменяемого пакета прогона | Данные |
| --- | --- |
| Идентификация | Собственный ID, начало/окончание |
| Сборка | Приложение, схема, реестры, декодеры, зависимости |
| Копия | ID, точка данных, контрольный отпечаток |
| Полнота | Найденные пары тип/формат, обнаруженные/прочитанные количества, незавершённые участки |
| Ошибки | Тип/ID/формат/безопасный код без полного содержимого |
| Итог | Совместимо / несовместимо / проверка не завершена; «нет данных» отдельно по пустому типу |

Пакет — защищённые файлы вне восстанавливаемой БД, контрольные суммы и запрет перезаписи завершённого прогона. Новая прикладная report-таблица не требуется. Исправление — новый прогон/ID. Точное место, формат и права хранилища ещё закрепляются при подготовке эксплуатации; обычная публичная Git-папка не предполагается. Контрольная сумма подтверждает целостность относительно доверенного manifest, сама не доказывает происхождение.

Изменение приложения/схемы/набора форматов требует новой проверки. Возврат старого приложения разрешён только если оно читает всю текущую историю, включая новые форматы. Возврат программы не восстанавливает автоматически старую БД и не удаляет новые данные ради совместимости. Выпуск/изменение схемы/restore — разные процедуры.

## 5. Копии, WAL и барьер восстановления

Сохраняется принятое: ежедневные зашифрованные копии, последние семь успешных вне сервера; Mac допустим для первого стенда. **Дополнительно принято архивирование PostgreSQL WAL** для изменений между ежедневной физической копией и более поздней точкой.

- Согласованное физическое копирование охватывает Auth и Shadow; с каждой оставшейся копией сохраняется необходимая непрерывная цепочка WAL.
- Успех доставки — подтверждение получателя/целостности, не наличие локального файла на сервере.
- Недоступность Mac — видимый сбой; журнал только на потерянном сервере не гарантирует восстановление этого участка.
- WAL содержит чувствительные данные и защищается как backup.
- Версии конфигурации и необходимые ключи восстановления учитываются/резервируются отдельно защищённым способом. Секретов в обычном отчёте/Git нет.
- Семь копий не означают произвольное удаление их WAL-зависимостей. Расписание/папка/передача/ключи/обслуживающий исполнитель, периодичность доставки WAL и измеренные RPO/RTO ещё не проверены.

Порядок восстановления:

1. Изоляция; рабочие входы, новые команды и worker закрыты.
2. Проверка копии и непрерывности WAL; достижение подтверждённой точки.
3. Явное описание непокрытого периода и доверенных свидетельств после исходного backup.
4. Сверка ключей/receipt, владения/claim, slots/session/review/settings, funding/journal/entries/snapshot, outbox/consumer dedup.
5. Отдельная сверка изменений credentials/login/назначений/отзывов после исходной копии с доступными доверенными доказательствами. Старая запись сама не возвращает полномочия.
6. Полный обход форматов, безопасный неизменяемый отчёт.
7. Только после подтверждённой сверки — отдельное разрешение открытия соответствующих функций/worker.

При неполном доказательстве периода после backup отсутствующий receipt не означает «никогда не выполнялось». Нельзя повторно запускать/финансировать утраченный результат по предположению. Утраченные сведения об отзыве также не заменяются старым credential. Затронутые действия остаются закрыты; копия не обещает вернуть отсутствующие после backup данные.

Проверить: восстановление с backup до start и до revoke, непрерывный/оборванный WAL, недоступный получатель, ложное локальное «успешно», сохранённый consumer receipt при старом lease, недостающие credentials/config keys, неизвестный формат, read-only сверка и явное открытие. Условия открытия должны быть доказаны, не обходиться успешной распаковкой.

## 6. Хранение истории M04

В первом стенде не вводятся архив details и удаление outbox. Обязательные receipt/details, consumer dedup, родители и история сохраняются целиком. Неожиданное отсутствие строки — техническая недоступность, не архив. Это решение текущего этапа, не бессрочная универсальная политика хранения; будущая очистка требует отдельного совместимого протокола и проверенной копии.

## 7. Связь с карточками сбоев БД

[Пакет F01–F24](database-fault-reconciliation.md), опубликованный в PR №168, сохраняется: H04 конкретизирует зависимости F14–F16; H05 — ограничения и гонки F01–F13/F21–F22; H06 — форматы/restore/время F17–F20/F23. F05 получает отдельное расширение C04 из передачи БД. F24 остаётся зависимым от изолированных будущих состояний; архив в первом стенде не вводится. Карточки не отмечаются выполненными от принятия параметров.
