## 1. Основа, разрешение и результат

Проверено более позднее прямое поручение владельца в чате бэкенда от 03.11.2026: передать D02/v6 на сверку «с учётом принятия U01–U03 и схемы из 78 таблиц». Оно следует после прежнего указания чата БД пока не принимать U01–U03. Статус уточнён по человеческому сообщению, а не только по формулировке PR или сообщению другого агента. Отдельно проверено прямое разрешение на двусторонний обмен заданиями/замечаниями по D02/v6; изменение принятых правил остаётся за владельцем.

Текущая основа: **P01–P05/U01–U03 приняты; 78 =36 Shadow +42 Auth. D02/v6 — проект; текущий принятый реестр v5.** C04/last_input_receipt_id, карта ошибок, строгий C06 и равноправие владельца 1/владельца 2 не переоткрываются. Все изменения принятых гарантий требуют отдельного решения; техническая точность D02 не считается принятой автоматически вместе с U01–U03.

Итог первой адресной вычитки — **8 замечаний BDR01–BDR08**. Они касаются ошибок/обязательных ссылок, восстановления scope, условной полноты аудита и ещё не полностью заданных служебных/криптографических вариантов. Пакет нельзя считать полностью сведённым с БД до адресного ответа на них. Это не утверждение, что реализация уже содержит дефект: реализации и предметных испытаний нет.

## 3. Замечания и рекомендуемые исправления

### BDR01. Истечение challenge нельзя свести к одному401 для всех путей

**Источник:** D02 §7, строка «Текущий challenge истёк» (строка193 baseline); прежний Auth §6 (строка101). **Связи:** AC04/05/09/12; AS03/05/06; HR03/05/07; DA01/04, MAP01/07, HE04/09.

D02 задаёт общий401 AUTH_VERIFICATION_FAILED без bad-code increment и допускает окончательный rejected result. Прежний контракт для истёкшего TOTP challenge требует409 AUTH_CONTEXT_STATE_CONFLICT без проверки кода; email expiry имеет другой путь. Не обозначено, что общий ряд D02 не распространяется на уже принятый TOTP или какие именно новые verify-пути он покрывает.

**Контрпример документа:** действительный user Auth-context, текущий TOTP challenge уже истёк, запрос с новым operation ID. Читатель общей матрицы D02 может сохранить verification_rejected там, где прежний маршрут возвращает конфликт стадии/срока до проверки кода. Это меняет не только HTTP, но и допустимую AC05/counter дельту.

**Исправление:** развернуть таблицу по challenge kind/route: email, TOTP, WebAuthn; для каждой строки указать HTTP/reasonCode, создаётся ли AC05, меняется ли counter/challenge, порядок replay и expiry. Явно сохранить прежние пути user Auth. Новое поведение новых маршрутов отметить проектом D02, не распространить на старые автоматически.

**Согласование:** сохранение прежнего контракта — редакционное устранение расхождения; изменение принятого TOTP поведения требует владельца. Новый точный профиль D02 входит в пакетную вычитку.

### BDR02. Семейство результата не заменяет точную матрицу обязательных refs

**Источник:** реестр §1.1 (строка54), R14/R33/R36 и D02 §6. **Связи:** AC03/05/20/25–30; AS18/19/21/22; HR03/11–14; B10/B11, MAP01/07.

Формулировка «Reset/case/recovery → result_case_id/result_case_version_id» слишком широка для закрытой физической спецификации. `mfa_reset_requested` и `staff_recovery_context_created` возникают до создания case. Наоборот, `recovery_registration_verify` создаёт limited credential и single case одной T, а общая формула «credential registration → result_credential_id» не перечисляет отдельный обязательный case-комплект этой ветви. Ветка bootstrap registration не имеет такого case.

**Контрпример документа:** R33 успешно потребил code и создал limited context, регистрации credential ещё не было. Если применить общий ряд буквально, полнота требует выдуманный case/version; если трактовать его как необязательный для всего recovery, можно пропустить case после R36.

**Исправление:** таблица по конкретному result.kind и action/purpose: mandatory refs, разрешённые NULL, источник и обратный комплект. Отдельно context-before-case, case-create, bootstrap/recovery registration, approval, full completion, late outcome и rejected. Для reset-request сохранить вывод AC30 по исходному context/client-operation tuple, не добавлять фиктивную case-ссылку.

**Согласование:** уточнение уже описанного порядка создания без ослабления D; не новый продуктовый выбор. Если предлагается менять порядок/состав создания case — отдельное решение.

### BDR03. Исторический case-scope R42 после single→pair должен разрешаться однозначно

**Источник:** D02 R39–R42/§6 (строки86–89/177); реестр GET-whitelist (строка50); AC04 scoped unique и AC03 current case. **Связи:** AC03/04/05/25–28; AS03/22; HR03/14; B11, MAP01/07, DA12.

GET `K/{context}/operations/{op}?action=...` не содержит case/version, хотя operation identity включает security_case scope. SR может иметь исторический single case и затем общий pair case. Фраза «scope определяется сохранённой связью результата/версии» не задаёт resolver для отсутствующего AC05 и не исключает совпадающий client operation ID/action в двух разных cases: такая пара не нарушает AC04 unique, поскольку scope различается.

**Контрпример документа:** старые single approval-options разрешены одному SR; затем pair-create сохранил старый case и сменил current pointer. В pair допустим тот же клиентский UUID при том же action в другом scope. Поиску через K нельзя выбрать current case либо первую совпавшую запись и выдать её за исходный результат. Наличие P-пути само по себе не определяет, что обязан делать старый K-путь.

**Исправление, рекомендация:** явно закрепить K operation lookup за историческим single-scope этой процедуры, P — за своим pair-scope; указать постоянный источник привязки и поиск unresolved через AC04, не обязательный AC05. Либо предложить другой однозначный locator. Определить скрытый/неподходящий scope и запрет fallback на current pointer. Не расширять client operation uniqueness до глобальной ради обхода этой неоднозначности.

**Согласование:** пояснение однозначного уже хранимого resolver — уточнение D02. Новое wire-поле, физическая immutable привязка либо новая уникальность — явное техническое решение для владельца, если существующих refs недостаточно.

### BDR04. Полнота AC33 должна различать grant-действие и limited pair

**Источник:** единая схема AC32/33 (строки100–101); реестр §4 (строки137/154), D02 §6 pair completion. **Связи:** AC04/27/28/32/33; AS22/24; HR14/16; B11/B13, MAP07, DA12.

AC33 имеет обязательные assignment/grant поля и описывает точные selected approvals для final case event. D02 отдельно требует для limited pair системного actor, доказательства обоих участников через AC27/28 и AC33 только для реально использованных действующих grants; ordinary grant у limited pair не возникает. Без variant D остаются две несовместимые трактовки: фиктивные grant/SL для pair либо пропуск будто бы обязательного child.

**Исправление:** развернуть final audit по reset, single recovery, pair и собственному self-service. Grant-based действия должны иметь достаточные AC33; limited pair — полный exact AC04/28/27/contexts комплект с типизированным system event без фиктивного SL/grant. Указать число и смысл evidence, actor каждого доказательства и случай, когда reset executor одновременно один из approvers: права исполнения и независимые approvals не подменяют друг друга.

**Согласование:** согласовать два текста без потери доказательств можно как уточнение. Удаление обязательной гарантии аудита/двух независимых владельцев либо выдача limited context обычного grant требуют владельца и не рекомендуются.

### BDR05. Закрытый перечень служебных witness-переходов пока не дан

**Источник:** единая схема §§5.5/8 (строки224/289) прямо требует его в D02; D02 §6 atomic sets и реестр §4 audit перечисляют более общие группы. **Связи:** AC07/16/32–35/39–42; AS15/16/24–28; HR04/09/16/17; HE03/08/10; MAP06–08, B09/B13.

Не задана закрытая таблица для ack, drain/evidence, standalone erasure, Q01 closure и безопасного outcome finalizer: какой writer/какие поля, существующий batch/run либо новый root, обязательный closure и как исключается новый бизнес-эффект. Сам список audit-kind не отвечает на эти вопросы. Имеющиеся фразы «eraser связывается с существующим batch/run» и «отдельный erasure — root secret» нуждаются в точном совместном прочтении.

**Исправление:** таблица допустимых служебных операций с указанными источниками/targets, границей commit и привязкой witness. Различить standalone secret erase, Q01 window closure и чистый ack; исключить как незажурналированный защищённый эффект, так и рекурсивные свидетельства об ack. Не подставлять N=0 для неизвестного closure.

**Согласование:** детализация принятого P04 — D02; новое исключение из обязательного witness или новый bypass closed gate требует владельца. Это документальная зависимость, не проверка latency/runtime D03.

### BDR06. Новый proof-профиль требует нормативного кодирования до его проверки

**Источник:** D02 §5 (строка165), реестр §§2/3 (строки76/121). **Связи:** AC06/08/22–24/38; AS03/18/19/26; HR02/03/09/12/13; MAP01/08, DA01/12, HE04/07.

`derived-context-proof-v1` описан как HMAC по domain/env/kind/context/source и исходному secret с length-prefix, но не полностью фиксирует literal domain, байтовое кодирование и размер prefix, точный secret input для R29/R33/R43 и отдельную verifier-формулу. Для `auth-sensitive-compare-v1` кодирование значительной части уже определено, но literal domain назван описательно. Key-bundle с разными ключами полезен, однако его назначение само не задаёт одинаковые входные bytes.

**Риск:** два совместимых по смыслу writer/reader могут выдать разные proofs/tags при одной версии формата. Тогда replay перестаёт восстанавливать тот же context либо отвергает равное намерение. Test vectors не должны незаметно стать местом выбора самого контракта.

**Исправление:** один нормативный профиль или точная ссылка: literal domains, порядок/encoding/lengths, источник исходного secret по маршруту, key-bundle и purpose, verifier отдельно от derivation, допустимые сроки replay/erase. D03 затем проверяет это кодирование и библиотечные возможности. Новые реальные ключи/векторы/криптографические испытания сейчас не создаются.

**Согласование:** профиль уже выделен как дополнительное техническое предложение D02, а не автоматически принятая U01. Его точная редакция требует принятия пакета D02; семантика исходного proof/разделение ключей сохраняются.

### BDR07. Security incident не имеет полного fence/run-варианта

**Источник:** реестр §3 AC01 closure_reason (строка86); единая схема AC41 (строка114), fence/reopen и audit. **Связи:** AC01/32/41/42; AS15/16/25/26; HR01/17; HE08/10, MAP04–06.

Closure reason включает `security_incident`, но AC41 purpose допускает только claim_unknown с обязательным draft либо environment_restore без draft. Для самостоятельного incident, который не claim и не restore, нет названного полного run-варианта, хотя fence-транзакция и audit требуют reconciliation_run.

**Исправление:** либо явно зарезервировать incident без поддерживаемого writer до отдельной дельты, либо предложить конкретный новый run-purpose/NULL/инвентаризацию/открытие. Не маркировать обычный incident как restore/claim ради обхода закрытого словаря.

**Согласование:** ограничить новый проектный enum реально поддерживаемыми путями можно в рамках вычитки D02. Расширять принятую AC41/операционный протокол без отдельного решения владельца нельзя. Новое поведение здесь не выбирается.

### BDR08. Late reenroll должен иметь полный factor/security/audit/notification комплект

**Источник:** реестр mfa_confirm reenroll и §1.1 (строки24/54), AC36 purpose/аудит (строки109/145–147); D02 §8. **Связи:** AC02/05/10/32/36/39; AS04/21/27; HR01/06/16/18; B02/B11/B13/B14, DA11, HE10.

Правильно сохранено: поздний `auth_completion_not_issued` не отменяет доказанную активацию фактора; result_factor_id остаётся. Но не приведена точная action/outcome строка для «factor активирован, full login не выдан»: завершение transition/mfa_requirement, audit изменения фактора, notification purpose/recipient и единый локальный finalizer. `auth.login_not_issued` свидетельствует об исходе входа, а не автоматически заменяет историю активации. Прежний `auth.factor_change_completed` отсутствует в новом закрытом whitelist; его смысл должен быть явно отображён на новые kind, включая reenroll.

**Исправление:** рядом с обычными enroll/disable/reset/recovery добавить обычный и late reenroll: доказанный factor state → security transition → result/refs → обязательные audit kind(ы)/notification → отсутствие либо полнота login. Сопоставить старое смысловое событие с новым whitelist без повторной activation/отзыва новых login из-за replay или ошибки письма.

**Согласование:** точное отображение принятого эффекта — D02. Новое поведение security/отзывов/уведомлений либо превращение доказанной activation в отказ требует владельца; U03 само по себе такой дельты не даёт.

## 4. Что согласуется между источниками

Следующие положения найдены согласованными на уровне документа; это не runtime-pass:

- AC38 отделён от временного AC07 и окна AC16; full completion содержит один matching source/result/login/credential/window/secret комплект. Erasure не удаляет verifier для предусмотренного старого logout proof; поздний Q01 по действительной cookie сохраняется.
- AC39 хранит внешний dispatch/outcome; локальный WebAuthn не получает фиктивный внешний dispatch. Техническая неизвестность не превращается в окончательный отказ/новый permit.
- AC19 уникален по consent; AC40 — до3 внутренних доказанных rollback-попыток в прежнем бюджете, а не второй HTTP-исполнитель. Claim сохраняет прежние receipt/ownership/audit и не попадает в CommandReceipt/Q05.
- AC41/42 отделяют fence/inventory/drain/исходы. Отсутствие строки в старом backup не доказательство rollback; старый executor не назначает себе новую epoch.
- AC07 сохраняет nonce/key metadata при законном erase ciphertext. HR §10 корректно отличает этот вариант от исторического all-NULL; live erase не уничтожает backup/WAL.
- Новые approvals одной версии — новые immutable AC28; execution фиксирует конкретные approvals, не mutable approvedBy. Два разных владельца остаются обязательными там, где требуется пара.
- Direct HTTP, исторический result и текущий допуск чтения различены, в том числе GET200 сохранённого отказа и поздний U03. Auth `reasonDetails`-объект соответствует отдельному прежнему Auth-контракту; он не переносится на старый Shadow список ошибок.
- AS §11 перечисляет дополнительные AC38–42 и изменённые связи. Старые AS73 не объявлены полноценными AS78; неизвестные сопутствующие counts/targets остаются зависимостями, не нулями.

## 5. Обязательный остаток manifest78 и доказательств

Для будущего полного manifest нужны все36 Shadow +42 Auth, scoped IDs и родители, изменения существующих AC03–09/16/27/28/32–35 и новых AC38–42, отдельные proof/decoder/epoch/key источники. Нельзя ограничиться добавлением пяти totals к старому seed73. Для каждой применимой AS дополнительно указать case/approval variant, обязательный audit/witness closure, quota и expected counts; BDR02–05/08 уточняют именно эти сведения. Provider/external evidence не входит в78 собственных таблиц.

Все AS/HR/HE/MAP/DA/ASC/UST/E/CC/F остаются **не выполнявшимися**. D03/BR08 — реальные возможности provider, all-matching TOTP steps, WebAuthn, ключи/время/locks/бюджеты/restore. M04 — без автоматического архива истории; M05/H06 — защищённое независимое evidence, копии/WAL/сверка. Общий срок удаления истории/ключей не назначен. D04 и разрешение разработки не возникают из этой вычитки.

## 6. Ответ и дальнейшее сведение

Адресный результат BDR01–BDR08 передан в чат бэкенда по проверенному человеческому разрешению на двустороннюю сверку. Ожидается ответ по каждому ID: согласие/возражение с источником, точная правка, затронутые AC/AS/HR и необходимость решения владельца. Проверяемые файлы бэкенда этим листом не меняются. ### 7.3. Единственное адресное уточнение повторной вычитки: BDR05-R1

В HEAD248b5b23 [единая карта](https://github.com/denius89/polymarket-copy-trading/blob/248b5b2315c0f21b977cc4e6abe92bea2eb7c338/docs/technical/first-session/auth-storage-unified.md) §5.5 строка224 и §8 строка287 безусловно называют самостоятельное erasure «root secret». При этом точная W07 в реестре строка270 правильно различает AC07→secret_material, AC06/09→context, AC08/AC24/consumed AC22→auth_operation. Буквальное применение общей фразы к AC06 потребовало бы фиктивной AC07-ссылки либо другого непринятого target.

Рекомендация передана бэкенду напрямую: обе общие фразы должны говорить «собственный intent/batch и typed root по W07»; secret_material только для AC07, остальные перечисленные context/auth_operation с полным closure; unconsumed AC22 writer не добавляется. Это редакционное сведение уже заданных вариантов, **не новое правило/поле/root/исключение P04**, не требует нового продуктового вопроса владельцу. Бэкенд внёс это изменение; последующая проверка конкретного HEAD и закрытие BDR05 зафиксированы ниже. До такой проверки замечание не считалось закрытым.

Отсутствие standalone eraser для непотреблённого истёкшего bootstrap handle не нарушение принятого срока: expiry уже закрывает proof; обязательный TTL физического удаления не назначался. Будущая политика удаления не получает автоматического разрешения нового writer/root. Политика ключей/backup/WAL остаётся M04/M05/H06; это не основание ослабить witness или удалить историю.
