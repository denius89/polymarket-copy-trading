## 1. Запрос выражает намерение

Actor/realm/environment устанавливает сервер. UserId/роль, баланс, готовые effective settings или разрешение запуска из браузера не являются доверенными. clientCommandId — UUID v4 клиента до отправки C04/C06, один ключ на одно намерение. requestSchemaVersion обозначает формат запроса; correlationId — отдельная диагностика.

| Операция | Состав предметного запроса |
| --- | --- |
| C04 create | Полный набор сохраняемых полей формы; сервер назначает draftId, ожидаемой версии нет |
| C04 update | draftId, expectedDraftVersion, полный набор сохраняемых полей формы |
| C05 | draftId, expectedDraftVersion, proposedTimezone |
| C06 | reviewId, expectedDraftVersion, явное ожидаемое состояние слота |

Полный набор формы: locale, step, entryContext, venueId, traderId, selectedMode, rawBudget, rawFixedAmount, rawCopyPercent, rawMarketLimitPercent, rawDailyBuyLimitPercent, proposedTimezone. Незаполненное значение передаётся NULL; отсутствие обязательного ключа не означает скрытый PATCH прежнего поля. Полные запросы/точные поля Auth имеют собственный протокол H01; этот список не превращает одноразовые credentials в C04/C06.

В C06 слот: absent без generation либо present с generation. Нулевое поколение не кодирует отсутствие. not_applicable допустим только в guest review, не в запросе user-запуска. Проверенная конфигурация берётся из immutable review. Вход/review не запускает сессию автоматически.

## 2. Дополнение C04 и durable результат

Расширяются существующие command_keys/command_receipts/command_receipt_details с условными требованиями по типу команды. C06 сохраняет все строгие обязательные связи успешного запуска.

Область ключа: environment + actor realm + постоянный actorId + commandType + clientCommandId. Для user — постоянный userId, без loginId. Для guest — серверный постоянный ID гостевого Auth-контекста, установленного до первого C04; ID без proof не даёт доступа. Создание/изменение draft — варианты намерения C04, а не способ обойти конфликт одного ключа.

| Успешный результат C04 | Смысл |
| --- | --- |
| draftId | Исходный созданный/сохранённый draft |
| ownershipId | Историческое основание владения при выполнении |
| draftVersion | Версия после исходного выполнения |
| changeKind | created / updated / unchanged |
| lastSavedAt, expiresAt | Моменты исходного результата |
| fieldErrors | Сохранённые безопасные ошибки полей |

Обязательные IDs/версия/исход сохраняются отдельными колонками. Полевые ошибки — типизированные details. Не добавляется полная история raw-ввода каждой правки. Новый короткий невалидный числовой ввод может быть успешно сохранён; это не означает валидные effective settings.

| Ситуация | Правило |
| --- | --- |
| Известный ключ | Текущий доступ → проверка исходного fingerprint → прежний receipt; без повторной записи draft |
| Новый ключ | Владение/доступность/used/expiry → expectedVersion до сравнения содержимого |
| Актуальная версия, те же значения | Сохраняется receipt unchanged; draft/version/lastSavedAt/expiry не меняются |
| Устаревшая версия, те же значения | VERSION_CONFLICT |
| Реальное изменение ввода | version+1 и новый TTL в той же транзакции с key/receipt/details |
| После успешного C06 | Новый C04 запрещён; прежний receipt доступен после авторизации, без оживления draft |
| Ошибка транспорта/доступа до допуска к ключу | Нет предметного receipt |
| Окончательный предметный отказ после допуска | Rejected receipt без изменения draft |
| Неизвестный commit | Выяснение результата исходного ключа, не новый ключ |

Пример: сохранение вернуло version5, следующая команда создала version6. Повтор первой возвращает результат version5; Q03 отдельно показывает version6. UI не перезаписывает новую форму старым receipt.

После claim guest proof больше не открывает draft/receipts. Текущий user восстанавливает прежний C04 через подтверждённую цепочку ownership/claim; ключ не переносится в user realm и не исполняется заново. Поиск должен работать также при потере ответа первоначального guest create. Изменение Q05, который в baseline описан только для user, передано БД/общему контракту явно.

Изменение draft и key/receipt/details атомарны. Не появляется durable pending. В [дополнении БД, блоки 1–2](database-c04-addendum.md) уже приняты XOR user/guest, scoped уникальности, исходные C04 result-поля/details и setup_drafts.last_input_receipt_id. Новый unchanged не меняет этот pointer, raw/version/TTL. Проверенные target/ownership для rejected, полные post-claim пути и типизированные FK C04/C06 предложены блоком 3; этот контракт не объявляет предложение принятым.

## 3. Типы, размеры и отображение

| Область | Принятое правило |
| --- | --- |
| Resource ID | Серверный UUID v4; внешние provider/venue IDs сохраняют собственную область и формат |
| Версии/sequence/generation и bigint-счётчики | Целочисленные строки даже для 1; без ведущих нулей, кроме 0 |
| Exact money | Сокращённая пара целочисленных строк n/d; d>0, ноль 0/1, до 64 цифр без знака на компонент |
| Знак | Начальные суммы положительны/неотрицательны по полю; противоположная ledger entry signed. Это не разрешение отрицательного бюджета |
| Нормализованные проценты | API decimal-строка в процентных пунктах; DB integer в сотых п.п.: 300 ↔ 3.00% |
| Raw строки | NULL, пустая строка, 20 и 20.00 различаются; без trim, NFC или числового переписывания; до 64 Unicode code points |
| Время | UTC с Z, ровно три знака миллисекунд; now ≥ expiresAt означает истечение |
| C04/C05/C06/claim body | Несжатый UTF-8 JSON до 65 536 исходных байт до разбора, включая пробелы; вложенность 8 с корнем 1 |
| JSON-поля дополнительных данных | До 16 384 байт собственного компактного UTF-8 представления каждого ограниченного поля |
| Структурная однозначность | Дубли имён, включая эквивалентные escapes, запрещены; неизвестные поля C04/C05/C06/claim запрещены, включая вложенные |
| Ошибки кодировки | Неисправимые/непредставимые строки отклоняются, не исправляются молча |

Полные сохранённые записи выводятся из колонок принятых четырёх физических блоков. Обычное имя snake_case → camelCase; record_schema_version → recordSchemaVersion=v1. Пара *_n/*_d отображается одним объектом n/d, необязательная пара — целиком NULL, полупары запрещены. Для процентов используется указанная единица, а не необработанное integer-значение БД.

Явные смысловые исключения: raw_loss_limit_percent → rawDailyBuyLimitPercent; loss_limit_percent → dailyBuyLimitPercent; effective_loss_limit_n/d → effectiveDailyBuyLimit. Это дневной лимит новых покупок, не stop-loss. Существующие raw_market_limit_percent/market_limit_percent сохраняют значение p по policy, не получают нового финансового смысла от имени. Необязательная причина/ссылка и пустые массив/объект сохраняют разные смыслы.

## 4. Четыре независимых формата

Форматы — полные сохранённые факты. API выдаёт разрешённое представление. Частичный административный ответ не декодируется как полный snapshot/v1.

### Review v1

Полевая основа — [setup_reviews](database-physical-catalog-review.md#8-shadowsetup_reviews--неизменяемый-результат-проверки): ID/среда/формат, draft/version/ownership/owner, venue и согласованная группа catalog/source/trader/revision/guards, обязательные policy/control refs/версии, selectedMode, пять raw-полей, proposedTimezone, normalizationValid, нормализованные настройки, наблюдение слота, allowedToStart/requiresAuthentication, primaryReasonCode/reasonDetails/warnings и checkedAt/expiresAt/createdAt.

При normalizationValid=false весь нормализованный набор NULL, а не частично действующие параметры. При true — B, p/d, P/D и только выбранный F либо q. Для выбранного известного trader заполнена вся согласованная группа; неполная тройка запрещена. Guest всегда requiresAuthentication=true, allowedToStart=false, slot not_applicable. User absent отличается от present с generation, даже если current pointer пуст. Политика/controls должны быть достоверно прочитаны: техническая недоступность не изображается предметным review.

Review живёт 10 минут, содержит собственную копию, ссылается на историческое ownership. allowedToStart — результат на момент проверки, а не право обойти C06.

### Settings v1

Полевая основа — [settings_revisions](database-physical-session-ledger.md): ID/среда/формат, session, sequence/previousRevision, B, sizingMode и выбранный F/q, p/d и точные P/D, policy/calculation refs, signalMaxAgeSeconds, commandReceipt, actorUser и createdAt.

Начальная sequence=1, previous=NULL; точная копия выбранных валидных параметров review. Неактивный raw-ввод остаётся в draft/review. Signal age=30 секунд из policy, не пользовательская настройка. Будущая политика не переписывает сохранённую settings.

### Snapshot v1

Полевая основа — [session_snapshots](database-physical-session-ledger.md): ID/среда/формат, session/version/sessionVersion, settingsRevision, ledgerSequence, projectionCalculationVersion, lifecycle/control/content/dataOrigin/coverage, unit, initialFunding/free/reserved/positionCost/positionValue/equity/tradingResult, tradeCount/positionCount/orderCount, asOf/createdAt.

Все суммы и счётчики обязательны. В первом пустом запуске initialFunding=free=equity=B; reserved/positionCost/positionValue/tradingResult=0/1, счётчики=0. Funding не добавляется дважды. Текущий снимок выбирается по pointer сессии; settings — по его ссылке, не по max(createdAt). Нет/повреждён обязательный snapshot — техническая недоступность после авторизации, без NULL→0, ремонта или нового funding.

### Receipt v1

Полевая основа — [command_receipts/details](database-physical-operations-access.md) с принятым дополнением §2. API объединяет key metadata, core outcome и details в один результат, не создавая второй источник истины. Формат parent receipt определяет details; у details нет независимой версии.

Успешный C06 требует исходные sessionId/settingsRevisionId/snapshotVersion/sessionVersion; успешный C04 — результат §2. Эти варианты не взаимозаменяемы. Rejected требует безопасную reasonCode; связанная блокирующая session допустима только собственная и при текущем разрешении. Outcome только succeeded/rejected; pending относится к наблюдению Q05. У каждого нового receipt ровно одни обязательные details; их отсутствие — неисправность, не доказанный архив.

## 5. Fingerprint и восстановление результата

command-jcs-v1: строгий разбор/структурная проверка → каноническое намерение → JCS → SHA-256, 32 байта request_hash. Фиксируются версия канонизации и алгоритм. [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) — техническое основание, прочитано 29.10.2026.

Включаются доверенная область/тип команды, версия запроса, target/операция, ожидаемые версии и значимые сохраняемые значения. Для C04 — все поля формы, в том числе сохраняемые locale/step, create/update и draft при update. Для C06 — review, ожидаемые версии/слот и проверенная конфигурация из immutable review; браузерные балансы не используются.

Порядок JSON-ключей и пробелы вне строк не влияют. Raw-строки влияют точно; нет trim/NFC. Cookie, loginId, correlationId и локализованные подписи не участвуют. Серверные новые IDs/моменты выполнения не должны делать одинаковое намерение различным при повторе.

Старый ключ сравнивается по сохранённой версии канонизации. Истёкший review, новая policy или новое устройство не переисполняют успешный ключ. Неизвестный/повреждённый receipt не равен отсутствию. Повтор после новой авторизации возвращает прежний успех/отказ; не создаёт второго start audit/outbox. Неизвестный commit выясняется на исходном ключе из основного хранилища; отсутствие результата при первом Q05 не доказывает rollback.

Для нового C06: повторный допуск после ожиданий; максимум три попытки всего при доказанном serialization/deadlock rollback; общий монотонный бюджет 5 секунд, включая ожидания и случайные паузы 50–150 мс. Пауза, не помещающаяся в остаток, не сокращается ради новой попытки. Unique violation разбирается отдельно, business rejection не повторяется, unknown commit не считается rollback. C04/C05 и claim получили явное отдельное принятие этих чисел в §§10/17; Auth использует отдельный бюджет §15. Это не общее разрешение повторять произвольную операцию.

## 6. T01 — точный разбор числового ввода

**Принято целиком.** Одинаково для ru/en: десятичная точка или запятая, один разделитель, только цифры 0–9; при разделителе цифры обязательны с обеих сторон. Ведущие/конечные нули допустимы. Исходный raw сохраняется точно, без trim/NFC/переписывания; канонизация команды также сохраняет различие строк.

| Ввод | Разбор / дальнейшая проверка |
| --- | --- |
| 3.5 / 3,5 | Одно точное число; locale не меняет смысл |
| 020 / 20.00 / 20,000 | Число 20, три разных raw-строки |
| 1,000 | Число 1; разделителей тысяч нет |
| 0,5 | Допустимая запись числа; диапазон зависит от поля |
| .5 / 20. | Недопустимая/незавершённая запись числа |
| NULL / пустая строка | Не заполнено / поле очищено; разные raw, ни одно не ноль |
| Пробелы, +/−/-, валюта, %, экспонента 2e2, NaN, Infinity | Недопустимая запись числа; не удаляются и не преобразуются |

Нет округления при разборе или подгонки к диапазону/шагу. Например q=3,2 нарушает шаг 0,5%; F=20.00 проходит целочисленный шаг как 20. Предел raw64 и точные денежные пределы сохраняются. Числовая валидность и структурная допустимость строки различаются: короткий ошибочный ввод можно сохранить C04. Изменение 20→20.00 меняет версию ввода, даже при равном числовом результате. Неактивный raw сохраняется, но не становится настройкой. Неверный выбранный набор блокирует запуск; частично действующие настройки не создаются.

## 7. T02 — ошибки полей и зависимые проверки

**Принято целиком.** Все независимо определимые ошибки, по одной основной ошибке на активное числовое поле. Приоритет внутри поля:

1. REQUIRED — NULL или пустая строка обязательного поля.
2. INVALID_DECIMAL — недопустимая запись, включая строку из пробелов.
3. OUT_OF_RANGE — нарушение принятого диапазона.
4. INVALID_STEP — нарушение принятой сетки.
5. FIXED_LIMIT_EXCEEDED — превышен вычисленный допустимый fixed.

Fixed-предел проверяется только при корректных необходимых B/p/d и собственных предыдущих проверках F; ошибка зависимостей не создаёт вымышленный предел. Формат/собственный диапазон/шаг F проверяются независимо. Неактивный F/q не даёт ошибки настроек, но ограничения структуры/длины обязательны. При невыбранном режиме не назначать его молча; проверять только определимые независимые поля.

Порядок массива: бюджет → размер выбранного режима → лимит на рынок → дневной лимит покупок. Если F превышает абсолютный максимум и вычисленный предел, основная ошибка поля OUT_OF_RANGE. Это порядок fieldErrors, не главной причины отказа всей операции.

## 8. T03 — основная причина отказа

**Принято целиком.** Порядок ответа фиксирован, не зависит от locale, порядка завершения проверок или порядка locks.

Сначала различаются этапы: (а) структурно недопустимый запрос/недействующий вход/нет доступа — безопасная соответствующая ошибка без раскрытия чужих данных; (б) точный повтор C04/C06 — текущий доступ, fingerprint и прежний результат, другой payload того же ключа даёт KEY_REUSE_CONFLICT; (в) новая допущенная команда — приоритеты ниже. Прежний результат не переоценивается по состоянию новой команды. Общая последовательность между независимыми ранними транспортными/Auth-защитами не назначается этим бизнес-приоритетом.

| Операция | Приоритет причин новой операции |
| --- | --- |
| C04 | DRAFT_USED → DRAFT_EXPIRED → VERSION_CONFLICT; числовые fieldErrors могут сопровождать succeeded |
| C06 | DRAFT_USED → DRAFT_EXPIRED → VERSION_CONFLICT → SESSION_NOT_SETTLED → CURRENT_SESSION_EXISTS → CAPABILITY_UNAVAILABLE → REVIEW_EXPIRED → REVIEW_STALE → SETUP_INVALID |
| Сохранённый результат C05 с allowedToStart=false | AUTH_REQUIRED для разрешённого guest → SESSION_NOT_SETTLED → CURRENT_SESSION_EXISTS → CAPABILITY_UNAVAILABLE → VENUE_REQUIRED → TRADER_REQUIRED → SIZING_MODE_REQUIRED → TIMEZONE_REQUIRED → NUMERIC_SETTINGS_INVALID |

Внутри CAPABILITY_UNAVAILABLE: PAPER_START_DISABLED → CATALOG_SOURCE_DISABLED → TRADER_START_DISABLED. Учитываются только применимые, разрешённо и достоверно установленные причины. Не выбранный trader не объявляется отключённым; зависимости не додумываются. Причины сессии относятся только к своей препятствующей session и фактическому состоянию; будущие состояния проверяются в изолированных fixtures, не добавляются как новые результаты запуска.

Для C05 сначала проверяется возможность законно создать review из доступного актуального draft; отказ в исполнении C05 не является сохранённым отрицательным review. Истёкший user login не преобразуется в guest. Guest review может показывать ошибки собственной формы при primaryReasonCode=AUTH_REQUIRED. Для C06 несовпадение expectedDraftVersion — VERSION_CONFLICT; иной устаревший контекст review — REVIEW_STALE. Один факт не дублируется разными пояснениями.

Необходимые policy/controls/данные должны быть прочитаны достоверно. Техническая недоступность не подменяется удобным business rejection; неизвестный исход выясняется с прежним ключом. Warnings SYNTHETIC_DATA/COPYING_NOT_CONNECTED не запрещают согласованный пустой запуск. Порядок Serializable-блокировок из H05 остаётся прежним.

## 9. T04 — типизированные пояснения

**Принято целиком.** FieldErrors — массив элементов field/code/params, один на поле по §7; пустой массив, если ошибок нет. Field — точное известное имя поля запроса; code — существующий реестр. Params — только разрешённые для данного кода безопасные значения; при отсутствии параметров пустой объект.

| Код | Допустимое содержание params |
| --- | --- |
| REQUIRED / INVALID_DECIMAL | Пустой объект |
| OUT_OF_RANGE | Минимум, максимум, единица измерения |
| INVALID_STEP | Шаг, точка отсчёта, единица измерения |
| FIXED_LIMIT_EXCEEDED | Максимальная допустимая fixed-сумма этих настроек, единица измерения |

Суммы — точные n/d в virtual_USD, проценты — decimal-строки в процентных пунктах. Точка отсчёта/границы/шаг взяты из policy именно этой проверки. Текст RU/EN формирует интерфейс по кодам; сообщения БД/библиотек не передаются. Имена внутренних ключей params, их закрытые типы и обязательность теперь определены в [карте §4](database-error-field-map.md); исполняемая машинная схема ещё не создана. Смысл и допустимый состав приняты T04, не произвольный JSON.

PrimaryReasonCode у review и reasonCode у отказа команды сохраняют имена. API reasonDetails — упорядоченный список элементов code/params: основная причина первой, остальные без дубликатов; при отсутствии причин пустой список. Для CAPABILITY_UNAVAILABLE передаётся принятое уточнение. Связь с препятствующей session выдаётся только при текущем доступе. Исходный raw/секреты/чужие данные/внутренние исключения сюда не копируются; собственные raw в отдельном разрешённом draft/review этим не запрещены.

FieldErrors и установленные пояснения — часть исходного сохранённого результата, не пересчитываются при replay по новой policy. Изменение формы учитывается в версии родительского формата. **Форма API и физический контейнер различаются:** у БД reason_data при отсутствии — пустой объект; это не разрешение заменить его голым API-массивом. Явное отображение объекта reason_data на список reasonDetails и fieldErrors review выполнено [порученным дополнением БД](database-error-field-map.md): reasons внутри объекта, fieldErrors в указанном варианте details/review. Новых колонок нет; контейнеры фиксируются явно этим дополнением. У succeeded C04 уже принято response_data.fieldErrors.

## 10. T05 — C04/C05: бюджет и повторы

**Принято целиком.** До 5 секунд с начала первой попытки серверного выполнения, включая получение соединения, locks, работу и паузы; до трёх попыток всего. Повтор только после доказанного serialization/deadlock rollback, пауза 50–150 мс внутри бюджета. Новую попытку не начинать при недостаточном остатке; начатые ожидания ограничены остатком. Предметный отказ/ошибка пользователя не повторяется автоматически. Как и в H05, unique violation разбирается отдельно, не универсальная retry-причина.

C04 unknown: выяснить исход исходного ключа, повторы с тем же payload/key. UI сохраняет ввод; новые сохранения этого draft с новым ключом не отправляет до выяснения, локально вводить можно. Подтверждённый rollback с исчерпанными попытками — техническая недоступность; следующая передача сохраняет исходный ключ.

C05 unknown: автоматический повтор прекращается, результат мог сохраниться. SERVICE_UNAVAILABLE не означает неверные настройки/отсутствие review. Пользователь может явно повторить проверку — новый immutable review, возможный прежний остаётся историческим. Для C06 нужен конкретный полученный и показанный результат. C05 не получает обычный командный key/receipt и не входит в Q05; потеря ответа не запускает сессию.

Таймер/разрыв HTTP не доказывает rollback. После возможного commit сначала определить исход; не выдавать rejected по одному истечению бюджета. Реальные таймауты драйвера/отмена и доказательство отсутствия позднего commit ещё требуют испытаний.

## 11. T06 — Q05 и ограниченный опрос

**Принято целиком.** Q05 читает C04/C06: committed — найден succeeded; rejected — найден окончательный отказ; pending — окончательный результат не установлен, не доказательство исполнения/отмены. Недоступное хранилище, повреждённый/нечитаемый результат — техническая ошибка, не pending. Нет/повреждены обязательные details — не pending и не новый ключ.

Одно чтение Q05 — до 5 секунд, без внутренних автоматических повторов. UI читает сразу после обнаружения unknown, затем интервалы между завершённым чтением и следующим — 1, 2, 5, далее 10 секунд; только один запрос одновременно. Автоматическое окно до 30 секунд, новое чтение не начинается, если его 5-секундный бюджет не помещается в остаток. После окна — «Результат пока не удалось подтвердить» и «Проверить снова», без нового ключа.

Закрытие/скрытие страницы прекращает опрос; при возвращении можно продолжить по прежнему ключу. Истёкший вход останавливает опрос; после входа исходное намерение/ключ сохраняются. Фоновый опрос не продлевает login. Ручная проверка — чтение, не повтор команды; повтор исполнения регулируется отдельно исходным ключом и сериализуемой защитой. Pending/30 секунд не разрешают новый key. Поздний C04 результат не заменяет новый локальный ввод/актуальный draft. Guest/post-claim доступ соответствует §2, полный физический поиск ещё уточняется БД.

## 12. T07 — nextAction

**Принято целиком.** Одно основное действие по основной причине/подтверждённому результату; дополнительные ошибки не создают противоречащие команды. NextAction — навигация, не полномочие и не автоматический запуск. Если безопасного подходящего действия нет, NULL; нового enum «ничего» нет.

| Условие | Действие |
| --- | --- |
| Нужен/истёк/отозван вход | authenticate |
| Требуется подтверждение TOTP | complete_totp |
| Разрешённое подключение TOTP | enroll_totp |
| Не выбрана площадка/трейдер | select_trader |
| Неполные/неверные настройки | continue_setup |
| Review истёк/устарел | review_setup |
| Конфликт версии/истёкший draft | recover_setup |
| C04/C06 unknown | resolve_command |
| Подтверждённый start | view_session |
| Препятствующая собственная session | view_session либо view_summary по фактическому состоянию/доступу |
| Подтверждённая временная недоступность/ограничение частоты | retry_later |

Recover_setup сначала загружает доступное текущее состояние и показывает расхождение с локальным вводом; не обещает восстановить отсутствующее, не затирает правки молча. Для used draft/запрета trader выбор зависит от проверенных данных; автоматической смены trader/создания draft нет. Ссылки/IDs цели только при текущем доступе; произвольного redirect нет. Retry_later не заменяет resolve_command при неизвестном исходе C04/C06. При чтении старого receipt навигация и доступность ссылок определяются текущим ответом, а сохранённый результат не переписывается. После входа восстанавливается прежнее намерение/ключ, не новый start.

## 13. T08 — частичный Q06

**Принято целиком.** Разрешённая группа выдаётся полностью; закрытая отсутствует в данных и перечисляется кодом в restrictedGroups. Используются только session.summary, session.settings, session.financial_snapshot, user.minimal_context. Если ограниченных групп нет, список пуст. Без разрешённой session.summary карточка целиком недоступна, не пустой успешный ответ.

| Состояние | Представление |
| --- | --- |
| Разрешённая группа | Все обязательные поля группы |
| Закрытая группа | Нет данных группы; её код в restrictedGroups |
| Действительно отсутствующее необязательное значение | NULL, только если разрешён полем |
| Действительно пустой разрешённый список | Пустой массив |
| Действительный ноль | Точный ноль принятого формата |
| Отсутствующее/повреждённое/неподдерживаемое обязательное данное | Техническая ошибка всего чтения, без успешной неполной карточки |

RestrictedGroups — сведения о проекции текущего ответа, не о физически отсутствующих полях snapshot. Нет внутренних назначений/причин ограничения/evidence в этом списке; закрытую группу нельзя заменять NULL/нулями/пустым объектом. Интерфейс показывает «Нет доступа». Все выданные группы принадлежат одному согласованному состоянию/версиям; частичный Q06 не выдаётся за полный snapshot/v1. Запись обязательного audit до успешной выдачи остаётся неизменным правилом; ошибка чтения/audit не маскируется как ограничение прав.

## 14. T09 — обычные чтения Q01–Q04/Q06

**Принято целиком.** До 5 секунд серверного выполнения с ожиданиями соединения/locks, без внутренних автоматических повторов. Технический сбой — ошибка и ручное «Повторить», без бесконечного обновления. Повтор — новый запрос с проверкой текущего доступа. Для всех этих ответов HTTP no-store; это не обещание стереть уже доставленные данные у человека.

Ошибка чтения не означает отсутствие session/пустой catalog. Ранее загруженные данные на экране при техническом сбое явно помечаются как прежние, с исходным asOf; они не подтверждают разрешение новой команды. Подтверждённая утрата доступа убирает закрытые данные с экрана/клиентского кэша. Поздний ответ не заменяет более новый и не возвращает данные после logout.

Каждый отдельный успешный Q06 проходит свежую авторизацию и собственный аудит. Повтор чтения не меняет session/финансы/version/asOf. Потерянный HTTP-ответ не отменяет сохранённый audit; audit подтверждает разрешённую подготовку, не доставку/просмотр человеком. Автоматические запросы не продлевают login; согласованная foreground-активность проверяется отдельно. Q05 регулируется §11, а не этим правилом ручного повтора.

## 15. T10 — C01–C03: одноразовые действия

**Принято целиком.** До 10 секунд серверного выполнения, включая Auth-компонент. Автоматического повторения действия, способного отправить письмо или использовать одноразовое подтверждение, нет. Таймаут/закрытие страницы не отменяет эффект. Каждая операция связана с защищённым контекстом попытки; повтор передачи сохраняет идентификатор этой операции. Контекст и результат — закрытый Auth-контур, не CommandReceipt Shadow; код/секрет в обычный receipt/hash не записывается.

- C01 unknown: «Не удалось подтвердить отправку; письмо могло прийти». Повтор передачи той же операции не отправляет второе письмо. Намеренная новая отправка — C03 с текущими лимитами.
- C02 unknown: выяснить состояние исходной попытки. Подтверждение уже завершилось — продолжить тот же созданный вход/этап TOTP; подтверждённо не завершилось — повтор только по правилам действующего challenge; выяснить нельзя — ограниченный экран без полного доступа и без ложного «код неверен».
- Восстановление C02 требует доказанного защищённого контекста, не одного attempt ID. Использованный код не создаёт независимый login. Неизвестный исход не разрешает снова потребить одноразовое подтверждение.
- C03 — отдельное явное действие, сохраняет семью/счётчики и все принятые cooldown/лимиты. Потеря ответа ничего не сбрасывает и не запускает новую отправку.

Техническая недоступность не AUTH_VERIFICATION_FAILED. TOTP-этап не полный вход. Без доказанных возможностей Auth различать повтор/новую операцию остаётся техническая зависимость; документ не обещает exactly-once доставки письма внешним провайдером. Ограничения OTP и правила действующего кода из [Auth-контракта](backend-auth-access.md) не меняются. Имена/поля защищённого recovery-протокола ещё требуют H01-спецификации.

## 16. T11 — C07 logout

**Принято целиком.** До 5 секунд, одна серверная попытка, подтверждённый успех — 204 без тела. Действующий текущий login отзывается. Этот login уже отозван/истёк либо достоверно отсутствует — выход завершён, повтор не ошибка. Unknown отзыва не объявляется успешным серверным выходом: выясняется состояние исходного входа.

UI сразу скрывает персональные данные/останавливает фоновые запросы, показывает «Завершаем выход», затем возможность повторить. После подтверждения очищаются относящиеся к этому входу cookie и персональный кэш. Само отсутствие cookie не доказывает серверный отзыв. Повтор/выяснение привязаны к исходному login защищённым сервером контекстом; клиентский ID не полномочие. Запоздалый ответ/повтор не отзывает новый login и не очищает его данные/cookie. Механизм защиты от запоздалого Set-Cookie требует отдельной проверки H01, не доказан одним UI-флагом.

Origin/CSRF сохраняются даже при идемпотентном результате. User logout не завершает staff login и наоборот; другие user-устройства остаются по принятой политике. Draft/receipt/paper session не удаляются; после нового входа неизвестная команда выясняется с исходным ключом. Действующий токен провайдера не обходит server-side отзыв Shadow. 204 не возвращается по одной технической невозможности прочитать состояние.

## 17. T12 — claim: повтор и unknown

**Принято целиком.** До 5 секунд/трёх попыток всего; автоматический повтор только после подтверждённого serialization/deadlock rollback, паузы 50–150 мс внутри бюджета. Неизвестный итог сначала выясняется, без второго ownership/заменяющего draft.

Порядок: полный user-вход → разрешённый поиск исходного claim → если передача завершена этому user, прежний результат без новых записей; если подтверждено незавершение, действующий guest proof и остальные условия до исполнения; чужой результат/владение не раскрываются; невозможно выяснить — техническая недоступность, не отсутствие результата.

Для восстановления уже завершённого claim его получателем не требуется действительность закрытого старого guest-доступа. Нужны полный текущий вход и доказанная цепочка ownership/claim. Один draftId недостаточен; повтор не переносит владение другому user. Границы scope разных независимых drafts одного guest context сохраняются.

UI удерживает локальный ввод, до выяснения не отправляет новые изменения этого draft. После подтверждения загружает актуальный draft без молчаливой потери локальных правок. Для start — новый user C05; прежний guest review исторический. Claim использует свой draft_claim_receipt/путь восстановления, не расширяет Q05 за пределы C04/C06. Конкретные маршрут/поля защищённого поиска и физические ссылки — оставшаяся полевая сверка с БД/H01.

## 18. T13 — строгая структура запросов

**Принято целиком.** C04/C05/C06/claim принимают только описанную форму: неизвестные поля (включая вложенные), отсутствие обязательного, неверный тип, недопустимый NULL, дубли имён/эквивалентные escapes, неизвестная версия запроса/enum или запрещённое сочетание — INVALID_REQUEST. Нет скрытого PATCH, coercion, подстановки defaults или чтения неизвестной версии как текущей.

Для всех четырёх: несжатый UTF-8 JSON, до 65 536 исходных байт до разбора, вложенность 8 с корнем 1. Превышение — REQUEST_TOO_LARGE; неподдерживаемые media type/сжатие — UNSUPPORTED_MEDIA_TYPE. Нет обрезания, исправления кодировки или удаления полей. Запрет coercion относится к wire-типам: rawBudget со строкой abc может сохраниться с field error; rawBudget как JSON number — структурный отказ.

Ранний отказ не меняет draft/ownership/session и не создаёт предметного receipt. Существующий результат того же ключа остаётся неизменным; невозможно сравнить намерение недопустимого запроса — нет разрешения исполнения. Диагностика без тела. Набор полей/версия Auth-протокола и claim полностью ещё не описаны; правило строгого декодирования не придумывает недостающую схему.

## 19. T14 — граница окончательного отказа

**Принято целиком.** Только после структуры, текущего доступа и допуска к scoped ключу новая C04/C06 может сохранить окончательный предметный отказ. Это одна транзакция key/receipt/details, без отдельного pending и без изменения предметного draft/финансов при отказе.

| Случай | Результат хранения |
| --- | --- |
| Структура/размер/media, недействующий вход, нет доступа, скрытый/чужой объект | Нет предметного receipt |
| RATE_LIMITED до исполнения | Нет предметного receipt |
| Известный key с другим payload | KEY_REUSE_CONFLICT; исходный результат неизменен |
| Новая допущенная команда и DRAFT_USED/EXPIRED, VERSION_CONFLICT, препятствие session, устаревший review, запрет start, неверный C06 | Сохраняется rejected с основной причиной/безопасными пояснениями |
| Подтверждённый технический rollback | Нет окончательного rejected этой операции |
| Unknown commit | Выяснение исходного ключа, не объявление отсутствия/отказа |

Право читать/идентифицировать принадлежащую цель отличается от права изменить used/expired draft: первое нужно до допуска к ключу, второе даёт предметный отказ после допуска. Истёкший/used свой draft не маскируется ранним access denied только ради отсутствия rejected receipt. При потере текущего доступа подробности не выдаются.

Сохранённый rejected окончателен для ключа даже после исчезновения препятствия. Новое намерение после исправления/нового review требует отдельного явного подтверждения и нового ключа; UI не меняет ключ для обхода отказа. Технический сбой/unknown сохраняют прежние параметры и ключ. C04 с числовой ошибкой может быть succeeded с fieldErrors. Прежние результаты доступны только с текущей авторизацией.

## 20. T15 — идентификаторы и диагностика

**Принято целиком.** RequestId — новый серверный UUID каждой HTTP-передачи; clientCommandId — UUID v4 клиента для одного намерения C04/C06, прежний на повторах; receiptId — постоянный ID окончательного результата. Три передачи: три requestId, один clientCommandId, один окончательный receiptId.

Сервер возвращает текущий requestId в X-Request-Id, включая ошибки и 204 без тела. Входящий клиентский идентификатор не становится доверенным серверным requestId. Заголовок чтения прежнего receipt относится к текущему чтению, receiptId — к исходному результату. RequestId не участвует в fingerprint и не переписывает сохранённый результат. CorrelationId необязателен, только диагностическая группировка, не авторизация/идемпотентность. Точный wire-формат/предел correlationId ещё не закреплён.

Q06: разные HTTP-запросы — разные requestId и собственная текущая авторизация/audit. Для повторяемых внутренних попыток одной HTTP-обработки requestId остаётся одним, не три новых пользовательских запроса. Действующий audit.request_id — серверная обработка, не денежный command key. ID не выдаёт права читать чужие записи. UI может показать «Код обращения» с requestId; тело/OTP/tokens/secrets в диагностике отсутствуют.

## 21. T16 — HTTP и исход команды

**Принято целиком.** Статус передачи не заменяет outcome/allowedToStart/состояние входа.

| Операция / результат | HTTP |
| --- | --- |
| C04 created | 201 |
| C04 updated / unchanged | 200 |
| C05 создал review, в том числе allowedToStart=false | 200 |
| C06 сохранил полный start | 201 только после commit |
| Claim подтверждён / восстановлен прежний успех | 200 |
| Q01–Q04/Q06 успешно вернули разрешённые данные | 200 |
| Q05 нашёл committed либо rejected | 200 |
| Q05 окончательный результат не установлен | 202 |
| C07 подтверждён | 204 без тела |

Точный replay успешного C04/C06 возвращает исходный статус успеха (в том числе 201) и прежние IDs, не создаёт новый результат. Replay rejected возвращает сохранённый отказ и согласованный статус; текущий access/technical error может закрыть выдачу, не меняя receipt. Q05 чтение rejected остаётся 200, а не исходный 409. Не добавлять HTTP как самостоятельную финансовую сущность/новую колонку без физической сверки: статус определяется типизированным исходом и версией контракта.

C05 200 не означает разрешение start; C04 2xx с fieldErrors не означает валидные настройки. Технический провал C05 не успешный отрицательный review. Коды/статусы ошибок остаются [в реестре](backend-code-registry.md); C01–C03 дополнены отдельным §22.

## 22. T17 — ответы C01–C03

**Принято целиком.** Отправка письма, промежуточное подтверждение и полный вход различаются явно.

| Установленный результат | Ответ |
| --- | --- |
| C01/C03: Auth подтвердил принятие отправки | 202, непрозрачный challenge ID и серверный момент допустимой повторной отправки |
| C02: email подтверждён, требуется TOTP | 200, полного входа нет, nextAction=complete_totp |
| C02: разрешено только подключение нового TOTP в recovery | 200, полного входа нет, nextAction=enroll_totp |
| C02: все требуемые подтверждения завершены, создан/восстановлен действующий login Shadow | 200, полный вход подтверждён, следующий разрешённый шаг по текущему состоянию |
| Исход неизвестен | Техническая недоступность, не успешная отправка/неверный код/полный вход |

202 подтверждает принятие отправки, не доставку человеку; неопределённый ответ Auth не 202 принятой отправки. C01/C03 не раскрывают существование account, TOTP или paper-session. Различия только после надлежащего подтверждения личности. Время resend — подсказка, сервер повторно проверяет реальные лимиты. Challenge ID сам не подтверждение/восстановление/вход.

Промежуточный этап разрешает только соответствующее Auth-действие: claim/start/защищённые user-данные закрыты. Cookie выдаются защищённо; OTP/refresh/секреты не поля обычного ответа и не диагностика. Полный вход не создаёт paper session. Точные поля/маршруты ответа, включая ограниченный proof восстановления неизвестного C02, ещё требуют компонентной спецификации H01; эти требования не означают проверенный Auth-адаптер.

## 23. Сверка согласованности дополнений

Проведена **документальная сверка**, а не DB/API/Auth испытания. Все T01–T17 соответствуют последовательным явным принятиям в чате; ниже зафиксированы стыки, которые нельзя потерять при реализации.

| ID | Проверенный стык | Согласованное прочтение / состояние |
| --- | --- | --- |
| K-B01 | Raw и строгий JSON | Строка abc допускается в C04 с fieldError; JSON number вместо raw-строки — ранний INVALID_REQUEST. Raw различия входят в fingerprint |
| K-B02 | Ошибка поля и причина операции | По одной ошибке на поле; primaryReason определяется отдельно по C04/C05/C06. Нет фиктивных зависимых расчётов |
| K-B03 | C04 no-op и immutable результат | Новый unchanged сохраняет свой CMD; last_input_receipt_id не меняется. Replay всегда исходный результат, не current draft |
| K-B04 | Доступ, ключ и бизнес-приоритет | Сначала разрешённый доступ к результату/цели; известный key не проходит заново used/expiry/версии как новая команда. Новый допущенный отказ сохраняется |
| K-B05 | Deadline и commit | 5/10 секунд не доказывают rollback. Unknown не становится rejected; C04/C06 сохраняют ключ, C05 не получает Q05 |
| K-B06 | Polling и серверный бюджет | Только один запрос, полные 5 секунд должны помещаться в 30-секундное окно; фиксированное число опросов не обещано; 30 секунд не срок хранения key |
| K-B07 | HTTP 200/201/202 и смысл | C05 отрицательный review — 200; Q05 rejected — 200; повтор created/start — прежний 201; Auth 202 не означает login/доставку |
| K-B08 | Исторический результат и текущая выдача | Receipt/fieldErrors/причины неизменны. X-Request-Id, nextAction и разрешённые ссылки/проекция относятся к текущему ответу, не перезаписывают receipt |
| K-B09 | Q06 partial и целый snapshot | RestrictedGroups не хранятся как недостающие части snapshot. Один snapshot/настройки/достаточный audit; ошибка обязательных данных — ошибка всего чтения |
| K-B10 | Повтор Q06 и audit | Каждая новая HTTP-передача имеет свой requestId/audit; внутренний rollback не создаёт лишний committed audit. Финансы/версия снимка не меняются |
| K-B11 | Logout и запоздалый ответ | Отсутствие cookie не доказательство revoke; late retry/Set-Cookie не должны затронуть новый login. Обязательное испытание H01 ещё не выполнено |
| K-B12 | Claim и закрытый guest | Для первичного claim нужен proof; после успеха получатель читает по user/цепочке. Отказ create без draft не получает вымышленной claim-цепочки |
| K-B13 | Auth replay и одноразовость | Attempt/challenge — не CommandReceipt. Повтор передачи не новое письмо/независимый login; отсутствие гарантии провайдера оставляет dependency |
| K-B14 | ReasonDetails и reason_data | API-список отображается в reason_data.reasons по [точной карте](database-error-field-map.md); succeeded хранит {}, rejected — обязательный reasons. Review.reason_details содержит reasons и fieldErrors. Карта документальна, декодеры/испытания не готовы |
| K-B15 | Настоящие права и UI-кэш | No-store/скрытие старого ответа не заменяют server-side guards. Автозапросы не продлевают login; nextAction не выдаёт полномочий |

Обнаружены не взаимоисключающие продуктовые правила, а **незавершённые отображения и компонентные механизмы**. Они явно перечислены ниже/в передаче БД. Отсутствие логического конфликта в этой сверке не подтверждает полноту исполняемой схемы или безопасность работающего сервиса.

## 24. Оставшиеся точные спецификации и доказательства

Принятые T01–T17 не выносятся на повторное продуктовое согласование. Перед кодом остаются:

1. Принятые полевые схемы C04/C05/C06/claim, Q01–Q06, receipt/review/settings/snapshot, nextActionParams/correlationId и каталог сведены в [дополнение](backend-api-forms-addendum.md). Их написание в чате больше не открытый продуктовый вопрос. Остались исполняемые схемы/декодеры, полная проверка API-проекций против сохранённых записей, точные C01–C03/C07/H01 и защищённые механизмы. Права и обязательный аудит Q06 при session=null остаются открытым DB-API-09, не ослабляются до принятия отдельного решения.
2. Полевая часть API reasonDetails/fieldErrors ↔ DB reason_data/response_data/setup_reviews.reason_details и Q03 provenance закрыта [точной картой](database-error-field-map.md). Предел каждого JSON-поля 16 КиБ сохранён. Остаются реализация декодеров и испытания, не выбор контейнеров/params заново.
3. Физические блоки C04 3–4 приняты и отражены последующими ADR-0064 §§36–37, не открывать их повторно. Остались реализация/декодеры и доказательства; пометки о предложении на baseline PR №172 исторические.
4. Точный H01-протокол до первого guest C04 и восстановления Auth/claim/logout unknown, адреса/защищённый контекст/cookie races/одноразовость и доказанная совместимость компонентов. C01–C03 здесь не включают спецификацию отдельного staff WebAuthn API или всех recovery endpoint.
5. Размещение/предел correlationId определены в дополнении §2. Остаются operational-таймауты доказуемой отмены/rollback, доверенный cursor Q02/проверка изменения каталога и порядок независимых ранних transport/Auth-защит. Принятый бизнес-приоритет их не заменяет.
6. Версии зависимостей/сборки/tzdb и протоколы эксплуатации/копий из H05/H06; независимые сценарии A01–A112, S/N/K, F01–F24, round-trip/JCS/64–65 границы, concurrency/unknown/Auth/DST/restore остаются запланированными.

Особый стык для полевой сверки: last_input_receipt_id указывает на создавшую текущий ввод команду, не на последнюю unchanged попытку. Семантика Q03 при изменившейся policy выражена в [карте §5](database-error-field-map.md): исторические fieldErrors источника текущего ввода и обязательный fieldErrorsSource, без пересчёта; C05 выполняет новую проверку. Это не меняет уже принятую неизменяемость каждого receipt или право нового C05.

Изменение версии исполнения/формата должно сохранять чтение прежнего результата; никаких миграций истории или установки компонентов этим документом не поручено.
