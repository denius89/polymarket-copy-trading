# Реализация интерфейсов и интеграция полигона

Обновлено 04.11.2026. Основание: [ADR-0067](../../decisions/0067_frontend_stack_and_polygon_delivery.md). Исполнение начато; этот план не означает готовность приложений.

## Исходное состояние

Проверенный main перед началом: `f53b54de5546752c8cf0042c5def4f97d6aaca05`. В нём `apps/web` содержит описание будущего приложения; root dev-команда — scaffold placeholder. Имеющиеся HTML-прототипы не подключены к продуктовым API. V00 содержит ограниченные испытанные Auth-маршруты, а не полную пользовательскую и административную систему.

Серверный чат сообщил о постоянном изолированном профиле `/opt/shadow-polygon` на существующем Oracle, отдельном томе PostgreSQL/Auth/тестовой почты и установке начального комплекта БД. Проверки после установки, браузерный доступ, перезапуск и восстановление имеют собственные результаты в серверном пакете; наличие контейнера не закрывает их автоматически.

## Последовательность исполнения

1. **Карта покрытия.** Исполнители составляют реестры user/admin: исходный экран/состояние и Figma-узел → маршрут → компоненты → API → условия доступа → проверки → статус установки. Ни один текущий принятый экран не теряется при объединении вариантов.
2. **Общая база.** Зафиксировать совместимые версии, сборку двух приложений, UI-kit, адаптивные оболочки и словари. Общие состояния не реализуются повторно разными стилями.
3. **Первый реальный проход.** Вход/коды/2FA в доступном объёме → каталог → настройки → проверка → явный запуск paper-сессии → та же сессия в разрешённом административном просмотре. API/хранение реализуются по принятым контрактам; зависимые шаги не выдают mock за успех. Закрытый guest claim не включается ради прохода.
   **Ограниченный тестовый профиль принят отдельно:** по POLYGON-SYNTH-01 от 04.11 разрешены C04/C05/C06 на закрытом полигоне без внешнего независимого журнала, с настоящими атомарными записями/receipts/constraints, актуальными проверками прав и локальным аудитом. Это не продуктовый P04 PASS. Backend/БД фиксируют точные отличия и проверки полного локального START, сервер устанавливает совместимый пакет. P04 для продукта не отменён; claim и расширение recovery/reopening закрыты. Q06 требует отдельного staffAuth/grants и обязательного аудита; user cookie не даёт административный доступ. Данное предметное решение больше не оставлять в ожидании владельца.

4. **Полное покрытие.** Остальные принятые экраны и состояния из живых карт по независимым проверяемым пакетам. Недостающие backend-контракты направляются их владельцам; вёрстка и ошибки продолжаются независимо.
5. **Интеграция и установка.** Проверить контракт/права/браузер/визуал, передать серверу точный пакет с контрольными суммами, установить на постоянном полигоне, выполнить smoke и сохранить результат. Следующий пакет не ждёт отдельного «дальше».

Начальная вспомогательная страница Auth — временный инструмент проверки. Её полезные договорённости/код передаются фронтенду; параллельный второй продуктовый интерфейс не развивается.

## Проверка каждого пакета

- Согласованный дизайн, фокус/клавиатура, читаемость, переполнение, мобильные и десктопные размеры; RU/EN в предусмотренном объёме.
- Переходы, обновление и прямое открытие маршрута, loading/empty/error/unknown, повторный клик и истечение доступа по контракту.
- Реальный API, проверка входных данных и серверного доступа; никакого staff-доступа через пользовательскую cookie. Секреты отсутствуют в bundle/логах.
- Проверенный lockfile/build, обязательные repository checks и соразмерные компонентные/интеграционные/браузерные проверки. Визуальный скриншот не заменяет проверку поведения.
- Установка фиксирует точные версии frontend/API/SQL, источник артефакта, smoke и rollback. Перезапуск не пересоздаёт базу, ключи или пользовательские контексты.
- Разрушающие проверки/restore выполняются на отдельных копиях. Успех восстановления подтверждается содержимым, а не только созданием backup.

## Статусы и вопросы

Использовать отдельные статусы: **дизайн сверён / реализована вёрстка / подключён API / проверено / установлено**. «Ожидает API» указывает точный контракт, ведущего и независимые оставшиеся шаги. «Не реализовано» не превращается в нулевые данные или фиктивный успех.

Существенные новые продуктовые правила, расходы, изменения безопасности и неустранимые системные блокировки направляются в административный чат. Обычные технические зависимости решаются напрямую. Персональный ключ второго владельца отложен по его ответу; этот шаг требуется перед его доступом, но не тормозит реализацию.

## Условие завершения всего поручения

Реестры обоих приложений покрывают текущие утверждённые экраны; проверены четыре клиентских варианта и админка; поддерживаемые действия проходят через API/БД; готовые сборки установлены; есть инструкция входа, карта доступных сценариев, проверенные restart/restore и честно обозначенные закрытые функции. Разрешение работы не приравнивается к пройденной приёмке полного продукта или запуску реальных операций.
