По поручению владельца после [сверки BI-01–BI-04](qa/business-interface-reconciliation-2026-10-27/README.md) выполнены [адресные исправления интерфейсов/сводок](design/client/business-rule-fixes-2026-10-27/README.md), подготовлен [технический план 139](139_shadow_technical_implementation_plan_2026-10-27.md). **19.10.2026 · прямое поручение владельца: остановить дальнейший технический разбор, сохранить план и вернуться к незавершённым интерфейсам.** Этот порядок заменяет предложения «следующий шаг» в технических записях 130–137 и журнале ниже. Документ сохраняет очередь; сам по себе не запускает её выполнение.

## Где остановились

Последний завершённый технический пакет: [аудит 137](137_profile_activation_audit_2026-10-19.md), [PR №41](https://github.com/denius89/polymarket-copy-trading/pull/41), main `50261b3617500311bccb57438db3d96a2b1ea7ea`. Принятые правила — [реестр ADR](decisions/README.md), последние ADR-0049–0059. Все документы, публичные записи и проверки сохранены в GitHub; незавершённые идеи не объявлены реализацией.

Ни один рыночный профиль не включён: [JSON](policies/paper-clob-market-profiles-v1.json) сохраняет runtimeEnabled=false. Физический engine/ledger/adapters, деплой и реальные сделки не начинались. Продолжать сбор потоков, исследования комиссий или программирование сейчас не нужно. Принятые бизнес-решения сохраняют силу; пауза не отменяет их и не закрывает оставшиеся вопросы.

## Ближайшая очередь: интерфейсы

1. Вернуться к текущему просмотру клиентских экранов и админки с владельцем/коллегой. Интерфейсы **не считать законченными**. Начинать с актуальных карт [клиента](design/client/sitemap.md), [админки](design/admin/sitemap.md), [handoff клиента](../design/client-ui-kit/HANDOFF.md) и спецификаций [117](117_user_interface_technical_specification_2026-10-09.md)/[115](115_admin_console_technical_specification_2026-10-09.md)/[116](116_admin_user_interface_consistency_2026-10-09.md), а не с исторического списка технических задач.
2. Составить короткий актуальный список незавершённых экранов/маршрутов и замечаний по выбранному пользователем сценарию. Этот checkpoint не является новой проверкой Figma и не подменяет текущие замечания старым аудитом.
3. При согласованных правках сверить влияние уже принятых решений: бюджет/фиксированный и процентный размер/лимиты, предупреждения при изменении активной сессии, copied/manual части, сокращения после 14-го дня, строгий финал/reset, late/unknown/dust, одна SELL, причины пропусков и соответствующие admin-состояния. Сначала определить затронутые состояния; не переносить backend-детали на пользовательские экраны и не начинать общий редизайн автоматически.
4. Проверять RU/EN × mobile/desktop, навигацию туда/обратно, сохранение контекста, сообщения/ошибки/ожидания и ясность финансовых чисел. Видимый макет, граф переходов и фактический ручной проход — отдельные доказательства. Незавершённые Present/loading/error проверки не объявлять пройденными.
5. После каждого согласованного блока обновлять handoff/карты/связанные спецификации и сохранять GitHub-пакет по действующему git-процессу. Критерий окончания этапа — завершение согласованного интерфейсного scope и зафиксированные результаты просмотра, а не количество нарисованных экранов.

В этой задаче Figma не открывалась и не редактировалась. Следующая работа — продолжение интерфейсов; конкретный экран определяется текущими замечаниями владельца. Сохранённый технический backlog не должен перехватывать этот приоритет.

## Отложенный технический план — после интерфейсного этапа и возвращения к нему владельца

| Порядок | Задача | С чего возобновить / результат |
|---|---|---|
| 1 | Освежить контекст | Читать актуальные main/ROADMAP/PROJECT_STATE и 130–137; сверить изменения интерфейсов/ADR. Датированные API-наблюдения и inspected SDK не считать автоматически свежими. Не повторять весь аудит с нуля. |
| 2 | Закрыть оставшиеся бизнес-детали реализации | Частичный SELL/отмена и частота сверки; достоверное время, IANA/календарная граница периода; версии/атрибуция отчёта. Использовать уже принятые части/стоимость/хвост, версии бюджета и BL-08 из 133–135. Нерешённые продуктовые варианты обсуждать отдельно, без выдуманных defaults. |
| 3 | Доказать временную пригодность профилей | 136/137 и QA-пакеты: связь source timestamp с publisher clock, совокупная ошибка ≤250 мс, monotonic age ≤2 с и snapshot acquisition ≤1 с, recovery/reorder/duplicate/failover. Локальный SNTP и HTTP /time сами по себе этот gate не закрывают. |
| 4 | Проверить расходы/внешние сетки по семействам | Polymarket CTF v1 — ближайший кандидат, затем отдельное evidence для v2; Limitless legacy и COLLATERAL проверять раздельно. Нужны authoritative raw fee/settlement vectors, единицы, precision, rounding и доказанная верхняя оценка расходов при разбивке/задержке. Две площадки остаются в целевом продукте. |
| 5 | Разрешить legacy Limitless | См. 137: whitepaper и текущая fee table расходятся; inspected SDK 1.2.0 использует rank/fallback вместо доказанного effective rate и более строгую сетку количества. Нужны авторитетный calculator/quote либо связанный с deployed implementation исходник, fee-owner context и проверка BUY/SELL/partial/delayed/fee-disabled. Не интерполировать тариф и не писать внешним участникам без отдельного поручения. |
| 6 | Принять решение о реализации ограниченного paper-среза | Только после возвращения владельца к этому этапу: согласовать scope, реализовать транзакционный ledger/idempotency/CAS, версии настроек/профилей и честные blocked-состояния; проверить инварианты по сохранённым exact/reference fixtures. Наличие этого плана не снимает gates разработки приложения. |
| 7 | Проверить возможность активации | Отдельная матрица по каждому конкретному market/venue/order-shape/fee-owner профилю. Включать только прошедшие проверки; неизвестное не заменять нулём. AMM, production/deploy и реальные сделки сохраняют отдельные ограничения/поручения. |
