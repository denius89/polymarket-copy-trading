# Backend review: идентичность события и доставка

По supplied описанию обнаружены два существенных дефекта; схемы, код и работающие API не предоставлены.

**Высокий риск потери событий:** глобальный dedup key `event_id` смешивает Polymarket и Limitless. При одинаковом ID второе независимое событие может быть отброшено либо конфликтовать при вставке. Минимальное предложение — ключ `(venue, event_id)`, если ID уникален внутри venue. Если его область уже, дополнительно нужны документированные сеть/тип/позиция события. Это предложение для проверки контракта, а не выполненная миграция. Повтор того же события одной площадки должен подавляться, событие другой — сохраняться.

**Высокий риск повторного денежного действия:** запись outbox подтверждает устойчивость намерения внутри БД, но не external exactly-once. Возможен сценарий: площадка приняла заявку, worker упал до локальной отметки, после рестарта повторил отправку. Нужны атомарность бизнес-изменения и outbox, стабильный operation/idempotency key и проверенная семантика площадки. При неопределённом ответе — unknown, сверка по внешнему идентификатору и запрет слепого повтора. Обещание «сверка не нужна» следует убрать.

План проверки: два venues с одинаковым ID принимаются; конкурентные повторы одного события создают одно намерение; crash до/после внешнего принятия и timeout не вызывают неподтверждённую повторную отправку. Эти проверки предложены, не запускались. Внешние гарантии остаются not_verified.
