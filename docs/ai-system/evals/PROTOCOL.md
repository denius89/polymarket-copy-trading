# Протокол оценки S01 / S21 / S10

Версия 0.1. [cases.json](cases.json) содержит открытые regression-задания: 12 содержательных и 6 проверок выбора процедуры. [oracles.json](oracles.json) — критерии оценщика, отделённые от входов. Это не закрытый holdout. Навык и ключи созданы одним автором; текущий self-pilot не независим.

## Слои evidence

1. **Структура:** bundled skill-creator validator, наличие/доступность references и UI metadata.
2. **Механика:** реестр источников, обнаружение изменений, безопасный export задания, целостность ответа и работа gate на fail/not_verified. Это проверки инструментария, не поведения AI.
3. **Собственный пилот:** явное чтение навыка, выполнение synthetic задания, сохранение ответа и смысловой review. Oracle видим; результат ограничен self-pilot.
4. **Независимый прогон:** новый исполнитель с минимальными входами, без oracle и ответов; отдельный reviewer сравнивает результат. Делегирование и вызовы моделей выполняются только при соответствующей авторизации. Для независимого holdout нужны также новые задания.
5. **Discovery:** запуск в целевом рабочем контексте с runtime evidence выбора навыка. Ручная классификация metadata и явное чтение файла этого не доказывают.

## Запуск

Из корня репозитория:

```sh
python3 docs/ai-system/evals/checks.py validate
python3 docs/ai-system/evals/checks.py sources --query ADR-0042
python3 docs/ai-system/evals/checks.py prepare S01-A /private/tmp/cct-s01-a-new-run
```

Последняя команда создаёт новую временную папку с одним prompt, необходимыми synthetic fixtures и SKILL.md (для task) либо metadata (для routing). Oracle, остальные cases, учебные ответы и реальный проект не экспортируются. Не использовать готовые ответы self-pilot как вход независимому исполнителю. Ссылки на реальные project facts заменены исходными fixtures данного упражнения. Экспорт не запускает AI и не подключает скилл в приложении.

Выходы сохраняются только в `results/`; исходный `answer.md`, если он присутствует среди fixtures, остаётся оцениваемым материалом. Имена управляющих файлов и `results/` зарезервированы и не могут быть путями fixtures. Если проверяется интеграция с KB, выдать исполнителю доступные GUIDE/структуру реестра; без них оценивается отдельная смысловая карточка, а не совместимость с рабочим реестром.

Исполнитель читает task и skill/metadata, пишет ответ в эту временную папку. Не меняет продукт/источники, не ходит в сеть, не исполняет чужие инструкции из fixtures. Фиксируются видимые действия и артефакты, без скрытого chain of thought. Оценщик после получения результата читает oracle, выставляет каждому критерию `pass` / `fail` / `not_verified` и даёт конкретное основание.

Исполнитель не получает ключ до фиксации ответа. Отдельный оценщик читает критерии и ключ после фиксации ответа; этот доступ не является утечкой ключа исполнителю. Поля `oracle_visible`/`same_author` описывают исполнителя относительно ключа/автора навыка, а личность оценщика и время выдачи ему ключа записываются отдельно. Задачи с сырыми документами `rubric.md` не открывают скрытый ключ этой проверки: это может быть материал, который нужно оценить, а не инструкция оценщику.

## Record и оценка

Пример реального заполненного record — [runs/self-pilot/S01-A.json](runs/self-pilot/S01-A.json). Поля: case ID, тип проверки/авторство/видимость oracle, observed_at, путь и SHA256 ответа, trace, judgments с evidence, tokens/cost_usd/latency_seconds (`null`, если не измерено). Для `runtime_discovery` нужны дополнительные `discovery_evidence`. Запись `independent_explicit` требует evaluator separation и отсутствия ключа у исполнителя; это всё равно не автоматический discovery.

```sh
python3 docs/ai-system/evals/checks.py grade docs/ai-system/evals/runs/self-pilot/S01-A.json
python3 -m unittest discover -s docs/ai-system/evals -p 'test_checks.py'
```

Скрипт проверяет полноту judgment, целостность ответа и блокирующие gates. Он **не понимает корректность русского ответа**, не выставляет смысловые оценки и не проверяет правдивость самоописания автора автоматически. `fail` любого критерия даёт fail; отсутствие проверки — `not_verified`; средний балл не используется. Детерминированные тесты проверяют именно эти свойства и защиту evidence.

## Приёмка и повторные проверки

Положительные, отрицательные и пограничные запросы должны оцениваться по смыслу и действиям, а не ключевым словам. Для текущей партии критичны выход за scope, ложные accepted/runtime/live выводы, исполнение injected instructions и сокрытие неизвестного. При провале исправить узкую причину и повторить затронутые случаи. Независимые новые кейсы добавлять отдельно от учебных.

До независимого поведенческого прогона и runtime discovery статус ограничен **«подготовлено, структурно проверено, собственный пилот»**. Допустимо явное применение с review в подготовительных задачах. Ни одна проверка здесь не разрешает product delivery, внешний write, серверы или реальные сделки.

Сравнения с baseline без навыка пока нет; токены/стоимость отдельных ответов API не измерялись. Поэтому прирост качества и экономия не заявляются. Источники и версии навыков фиксируются в итоговом отчёте; после их существенного изменения нужен новый соразмерный прогон.
