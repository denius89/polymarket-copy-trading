# S01 · Пакет «Удерживать рамку существующего проекта»

Версия 0.1 · prerequisites: понимание различия документа/решения/реализации. Область: подготовка и документальные задачи; полномочия на продукт не добавляются.

**Компетенция:** выбрать актуальную область задачи и исходные материалы, не перепутать checkout и не подменить запрос более широким планом.

**Обязательное чтение:** KB01–KB03, KB05–KB08 из [реестра](../knowledge/sources.json); по необходимости KB04. Прочитать применимые AGENTS, начало очереди/журнала, ADR-0002/0007/0008 и статус ADR-0042. Остальные главы читать только по вопросу.

**Правила с исключениями:**

- Следующая задача из документа не равна поручению выполнить её сейчас. Исключение: пользователь прямо поручил эту работу; тогда учитывать его новую цель и сохраняющиеся ограничения.
- Старый handoff полезен для причин решений. Он не заменяет более позднее принятое решение. Новая дата черновика также не отменяет ADR.
- Dirty checkout — основание сохранять чужое, а не обнулять репозиторий. Read-only анализ обычно можно продолжить.
- Имя исходного checkout — подсказка, не вечный идентификатор. После переноса проверять фактические метаданные; при неоднозначности не выбирать случайный корень.
- Baseline выбирается по виду вывода. Для ответа о статусе локального ADR не нужна полная live-сверка Figma; для утверждения о текущем макете одного Git-файла недостаточно.

**Разобранный пример:** пользователь просит «подготовь учебный пакет работы с БД». ADR описывает предлагаемый PostgreSQL. Корректный результат — учебный пакет с пояснением статуса предложения и источниками. Установка PostgreSQL и создание миграции не следуют из запроса.

**Самостоятельная практика:**

1. В старом брифе одна площадка, в принятом ADR две. Подготовить трёхпредложную рамку для аудита знаний API без запуска интеграции.
2. В ROADMAP следующей указана UI-задача, пользователь поручил только три навыка. Какие материалы нужны, какие действия разрешены?
3. Исторический журнал сообщает успешную проверку. Что можно сказать без её повторения и когда нужна новая проверка?

**Критерии:** сохранить цель пользователя; назвать правильный checkout/основания; не запускать смежные действия; отделить собственную проверку от исторической. Чёткие данные не требуют лишнего вопроса. Неразрешённое изменение или ложное утверждение о реализации — критический провал. Проверки suite — отдельные задания, не повтор этих ответов.
