Сохранить полезные результаты раздельно: screenshot подтверждает визуальный RU mobile paper happy path только build b7; 100% unit coverage относится к formatters. Recorded fixture охватывает venue P и одного tenant. Это основания для повторного использования узких проверок, но изменения permissions и withdrawal retry требуют других свидетельств. Mock с немедленным completed исключает опасные промежуточные состояния и не служит независимым oracle исполнения.

Минимальная acceptance matrix по риску:

1. Tenant/permissions: tenant A читает и изменяет только A; запросы к B отклоняются без выдачи данных и побочных изменений. Support получает только чтение. Проверить прямые запросы, смену роли и revoke во время pending операции. Oracle — заданная policy и независимая проверка состояния tenant B. Сейчас границы tenant/permissions не проверены.
2. Withdrawals: recorded/synthetic timeout после отправки, unknown, duplicate, late/out-of-order receipt, отказ и recovery. До reconciliation unknown не разрешает повторную отправку; один intent не создаёт два списания, остатки и резервы меняются только по подтверждённым переходам. Отдельно проверить гонку двух запросов на один бюджет; ожидаемые суммы брать из независимого ledger, а не formatter/mock.
3. Client/admin E2E: провести изолированный пользовательский путь withdrawal со статусами и admin/support путь с отказами полномочий. Сейчас client runtime E2E не подтверждён, admin E2E явно не запускался; новый план не повышает эти статусы.

По локалям RU имеет только визуальный кадр, EN не проверена; mobile runtime и desktop неизвестны. По venues P имеет только recorded evidence, вторая venue не проверена. После денежных и permission сценариев достаточно целевых RU/EN проверок новых статусов и доступности на mobile, с отдельной фиксацией оставшихся пробелов.

Реальный withdrawal на $1 исключён условиями задачи и не закрывает перечисленные риски. Приёмка ограничивается выполненными изолированными сценариями; обе venues готовыми объявлять оснований нет.
