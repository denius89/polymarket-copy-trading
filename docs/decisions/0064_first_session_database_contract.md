# ADR-0064: Контракт данных первого сценария

28.10.2026 · **Принято владельцем поэтапно в чате «Copy Trading — база данных». Только проектирование; код, SQL, миграции и развёртывание не поручены.**

Baseline чтения и подготовки: main `f2d8a6b9f3107105a8dfe4fac1cb1c7bdddd11b5`. Основание — последовательные подтверждения владельцем предложений ниже, от одной БД с разделением Auth/Shadow до сохранения истёкших черновиков/проверок. Это фиксация состоявшегося обсуждения, не автоматическое принятие всех прежних предложений T0.

## 1. Размещение, личность и доступ

- Для первого полигона одна база PostgreSQL, отдельные схемы Auth и Shadow, разные служебные роли и минимальные права. Разделение названий само по себе не ограничивает доступ. Совместимость конкретного состава/версии Supabase ещё проверить.
- У аккаунта Shadow постоянный собственный ID; отдельная AuthIdentity связывает его с подтверждённой личностью провайдера. Одна личность провайдера не связывается с двумя пользователями Shadow. Email не объединяет аккаунты автоматически и не даёт staff-права. Удаление записи провайдера не удаляет каскадно историю Shadow; перенос привязки требует доверенной процедуры.
- Каждый login — отдельная запись с типом/владельцем, неизменяемой версией политики сроков, временем полного входа/подтверждённой активности, предельным сроком и состоянием/причиной отзыва. Refresh не новый вход; политика денег отделена от политики входа. Секреты не помещаются в обычные поля или журнал.
- Для рабочего входа создание нового login, отзыв старого и обновление указателя текущего выполняются неделимо после успешной проверки passkey и назначения. Неуспешная/незавершённая попытка старый login не отзывает. Конкурентные успешные входы оставляют один действующий login на физического сотрудника; несколько назначений не обходят это правило. Пользовательские входы на разных устройствах остаются независимыми.
- Assignment хранится отдельно от login: сотрудник, согласованная роль, scope, статус, срок и версия. Каждый административный просмотр проверяет текущие права; роль при входе не является разрешением на весь его срок. Разрешённое чтение аудитируется. Владелец 1 и владелец 2 имеют отдельные равноправные назначения; реальные идентичности и секреты в Git не записываются.

## 2. Черновик и проверка

- Черновик хранится на сервере. Гость доказывает владение защищённым случайным handle; после подтверждённого входа сервер привязывает конкретный черновик к пользователю. Одного draftId недостаточно. Межустройственное восстановление до подтверждённой привязки не обещается.
- Допустимо несколько независимых черновиков пользователя с отдельными версиями/сроками. Продолжается конкретный черновик входа; автоматического слияния/перезаписи нет. Запуск использует только свой черновик; остальные сохраняются, не обходя одну текущую сессию. Отдельный экран управления черновиками не добавляется.
- Draft содержит только актуальный ввод и version, без полной истории каждой правки/undo. Устаревшее сохранение не перезаписывает новый ввод. Неактивные поля формы не становятся действующими настройками.
- Review — отдельный неизменяемый снимок показанных параметров, выбранного mode/зоны, владельца, draftId и проверенной draft version, policy/catalog/control versions, slot generation, времени и срока. Это копия значений, не зависимость от сохранности прежней редакции изменяемого draft. После гостевого входа нужна новая привязка/проверка.
- Сроки остаются прежними: draft 7 дней после сохранения изменений, review 10 минут после серверной проверки; чтение и одинаковый повтор не продлевают их. Изменение значимых условий требует новой проверки и отдельного подтверждения.
- **Только на синтетическом полигоне** истёкшие draft/review физически сохраняются до отдельной плановой очистки после проверенной копии. Истечение запрещает продолжение/запуск и не возрождается чтением. Очистка сохраняет настройки сессий, финансовую историю и защиту от повторного исполнения команд; её механизм ещё проектируется. Это не политика хранения реальных персональных данных.

## 3. Запуск и результат команды

- Номер команды создаётся до отправки и сохраняется при повторах/обрыве связи. Уникальность: environment + постоянный actor (user или отдельный staff principal) + commandType + key. Область не зависит от login/браузера/устройства. Одинаковые key/payload возвращают прежний итог, иной payload — конфликт. После новой проверки новое явное намерение получает новый key; доступ проверяется заново.
- Окончательные проверенные бизнес-отказы сохраняются в receipt. Ошибка БД/неизвестный сетевой исход не превращаются в долговечный отказ: выясняется результат, при необходимости повторяется прежняя команда. Ключ не заменяет авторизацию. Auth credentials не включаются в обычные receipt/hash журналы.
- UserSessionSlot единственный по user/environment/paper, общий для Polymarket и Limitless. Строка блокируется при запуске; generation не позволяет использовать проверку прежнего состояния после смены слота. Первый commit занимает слот; конкурентный запуск получает свой current-session/отказ без второго funding. Освобождение только по строгому финалу ADR-0051; команды завершения в этот срез не входят.
- Одна транзакция сохраняет session, settings revision 1, initial funding и journal, snapshot 1, slot/generation, отметку использованного draft, успешный receipt, audit и outbox. Всё либо ничего; ответ после commit. Потерянный ответ восстанавливается по исходному ключу.
- Повторная проверка допуска и запись запуска согласованы с изменением прав, правил и доступности трейдера. Ограничение первым — отказ; запуск первым — сохранённый результат/версии, затем действие ограничения по его правилам без удаления истории. Механизм сериализации, точные locks/isolation/retries ещё проверить.

## 4. Учёт, точность и ограничения

- Journal — источник денежных сумм; FundingFlow объясняет происхождение, не прибавляется к учёту вторично. Snapshot — сохранённая производная, восстанавливаемая из учёта и относящихся версий состояния; отдельно редактировать его баланс нельзя.
- Перед commit база проверяет уравновешенность journal и единственность initial funding на session. Для старта — две противоположные записи в одной единице virtual_USD; точная сумма ноль. Нельзя компенсировать разницу смешением единиц. Отрицательная запись источника не долг пользователя. Исторические записи не редактируются: исправление отдельной корректировкой с причиной; команда исправления не входит в первый срез.
- Денежные величины и внутренние доли хранятся парой целых n/d: d>0, gcd=1, ноль=0/1. Интерфейсное округление не меняет учёт; превышение технического предела отклоняется без скрытого округления. Тип хранения уточнён принятым дополнением ниже; пределы чисел и производительность ещё проверить.
- Процентные настройки — целые сотые процентного пункта: 3%=300, 3,5%=350, расчёт через /10000 точно. Возможность представить число не расширяет допустимые диапазоны/шаги ADR-0058. Формат DTO/API должен передавать единицы однозначно; его точные имена/версия ещё проектируются совместно.
- База проверяет принадлежность settings/funding/journal/snapshot своей сессии, currentSession владельцу/среде слота, Trader площадке/источнику и Review владельцу Draft. Ошибочная связь отклоняет сохранение; это не заменяет серверную авторизацию.
- Опубликованные версии правил неизменяемы и содержат полный набор правил; действующая выбирается отдельным указателем. Review и settings сохраняют использованную версию. История не пересчитывается по новой публикации; значимые изменения до запуска требуют нового review.

## 5. Чтение и события

- Snapshot неизменяем и связан с session, settings revision, ledger sequence и asOf. Клиент/админка получают целую разрешённую версию; старый ответ не откатывает новую. Snapshot 1 доступен после commit без ожидания worker.
- AuditEvent и OutboxEvent — разные сущности. Audit хранит неизменяемый факт/результат, outbox — постоянный ID события и изменяемое состояние доставки. Повторная доставка распознаётся получателем и не повторяет выполненное действие. Initial funding выполняется только транзакцией запуска; outbox не создаёт его повторно. Конкретная схема обработки сбоев потребителя ещё проверяется, exactly-once внешнего эффекта не обещается.

## 6. Следствия и незакрытые вопросы

Нормативная карта и ограничения — [data-model](../technical/first-session/data-model.md); общий контракт [команд](../technical/first-session/commands.md) и [приёмка](../technical/first-session/acceptance.md) обновлены совместно. Два чата используют эти документы; факт автоматической синхронизации переписок/сообщения другому чату не заявляется. Множественные черновики и их retention отражены в общей точке входа для административного обсуждения.

Открыты пределы чисел/размеры/окончательные имена полей, API schemaVersion и точные DTO, техническое исполнение guest claim и Auth/Owner policy, порядок locks/isolation/retries, дополнительные индексы по измеренным запросам, протокол consumers/dedup, исполнение очистки и совместимых миграций/restore. Принятые базовые типы, владение и компактная запись защиты команды уточнены ниже. Сроки рабочего сервиса и реальных персональных данных не выбраны. T1/T2 не начаты; тесты будущей БД/API не выполнены. BUY/SELL, резервы, отчёты, score и live не добавляются.


## 7. Принятое дополнение: владение, чтение и физические типы

28.10.2026 · Последовательные подтверждения владельца после PR №136, включая последнее «да» на минимальный подход к индексам. Baseline: main `476ec7d35db0845ce0bd510543f5bf94ca8d7b5c`. Всё ещё только проектирование.

1. **Однократный guest claim.** После полного входа и доказанного владения атомарно закрепить draft за пользователем, закрыть доступ прежним guest handle и сохранить факт привязки. Повтор тем же пользователем возвращает прежний результат; другой аккаунт присвоить draft не может. Перед запуском новый review.
2. **Неизменяемые записи владения draft.** Первая фиксирует гостя без самого секретного ключа, следующая — передачу аккаунту. Draft указывает на действующую запись; каждый review — на запись, действовавшую при проверке. Историческое владение не даёт текущего доступа и не требует истории всех правок формы.
3. **Версии трейдера.** Постоянный Trader содержит venue/source/external ID, отдельная неизменяемая TraderRevision — использованные имя, происхождение и версию каталога. Review/session ссылаются на конкретную revision; актуальная eligibility проверяется отдельно. Полная статистика не копируется в каждую сессию.
4. **Выдача данных в админку.** Данные возвращаются только после сохранения события «Данные разрешены к выдаче»: staff/assignment, session/snapshot version, серверное время и request ID. Проверка прав, выбор снимка и запись события согласованы. Сбой записи — отказ выдачи с возможностью повторить запрос. Событие не доказывает доставку/фактический просмотр экрана.
5. **Компактная защита команды.** Даже после будущего разрешённого удаления подробного ответа сохраняются environment/actor realm/actor/command type/key, request fingerprint, окончательный исход и ID результата, если создан. Старый key не исполняется снова; недоступность подробностей объясняется явно; иной payload конфликтует. Сейчас на полигоне сохраняются полные receipts; cleanup ещё не реализован.
6. **Собственные ID — UUID v4.** Сервер создаёт ID ресурсов; клиент создаёт command ID до отправки. PostgreSQL uuid, API — стандартная строка. Provider/venue IDs отдельные, вместе с источником; счётчики версий остаются целыми. UUID не доказательство доступа.
7. **Моменты — timestamptz.** Серверные моменты создания/запуска/истечения/отзыва; API UTC с Z. IANA-зона сессии отдельная. Вычисленный evaluation deadline хранится вместе с зоной и версией расчёта. Правило 14 календарных дней сохраняется; выбор DST-разрыва/повторения ещё не принят этим типом.
8. **Базовые типы.** n/d — numeric без объявленного округляющего scale, с проверкой конечных целых и правил дроби; проценты — integer; версии/последовательности — bigint с допустимыми границами; статусы/типы — text с ограниченным списком значений. Большие целые в API — строки. Numeric(p,0), приводящий дробь к целому округлением, не подменяет проверку. Предел длины n/d ещё выбрать до реализации.
9. **Колонки и JSON.** Владельцы, ссылки, деньги, настройки, статусы, версии и сроки — обычные типизированные поля. Jsonb — дополнительный безопасный контекст предупреждений/причин/событий; у него описаны структура, версия и предел размера. Корректность JSON не доказывает контракт. Нет второй независимо редактируемой копии денег/владельца внутри JSON.
10. **Обязательность и NULL.** Обязательные владельцы (с учётом guest/account варианта), среды, ссылки, версии и created timestamps заполнены. Денежные суммы созданной сессии точные и заполненные; нули подтверждают EMPTY, не неизвестность. NULL только с заданным смыслом: нет current session, нет отзыва, невыбранное F либо q. В effective settings действует ровно выбранный mode. Отзыв login требует даты и причины.
11. **Минимальные индексы.** Сначала ключи и уникальность slot, команды, settings/snapshot versions, Auth identity, Trader identity, initial funding. Дополнительные индексы — под конкретные backend-запросы после проверки выполнения на test-БД. Это план, не измеренная производительность.

Свойства типов сверены 28.10.2026 с официальными документами PostgreSQL: [UUID](https://www.postgresql.org/docs/current/datatype-uuid.html), [время и отдельная IANA-зона](https://www.postgresql.org/docs/current/datatype-datetime.html), [numeric и округление](https://www.postgresql.org/docs/current/datatype-numeric.html), [ограничения](https://www.postgresql.org/docs/current/ddl-constraints.html), [jsonb](https://www.postgresql.org/docs/current/datatype-json.html). Страница current не фиксирует версию будущего развёртывания; версии/совместимость состава ещё проверить.
