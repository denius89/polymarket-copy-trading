# ADR-0063: Supabase Auth для входа пользователей

27.10.2026 · Статус: **принято владельцем — выбор провайдера пользовательского входа**.

## Основание и решение

Владелец подтвердил: «Да, согласуем Supabase Auth. И хочется еще гугл 2фа». Выбран **Supabase Auth** для email passwordless-входа пользователей Shadow. Основной способ — код из письма, возможность одноразовой ссылки сохраняется по ADR-0048. Наш сервер сохраняет владение прикладными данными/правилами, проверяет вход и права; Supabase identity не является финансовой сессией или назначением сотрудника.

Это выбор провайдера, не создание аккаунта, подключение сервиса, покупка тарифа, выбор региона/хостинга всей БД или запуск кода. Модульная основа ADR-0062 сохраняется.

## Запрошенное дополнение и открытые детали

- Запрос «гугл 2фа» предварительно трактуется как Google Authenticator / совместимый TOTP, не Google OAuth. Поддержка у провайдера подтверждена документацией. Обязательность, первый релиз/срез и восстановление при утрате фактора ещё не согласованы.
- Amazon SES, числовые ограничения email-кодов, добровольность TOTP для paper и условия безопасного восстановления описаны в [предложении](../technical/first-session/auth-policy.md). **Не считаются принятыми вместе с провайдером.**
- Вход персонала/владельцев, роли, ключи и денежные подтверждения остаются отдельным решением. Email+TOTP не заменяет принятые независимые подтверждения владельцев.

## Проверка до реализации

Проверить совместимость управляемого Supabase с серверными cookies/отзывом, защищённым продолжением черновика и полным контрактом входа. Лимиты должны действовать не только в UI, но и при прямом обращении к Auth endpoints. Серверная проверка второго фактора обязательна для выбранного защищённого scope. Установка, API-эксперименты с аккаунтом, код и Figma не выполнялись.
