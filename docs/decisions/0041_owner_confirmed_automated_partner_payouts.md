# ADR-0041: Выплаты после подтверждения Owner с автоматическим исполнением

Дата: 09.10.2026. Статус: принято основателем.

## Решение

- Owner открывает партнёра, выбирает площадку и доступный маршрут, проверяет реквизиты, весь доступный баланс и комиссию, затем нажимает «Выплатить» и «Подтвердить» в админке. Подключение внешнего кошелька и ручная подпись каждой выплаты не являются обязательными шагами пользовательского сценария.
- После подтверждения система резервирует обязательства, проверяет Owner, актуальные условия, доступность маршрута, источника, средств и аварийные ограничения; выполняет авторизацию/подписание и отправку через адаптер выбранной площадки; отслеживает и сверяет результат. Подтверждение Owner само по себе не означает выплату и не заменяет evidence исполнения.
- Все принятые правила ADR-0037/0040 сохраняются: два личных Owner-аккаунта, Owner-only, полный доступный баланс выбранной площадки, неподтверждённые начисления исключены, расчёт USDT 1:1 с USD, плательщик комиссии настраивается Owner, audit, запрет повторной отправки при unknown.
- Средства только собственные средства сервиса. Партнёрские выплаты не выполняются из пользовательских кошельков. Собственная реферальная задолженность рассчитывается Shadow, а не принимается как встроенная функция withdrawal API площадок.
- Limitless: целевой способ — managed server-wallet withdrawal API при наличии поддерживаемого собственного кошелька сервиса и права withdrawal. Получатель должен соответствовать разрешённым адресам; управление allowlist требует отдельной авторизации. Наличие API не подтверждает, что собственные поступления сервиса уже доступны в таком кошельке.
- Polymarket: целевой способ — программный перевод собственного кошелька сервиса через SDK/поддерживаемый wallet flow; Bridge API используется для подтверждённых межсетевых/межвалютных маршрутов. Нужны отдельные полномочия signer; торговые и Builder API credentials сами не заменяют подпись перевода.
- Права API, разрешённые адреса и защищённый signer настраиваются при интеграции. Секреты не раскрываются в UI, браузере, журнале или репозитории; финансовое право API/signer ограничивается согласованным контуром сервиса. Конкретный механизм хранения/вызова signer уточняется в техническом контракте.
- Если целевой маршрут не поддерживает этот способ на доступном проекту аккаунте, он показывается как недоступный до решения технической детали; успешное исполнение не имитируется. Новое обязательное подтверждение в другом приложении не вводится молча.
- Это архитектурное решение, не разрешение на live-выплаты. Проверка сетей, активов, маршрутов, получения комиссий и источников средств остаётся на этапе интеграции API до live. Обязательная вторая подпись каждой выплаты не вводится.

## Официальные основания

- [Limitless withdrawal](https://docs.limitless.exchange/api-reference/portfolio/withdraw): server wallet, withdrawal scope, допустимые destination и allowlist.
- [Limitless Programmatic API](https://docs.limitless.exchange/developers/programmatic-api): backend-only HMAC credentials и managed wallets.
- [Polymarket Builder Fees](https://docs.polymarket.com/programs/builders/fees): начисленные builder fees распределяются в связанный с builder profile кошелёк.
- [Polymarket Wallets and Authentication](https://docs.polymarket.com/trading/wallets-auth): программный transfer ERC20 и wallet-specific signer/relayer flow.
- [Polymarket withdrawal](https://docs.polymarket.com/trading/bridge/withdraw): подготовка bridge destination, отдельная отправка средств и status tracking.

## Проверка

Owner видит один confirmation в админке; backend отказ для других ролей; повторный клик не создаёт второй перевод; funds/route/auth unavailable блокируют отправку; unknown сохраняет резерв; paid только после сверки полной суммы с применённой комиссией. Интеграционный gate подтверждает реальный собственный источник и полномочия до включения live.
