# Текущая очередь проекта

Срез на **9 октября 2026**. По прямому поручению владельца подготовлен [полный технический документ админки 115](115_admin_console_technical_specification_2026-10-09.md) и выполнена [сверка с пользовательским UI 116](116_admin_user_interface_consistency_2026-10-09.md). Подготовлено [задание на дизайн админки 118](118_admin_console_figma_design_brief_2026-10-09.md); сначала совместная вычитка с коллегой. Дизайн и реализация админки не начинались.

Согласовано [ADR-0030](decisions/0030_shadow_funding_interface_emergency_controls.md): DEPOSITS_OFF / WITHDRAWALS_OFF управляют доступностью функций через Shadow, отдельно для обеих площадок; в demo показаны как не подключённые. Реальное исполнение остаётся за live-gates.

Согласовано [ADR-0031](decisions/0031_admin_permissions_and_autonomous_publishing.md): маркетинг и все тексты публикуются самостоятельно по scopes, с audit/rollback; обязательные согласования внутри админки отсутствуют. Восстановление GLOBAL_STOP/TECH_MODE — Owner и второй независимый подтверждающий.

Согласовано [ADR-0032](decisions/0032_admin_connection_health_and_session_revocation.md): health/metadata обеих площадок и отзыв admin-сессий в первой версии; ротация credentials интеграций следующим этапом.

Согласовано [ADR-0033](decisions/0033_in_app_marketing_first_external_campaigns_later.md): объявления внутри приложения и контроль доставки — первая версия; массовые маркетинговые email/Telegram/push-кампании — следующим этапом.

Согласовано [ADR-0034](decisions/0034_managed_content_and_localization_foundation.md): управляемые тексты, переводы и версии закладываются сразу; конструктор лендинга — отдельный поздний этап.

Согласовано [ADR-0035](decisions/0035_two_owners_and_owner_only_pricing_publication.md): два отдельных Owner, только они публикуют тарифы/реферальные правила/VIP-условия; подготовку можно делегировать. Выплаты партнёрам должны проектироваться через интерфейс финансов; детали исполнения ещё открыты.

Согласовано [ADR-0036](decisions/0036_support_queue_and_conversation_first_release.md): обращения, переписка, назначение сотруднику и связь с сессией входят в первую админку; вложения и SLA позже.

Согласовано [ADR-0037](decisions/0037_partner_payouts_owner_only.md): выплаты партнёрам через интерфейс создают, изменяют и отправляют только два Owner. Сценарий автоматического исполнения принят ADR-0041; конкретные права signer/API и технический контракт проверяются при интеграции.

Согласовано [ADR-0038](decisions/0038_owner_configurable_referral_and_tariff_parameters.md): численные параметры тарифов, реферальные уровни и VIP-условия вводятся вручную Owner через админку, с validation, simulator, versions и effective time. Стартовые числа не блокируют дизайн.

Согласовано [ADR-0039](decisions/0039_owner_assignable_user_vip.md): Owner назначает/изменяет/снимает user VIP в карточке пользователя; срок и индивидуальные параметры настраиваются, история сохраняется; partner VIP отдельно.

Согласовано [ADR-0040](decisions/0040_platform_usd_accounting_and_venue_payout_options.md): единый расчёт в USD по всей платформе; все подтверждённые варианты выплат по выбранной площадке Polymarket/Limitless. Для USDT согласован фиксированный расчёт 1 USDT = $1. Комиссия перевода показывается отдельно; Owner настраивают её плательщика (сервис/партнёр), с preview и сохранением применённого правила. Частичных выплат нет: выплачивается весь доступный баланс выбранной площадки, неподтверждённые начисления исключены. Правила недостатка средств, зависшей выплаты и неизвестного результата согласованы; неизвестный результат блокирует повтор и освобождение резерва до сверки. Сети/активы/маршруты, поступление комиссии и источники выплат проверяются на этапе интеграции API до live, не блокируют дизайн. Принцип автоматического исполнения принят в ADR-0041; конкретные полномочия signer/API и технические контракты исполнения/пересчёта/округления проверяются при интеграции.

Согласовано [ADR-0041](decisions/0041_owner_confirmed_automated_partner_payouts.md): Owner подтверждает полную выплату в админке, система подписывает/авторизует, отправляет и сверяет результат. Внешний кошелёк не является обязательным шагом каждой выплаты. Конкретный доступ обеих площадок проверяется при интеграции до live.

## Текущий цикл

09.10.2026: по решению основателя [117 — техническая спецификация пользовательского интерфейса](117_user_interface_technical_specification_2026-10-09.md) сохранена как есть; открытые вопросы обсуждаем на этапе программирования. Изменение Figma и начало реализации этим сохранением не разрешены.

1. Рассмотреть [техническую спецификацию 115](115_admin_console_technical_specification_2026-10-09.md): полный контур ADM-01–18, данные/API/events, RBAC, pricing/VIP/ledger/payout, content/marketing/support, health/emergency и эксплуатация.
2. Проверить [сверку 116](116_admin_user_interface_consistency_2026-10-09.md): общий user/admin источник состояний; структурно прочитаны 35 опорных Figma узлов в четырёх версиях. Emergency/VIP/announcement UI и свежий Present остаются отдельными незакрытыми задачами.
3. Совместно вычитать [задание на дизайн админки 118](118_admin_console_figma_design_brief_2026-10-09.md): полнота ADM-01–18, навигация/компоновка, сценарии P-01–P-12 и критерии приёмки. После принятия редакции и отдельного поручения начать дизайн пакетами из 118; реализацию запускать отдельным этапом по 115. Технические infrastructure варианты предложены, а не автоматически утверждены; никаких аккаунтов/live действий этот этап не разрешает.
4. Конкретные сети, активы, маршруты, receiving/source accounts, permissions/signer, precision/fee settlement и finality проверять при интеграции API до отдельных venue live-gates.

Изображения и связи последних мобильных и десктопных изменений проверены. В desktop RU/EN убран подтверждённый дубль CTA, возврат сокращён до «Трейдеры» / Traders, ошибочное переключение новой сессии на подготовленный пример удалено, список обращений связан с существующей общей формой поддержки. Ручной Present этой итерации не выполнен из-за отсутствия Computer Use-доступа к Figma; старые проходы не заменяют новую приёмку.

Параллельно подготовлены API-справочники: [Polymarket — открытый PR 14](https://github.com/denius89/polymarket-copy-trading/pull/14), [Limitless — открытый PR 15](https://github.com/denius89/polymarket-copy-trading/pull/15). Оба описаны авторами как draft/documentation only, не объединены с `main`, отстают от него и не являются реализованными адаптерами.

## Gate 1: разрешение проектирования

Можно начинать Figma и детальные wireframes, когда:

- согласованы первый пользователь и основной сценарий;
- основатель и коллега согласовали визуальное направление, UI kit и референсы;
- выбраны интерфейс и набор экранов MVP;
- комиссия имеет один тестовый вариант;
- GEO не требует проектировать заведомо недоступное исполнение;
- продуктовые обещания не содержат гарантии заработка.

## Gate 2: разрешение технических spikes

Можно писать изолированные экспериментальные программы, когда для каждого spike указаны гипотеза, безопасные данные, критерий успеха и предел затрат. Основные проверки:

1. полнота и задержка событий лидера Limitless;
2. Limitless partner capabilities, sub-account и scoped HMAC token без `withdrawal`;
3. Polymarket Builder profile, Session Keys и scoped execution без вывода;
4. delegated/session signing, жизненный цикл ордера и неизвестные состояния на обеих площадках;
5. virtual lots и reconciliation на записанных данных;
6. сквозные пути пополнения на минимальной тестовой сумме;
7. user-controlled recovery/withdrawal path и отзыв автоматизации.

Spike не является началом MVP и не разрешает торговлю пользовательскими средствами.

Исполнимые протоколы и критерии остановки находятся в [плане Polymarket](21_polymarket_access_and_spike_plan.md) и [плане Limitless](22_limitless_access_and_spike_plan.md). Общие результаты фиксируются по [контракту адаптеров](23_dual_venue_adapter_contract.md), чтобы две проверки были сопоставимы.

## Gate 3: разрешение paper-trading MVP

Нужны:

- выбран источник публичных или записанных данных и подтверждено право его использовать;
- согласованные документы 01–03;
- утверждённый user flow;
- схема событий, ledger и инварианты risk engine;
- тестовые fixtures без секретов и персональных данных;
- paper-режим технически не способен отправить реальный ордер;
- отдельное решение основателя о возобновлении разработки.

Аккаунты площадок, trading credentials, delegated signing, funding и withdrawal/recovery не являются gate для paper MVP. Они проверяются позже в authenticated sandbox и live gates отдельно для каждой площадки.

## Следующие этапы

1. **Paper trading:** реальный поток данных, симулированное исполнение, журнал и метрики.
2. **Личный live-тест:** отдельный кошелёк, минимальный капитал и жёсткие лимиты после security review.
3. **Закрытая альфа:** небольшая приглашённая группа после legal/security gates.
4. **Проверка монетизации:** фактический оборот, удержание, поддержка и готовность платить.
5. **Масштабирование:** новые GEO, партнёры и последовательное live-включение второго обязательного execution adapter только после данных предыдущих этапов.

## Ближайший рабочий цикл

Итог выполненной пользовательской Figma-итерации — [отчёт 53](53_design_cycle_final_report_2026-09-30.md). Следующий шаг — пройти с коллегой [инструкцию 54](54_colleague_figma_clickthrough_guide.md), исправить обнаруженные разрывы и затем решить, готов ли дизайн к отдельному frontend-gate. Эти документы не снимают паузу с разработки и live-операций.

Основатель принял стартовые параметры paper MVP без правок; они зафиксированы в ADR-0012 и разделе 18 документа 34. Продуктовые defaults больше не блокируют следующий дизайн-цикл.

Следующий результат — завершить обновлённый Figma-пакет по документам 34, 35, 40–44: после среза первого входа, навигации, центров уведомлений, реферального раздела профиля и карточек исходов закрыть оставшиеся детальные пути частичного исполнения, пропуска и ошибки закрытия, личную историю с трейдером, раздельные live-пути и балансы Polymarket/Limitless и обязательную 2FA только для реальных средств. Для реферального сценария отдельно определить доступ: каждый клиент или назначенный партнёр; реальные начисления не входят в демо. Затем проверить RU/EN на mobile и desktop, включая 320/360 mobile и 1280 desktop, и передать кликабельный прототип основателю и коллеге. Поиск трейдеров остаётся без переработки. Инструкционное видео — финальный этап после готовности всех экранов в Figma. Frontend начинается только после отдельного решения. API-регистрации остаются отложены до интеграционного этапа.
