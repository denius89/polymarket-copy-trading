# Кошельки и подпись Shadow: проверка возможностей

29.10.2026 · Только документальное исследование и рекомендация на согласование. Baseline проекта: `870ef0b43434f42c38bee74b48bfe5e2e7b8c629`. Официальные страницы прочитаны в дату проверки. Аккаунты, права, ключи и сделки не создавались; SDK/контракты и отказы в исполнении не испытаны. Результат не разрешает live, не меняет ADR-0062/0064/0065 или paper-срез. Партнёрское согласие Limitless не доказывает выданные scopes.

## Вывод для выбора

Предлагается **пользовательский отдельный торговый кошелёк для каждой площадки, без импорта основного ключа в Shadow; ограниченная автоматическая подпись в отдельном контуре**. Polymarket: Deposit Wallet + CLOB Session Key. Limitless: предпочтителен пользовательский EOA с внешним policy signer, если совместимость и независимый выход подтверждены; альтернативный managed partner wallet имеет другой контроль средств и пока не принят. Turnkey — первый кандидат для проверки подписи; Privy — альтернатива. Провайдер и окончательная live-архитектура требуют отдельного согласования.

Это не утверждение о наличии одинаковой схемы на обеих площадках. До закрытия зависимостей обе площадки сохраняются в paper-продукте; автоматический live по неподтверждённому пути выключен.

## Подтверждённые возможности площадок

| Вариант | Документировано | Что остаётся проверить |
| --- | --- | --- |
| Polymarket Deposit Wallet + Session Key | Beta; отдельный EOA signer без вывода, выбор CLOB вместо All/Combos; разрешение Builder на управление. Срок 180 дней, меньший сейчас не настраивается. Отзыв останавливает торговлю и отменяет свои заявки; полный отзыв асинхронный, до подтверждения on-chain | Доступ Shadow, отдельный бюджет, внешние лимиты и независимый от Shadow отзыв/вывод; совместимость кошелька пользователя |
| Polymarket старые Safe/Proxy | Это отдельные legacy-типы, а не эквивалент Deposit Wallet | Session Keys ограничены Deposit Wallet; миграцию нельзя считать уже доступной |
| Limitless EOA | Пользовательская EIP-712 подпись заявки + scoped HMAC; partner EOA не требует delegated_signing | Фоновый внешний signer должен реально подписывать допустимые структуры; базовый пользовательский кошелёк требует подписи каждой заявки |
| Limitless managed child | Партнёр создаёт управляемый Privy wallet; trading + delegated_signing позволяют unsigned order с подписью на стороне площадки | Контроль ребёнка конечным пользователем, самостоятельные recovery/export/revoke/exit и лимиты на каждого ребёнка не доказаны |

Источники: [Polymarket session keys](https://docs.polymarket.com/trading/session-keys), [типы кошельков](https://docs.polymarket.com/trading/wallets-auth), [Limitless partner modes](https://docs.limitless.exchange/developers/programmatic-api), [authentication](https://docs.limitless.exchange/developers/authentication).

У Polymarket документирован scope площадки, но не денежный потолок конкретной копии. Торговый ключ может причинить убыток через цены/оборот, даже без перевода. Есть отдельная видимость заявок/сделок session signer; сверка только через owner API неполна. В примере срока есть расхождение: prose требует 180 дней, TypeScript считает 4315 часов. Не переносить константу в реализацию без подтверждения площадки.

У Limitless withdrawal отделён от trading. В managed partner flow назначение по умолчанию — адрес партнёра; allowlist принадлежит партнёру, меняется через Privy identity. Это **не доказательство вывода, подтверждённого самим конечным пользователем**. Рабочему торговому процессу не выдавать withdrawal, управление allowlist, создание новых прав или identity партнёра. Отзыв API token документирован, но его действие на уже подписанные/стоящие заявки и права одного child требует проверки. Источники: [вывод](https://docs.limitless.exchange/api-reference/portfolio/withdraw), [отзыв токена](https://docs.limitless.exchange/api-reference/api-tokens/revoke-token).

## Предлагаемые границы Shadow

1. Основные сбережения пользователя остаются вне торгового кошелька. Пополнение выделенного счёта — отдельное действие пользователя, без автоматической подпитки из основного. Баланс/позиции/прибыль выделенного счёта тоже под риском; бюджет формы не является криптографическим пределом. Без изоляции новых пополнений и активов невозможно обещать «потеряется максимум первоначальные $100».
2. Shadow backend формирует намерение, отдельный signer разрешает подпись. Рабочий backend не владеет root/quorum и не может менять ограничения, экспортировать ключ, добавлять владельца или расширять доступ. Сервисный ИИ не получает signing credentials и не принимает решение о доступе к средствам.
3. Default deny; разрешены только нужные EIP-712 структуры, chain/domain/verifyingContract, ожидаемые maker/signer/asset/side/amount/price. Запрещены произвольные digest/transaction/permit/transfer/approval/owner-change подписи. Подписант не доверяет одному названию метода или присланной backend-ом цене. Лимиты на заявку не равны суммарному дневному лимиту; последний требует независимого атомарного учёта/резервов и сверки исполнений.
4. Вывод/изменение внешних разрешений подтверждает пользователь вне автоматического контура. Восстановление email/TOTP через админов Shadow не должно давать восстановление владельца кошелька. Отдельно проверить компрометацию интерфейса, подмену адреса, аккаунта и ложные запросы повторной подписи.
5. При инциденте — запрет новых подписей, внешнее ограничение/отзыв, отмена открытых заявок и сверка исполнений/остатков. Пауза Shadow, logout и отзыв HTTP token не считать автоматически отзывом уже выданных подписей. Unknown не означает отменено. Недоступность Shadow должна иметь проверенный аварийный выход.

[Turnkey policies](https://docs.turnkey.com/features/policies/overview) разрешают условия и quorum, но root quorum обходит policies: root на том же backend уничтожит границу. [Policy language](https://docs.turnkey.com/features/policies/language) поддерживает разбор EIP-712. Это основание выбрать кандидата для проверки, не доказательство готового бюджета/адаптера Shadow. [Privy policies](https://docs.privy.io/controls/policies/overview) также описывают EIP-712, ограничения контрактов/сетей и signer-time; policies собственного приложения нельзя автоматически приписать managed кошелькам Limitless.

## Угроза → защита → требуемое доказательство

| Угроза | Защита | Доказательство до live / оставшийся риск |
| --- | --- | --- |
| Взлом backend или изменение БД | Внешний signer и отдельный пользовательский trading scope | С полностью скомпрометированными прикладными правами нельзя вывести, экспортировать, изменить policy или подписать запрещённый payload. Разрешённая плохая торговля остаётся риском |
| Кража одного торгового credential | Индивидуальная область и отзыв | Нельзя действовать за другого пользователя/площадку; проверить общие partner credentials Limitless и масштаб ущерба |
| Много небольших заявок/повторы/гонки | Суммарный независимый лимит, reserve/nonce/dedup | Параллельные подписи и повторы не обходят потолок. Отдельный cap лишь на размер заявки недостаточен |
| Подмена рынка/цены/fees | Привязка подписи и независимая проверка рыночных данных | Нельзя купить чужой asset или по подставленной цене; даже корректная цена не гарантирует прибыль |
| Утечка owner/recovery или policy-root | Пользовательский контроль и независимые подтверждения | Backend/поддержка не могут захватить wallet через reset. Компрометация устройства/провайдера остаётся риском |
| Падение Shadow или провайдера | Независимый выход и регламент отмены | Пользователь отключает торговлю/получает средства без исправного Shadow; учесть gas, остаточные заявки, late fills и незакрытые позиции |

## Вопросы площадкам и проверки следующего этапа

**Polymarket:** подтвердить Builder beta enablement; точный срок/расхождение примера; owner-controlled отзыв и вывод при недоступности Shadow/Builder API; момент блокировки CLOB и завершения отмен; redeem/merge вне торгового session scope; полный источник сверки session orders. Проверить отсутствие вывода и произвольных wallet calls украденным session key.

**Limitless:** подтвердить actual scopes Shadow; поддержку EOA с внешним EIP-712 signer для нужных профилей; индивидуальный отзыв автоматизации; право конечного пользователя самостоятельно восстановить/экспортировать managed child и выйти; возможность ограничить partner credentials конкретным child, бюджетом и ценой; права на изменение scope; отмену старых заявок после revoke. Зеленый свет партнёра не отвечает на эти вопросы автоматически.

**Turnkey/Privy:** отдельно подтвердить допустимость prediction-market/copy-trading продукта, стоимость, доступность по юрисдикциям и совместимость актуальных SDK. Определить root/owner/recovery вне backend, запрет обходных raw-digest методов, устойчивость общей суммы к гонкам и поведение при сбое. Аудит провайдера не заменяет независимую проверку интеграции Shadow.

Предлагаемый выбор: сохранить paper-first; для будущего Polymarket ориентироваться на Deposit Wallet + CLOB Session Key; для Limitless исследовать user-controlled EOA + policy signer, не принимать managed partner wallet без независимого user exit. Оба live-пути открываются каждый по своим доказательствам. Код, тесты живых счетов и обращения партнёрам данным документом не запускаются.
