# Данные и рейтинг · контракт дизайна 09

Основание: прямое уточнение владельца 13.10.2026 — нужен внутренний валидатор, сбор данных трейдеров, настройки сборщиков и рейтинга; список является результатом, а не основой раздела. Работа только над дизайном.

## Согласованное и предложенное
Сохраняется [ADR-0011](../../../decisions/0011_shadow_controls_rating_admin_and_ui_foundation.md): «Качество копирования» 0–100; веса 30% данные / 25% просадка / 25% копируемость / 20% стабильность после расходов. Для полноценного рейтинга: 30 дней, 20 подходящих действий, актуальность, отсутствие необъяснённых расхождений. Число копировщиков не влияет. Ручной поиск не требует рейтинга.

Владелец расширил дизайн ADM-07: допускается настройка правил и расчёта, но не ручное назначение баллов отдельному трейдеру или исправление фактов источника. Старое ограничение «только наблюдение» заменено в этой области.
Права на новые команды пока предложение для совместной вычитки: просмотр/диагностика по отдельным scopes, подготовка черновиков отдельно; применение численных настроек/методик — Owner. Это не изменяет действующие права сотрудников самим макетом.

## Информационная структура
Вход «Данные и рейтинг» в группе Управление. Пять вкладок: обзор, сбор данных, валидатор, рейтинг, результаты. Старый ADM-06 остаётся диагностикой потоков/подключений, а новый блок объединяет ADM-07 с настройками. Один источник health/metadata и ссылки в существующий ADM-15; не дублировать секреты или credentials.

## Сборщики
Раздельный профиль по venue/environment/source/account. Назначение этого управления — discovery каталога и публичная история для рейтинга; торговой signal/execution pipeline управляет отдельный контур. Изменение периода не меняет trading/risk policy и не обходит live gates.
Настраиваемые поля: назначение коллектора, интервал, окно истории, профиль нагрузки/страниц, правила retry/backoff и concurrency по capabilities интеграции. В первом макете показаны интервал и окно; дополнительные API-specific поля добавляются после подтверждения API.
Запрет произвольного provider URL/source-wallet injection, без ключей/seed и ручной подмены фактов.
Изменение P-1 → P-2 проходит validation → preview → command accepted → confirmed applied либо unknown/failed. Backend должен проверять profile compatibility, rate limits, freshness invariants, актуальную версию и actor authority. Прототип демонстрирует pending/confirmed/unknown; confirmed-failed и version conflict остаются общей последующей вычиткой состояния.
Пауза останавливает будущие catalog/history jobs, сохраняет собранные события/checkpoints; не является global stop и не закрывает пользовательские сессии. Эффект на downstream свежесть показывается. Новая попытка — чтение/сверка той же команды; unknown не разрешает слепое повторное применение.

## Внутренний валидатор
Три независимых результата:
1. Идентичность: формат по площадке, ответ источника, found/not_found/unknown.
2. Пригодность данных: полнота обязательных полей, fresh/stale/unknown, дедупликация, пропуски, provenance, отсутствие необъяснённых расхождений.
3. Допуск в рейтинг/каталог: требования методики, и затем вычисленные баллы либо insufficient_data.

Не смешивать invalid format, not_found, insufficient_data и unavailable. Not found допустим только при подтверждённом ответе нужного источника с известным охватом. Источник недоступен не делает адрес несуществующим.
Отсутствие рейтинга само по себе не запрещает ручной выбор. Это не разрешение копировать при неготовой площадке/непроверенном адресе: реальное действие проходит существующий copy/readiness/risk contract.
Адреса показаны полностью. Метрики и исходные события read-only; исправление происходит через исправление адаптера/новое получение данных, а не переписывание фактов сотрудником.
V-2 демонстрирует настройку срока актуальности только рейтинговых данных. Минимум дней/действий и веса хранятся в RatingPolicyVersion, не дублируются в ValidatorPolicyVersion. Обязательные проверки идентичности/дедупликации/необъяснённых расхождений не имеют UI-обхода.
Новый numeric freshness threshold — demo предложение, не принятие production SLA и не изменение live order freshness policy.

## Рейтинг
RatingPolicyVersion / NormalizationMethodVersion / DataSnapshot / RatingSnapshot связаны явно. Веса суммируются в 100%, недопустимы отрицательные/нечисловые/выходящие за диапазон значения. Unknown источники, недостаточная история и необъяснённые расхождения не получают нулевые или выдуманные баллы.
Owner редактирует черновик, сравнивает текущую/новую версию на одном immutable снимке, видит включённые/исключённые профили и причины. Сохранение не меняет каталог. Публикация фиксирует author/time/before-after/source/policy versions; разрешение и expected revision проверяются при применении.
Расчёт новой версии запускается отдельно; UI ждёт подтверждённого полного нового snapshot до переключения клиентского каталога. В production текущая публикация сохраняется до готовности новой, неполная смесь методик не выдаётся. Unknown publication/recompute status не считается completed.
Откат создаёт R-3 со значениями R-1, сохраняет R-1/R-2 и историю. Прошлые торговые решения и сделки не пересчитываются. Изменение допуска/порядка каталога не останавливает существующее копирование.

## Учебные данные
Все адреса синтетические: 0x + повтор 11/22/33/44 (20 раз); это не адреса реальных клиентов.
DS-DEMO-01: A/PM 45 дней 64 действия score79; B/PM 12 дней 8 действий insufficient; C/PM 40 дней 22 действия score64; D/LL source unavailable, score null.
R-1: A/C подходят; B/D не получают рейтинг. R-2 (исключительно demo предложение): веса остаются 30/25/25/20, минимум действий повышен с20 до25; теперь подходит только A. C остаётся найденным валидным адресом, score null в R-2, а не 0. В R-3 значения R-1 восстановлены.
Пример субоценок A: 80×0.30 +72×0.25 +88×0.25 +75×0.20 =79. Субоценки заданы fixture, не доказаны реальным API и не задают неутверждённые алгоритмы нормализации.
P-1:5 минут/90дней; P-2:10минут/90дней. V-1:10минут; V-2:15минут. Это тестовые значения, не реальные capabilities, limits, SLA или принятие новых настроек.
Polymarket running demo и Limitless unconfigured — сценарии дизайна, не статус реальных подключений; обязательность обеих площадок сохраняется.
Публикатор примеров — Елена Морозова/Owner. Статический прототип не хранит изменения в backend; начальные вкладки показывают исходный снимок. Отдельный экран результата R-2 сохраняет контекст новой оценки.

## Сверка с клиентским UI
| Админка | Клиентский интерфейс |
| --- | --- |
| Подтверждённый rating snapshot R-1 | Каталог/карточка используют одну методику, период и fresh source |
| Недостаточно истории B | «Недостаточно данных», без нулевого score; manual lookup остаётся |
| Не готов источник D | «Не удалось получить данные», не not_found и не зелёное readiness |
| Preview R-2 | Клиентский каталог не меняется |
| Snapshot R-2 confirmed | C исключён из основного рейтинга, ручной выбор не блокируется рейтингом |
| Collector pause | История сохраняется, freshness деградирует; существующие сессии не закрываются этой командой |
| R-3 restore | Новая версия каталога; прошлые сделки/отчёты не переписываются |

Клиентские страницы здесь не меняются. Нужна совместная вычитка объяснения рейтинга/period/freshness, manual address outcomes и publication snapshot consistency до разработки.

## Открыто перед реализацией
- Real venue capabilities, discovery/identity coverage, pagination, API limits, history window, rate/backoff/retry budgets.
- Eligible event definition по каждому venue, normalization functions, учёт расходов, comparability и rounding.
- Политика freshness, надежность source timestamp, аномалии и gap rules.
- Права новых команд, expected revision/идемпотентность и audit model.
- Полный failure/empty/stale/concurrency/recompute/manual role pass; импорт/экспорт/массовые исключения пока не добавлены.

Контракт не означает готовую API-интеграцию или новое принятие численной модели R-2. Точные storage/endpoints — этап реализации после принятия дизайна.
