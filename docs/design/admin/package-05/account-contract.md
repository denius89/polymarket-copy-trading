# Личный аккаунт сотрудника · контракт дизайна

12.10.2026. Дополнение ADM-14. Принят владелец план личного кабинета и размещение как в клиентском UI; детали auth-provider остаются открытыми. Не является реализованным API.

## Вход и навигация

Иконка 44×44 справа на каждом авторизованном экране открывает «Мой профиль» напрямую. Карточки: Личный аккаунт (имя/аватар, язык), Вход и безопасность (security, свои сессии), Выход. Роль/доступ читаются в карточке identity. Нет нового пункта основного sidebar и повторного языкового переключателя снаружи. После обычного logout сразу экран входа. Рабочая роль/финансы не меняются.

## Разделение полномочий

Self-service доступен каждому активному StaffAccount: Owner A/B, Operations и custom roles. Каждая команда проверяет серверную identity и принадлежность изменяемого профиля/сессии. Право access.revoke относится к чужим staff-сессиям и не требуется для выхода из собственной сессии. Клиентский UserAccount не становится StaffAccount. Менять свою роль, выдавать права, блокировать чужой аккаунт, раскрывать integration secrets через профиль нельзя. Suspended/revoked staff не получает обход через self-service.

## Личные данные и язык

Изменяем имя и аватар, показываем email входа. Роль и grant list только для чтения. В прототипе аватар — инициалы, а загрузка/предпросмотр — статические макеты. До реализации выбрать image-size/type limits, проверку/хранение/удаление файлов и crop; ограничения не выдуманы.

Предпочтение языка — поле текущего StaffAccount (RU/EN). Оно не публикует переводы проекта и не меняет язык другого сотрудника. В продукте: применить после подтверждённого сохранения, сохранить текущий маршрут и рабочие данные; при ошибке оставить прежний язык. До авторизации использовать сохранённое безопасное предпочтение устройства/браузера либо default; приоритет выбора уточнить с auth implementation. В Figma cross-page URL показывает другую языковую ветвь, а не работает как серверное хранение.

## Безопасность

Пароль/email/MFA требуют свежего re-auth. На макетах парольный вход и authenticator — только provider-dependent пример. Для SSO/IdP вместо локальной парольной формы должен быть поддержанный безопасный переход к настройкам провайдера; не хранить второй пароль без архитектурного решения.

Email: ввод нового адреса → re-auth → verification нового адреса → confirmed. Старый email действует до завершения. Уведомляем прежний адрес; без успешного подтверждения не объявляем смену состоявшейся. В макете нет настоящего отправления писем.

MFA: подключение → проверка нового способа → enabled. Замена: подтверждение старым или разрешённым recovery-способом → настройка нового → успешная проверка → прежний метод отозван. Отмена сохраняет старую защиту. Отключение обязательной MFA не предлагается. Потеря метода: действующий recovery-code либо защищённое восстановление identity. Обход на основании роли или кнопка self-assign Owner запрещены; потеря обоих Owner — ADR-0043 external runbook.

Резервные коды: скрыты по умолчанию; новый набор требует re-auth и отменяет прежний. Однократный показ/сохранение в продукте, значения не попадают в audit/export. В дизайне — только недействительные подписи DEMO. Конкретный поддержанный механизм зависит от провайдера.

Предложенное поведение показанных ветвей: после подтверждённой смены пароля/email/MFA другие сессии завершаются, текущая свежеподтверждённая остаётся. При реализации согласовать с возможностями auth-provider; его reset/revocation должен применяться на сервере. Связанные security-sensitive approvals нельзя сохранять действительными вопреки актуальной auth/security policy.

## Свои сессии и logout

Показываем устройства/браузер, ID сессии, время входа/последней активности, текущую сессию. При наличии достоверного источника — приблизительное место; если сведения отсутствуют, unknown. Demo Warsaw — вымышленная подпись, не геолокация реального сотрудника.

Завершение выбранной другой сессии или всех остальных требует подтверждения; текущая остаётся активной. Logout текущей сессии — сразу без второго диалога. Сервер отзывает сессию и отклоняет дальнейшие защищённые запросы; навигация на login сама по себе не является отзывом. При неподтверждённом результате показываем uncertainty и обновление статуса, не ложный успех. Expired/revoked состояния используют экраны пакета 04. Возврат кнопкой браузера после logout не должен восстановить доступ.

## Audit, данные и реализация

Логируем actor/self-account ID, вид изменения, результат, время, correlation/event ID; маскируем чувствительные поля по policy. Ни пароль, ни коды MFA/seed/recovery-secret не попадают в запись. Для сессий сохраняем ID отзыва и подтверждённый результат. Имя/avatar/locale не требуют постоянного согласования Owner, но имеют историю изменения.

При проектировании API использовать защищённый self-account resource: чтение/изменение собственного профиля/locale, own-session list/revoke, provider-backed email/password/MFA challenges. Конкретные endpoints и payloads пока не реализованы. Для мутаций — server authz, ownership, CSRF/session protections, replay/rate limits и корректные failure states по выбранному provider. Не использовать ID чужой staff-карточки как subject self-account.

## До реализации

Выбрать auth/MFA provider и password/SSO mapping; правила re-auth/expiration; способы identity recovery и ответственных; доставку security email; безопасное хранение recovery materials; avatar limits; сроки хранения session metadata/audit. Общие self-service screens не заменяют тесты для Owner B, Operations и разных custom roles. UI-only прототип не доказывает auth security.

Recovery потерянной MFA: login → lost method → разрешённое резервное подтверждение → ограниченная настройка/проверка новой MFA → отзыв прежнего метода и сессий → новый login. Sidebar и личный профиль отсутствуют; recovery challenge не является полноценной admin-сессией.
