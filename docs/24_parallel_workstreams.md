# Следующие параллельные потоки работы

Дата: 25.09.2026. Статус: исторический технический план. После ADR-0009 API-регистрации отложены, агентский поток исключён из MVP, а текущая очередь находится в [ROADMAP](ROADMAP.md) и [аудите готовности](31_project_readiness_audit.md).

## Цель текущего блока

Закрыть доступы и архитектуру двух обязательных площадок так, чтобы следующий этап разработки состоял из ограниченных проверяемых spikes, а не из написания MVP на предположениях.

## Поток A — Polymarket

Результаты:

- создан проектный Builder profile;
- зафиксированы builder code, tier и доступные limits без публикации секретов;
- отправлен запрос на Session Keys;
- подготовлены read-only, permission и order-lifecycle spikes;
- определены критерии перехода адаптера из `research` в `paper` и затем в `live_candidate`.

Зависимость от основателя: проектный аккаунт/кошелёк, регистрация Builder profile и отправка внешнего запроса.

## Поток B — Limitless

Результаты:

- аккаунт зарегистрирован только через FutureHaus;
- подана partner application;
- подтверждены capabilities и scopes без `withdrawal` у execution worker;
- письменно уточнены скидка 10%, GEO, data use, recovery и withdrawal path;
- подготовлены latency и sub-account lifecycle spikes.

Зависимость от основателя: регистрация кошельком проекта и отправка partner application.

## Поток C — общий контракт adapters

Результаты:

- единые модели market, leader event, order, fill, fee, position и virtual lot;
- capability flags, которые не скрывают различия площадок;
- общие lifecycle states, reason codes и правила неизвестного состояния;
- idempotency и reconciliation contracts;
- отдельные readiness gates для `read_only`, `paper`, `live_candidate` и `live_enabled`.

Зависимость от внешних доступов отсутствует. Контракт уточняется после spikes, но не должен требовать переписывания core.

## Поток D — проверка продукта и канала

Можно выполнять параллельно с ожиданием API-доступов:

- 6–10 проверок позиционирования на потенциальных пользователях;
- агентский пакет v0: сообщение, одностраничное объяснение, FAQ, onboarding и dashboard;
- выбор первого GEO для live-кандидата;
- проверка понимания shadow mode, риска и отсутствия гарантии прибыли.

## Порядок технических работ после доступов

1. Recorded read-only ingestion обеих площадок.
2. 72-часовое измерение полноты, дублей и p50/p95/p99 задержки.
3. Нормализация событий и replay fixtures.
4. Симулятор orderbook execution и полной комиссии.
5. Virtual lots и reconciliation на записанных данных.
6. Permission lifecycle на отдельных тестовых аккаунтах без пользовательских средств.
7. Paper-trading vertical slice обеих площадок.
8. Архитектурный и security review.
9. Отдельное решение основателя о личном live-тесте каждой площадки.

## Что пока не запускается

- production frontend;
- реальные пользовательские сделки;
- хранение рабочих API secrets в репозитории;
- одновременный live-запуск двух площадок;
- публичное обещание доступности по GEO;
- рекламные обещания доходности.

## Gate на начало paper-trading MVP

Работу над paper MVP можно начинать, когда:

- приняты документы 21–23;
- закрыты противоречия документов 01–03;
- получены либо однозначно ограничены оба API access path;
- утверждён adapter contract;
- для spikes подготовлены безопасные fixtures и критерии успеха;
- выбран первый GEO исследования;
- основатель отдельно снял паузу разработки.
