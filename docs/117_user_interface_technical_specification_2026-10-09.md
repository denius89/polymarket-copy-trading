## 1. Назначение и статус

Документ описывает пользовательский web-интерфейс, созданный в [Figma](https://www.figma.com/design/lxPP2um7FvIbt02K8eeH4T), и требования к его последующей реализации. Он охватывает Mobile RU, Mobile EN, Desktop RU и Desktop EN. Это спецификация и передача в разработку, а не реализованное приложение и не новая приёмка прототипов.

Используем три статуса:

- **Принято** — действующая бизнес-логика, ADR или прямое решение владельца.
- **Предлагается** — технический способ исполнения; требует проверки при проектировании, не становится новым бизнес-правилом от появления в этом документе.
- **Открыто** — решение или интеграционная проверка отсутствует. Figma-пример не закрывает такой вопрос.

Фактические экраны задают композицию и пользовательский путь. Поведение определяется последними решениями владельца, [MVP_BUSINESS_LOGIC](MVP_BUSINESS_LOGIC.md) и [ADR](decisions/README.md). При конфликте не реализуем случайное состояние макета как бизнес-правило. Дополнительные источники: [стандарт интерфейса 41](41_product_design_and_frontend_standards.md), [исправления 113](113_button_copy_and_reaction_fixes_2026-10-06.md), [техническая спецификация админки 115](115_admin_console_technical_specification_2026-10-09.md), [сверка 116](116_admin_user_interface_consistency_2026-10-09.md).

Первая версия — самостоятельное mobile-first приложение для совершеннолетнего новичка, на TypeScript, с RU/EN. Polymarket и Limitless обязательны в целевом продукте; состояние, счета и исполнение разделены по площадке. В первом выпуске торговля paper/shadow: нет настоящих ордеров, денежных переводов или автоматического перехода в live. Агентский кабинет, админка, массовый внешний маркетинг и live-интеграции не входят в этот интерфейс.

## 4. Первый вход, пример и авторизация

**Уточнение 19.10.2026:** принят [ADR-0048](decisions/0048_unified_registration_and_first_entry.md). Четыре Final-версии обновлены [пакетом входа](design/client/adr48-entry-fixes-2026-10-19/README.md): актуальные связи и границы проверки находятся там; старые результаты QA не подтверждают новый сценарий.

Основной путь: «Начать» на лендинге → единый email-вход/регистрация → выбор трейдера нового пользователя → настройка → проверка → отдельный запуск. Гостевой путь: каталог → профиль → настройка → проверка → вход → возврат к проверке → отдельный запуск. Переход из настройки на проверку доступен гостю. Подтверждение email ничего не запускает.

После входа существующая активная/приостановленная сессия или позиции/сверка, препятствующие новой, имеют приоритет над черновиком: показать текущее состояние и объяснение, сохранить черновик. Без такого препятствия черновик продолжается с достигнутого шага; новый аккаунт без черновика открывает каталог. Для завершённой сессии без позиций/сверки — Главная с итогом и действием выбора трейдера.

Язык, площадка, трейдер, параметры, шаг и контекст входа сохраняются при ошибке/истечении кода, повторной отправке, Back и reload. На другом устройстве продолжение возможно только после фактического восстановления черновика; иначе предложить исходное устройство или новую настройку. Перед запуском повторно проверить трейдера, правила и параметры, показать изменения пользователю. Механизм хранения/переноса черновика остаётся техническим решением.


Подготовленный пример и новая сессия — разные пространства данных. «Открыть пример / Open example» запускает изолированный fixture-контекст и открывает подготовленную главную. Это не resume реальной пользовательской сессии. Нельзя записывать пользователя в active только из-за просмотра примера, начислять ему примерный результат или подмешивать fixture-ордера в историю.

Новая сессия создаётся после проверки настройки и входа. Стартовое состояние — EMPTY: демо-бюджет $200, без позиций, событий и ордеров до появления допустимого сигнала. Пустые экраны объясняют причину и следующий шаг. Нельзя заменить EMPTY активным примером ради наполнения интерфейса.

Гость просматривает каталог, заполняет черновик и открывает проверку без аккаунта; сохранение пользовательской сессии и запуск требуют email passwordless. Основной вход с лендинга использует тот же процесс. Одноразовый код — основной вариант, одноразовая ссылка сохраняется по ADR-0012/0048. Предлагаемые состояния auth: ввод → отправка → ожидание/ввод кода → проверка → успех; ошибки: неверный/истёкший код, rate limit, временная недоступность. Повторная отправка не размножает аккаунт и не теряет черновик. TTL, cooldown, лимиты попыток, 2FA/recovery-политика и провайдер требуют отдельного решения; макеты не задают security-политику.

Telegram — необязательный канал уведомлений, не обязательный способ входа. Выход завершает локальную сессию и удаляет пользовательский cache; повторный вход не создаёт вторую демо-сессию. Предлагаются защищённые HttpOnly/Secure cookies, CSRF-защита изменяющих запросов и проверка разрешений на сервере; конкретная auth-инфраструктура пока не утверждена.

## 5. Трейдеры и настройка копирования

Каталог показывает площадку, идентификатор/адрес, качество данных, период, показатели и доступность копирования. Пользователь может выбрать из каталога либо вставить адрес. Адрес валидируется адаптером выбранной площадки; неверный формат, не найден, неподдерживаемая площадка и недостаточные данные — разные причины. Нельзя автоматически назначить Limitless-адресу Polymarket-профиль.

Периоды профиля: 24h, 7d, 30d, 90d и доступный общий период. Переключение периода не меняет трейдера и не создаёт сессию. История и рынки используют тот же venue/trader context; Back возвращает к списку трейдеров. Короткий словарь кнопок принят в 113: «Трейдеры / Traders», «Открыть пример / Open example»; доступное имя может содержать более полный контекст.

Рейтинг качества копирования 0–100: качество данных 30%, drawdown 25%, copyability 25%, стабильность после расходов 20%. Допуск требует 30 дней и 20 действий, актуальных и согласованных данных. Формулы нормализации/источники/обновление ещё открыты. Отсутствие рейтинга показываем как недостаточность данных, не как нулевой балл; не обещаем доход и не подменяем рейтинг прошлой доходностью.

Форма настройки хранит venue, traderId/address, демо-бюджет, sizing mode, лимиты и версию политики. Два режима размера BUY:

- фиксированная сумма, пример $20;
- процент от суммы **BUY выбранного трейдера**, стартовый пример 3%, редактируемый пользователем. Это не процент от собственного бюджета.

Согласованный стартовый preset при бюджете $200: максимум позиции $20 (10%), дневные покупки $30 (15%), возраст сигнала 30 секунд. Диапазоны, шаг, decimal precision, минимумы площадок и точный upper bound расходов требуют решения. Нельзя вычислить новые presets из видимых Low/Medium/High.

Проверка настройки показывает размер копии, защитные ограничения, площадку, трейдера, демо-режим и то, что пропущенные покупки не догоняются. Ошибки отображаются у поля и в сводке; фокус переходит к первому неверному полю. Смена режима сохраняет ввод в черновике, но сервер получает только выбранный способ. Save/start повторно валидирует текущую версию политики.

Размер новой копии фиксируется sizingRevision при получении уникального сигнала; до допуска его проверяет текущая admissionRevision с живыми ограничениями и ledger по ADR-0056/134. Существующие допущенные ордеры, резервы и позиции не пересчитываются задним числом. Эффективные ограничения включают системный ceiling; пользователь не может его превысить. Совмещение лимитов, источники effective values и порядок основной причины приняты в ADR-0057/135; сравнивать собственные остатки разных квот, а не min сырых потолков.

## 6. Сессия и главная

Одна активная сессия на пользователя. Предлагаемые внутренние состояния: DRAFT, ACTIVE, PAUSED, STOPPING, STOPPED, COMPLETED; EMPTY — состояние наполненности новой сессии, не отдельное разрешение торговать. Названия окончательных enum согласуются с lifecycle BL-07. Отображаемые состояния должны различать запрос перехода и подтверждённый переход.

Главная показывает режим, выбранного трейдера/площадку, период, статус сессии, USD-equity, доступно, резерв, стоимость позиций, результат и последние события. Все показатели одного snapshot согласованы по версии и времени. Обновление не должно на мгновение суммировать новый резерв со старым available.

Pause останавливает новые/увеличивающие BUY, но выходы и защита продолжаются. Resume требует серверной проверки emergency/capabilities и текущих правил. Stop & keep прекращает копирование, отменяет ожидающие ордеры с подтверждением, оставляет позиции в ручном управлении. Close & stop запрашивает закрытия; не сообщает об окончании до подтверждённого результата. Окончательный учёт, новая сессия и сброс следуют ADR-0050/0051 выше; открытые позиции/сверка блокируют финал, принудительной ликвидации нет.

Таймзона сессии фиксирована IANA. Дневной лимит сбрасывается в локальную полночь этой зоны; смена языка или зоны устройства не создаёт новый день. Незавершённые резервы сохраняются. Reminder после 60 минут активного foreground; background не расходует этот таймер.

## 7. Сигналы, ордеры, позиции и события

Покупка допускается только целиком по желаемому размеру с необходимым резервом и всеми действующими лимитами. Если desired $20, а свободно $8, действие пропускается; покупку на $8 не создаём. Причину показываем в событии. Пропуски не превращаются в отложенные автоматические покупки.

Дедупликация по source action обязательна на сервере. Admission и reservation атомарны; порядок конфликтующих сигналов стабилен по приёму системой. UI не управляет этим порядком и не запускает второй ордер при reconnect.

Известная недостаточная глубина до admission → полный skip. Частичное исполнение после admission сохраняет исполненную часть; отмена остатка требует подтверждения. Cancel requested не равен cancelled. Late fill учитывается после запроса отмены. Unknown/timeout не равен failed: резерв не освобождается, retry и конфликтующие рискованные действия блокируются до сверки.

| Экран | Обязательные данные | Действия и условия |
| --- | --- | --- |
| Список ордеров | Площадка, рынок/outcome, BUY/SELL, desired, filled, remaining, статус, время | Фильтр, деталь; отмена только по capability |
| Деталь ордера | Source action, applied policy, резерв, fills/расходы, история состояний | Cancel/change с подтверждением, причина запрета |
| Подтверждение отмены | Уже исполнено, остаток, последствие | Принять запрос, далее pending до подтверждения |
| Изменение ордера | Текущая версия и допустимые поля | Серверная revalidation; способ amend/cancel-replace зависит от адаптера |
| Список позиций | Площадка, рынок, quantity, cost, valuation, P&L, связь с копированием | Деталь; manual/detach или close по capability |
| Деталь позиции | Lots/source ownership, realised/unrealised, цена и её свежесть | Пропорциональный выход, ручные действия без скрытого SELL |
| Закрытие | Количество, оценка/расходы и предупреждение об изменении цены | Запрос закрытия, не мгновенное обещание продажи |
| События | Source, decision, reasonCode, время, связанные IDs | Переход к своему ордеру/позиции, понятное объяснение |

Внешние quantity/price/денежные факты представляются точными единицами/decimal-строками; внутренние количества, стоимость и атрибуция частей — точные рациональные n/d по ADR-0055/133. Нельзя переводить их в конечный decimal с потерей точности. Pending/unknown qty нельзя рисовать как ноль. Если valuation не подтверждена, выводим недоступность/последнее значение со stale-временем, а не выдуманный P&L.

Пропорциональная продажа трейдера применяется к отслеживаемому остатку. Manual/detached-позиции в неё не входят. Detach означает прекращение копирования позиции, не продажу. Ручное закрытие блокирует автоматический повторный вход до явного разрешённого решения. Основа учёта частей, ручного распределения и освобождения лимита — ADR-0049 выше; политика late/очереди/шага/dust принята ADR-0052–0054; арифметика частей принята ADR-0055/133; физическая схема ownership, SELL-ликвидность и runtime остаются BL-05/06.

Уточнение 12.10.2026 по [ADR-0043](decisions/0043_admin_money_security_and_incident_recovery.md): настоящий funding остаётся future/live-gated. Для поддержанных маршрутов состояния и evidence заданы в [115 §6.3](115_admin_console_technical_specification_2026-10-09.md): instruction/observed/confirming/доступность отдельно, withdrawal request/authorization/reserve/dispatch/submitted/confirmed/unknown отдельно. Подтверждённая внешняя reservation не подменяется внутренним обещанием удержать пользовательские средства.

## 8. Средства, операции и площадки

Единая единица платформы USD. Для USDT принято 1 USDT = $1; остальные активы не считаются автоматически равными USD. Сохраняются исходный asset, amount, сеть/площадка и применённое правило конвертации. Демо-средства явно отделены от настоящего кошелька, средств сервиса и партнёрских обязательств.

В подтверждённом snapshot equity = available + reserved + valuation позиций при согласованной учётной модели. Пример Figma: 209.77 = 180.38 + 5.79 + 23.60. Это fixture, не системная константа. Резерв — не списанный расход. Нельзя повторно включать reserve в cost и затем ещё раз вычитать из equity.

В демо Polymarket/Limitless disconnected; балансы реальных площадок недоступны. Deposit/withdraw открывают объяснение future-функции и возврат. В первой реализации эти CTA не запрашивают подпись и не выполняют транзакцию. Реальные балансы не заменяем нулями из-за отсутствующего подключения.

Список операций показывает тип, площадку, сумму/asset, статус, время и связанный объект. Деталь объясняет reserved/released/settled, комиссии и причину коррекции. Время создания, исполнения и подтверждения не подменяют друг друга. Данные приходят из ledger projection, а не из сложения строк UI.

В alpha сервисная комиссия 0%. $0.01/$0.20 расходов в макете не означают действующий сервисный тариф 1%. Будущие тарифы и реферальные правила версионируются и настраиваются Owner; UI показывает применимую опубликованную версию и отдельно расходы исполнения.

## 9. Отчёт и история

Отчёт показывает период, начальный бюджет, результат, расходы, drawdown, eligible actions, принятые/пропущенные покупки с причинами и достаточность данных. Оценка требует минимум 7 календарных дней и 10 eligible actions; наблюдение максимум 14 дней. Недостаточность на 14-й день не превращается в негативную оценку или фиктивный score.

Realised/unrealised результаты и необработанные состояния разделяются. Данные воспроизводимы по policy version, источникам и snapshot. Backtest/benchmark и формулы дополнительных метрик ещё требуют подтверждения; график макета не служит вычислительной спецификацией. Экспорт, срок хранения, раннее окончание/перезапуск при открытых позициях требуют отдельных решений.

## 10. Поддержка, помощь и отзывы

Путь общего обращения: список → новая форма → проверка → создание → подтверждение → публичная переписка. Не связываем автоматически с произвольной сделкой. Пользователь может передать session context; order/position/event context допустим только из явно выбранного собственного объекта.

Предлагаемые поля формы: тема, текст, необязательный контекст. Required/maxlength, закрытие и повторное открытие уточняются в контракте поддержки; не выдумываем лимит символов. Создание idempotent; ошибка отправки сохраняет введённое. Успешный экран только после подтверждённого создания с ticketId. В Figma отправка симулируется.

Публичный thread включает сообщения пользователя и ответы сотрудников. Назначение сотрудника и внутренняя история обслуживаются админкой. Internal notes, employee scopes, приватные incident metadata никогда не попадают в user DTO. Вложения и SLA — позднее. Статусы ticket DTO должны быть согласованы с support-модулем, а не с цветом карточки.

FAQ имеет стабильный articleId и опубликованный текст по языку. Раскрытие ответа не создаёт обращение. Возврат сохраняет поиск/раскрытие. Отзыв — отдельная feedback-сущность, форма → подтверждение, без обещания support-ответа; нельзя отправить его в случайный ticket.

## 11. Профиль, уведомления, рефералы и VIP

Профиль отображает текущий email, язык, доступные настройки и реферальные сведения. Не выдаём простую UI-правку email за подтверждённую смену идентичности: verification/recovery контракт открыт. Секреты, коды и подписи не храним в localStorage.

In-app уведомления обязательны. Telegram по выбору: критические сразу; weekly по умолчанию, daily опционально. Изменение preferences не отключает необходимые security/transactional сообщения. Недоставленное внешнее уведомление не скрывает событие внутри приложения. Notification deep link проверяет доступ пользователя и текущую сущность.

In-app announcements первой версии используют опубликованный контент и правила показа. Массовые внешние маркетинговые каналы позже. Сообщение объявления не может изменять политику исполнения.

Реферальный блок показывает собственный код/ссылку, подтверждённые показатели и применимую версию правил. Порогов/процентов из ранней переписки не зашиваем. Доступные и pending начисления различаются. User VIP назначается Owner, отличается от partner VIP; показывает только действующие пользовательские условия, срок и применимость. Отсутствующие в Figma состояния VIP и announcements являются пробелом дизайна, а не разрешением расширить текущую реализацию.

## 12. Emergency, health и общие состояния

Capabilities вычисляются сервером по user/session/venue, политике, правам, health и emergency. Клиент объясняет доступность, но не является security enforcement.

GLOBAL_STOP, TECH_MODE, DEPOSITS_OFF, WITHDRAWALS_OFF имеют effective scope и reason. Funding flags запрещают операции через Shadow, не заявляют блокировку самостоятельных действий пользователя вне сервиса. Уже отправленные действия продолжают наблюдаться и сверяться. При недоступном control state новые действия блокируются fail-closed; существующие данные могут читаться с обозначенной свежестью. Конкретное поведение отдельных exit/resume действий берём из общей control-модели, не объединяем все flags в один «всё отключено».

| Состояние UI | Требование |
| --- | --- |
| Initial loading | Skeleton без ложных нулей и прыгающих кнопок |
| Empty | Причина, доступный следующий шаг, без активных fixture-сделок |
| Partial data | Доступные значения и явные недоступные поля |
| Stale | Последнее подтверждённое значение, updatedAt, причина/refresh |
| Offline | Banner, чтение безопасного cache; изменяющие операции не отправляются молча позже |
| Pending command | Защита от повторного клика, статус запроса и ссылка на объект |
| Unknown result | Объяснение сверки, блокировка retry, reserve сохраняется |
| Validation error | Ошибка у поля, сохранённый ввод, фокус и aria-связь |
| Conflict | Новая версия данных и повторная проверка, без автоматического overwrite |
| Session expired | Повторный вход и восстановление безопасного черновика |
| No permission | Понятная недоступность без чужих подробностей |
| Maintenance | Scope/причина/доступные безопасные разделы; нет выдуманного ETA |

Полная визуальная матрица этих состояний, включая emergency и VIP, ещё не нарисована/не принята. Реализация требует согласования недостающих представлений, не повторного изменения принятой финансовой логики.

Дополнение ADR-0043: при запрете пополнения старый адрес может принимать перевод; обнаружение и сверка продолжаются, UI показывает подтверждённую доступность или ожидание проверки. Unknown не даёт повторно отправить вывод. После emergency старый неотправленный вывод требует нового preflight и подтверждения пользователя; staff recovery не заменяет его согласие. Submitted/unknown сначала сверяются. Точечная блокировка и market-deviation gate затронутого маршрута входят в allowed_actions; прямой кошелёк не объявляется замороженным. PARTNER_PAYOUTS_OFF и Owner approvals относятся к сервису, не к клиентской выплате. Внутренний 1 USDT = $1 сохраняется без исторического пересчёта. Полная Figma-матрица дополнений ещё не нарисована.

## 13. Контракты данных — предложение

User UI и админка читают общие безопасные projections. [ADR-0042](decisions/0042_admin_modular_backend_and_shared_projections_proposal.md) предлагает модульный TypeScript backend, PostgreSQL и durable inbox/outbox с отдельными API/workers. Это инфраструктурное предложение, не принятое обязательство использовать конкретный framework, broker или hosting.

Пример общего envelope:

```typescript
type Money = { amount: string; currency: 'USD' };
type Decimal = string;
type Observed<T> =
  | { state: 'known'; value: T; asOf: string }
  | { state: 'stale'; value: T; asOf: string; reasonCode: string }
  | { state: 'unavailable'; reasonCode: string };
type Capability = { allowed: boolean; reasonCode?: string };
type Snapshot<T> = {
  schemaVersion: number;
  version: string;
  asOf: string;
  data: T;
  capabilities: Record<string, Capability>;
};
type CommandReceipt = {
  commandId: string;
  status: 'accepted' | 'applied' | 'rejected' | 'reconciling';
  resourceId?: string;
  reasonCode?: string;
};
```

Enum здесь проектный, окончательно согласуется с domain/contracts. Внешние decimal-строки парсятся точно; внутренние DTO атрибуции частей/стоимости/расходов и хвоста сохраняют нормализованные numerator/denominator как строки целых по ADR-0055/133. Старый общий decimal DTO не является форматом для 1/3; binary floating point не применяется к денежному учёту. UTC timestamps ISO8601; локальный display отделён от фиксированной зоны сессии. ID opaque, не wallet-secret и не порядковый публичный номер аккаунта.

| DTO | Минимальная полезная нагрузка |
| --- | --- |
| UserProfile | id, verifiedEmail state, locale, notificationPreferences, effective VIP summary |
| TraderSummary/Detail | venue, traderId, publicAddress, eligibility/reason, metrics with period/freshness, quality breakdown |
| SetupDraft | venue, trader, sizing discriminated union, budgetUSD, limits, policyVersion |
| SessionView | id, mode, lifecycle, timezone, start/end, settingsVersion, report eligibility, money snapshot |
| OrderView | id, sessionId, venue, sourceActionId, side, market/outcome, desired/filled/remaining, reserve, state, fills |
| PositionView | id, ownership mode, lots/remaining tracked qty, cost/valuation, realised/unrealised, related orders |
| ActivityView | id, occurredAt/receivedAt, decision, reasonCode, source evidence reference, related owned resources |
| FundsView | paper totals; venue connection state; observed venue balances; asset/conversion metadata |
| OperationView | ledger reference, operation type, amount/asset, state, created/settled times, related resource |
| TicketView | ticketId, public status/messages, user-supplied context, public reply availability |
| NotificationView | id, semantic type, published contentVersion, read state, safe destination |
| ReportView | period, aggregate metrics, adequacy, evidenceVersion, unresolved counts |

Каждый user DTO фильтруется на сервере. Не отдаём credentials, private keys, internal notes, staff permissions, чужие счета и служебные финансовые показатели. Source evidence раскрывается только в допустимом пользовательском объёме.

## 14. API и асинхронные команды — предложение

Пути условные; API не реализовано. Browser не обращается напрямую с сервисными credentials к площадке. Venue adapter скрывает различия источников и исполнения, не превращает их в одинаковые гарантии.

| Чтение / команда | Назначение |
| --- | --- |
| GET `/api/me`, `/api/content/:locale` | Identity, preferences, совместимая published content version |
| POST `/api/auth/request`, `/verify`, `/logout` | Passwordless вход и выход |
| GET `/api/traders`, `/api/traders/:venue/:id` | Cursor list, фильтры, профиль/период |
| POST `/api/traders/resolve` | Проверка введённого venue/address |

| GET `/api/sessions/current`, `/api/sessions/:id/report` | Главная/lifecycle, отчёт |
| PATCH `/api/sessions/:id/settings` | Версионированные настройки новых сигналов |
| POST `/api/sessions/:id/commands` | Pause/resume/stop с ожидаемой версией |
| GET `/api/positions`, `/api/orders`, `/api/activity` и `/:id` | List/detail только своего контекста |
| POST `/api/orders/:id/commands`, `/api/positions/:id/commands` | Cancel/change/close/detach |
| GET `/api/funds`, `/api/funds/:venue`, `/api/operations` и `/:id` | Согласованный ledger snapshot |

| POST `/api/support/tickets/:id/messages` | Публичный ответ пользователя |
| POST `/api/feedback`; GET `/api/help` | Отзыв отдельно, published FAQ |
| PATCH `/api/me/preferences`; GET `/api/me/referral` | Язык/notifications и собственная referral projection |
| GET `/api/commands/:id` | Подтверждённый результат команды |

Изменяющая команда содержит idempotency key и expected resource/settings version. Сервер сохраняет durable receipt; повтор после network timeout возвращает тот же результат. Примерный ответ 202 accepted означает запрос принят, не означает ордер отменён или позиция продана. При 409 UI обновляет состояние и просит повторно проверить намерение. При validation failure показываем reasonCode и поле; пользовательский текст локализуется по коду, а не по сырой ошибке провайдера.

Для обновления предлагается один согласованный канал snapshots/events (SSE, WebSocket или polling выбирается отдельно). Events имеют id/version; reconnect выполняет catch-up или полный refresh. Старое событие не откатывает новый snapshot. Финансовые значения не рассчитываются оптимистично; прочтение notification допустимо оптимистично с rollback. Offline-очередь close/cancel/start/funding запрещена без отдельной безопасной модели.

Нужны cursor pagination, ограничение page size, стабильная сортировка, request cancellation при смене фильтра и согласование query cache по user/venue/session. Лимиты запросов, retry backoff и SLO определяются после интеграционных измерений, а не выдумываются из Figma.

## 15. Frontend, адаптивность и доступность

Предлагаем разделение: app shell/routes; feature modules auth/traders/session/orders/positions/funds/support/profile; общие domain/contracts, UI components и locale resources; API client/query state. Domain admission и финансовая арифметика остаются на сервере. Конкретный React/framework, router, query/form/decimal libraries, версии и hosting пока не утверждены.

Формы отделяют draft от persisted values; серверные данные не дублируются в нескольких независимых stores. Filters/date range можно хранить в URL; приватные тексты support/auth в URL не помещаем. Cleanup при logout удаляет данные прежнего пользователя. Prepared fixtures маркируются mode/example и не используют production command endpoint.

Компоненты: app shell, nav item, button/icon button, amount display, status badge, venue badge, metric card, trader card, filters/tabs, table/list row, form field, confirmation dialog, drawer, empty/error state, toast/banner, support thread, chart с текстовым эквивалентом. Дизайн-токены извлекаются из актуального файла перед вёрсткой; не назначаем неизвестные HEX/font/spacing как принятые значения.

Макеты: mobile 390×844, desktop 1440×960. Промежуточные breakpoint и tablet layout предлагаются на этапе layout; экранные размеры не означают фиксированный viewport приложения. Проверки: узкие 320/360, исходные 390, desktop 1280/1440 и масштаб текста 200%. Таблица на mobile становится читаемой карточкой/управляемой прокруткой без потери ключевых действий и смысла.

Предлагаемый baseline WCAG 2.2 AA: keyboard navigation, видимый focus, label/error association, понятные accessible names, контраст, семантические headings, announcements асинхронного результата, modal focus trap и возврат focus. Цель для touch controls — 44×44 CSS px по проектному стандарту. Статус/убыток/ошибка объясняются текстом, не только цветом. Reduced motion учитывается; длинные RU-строки и неизвестные суммы не обрезают критический смысл.

## 16. Локализация и управляемый контент

Все product copy используют semantic keys, например `session.example.open`, `traders.back`, `order.cancel.pending`, `funds.balance.unavailable`. Нельзя строить предложения конкатенацией кусочков RU/EN или сохранять перевод как domain status. Числа/даты форматируются по locale; исходная точность и идентификаторы не меняются.

ADR-0034: published content versions, согласованные RU/EN bundles, проверка missing keys/placeholders, совместимость schema и valid baseline/cache fallback. Контент меняет тексты, не разрешения, численные лимиты и execution rules. При отсутствии нового текста используем последний совместимый bundle/базовую версию; необработанный ключ не показываем пользователю.

В будущем RTL возможно через logical CSS и независимость layout от направления; перевод новых языков не входит в текущий объём. Wallet/address/ID сохраняют корректное направление и копируются полностью. Цена, доля и USD amount явно различаются; `% trade` поясняет базу расчёта.

## 17. Безопасность, наблюдаемость и эксплуатация

Каждый запрос проверяет identity, ownership, capabilities и версии на сервере. Rate limits для auth, resolve, support, feedback и commands; конкретные числа открыты. Пользовательский текст escaped, rich content sanitised; deep links из уведомлений ограничены безопасными destinations. CSP/CORS/CSRF, dependency scanning и session expiry проверяются до выпуска.

Logs используют correlationId/commandId/resourceId без auth codes, secrets, cookies и полного support body. Метрики: успешность auth/start, validation failures, command latency, stale projections, unknown reconciliation, delivery/support failures. Технический timeout не отображается как окончательный финансовый результат. Аналитика поведения не подменяет audit и ledger.

Юридические/географические ограничения и live eligibility определяются отдельно для продукта/площадок до реальных операций; отсутствие KYC экрана не является техническим доказательством исключения требований. Этот документ не добавляет новые GEO-ограничения и не запускает юридический аудит.

## 18. Проверка и критерии готовности

| Сценарий | Ожидаемый результат |
| --- | --- |
| Guest → setup → auth → start, RU/EN | Черновик сохранён, одна новая EMPTY-сессия, example не импортирован |
| Открыть пример, затем создать своё демо | Fixture отделён, собственная история пуста |
| Два клика/повтор запроса start | Один receipt и одна сессия |
| Сигнал $20 при доступных $8 | Полный skip, объяснение причины, ордер $8 отсутствует |
| Копирование 3% от BUY трейдера | База — trader BUY, не собственный бюджет; rounding по согласованному контракту |
| Desired $20, fill $12 после admission | $12 сохранены; $8 остаток отменяется с подтверждением |
| Cancel request + late fill | Fill учтён; reserve снимается только после подтверждённой сверки |
| Unknown/timeout + повтор/reconnect | Нет второго исполнения или преждевременного release |
| Pause + SELL трейдера | Новый BUY запрещён; разрешённый выход продолжается |
| Detach | Не происходит скрытая продажа; tracked/manual доли не смешаны |
| Смена risk rules / timezone устройства | Старые действия не пересчитаны; дневная зона прежняя |
| Неподключённый Limitless | Balance unavailable; нет fake-zero, депозит ведёт в future |
| Snapshot out-of-order/offline | Нет отката totals и скрытой очереди финансовых команд |
| Support creation retry | Один ticket, контекст явный, internal notes не раскрыты |
| Feedback success/back | Отзыв отдельно; возврат в актуальную funds/home ветку |
| Недостаточно данных отчёта на 14-й день | Нет фиктивного score; показывается недостаточность |
| Emergency scope и unavailable controls | Запрет применён сервером; чтение/сверка не остановлены случайно |
| VIP/content version update | Эффективная версия и время сохранены, прошлый учёт не переписан |
| RU↔EN, mobile↔desktop | Эквивалентные destinations, права и состояния, без переполнения |
| Чужой ID / logout другого пользователя | Нет утечки данных и старого cache |

Нужны domain unit tests для admission/резервов/lifecycle, contract tests projections/API, adapter simulations для fills/unknown, component tests форм/доступности и E2E ключевого пути в обеих локалях. Visual regression проверяет реальные viewport и состояния, не только четыре статичных home. Скриншот и чтение reactions не заменяют ручной Present.

Готовность к разработке первого среза: согласованные contracts/вертикальный scope, закрытые критичные BL для его поведения, fixtures, capability matrix и API error model. Готовность к пользовательской проверке: тесты среза, RU/EN responsive/accessibility, ручной click-through текущих прототипов и отсутствие fixture/live смешения. Live имеет отдельные gates каждой площадки и не разрешается этим документом.
