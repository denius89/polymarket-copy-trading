# Инструкции для Codex

## Перед началом задачи

1. Открыть `docs/ROADMAP.md` и соотнести запрос пользователя с актуальной очередью. Не начинать новую область работ и не принимать продуктовые решения только потому, что они перечислены в плане.
2. Прочитать `docs/PROJECT_STATE.md` как подробный журнал решений; его дата обновления может отставать от ROADMAP.
3. Найти связанные материалы через `docs/README.md` и прочитать соответствующие ADR.
4. Использовать `references/Polymarket_Project_Dialogue_Handoff.md` только как локальный исходный контекст, если файл доступен. Публичные документы должны оставаться понятными без него.
5. Проверить остаток лимита перед крупным исследованием или архитектурной задачей.

## Текущий приоритет

Следовать вводному разделу `docs/ROADMAP.md`, живым картам `docs/design/client/sitemap.md` / `docs/design/admin/sitemap.md` и связанным последним handoff/проверкам. Документ 109 и более ранние обзоры — исторические срезы. Сейчас заканчиваем пользовательские интерфейсы после просмотра с коллегой. Исторические планы в свёрнутых разделах и старые отчёты не разрешают автоматически начинать бизнес-аудит, админку, frontend или реальные сделки. API-справочники находятся в `docs/api/polymarket/` и `docs/api/limitless/`; дата их свидетельств указана внутри, актуальность API проверяется под конкретную задачу. Принятые ADR сохраняют силу; новая задача не должна переопределять их без решения владельца.

## Рабочий процесс

- Один цикл должен давать один проверяемый результат.
- Реализовывать минимальный вертикальный срез и не расширять объём без необходимости.
- После изменения интерфейса проводить визуальную проверку.
- После изменения поведения выполнять соразмерные тесты.
- После завершения обновлять `docs/PROJECT_STATE.md`.
- При изменении очереди или gate обновлять `docs/ROADMAP.md`.
- Архитектурные решения фиксировать отдельным файлом в `docs/decisions/`.
- Перед коммитом выполнять `npm run check` и `git diff --check`.

## Безопасность

- Не сохранять приватные ключи, seed phrase, session cookies и рабочие API secrets.
- Реальное исполнение должно быть выключено по умолчанию и включаться явным флагом окружения.
- Не выполнять реальные сделки без отдельного решения основателя о переходе из paper trading.
- Любое неизвестное состояние ордера должно блокировать дальнейшее рискованное действие и создавать запись инцидента.

## Проектные границы

- Polymarket и Limitless обязательны для целевого продукта; core проектируется venue-neutral.
- Limitless остаётся первым партнёрским spike, Polymarket исследуется параллельно; live-gates раздельные.
- Первый интерфейс — самостоятельный mobile-first web app.
- Основной пользователь MVP — совершеннолетний неопытный любитель ставок с самостоятельным входом; агентский кабинет находится вне MVP.
- Первый языковой набор — English и Russian.
- Основной язык — TypeScript.
- Материалы в `references/` считаются read-only.

## Передача Figma в разработку

По поручению владельца поддерживать актуальный GitHub-контекст для последующей разработки Codex. Для клиентского интерфейса соблюдать [design/client-ui-kit/HANDOFF.md](design/client-ui-kit/HANDOFF.md): после каждого согласованного изменения Figma обновлять связанные реестры, токены, спецификации, доказательства проверки и PROJECT_STATE в том же пакете. Перед программированием читать свежий main и сверять затронутые узлы с Figma; фиксировать исходный commit SHA и дату чтения. Не считать прототип серверным контрактом, открытые вопросы — принятыми решениями, а construction scripts — точным backup Figma. Для админки учитывать также требования передачи в документе 118.

Загружать только нужный навык и его предметные references. Все процедуры этой подготовки сохраняют текущие ограничения; наличие S18/S19 не разрешает настройку серверов/выпуск. Отчёт новых 20 процедур — `docs/ai-system/evals/independent-catalog-2026-10-17/REPORT.md`; один независимый synthetic кейс не означает полную приёмку профессии или automatic discovery.

Первая партия AI-подготовки находится в `.agents/skills/`: `cct-project-context` (S01 — рамка существенной задачи/продолжения), `cct-knowledge-curation` (S21 — источники и учебные пакеты), `cct-ai-quality` (S10 — review результата AI и проверка навыков). Применять по соответствующей задаче, не загружать все три для простого вопроса. Для родительской папки проекта настроена локальная ссылка `.agents/skills` на каталог репозитория. Обнаружение всех 23 metadata и implicit чтение проверены в новых CLI-сессиях; детали — `docs/ai-system/evals/independent-deep-2026-10-17/REPORT.md`. Обновление discovery уже открытого Desktop-чата отдельно не проверено: при отсутствии навыка в его контексте читать нужный SKILL.md явно. Статус и пределы проверки — `docs/ai-system/FIRST_BATCH.md`; доказательства — `docs/ai-system/evals/REPORT.md`. Они не разрешают разработку продукта или внешние действия.

Impeccable установлен в `.agents/skills/impeccable/` (источник и зафиксированная версия — `docs/qa/impeccable-2026-10-16/installation.json`). Использовать его при явно поставленной задаче оценки/доработки интерфейсов; из чатов с рабочей папкой выше репозитория сначала читать этот SKILL.md явно. Автоматическое обнаружение навыка зависит от рабочей папки сессии.

Принятые ADR, текущий UI kit и границы поручения имеют приоритет над эстетическими предпочтениями внешнего навыка. Для Figma допускается критика макетов по изображениям и свойствам узлов; DOM-детектор, runtime-доступность и производительность нельзя объявлять проверенными по макету. Задача проверки дизайна не разрешает автоматически его изменять. Автоматические edit hooks при этой установке не включались.

## Источники визуальных идей

По пожеланию владельца от 19.10.2026 при разработке новых дизайнов и существенной визуальной переработке использовать Behance, Pinterest и похожие площадки (например, Dribbble, Awwwards, Mobbin) как источники идей. Искать референсы по конкретному сценарию и типу интерфейса; показывать небольшую релевантную подборку со ссылками и объяснять, какие приёмы предлагается адаптировать. Если источник недоступен, явно обозначать это и использовать доступные альтернативы, не выдавать непросмотренные материалы за изученные. Для точечной правки текста или выравнивания отдельный поиск не обязателен.

Адаптировать идеи к задачам пользователя, существующему UI kit, финансовой ясности, RU/EN и mobile/desktop. Референсы не являются доказательством удобства, доступности или корректности бизнес-логики. Сохранять цельность продукта; не переносить чужие брендовые материалы и не менять согласованный дизайн только ради сходства с референсом.

## Сохранение и завершение каждой задачи

По постоянному поручению владельца от 19.10.2026 соблюдать [REPOSITORY_GUIDE](docs/REPOSITORY_GUIDE.md). Каждый содержательный законченный блок и материал перед длительным перерывом сохранять вне компьютера: документы/навыки/код/малые результаты — в GitHub, большие исходные данные и закрытые резервные материалы — на Google Диске с manifest, SHA256 и записью в `docs/storage/catalog.json`. Локальный commit/stash не считать облачным сохранением. При невозможности загрузки явно сообщить, что осталось только локально.

Разрешение на публикацию проектных материалов, проверенные commit/push/PR/merge и уборку завершённых веток/worktrees уже дано; повторно его не запрашивать. Оно не разрешает deploy, реальные сделки, изменение прав доступа или публикацию чувствительных данных. Незавершённую и чужую активную работу сохранять отдельно, не смешивать с пакетом.

До merge выполнить `npm run check`, `npm run test:repository`, `git diff --check` и соразмерные предметные проверки. После merge подтвердить результат в удалённой main, проверить удаление head-ветки в Actions, синхронизировать основную папку и удалить локальные ветку/worktree своей завершённой задачи. До удаления worktree проверить ignored-файлы и их архивную копию. Если head продвинулся или появилась уникальная работа — остановить удаление этой ветки и сохранить новое. Не оставлять временные служебные ветки и рабочие копии после выполнения.
