# Инструкции для Codex

## Контекст и текущая задача

В начале существенной темы прочитать вводную актуальную часть `docs/ROADMAP.md` и `docs/PROJECT_STATE.md`, затем только связанные материалы. Для продолжения установленной задачи не перечитывать весь журнал/каталог; обновлять контекст при новых изменениях, конфликте или неизвестном правиле. Простой вопрос или точечная правка не требует полного погружения.

Очередь задают актуальное поручение владельца и ROADMAP. После согласования админки v1 и исправлений BI-01–BI-04 текущая очередь — технический план 139; реализация запускается отдельным поручением. Актуальные узлы и входы интерфейсов — в `docs/design/client/sitemap.md` / `docs/design/admin/sitemap.md` и последних связанных пакетах. Документ 109 и более ранние обзоры — исторические срезы. Старые планы не разрешают автоматически возобновлять backend, исследования или реальные сделки. API-пакеты находятся в `docs/api/polymarket/` и `docs/api/limitless/`; их актуальность проверяется под конкретный вопрос. Принятые ADR сохраняют силу.

`references/Polymarket_Project_Dialogue_Handoff.md` использовать как дополнительный исторический контекст при необходимости. Проверку остатка лимита выполнять перед крупной работой, не каждой репликой.

## Рабочий процесс

- Один цикл должен давать один проверяемый результат.
- Реализовывать минимальный вертикальный срез и не расширять объём без необходимости.
- После изменения интерфейса проводить визуальную проверку.
- После изменения поведения выполнять соразмерные тесты.
- После завершения обновлять `docs/PROJECT_STATE.md`.
- При изменении очереди или gate обновлять `docs/ROADMAP.md`.
- Архитектурные решения фиксировать отдельным файлом в `docs/decisions/`.
- Перед коммитом выполнять `npm run check` и `git diff --check`.

## Безопасность

- Не сохранять приватные ключи, seed phrase, session cookies и рабочие API secrets.
- Реальное исполнение должно быть выключено по умолчанию и включаться явным флагом окружения.
- Не выполнять реальные сделки без отдельного решения основателя о переходе из paper trading.
- Неизвестное состояние ордера блокирует затронутое рискованное действие и требует сверки/инцидента по действующему правилу; не останавливать из-за этого независимую правку дизайна.

## Проектные границы

- Polymarket и Limitless обязательны для целевого продукта; core проектируется venue-neutral.
- Limitless остаётся первым партнёрским spike, Polymarket исследуется параллельно; live-gates раздельные.
- Первый интерфейс — самостоятельный mobile-first web app.
- Основной пользователь MVP — совершеннолетний неопытный любитель ставок с самостоятельным входом; агентский кабинет находится вне MVP.
- Первый языковой набор — English и Russian.
- Основной язык — TypeScript.
- Материалы в `references/` считаются read-only.

## Передача Figma в разработку

По поручению владельца поддерживать актуальный GitHub-контекст для последующей разработки Codex. Для клиентского интерфейса соблюдать [design/client-ui-kit/HANDOFF.md](design/client-ui-kit/HANDOFF.md): после согласованного изменения Figma обновлять только затронутые записи реестров, токенов, спецификаций и доказательства проверки в существующем тематическом пакете, а также PROJECT_STATE. Неизменившиеся токены и весь handoff ради подписи не переписывать. Перед программированием читать свежий main и сверять затронутые узлы с Figma; фиксировать исходный commit SHA и дату чтения. Не считать прототип серверным контрактом, открытые вопросы — принятыми решениями, а construction scripts — точным backup Figma. Для админки учитывать также требования передачи в документе 118.

## Проектные навыки

Каталог S01–S23: `docs/ai-system/CATALOG.md`; правила применения: `docs/ai-system/OPERATING_RULES.md`. Выбирать минимальный подходящий набор, без обязательной цепочки зависимостей и чтения учебных пакетов. Имя области в задаче не повод запускать полный audit. Исторические eval-отчёты описывают прежние версии, а не текущее качество работы.

Для обычной работы с админкой начинать с текущего сценария, живой карты и UI kit. Сохранять согласованную архитектуру интерфейса. Перед созданием нового экрана проверить существующее состояние/компонент; не добавлять разделы, роли, показатели или финансовые правила из общих checklist. Явно порученное расширение выполнять в его объёме. Для общего просмотра давать актуальное меню сценариев, для точечной правки — нужный экран.

Impeccable (`.agents/skills/impeccable/`) использовать для подходящей визуальной работы в пределах поручения; базовый режим админки — Operate. Обычная вычитка денег не требует полного critique/audit Impeccable. Сначала действующие ADR, задача и UI kit, затем внешние эстетические рекомендации. Аудит по изображениям Figma не подтверждает DOM/runtime/performance; DOM-детектор редактора Figma не проверяет продукт. Локальная ссылка `.agents/skills` родительской папки ведёт в репозиторий; при отсутствии навыка в контексте читать его явно. Bundled-навыки и автоматические hooks этим поручением не меняются.

## Источники визуальных идей

По пожеланию владельца от 19.10.2026 при разработке новых дизайнов и существенной визуальной переработке использовать Behance, Pinterest и похожие площадки (например, Dribbble, Awwwards, Mobbin) как источники идей. Искать референсы по конкретному сценарию и типу интерфейса; показывать небольшую релевантную подборку со ссылками и объяснять, какие приёмы предлагается адаптировать. Если источник недоступен, явно обозначать это и использовать доступные альтернативы, не выдавать непросмотренные материалы за изученные. Для точечной правки текста или выравнивания отдельный поиск не обязателен.

Адаптировать идеи к задачам пользователя, существующему UI kit, финансовой ясности, RU/EN и mobile/desktop. Референсы не являются доказательством удобства, доступности или корректности бизнес-логики. Сохранять цельность продукта; не переносить чужие брендовые материалы и не менять согласованный дизайн только ради сходства с референсом.

## Сохранение и завершение каждой задачи

По постоянному поручению владельца от 19.10.2026 соблюдать [REPOSITORY_GUIDE](docs/REPOSITORY_GUIDE.md). Каждый содержательный законченный блок и материал перед длительным перерывом сохранять вне компьютера: документы/навыки/код/малые результаты — в GitHub, большие исходные данные и закрытые резервные материалы — на Google Диске с manifest, SHA256 и записью в `docs/storage/catalog.json`. Локальный commit/stash не считать облачным сохранением. При невозможности загрузки явно сообщить, что осталось только локально.

Разрешение на публикацию проектных материалов, проверенные commit/push/PR/merge и уборку завершённых веток/worktrees уже дано; повторно его не запрашивать. Оно не разрешает deploy, реальные сделки, изменение прав доступа или публикацию чувствительных данных. Незавершённую и чужую активную работу сохранять отдельно, не смешивать с пакетом.

До merge выполнить `npm run check`, `npm run test:repository`, `git diff --check` и соразмерные предметные проверки. После merge подтвердить результат в удалённой main, проверить удаление head-ветки в Actions, синхронизировать основную папку и удалить локальные ветку/worktree своей завершённой задачи. До удаления worktree проверить ignored-файлы и их архивную копию. Если head продвинулся или появилась уникальная работа — остановить удаление этой ветки и сохранить новое. Не оставлять временные служебные ветки и рабочие копии после выполнения.
